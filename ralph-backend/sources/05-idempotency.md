# Idempotency

### The definition

An operation is idempotent if performing it multiple times has the same effect as performing it once. `SET x = 5` is idempotent; `x += 5` is not.

### Why it's non-negotiable

Every distributed system delivers at-least-once. Networks time out without telling you whether the operation succeeded. Retries are automatic and often invisible. **You cannot build a correct distributed system without idempotency somewhere** — the only question is whether you designed for it or discovered you needed it in production.

The canonical failure: a payment request times out, the client retries, and the customer is charged twice. The server did nothing wrong — it succeeded both times.

### The idempotency key pattern

The client generates a unique key per logical operation (a UUID) and sends it with the request. The server:

1. Checks whether it has seen this key
2. If yes, returns the **stored response** from the first attempt — it does not re-execute
3. If no, executes, stores the result against the key, returns it

Critical details people miss:

- **The key must be generated by the client, once, before the first attempt** — and reused across retries. A key generated per-attempt defeats the purpose entirely.
- **Store the response, not just the fact of execution.** The retry needs to receive the same answer, not a "duplicate" error.
- **The check and the execution must be atomic** — otherwise two concurrent retries both see "not seen" and both execute. Use a unique constraint on the key, or a transaction, or a distributed lock.
- **Keys need a retention window** — long enough to cover any realistic retry (24h is common), then expire.

### Natural idempotency

Sometimes you get it free by design:

- **Conditional writes** — `UPDATE ... WHERE version = 7`. The second attempt matches nothing.
- **Upserts on a natural key** — the operation converges to the same state.
- **Set semantics** — adding an element that's already present is a no-op.
- **Deriving state rather than mutating it** — recomputing a total from an event log is idempotent; incrementing a counter isn't.

Prefer these over key-tracking where you can. Less machinery to get wrong.

### HTTP semantics

GET, PUT, DELETE are defined as idempotent; POST is not. This is why "create" endpoints are the ones that need explicit idempotency keys, and why PUT-with-client-generated-ID is sometimes a cleaner API design than POST.

### In the room

> "The write tools carry an idempotency key generated when the action is first approved, so a Temporal retry after a timeout can't isolate the same host twice. The key is checked and the action recorded in one atomic operation — otherwise two concurrent retries both see 'not executed' and both fire."

**Where this appeared in the Simbian design:** `execute_write_tool` is idempotency-keyed precisely because a retried containment action is a customer-visible incident.
