Requirements

Functional Requirements

AreaMust have (v1)Nice to have
Checkout Form Multi-step flow (cart → shipping → payment → confirmation), card input with masking/BIN detection, address autocomplete Saved payment methods, buy-now-pay-later
Security Stripe Elements hosted fields, PCI SAQ-A scope Custom card form (SAQ-D — out of scope)
Payment Methods Card (Visa/MC/Amex), basic wallets (Apple Pay / Google Pay) iDEAL, BLIK, Pix, UPI, BNPL
Real-time Payment status polling / SSE after confirmation Live transaction dashboard
Errors Decline handling, 3DS challenge, retry UX Full circuit breaker / provider failover

Non-Functional Requirements

Latency

Checkout page LCP < 2.5s; form TTI < 3s on 4G; confirmCardPayment TTFB < 1s

Scale

Handle 10k concurrent checkout sessions; multi-tab same cart conflict detection

Reliability

Idempotency for all payment mutations; offline queue for pre-auth steps; webhook-to-UI reconciliation

Security

PCI SAQ-A via hosted fields; CSP with Stripe allowlist; no raw PAN/CVV in browser memory

Metrics · Constraints · Assumptions

  • Metrics: Checkout conversion rate, payment success rate by decline code, 3DS completion rate, Stripe.js load time p95
  • Constraints: Raw card data NEVER touches our DOM/server (only Stripe iframe); Stripe.js must load on every page; mobile Safari SSE limits
  • Assumptions: Stripe as primary PSP; single-currency v1; authenticated sessions; BFF owns Stripe secret key

Data Model

~5 min · Entities · Relationships · PaymentIntent FSM
▼

Frontend operates on three core entities: the Cart (ephemeral), the CheckoutSession (server-persisted), and the PaymentIntent (Stripe-owned). We never model raw card data.

Cart { id, items: LineItem[], subtotal, currency, appliedCoupons: Coupon[], expiresAt // server-side cart TTL } CheckoutSession { id, cartId, userId?, step: 'cart' | 'shipping' | 'payment' | 'confirmation', shippingAddress: Address, selectedPaymentMethodId?, idempotencyKey, // per-attempt, rotated on each "Pay" click createdAt, updatedAt } PaymentIntent { // Stripe-owned, mirrored to our DB id: 'pi_xxx', amount, currency, status: PIStatus, // FSM state clientSecret, // short-lived, never stored in localStorage paymentMethodId?, lastPaymentError?: StripeError, nextAction?: NextAction // 3DS redirect / iframe challenge } Order { id, paymentIntentId, userId, items, status: 'pending' | 'paid' | 'failed' | 'refunded', paidAt?, webhookVerifiedAt } type PIStatus = | 'requires_payment_method' | 'requires_confirmation' | 'requires_action' | 'processing' | 'succeeded' | 'canceled'

Key relationships

OperationBehavior
User clicks PayPOST /payment-intents/confirm → Stripe confirmCardPayment → PI status → processing
3DS requiredPI nextAction triggers ThreeDSModal mount; on complete → PI → succeeded
Webhook arrivesDB Order.status = 'paid'; SSE pushes to active frontend session
Tab re-entry after closeGET /checkout-session → restore step + PI status; re-render correct UI
Card declinePI.lastPaymentError populated; FSM → requires_payment_method; user can retry

API Design / BFF

~10 min · Protocols · Endpoints · Streaming lifecycle · Idempotency
▼

Protocol choice

PatternUse in paymentsWhy
REST/HTTPSCart CRUD, session management, PaymentIntent confirm, order fetchIdempotency-Key header; standard error taxonomy; caching for GET
SSEPayment status push after confirmationServer→client push; no polling; AbortController cancel; works with standard auth cookies
postMessageStripe Elements iframe → parent pageCross-origin card data isolation — PCI requirement
WebSocketLive dashboard (multi-concurrent payments)Full-duplex for high-frequency event push; not needed for single-session checkout
Polling (fallback)Payment status if SSE unavailableExponential backoff; safe fallback for restrictive network proxies

Core endpoints (BFF)

MethodEndpointPurpose
POST/checkout/sessionCreate or resume CheckoutSession; returns sessionId + step
PATCH/checkout/session/:id/stepAdvance to next step (validates current step server-side)
POST/payment-intentsCreate PI server-side; returns clientSecret (never stored, used once)
POST/payment-intents/:id/confirmTrigger confirmCardPayment; idempotent via Idempotency-Key
GET/payment-intents/:id/statusPoll fallback for PI status
GET/payment-status-stream?piId=:idSSE stream for real-time PI status updates
POST/webhooks/stripeVerify Stripe-Signature; update Order; push to SSE clients
GET/orders/:idConfirmation page data fetch

Streaming / async payment lifecycle

User clicks Pay → [1] POST /payment-intents/confirm (Idempotency-Key: session.idempotencyKey) [2] BFF calls stripe.paymentIntents.confirm() [3] If 3DS required: return nextAction to frontend → render ThreeDSModal [4] After 3DS: PI status = processing → SSE pushes update [5] Stripe webhook → BFF verifies sig → updates Order → SSE broadcast → UI → ConfirmationPage

Network lifecycle notes

  • Idempotency: rotate key per attempt; safe to retry POST on timeout without double-charge
  • Cancel: if user navigates away during processing, Order status resolved by webhook (frontend re-reads on return)
  • 3DS redirect recovery: store PI id in sessionStorage before redirect; restore on return to correct UI state
  • Backoff: poll fallback at 1s, 2s, 4s, 8s (cap 30s); show "still processing…" after 10s

Deep Dive

~10 min · Pick 1–2 areas the interviewer cares about
▼

I'll lead with Security (PCI/iframe model) and Resilience — happy to switch to Performance or i18n if you prefer.

  • PCI scope: Stripe Elements = SAQ-A; card data never in our DOM, memory, or server logs
  • iframe isolation: Stripe renders CardNumberElement in cross-origin iframe on js.stripe.com; postMessage only exchanges tokens (pm_xxx), never PANs
  • CSP: frame-src https://js.stripe.com https://hooks.stripe.com; script-src 'self' https://js.stripe.com; connect-src 'self' https://api.stripe.com
  • clientSecret: keep in memory only (not localStorage, not URL params); expires after PI use; rotate idempotency key per attempt
  • Clickjacking: X-Frame-Options DENY on checkout page + frame-ancestors 'none' in CSP; Stripe iframe is explicitly allowed via frame-src, not by weakening our own page framing policy
  • 3DS: iframe modal challenge or redirect; validate redirect return params server-side via webhook; never trust client-side redirect_status alone
  • Stripe.js: load on every page (Stripe recommends this for fraud signals); use <script async> + preconnect to js.stripe.com
  • CLS prevention: reserve fixed height (e.g. 48px) for Elements iframe mount container; don't let it reflow surrounding content
  • Bundle split: core checkout critical path is <60KB; defer Stripe.js (already async); lazy-load Apple/Google Pay button SDKs only when available
  • TBT / INP: move heavy Stripe SDK work off main thread by loading async; INP-safe by debouncing BIN detection to 300ms
  • One-click checkout: preload PI on product page hover/intent; preconnect Stripe on page load; so that "Pay" click triggers confirm only, not create + confirm
  • LCP: inline critical CSS; preload hero product image; SSR order summary so content is above-fold on first byte
  • Idempotency: every POST /payment-intents/confirm carries Idempotency-Key from sessionStorage; safe to retry on network timeout without double-charge
  • 3DS redirect recovery: stash PI id + step in sessionStorage before redirect; restore on return to correct UI state
  • Offline detection: navigator.onLine + online/offline events; show "you're offline, your cart is saved" banner; queue retry on reconnect
  • Webhook ground truth: never trust only client-side PI status; always wait for webhook-confirmed Order.status before showing success
  • Circuit breaker: after 3 consecutive 5xx from /payment-intents/confirm in 60s, show "payment system temporarily unavailable" with retry-after countdown; don't let user hammer degraded backend
  • Tab re-entry: GET /checkout-session on tab focus to reconcile FSM state with server PI status; BroadcastChannel for multi-tab same cart conflict detection
  • Funnel events: checkout_started, step_completed (step, duration_ms), payment_form_engaged, pay_button_clicked, payment_succeeded / payment_failed (decline_code, attempt_number)
  • PCI-safe sanitization: Sentry beforeSend strips card_number, cvv, full_name from breadcrumbs; analytics allowlist only (pi_id hashed, decline_code, country)
  • Performance marks: performance.mark('stripe-js-start') before script inject → performance.mark('stripe-js-ready') in Stripe onReady callback; performance.mark('elements-mounted') in Elements onChange
  • Real-time dashboard: payment_success_rate (1m rolling window), decline_rate by code, 3DS completion %, Stripe.js p95 load time; alert if success_rate < 90% for 5 min
  • Deploy regression: correlate deploy timestamp with Sentry error spike and Datadog payment_failed rate; cross-check Stripe Dashboard for PSP-side failures vs. our API errors
  • Currency formatting: Intl.NumberFormat(locale, {style:'currency', currency}) for display; always store/transmit in minor units (integer cents); special-case JPY (0 decimals), KWD (3 decimals)
  • Tax display: server provides {amount, taxIncluded: boolean, taxAmount}; component renders "incl. VAT" or "+ tax" based on flag; never derive tax on frontend
  • RTL: CSS logical properties (margin-inline-start not margin-left); card number field kept LTR via dir="ltr" on the input; CVV icon flips position; error messages align-start
  • Local payment methods: server returns ranked PaymentMethod[] for locale; frontend renders in server order; each method has {type, displayName, logoUrl, flow: 'redirect'|'iframe'|'async'}; iDEAL/BLIK are redirect; Pix/UPI are async (polling for QR scan); konbini is async + shows convenience store selector
  • Server error translation: decline codes mapped to i18n key in frontend dictionary; fallback to generic "payment_failed" if code unknown; never show raw PSP error strings to users

Interview close (30 sec)

Three patterns I'd repeat: (1) card data stays in Stripe's iframe — scope our PCI to SAQ-A and never touch raw PANs; (2) idempotency keys + webhook ground truth — rotate per attempt, never trust client-side confirmCardPayment alone; (3) PaymentIntent as FSM — model status transitions explicitly so every UI state is deterministic and recoverable.
