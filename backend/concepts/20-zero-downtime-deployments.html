Zero-Downtime Deployments

Blue-green, canary, and rolling deployment strategies, plus the expand-contract pattern for safe schema migrations — shipping changes without a maintenance window or a broken in-flight request.

Theory

The actual constraint: two versions run at once, whether you admit it or not

"Zero-downtime" is not really a deployment mechanism — it's a compatibility guarantee. The instant you stop taking a maintenance window, there is a window, possibly seconds, possibly hours, where old code and new code are both handling live traffic against the same shared state: the same database, the same cache, the same message topics. Every deployment strategy below is just a different policy for how traffic is split across that window. If the old and new versions can't coexist — because the new version wrote a row shape the old version can't parse, or the new version expects a column that doesn't exist yet — the strategy doesn't matter, you'll have a partial outage regardless of how cleverly you shift traffic percentages.

Blue-green: two full environments, an instant switch

Run two identical production environments, blue (currently live) and green (idle or serving nothing). Deploy the new version to green in full, run health checks and smoke tests against it while it receives zero real traffic, then flip the router/load balancer to send 100% of traffic to green in one atomic switch. Blue stays warm and untouched, so rollback is just flipping the router back — typically the fastest rollback of any strategy, on the order of the LB's config-reload time, not a redeploy. The cost is infrastructure: you provision 2x capacity (at least transiently), and the switch is all-or-nothing — there's no gradual exposure, so a bug that only manifests under real production traffic patterns (not synthetic smoke tests) still hits 100% of users the instant you cut over.

Canary: gradual exposure with an automated decision gate

Deploy the new version to a small subset of capacity and route a small, increasing percentage of real traffic to it — a common progression is 5% → 25% → 50% → 100%, with a bake period at each stage. The defining feature isn't the gradual traffic shift by itself, it's that promotion to the next stage is gated on an automated analysis of real production signal — error rate, p99 latency, saturation — compared against the old version's baseline or against an SLO threshold. If the canary's metrics regress past a threshold, the system automatically rolls back: traffic is routed back to the old version and the canary is torn down, without a human in the loop. This is the strategy actually built to catch a bad deploy before it reaches everyone, at the cost of needing real analysis tooling (Prometheus/Datadog metrics wired to a canary controller — Argo Rollouts, Flagger, Spinnaker) rather than just a router flip.

Rolling: replace instances incrementally in the same pool

Kubernetes' default RollingUpdate strategy: instances in a single pool are replaced a few at a time, controlled by maxUnavailable (how many can be down simultaneously — capacity dip) and maxSurge (how many extra instances can be started above the target count — cost spike) while the rollout proceeds. It's the cheapest strategy — no second full environment — but it's also the one with the weakest built-in safety net: there's typically no automated error-rate analysis gating each step the way canary has. If the new version has a bug, a rolling update will happily march it to 100% of instances unless a human notices and intervenes, or a readiness-probe failure specifically catches it. Rolling updates also guarantee the longest window of mixed-version coexistence, because the rollout takes multiple steps end-to-end rather than one atomic cutover.

Expand-contract: the schema-migration version of the same problem

Rolling and canary both mean old and new application code query the same database simultaneously for the rollout's duration. A schema change that both versions must tolerate needs three phases, not one: expand — add the new column/table/index without touching or requiring the old shape (old code ignores it, new code doesn't depend on it yet); deploy the app change that dual-writes or backfills so both shapes stay populated; then, once the old version is fully rolled off, contract — drop the old column/table. Skipping straight to a single migrate-and-deploy step is exactly the dual-write/schema hazard that turns "just add a database migration" into an incident during any rollout longer than an instant.

The trade-off that actually matters

All three strategies trade the same three things against each other in different proportions: infrastructure cost (blue-green pays 2x, canary pays for a small extra slice, rolling pays close to nothing extra), blast radius before detection (blue-green is all-or-nothing, rolling has no analysis gate so it can silently reach 100%, canary is explicitly built to cap exposure), and rollback speed (blue-green's router flip is fastest, canary's automated rollback is fast but scoped to the canary slice, rolling's rollback is itself another rollout in reverse and takes as long as the forward rollout did). The senior-level question isn't "which strategy is best" — it's "what's this specific change's blast radius if it's wrong, and does the strategy's detection window match it."

Named failure modes

Connection draining cut short

Terminating an old instance during rolling/blue-green without waiting for in-flight requests to finish (and without first deregistering it from the load balancer and letting the deregistration-delay window elapse) drops live requests mid-response — the single most common cause of a "zero-downtime" deploy that wasn't.

Long-lived connections breaking

WebSockets, gRPC streams, and long-poll HTTP connections don't get a clean request boundary to drain at — an instance going away mid-rollout severs them outright unless the client has reconnect/backoff logic, which is a client-side requirement the deploy strategy alone can't fix.

Schema incompatibility mid-rollout

A migration that renames or drops a column the old version still reads/writes breaks the old version for the entire rollout window — the reason expand-contract exists instead of a single-step migration.

No analysis gate on rolling updates

Absent an explicit canary-style analysis step, a rolling update has nothing stopping a regression from reaching 100% of instances other than a human watching dashboards — a real gap compared to canary's automated rollback.

Where this shows up in practice: a service behind a cloud load balancer or an Nginx/Envoy ingress needs its deregistration delay (health-check-driven removal from the routing pool) set longer than its slowest in-flight request — otherwise every rolling deploy quietly drops a percentage of requests that never shows up in a smoke test, only in production 5xx counters.

Interview Line

"Zero-downtime isn't really about the deployment mechanism, it's a compatibility guarantee — for however long the rollout takes, old and new code are both live against the same database and the same cache, so the real question is whether they can coexist, which is what expand-contract migrations are for. Blue-green gives you the fastest rollback because you just flip the router back to a warm standby pool, but it's all-or-nothing exposure and costs double the infra. Canary is the one I actually trust for catching a bad deploy before it reaches everyone, because promotion is gated on real error-rate and latency analysis against a baseline, not just a percentage schedule — Argo Rollouts or Flagger wired to Prometheus, not a human eyeballing a dashboard. Rolling is the cheapest and most common default, but it has no built-in analysis gate, so a regression will march to 100% of instances unless something's watching — that gap is exactly why I push for canary-style analysis on anything with real blast radius, and plain rolling for anything low-risk."

Key Takeaways

  • Match strategy to blast radius, not to fashion — blue-green for changes where you want instant, manual rollback and can afford 2x capacity; canary for anything with real user-facing risk and metrics worth gating on; rolling as the cheap default for low-risk, routine deploys.
  • Rolling updates have no automated safety net by default — Kubernetes' RollingUpdate will happily reach 100% of instances with a regression unless you bolt on an analysis step (readiness probes catch crashes, not silent correctness bugs or elevated error rates).
  • Expand-contract is the schema-migration analog of backward compatibility — add before you need it, dual-write/backfill, only then remove; skipping straight to migrate-and-cutover is what breaks the old version mid-rollout, the same dual-write hazard 07-change-data-capture warns about, just at the schema layer instead of the event layer.
  • Connection draining is a load-balancer setting, not a deploy-tool setting — the LB's deregistration delay (09-load-balancing) must exceed your slowest in-flight request, or a rolling/blue-green cutover silently drops a percentage of requests that never shows up in a smoke test.
  • Canary's auto-rollback is the same instinct as a circuit breaker — both watch a real-time error-rate signal and trip an automatic reaction past a threshold rather than trusting a human to notice in time (06-circuit-breakers-bulkheads); the SLO/error-budget signal it gates on is exactly what 17-observability is built to expose.
  • Long-lived connections (WebSockets, gRPC streams) need client-side reconnect logic — no deploy strategy alone prevents them from being severed when the instance holding them is replaced, because there's no clean request boundary to drain at.
