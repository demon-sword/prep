Service Discovery

Client-side vs server-side service discovery, DNS-based discovery, and service registries (Consul, etcd, ZooKeeper) — how services find each other as instances scale up and down.

Theory

The problem discovery solves

In a static world you hardcode payments-service.internal:8080 and move on. In an autoscaled, container-orchestrated world, instances come and go constantly — a deploy replaces every instance, a scale-up adds ten more, a crash removes one without warning — and IPs are ephemeral. Service discovery is the answer to one question asked continuously: "given a service name, what set of addresses can I send a request to right now?" Get the answer late and you route into a hole; get it wrong and you never notice until users do.

Client-side vs server-side discovery

Client-side discovery

The client queries the registry directly (or holds a periodically-refreshed cache of it) and picks an instance itself, often with an embedded load-balancing library. Classic example: Netflix Eureka + Ribbon. One fewer network hop than going through a proxy, and the client can make locality-aware choices (same-AZ instance) with full context. The cost: every client in every language needs the discovery + LB logic, and every client is now trusting a registry snapshot that may already be stale by the time it dials.

Server-side discovery

The client calls a fixed, stable endpoint — a load balancer, a Kubernetes Service, or a sidecar proxy (Envoy) — and that intermediary owns the registry lookup and the routing decision. The client's code is trivial: one DNS name, no registry client, no LB library to keep in sync across every service's tech stack. The cost is an extra hop, and the intermediary itself becomes a piece of infrastructure that must scale and stay available. This is also usually the safer default for staleness: the intermediary is exactly where active health checks live (see 09-load-balancing), so it can eject a dead instance faster than the registry's own lease would expire.

DNS-based discovery

The simplest version: resolve a service name to a set of A/SRV records that change as instances scale. It costs nothing extra to adopt — every language already has a DNS resolver — but it inherits DNS's baggage: TTL-driven caching means clients (and every resolver, forwarder, and OS cache in between) hold stale answers for as long as the TTL says, regardless of whether the instance behind that IP is now dead. Some resolvers also ignore TTL entirely and cache until process restart. DNS has no way to signal "half of these are unhealthy right now" — it hands back a set and stops caring. This is why DNS-based discovery is common for coarse-grained, slow-changing topology (which cluster, which region) and rare as the sole mechanism for fast-changing pod-level routing.

Service registries: heartbeats, TTLs, and health

A registry (Consul, etcd, ZooKeeper, or Kubernetes' own etcd-backed API) is the general-purpose version of DNS-based discovery: instances explicitly register on startup and hold a lease that they must renew with periodic heartbeats. Stop heartbeating and the lease expires after its TTL, and the registry evicts the entry. This is the same lease/TTL idea as a distributed lock (15-distributed-locking) applied to liveness instead of mutual exclusion — the registry isn't told "I died," it just stops hearing from you and assumes it after a timeout.

That timeout is the crux of the mechanism: a shorter TTL means faster eviction of dead instances but more heartbeat chatter and more registry writes at scale; a longer TTL means less overhead but a longer window where a crashed instance still looks live to anyone reading the registry. This window has a name worth using out loud: the stale-registry window, and it's structurally identical to the health-check detection-lag window in load balancing — both are "how long can a dead node keep receiving traffic because nobody has proven it's dead yet."

Because a registry is itself a piece of distributed state that many clients read and write concurrently, the registries used in production are typically backed by a consensus protocol — etcd runs Raft, ZooKeeper runs ZAB, Consul runs Raft internally too. That's a direct link to 11-consensus-algorithms: the registry needs its own writes (register, heartbeat, deregister) to be linearizable across a cluster of registry nodes, or two registry replicas could disagree about who's alive.

The trade-off that matters

Every discovery mechanism is trading staleness window against overhead. Push the TTL down and heartbeat interval down, and you get fresher answers at the cost of more writes hammering the registry (and a registry that itself becomes a bottleneck under enough churn). Push them up and the registry gets cheap and simple, but you're accepting that a nontrivial fraction of "live" answers are lies for a few seconds after any crash. No registry design closes this window to zero — the fix is layering a second, faster signal (active health checks at the LB/sidecar, per 09-load-balancing) on top of the registry's slower liveness signal, rather than trusting registry freshness alone.

Load balancing and service discovery are two halves of the same problem: discovery answers "who's alive," load balancing answers "which of them gets this request." A registry with stale entries makes even the smartest routing algorithm route into a hole — which is exactly what the visualization below demonstrates directly.

Interview Line

"The question I actually care about is who's doing the health checking and how stale can their answer be. A registry's TTL/heartbeat mechanism only tells you 'this instance hasn't explicitly told me it's gone' — it does not tell you it's actually healthy, and that gap is a real window where dead instances keep receiving traffic. That's why I lean server-side discovery through an LB or sidecar by default: it gives me a second, faster active-health signal on top of the registry's slower lease expiry, instead of every client trusting a possibly-stale registry snapshot directly. And because the registry itself is shared mutable state read by every client, it's backed by a consensus protocol under the hood — Raft in etcd and Consul, ZAB in ZooKeeper — so 'is the registry consistent' quietly becomes a consensus question too."

Key Takeaways

  • TTL/heartbeat is a liveness guess, not a health check — a crashed instance that never deregisters looks LIVE in the registry until its lease expires. That stale window is structurally the same problem as LB health-check detection lag (09-load-balancing), just measured against a different clock.
  • Client-side discovery trades a network hop for staleness risk — one fewer hop than going through a proxy, but every client language needs its own discovery + LB logic, and every client dials directly off a registry snapshot that can already be lying.
  • Server-side discovery pushes staleness mitigation into one place — the LB/sidecar can run active health checks far faster than any registry TTL, so it's usually the safer default even though it costs an extra hop and makes the intermediary itself a scaling concern.
  • DNS-based discovery inherits DNS's caching problem — TTLs are honored inconsistently across resolvers, and DNS has no concept of "half of these records are unhealthy." Fine for coarse, slow-changing topology; risky as the only mechanism for pod-level routing that changes every deploy.
  • Registries are consensus systems wearing a directory-service costume — etcd (Raft), Consul (Raft), ZooKeeper (ZAB) all need a majority quorum to agree on registry writes, which ties discovery directly back to 11-consensus-algorithms: it's the same "who's allowed to say what's true" problem, applied to service liveness instead of leader election.
  • Shrinking TTL to fix staleness has a ceiling — push heartbeat interval down far enough and the registry itself becomes the bottleneck under heartbeat write volume at fleet scale; the real fix is a second, faster signal (active health checks), not chasing a zero-staleness registry.
