Concurrency Control (Optimistic, Pessimistic, MVCC)

Optimistic vs pessimistic locking, and multi-version concurrency control (MVCC) — how databases let readers and writers avoid blocking each other, and when optimistic locking's retry cost bites.

Theory

Same problem, three strategies

Two transactions want to read-modify-write the same row at close to the same time. Whatever mechanism you use has to prevent the lost-update anomaly — T1 reads balance = 100, computes 150, T2 reads balance = 100, computes 130, both write, and one of the writes silently disappears — while still letting the database do useful concurrent work instead of serializing everything behind a single global lock. Pessimistic locking prevents the anomaly by reserving the resource before anyone touches it. Optimistic locking lets everyone proceed unlocked and only checks for a conflict at commit time. MVCC (multi-version concurrency control) sidesteps the question almost entirely by never overwriting a row in place — every write creates a new version, and every transaction reads whichever version was live when its snapshot was taken. All three are correct if implemented right; they differ in where the cost lands.

Pessimistic locking

SELECT ... FOR UPDATE (or an explicit row/table lock) acquires an exclusive lock on the row before reading it. Every other transaction that wants to touch that row blocks — not fails, blocks — until the lock holder commits or rolls back and releases it. This is simple to reason about (nothing ever computes against stale data) and wastes zero work: a blocked transaction is waiting, not burning CPU re-deriving an answer it's about to throw away. The cost is throughput under contention — a hot row becomes a queue — and the moment two transactions try to lock two rows in opposite orders you get a genuine deadlock; the engine detects the cycle via a wait-for graph and unilaterally aborts one transaction (the "victim") to break it, which means your application still needs a retry path even in the pessimistic case.

Optimistic locking

No lock is taken on read. Instead, every row carries a version column (or a last-modified timestamp), and every write includes it in the predicate: UPDATE accounts SET balance=150, version=6 WHERE id=1 AND version=5. If another transaction committed a change in between, the row's version has already moved past 5, the predicate matches zero rows, and the application sees the conflict as "0 rows affected." It then has to explicitly retry: re-read the current row, recompute the change against the new state, and try the write again. JPA/Hibernate's @Version field, DynamoDB conditional writes, and REST APIs using If-Match: etag are the same pattern at different layers. Optimistic locking is nearly free when conflicts are rare — no lock overhead, no blocked threads — but every conflict means the whole read-modify-write cycle happened for nothing and has to run again, and that retry cost is what actually decides whether it's the right call.

MVCC

Postgres, MySQL/InnoDB, and Oracle all implement this at the storage-engine level by default. Instead of overwriting a row in place, an update writes a brand-new row version — Postgres literally appends a new tuple with a new xmin and marks the old tuple's xmax — and leaves the old version around until nothing can see it anymore. Every transaction gets a consistent snapshot — the set of versions committed as of its start (or, in read-committed mode, as of each statement) — and reads against that snapshot, so readers never block writers and writers never block readers; they're literally looking at different tuples. The cost shows up later: old versions pile up until a background process reclaims them (Postgres's VACUUM), and if vacuum falls behind — a single long-running transaction holding back the oldest visible snapshot is the classic cause — table and index bloat grows unbounded and query latency degrades system-wide, a real production incident category, not a theoretical one. Writers to the same row still serialize eventually: Postgres takes a brief row-level lock only at write time (not for the transaction's whole lifetime), and the second writer either quietly re-applies against the now-current row (read committed) or aborts with "could not serialize access due to concurrent update" (serializable, via SSI — serializable snapshot isolation) if letting it through would produce an anomaly.

The trade-off that actually matters

Contention rate decides this, not preference. Under low contention, optimistic locking and MVCC both win — no lock wait, no blocked threads, and conflicts are rare enough that the occasional retry is noise. Under high contention, optimistic locking's retry cost compounds exactly when you can least afford it: contention is usually a symptom of load, so retry storms show up in p99 latency right when the system is already struggling, and in the worst case throughput can collapse as everyone keeps re-deriving work that keeps getting invalidated. Pessimistic locking's wait time is worse in the low-contention case (you pay lock overhead for collisions that mostly don't happen) but degrades more gracefully under high contention — a blocked transaction is waiting, not wasting CPU on a doomed computation. MVCC is the default most engineers should reach for because the database gives it to you for free at the storage layer; the real decision left on the table is the isolation level — repeatable read/snapshot isolation prevents dirty and non-repeatable reads but not write skew, serializable does, at the cost of more aborts under contention.

Deadlock (pessimistic)

Two transactions lock rows A and B in opposite order — each waits on the other forever until the engine's wait-for-graph detector kills one as the victim.

Retry storm (optimistic)

Under high contention, every transaction repeatedly does the full read-modify-write cycle only to have its version check fail, wasting CPU exactly when the system is already loaded.

Write skew (MVCC / snapshot isolation)

Two transactions each read overlapping data and each write disjoint rows that individually look valid, but the combined result violates an invariant neither transaction could see — e.g. two on-call engineers each confirm "at least one other is covering" and both go off duty, leaving zero.

Vacuum lag / table bloat (MVCC)

A long-running transaction holds back the oldest visible snapshot, old row versions can't be reclaimed, and table/index bloat degrades every query — not just the hot row's.

Where this generalizes: the same "reserve up front vs. check at commit vs. version everything" menu reappears one layer up in 15-distributed-locking — a distributed lock is pessimistic concurrency control stretched across a network, and it inherits the same failure mode (a lock held past its real validity, e.g. after a GC pause) unless it's paired with a fencing token, which is really just optimistic locking's version-check idea bolted onto a lock.

Interview Line

"Pick a concurrency-control strategy by contention rate, not by habit. If two transactions almost never touch the same row, optimistic locking is basically free — read without a lock, write with a WHERE version = X, and if it fails, retry; the whole cost only shows up when you actually collide. But past a certain conflict rate optimistic locking becomes a liability — you're doing the full read-modify-write work and throwing it away on every collision, so retry storms show up in your p99 exactly when the system is already under load, which is the opposite of what you want. Pessimistic locking is the right call there — block up front, pay the wait time explicitly instead of paying it as wasted retried work. What I actually reach for by default is MVCC, because Postgres, InnoDB, and Oracle all give it to you for free at the storage-engine level — readers get a consistent snapshot without ever blocking a writer and vice versa — and the only thing left to actually think about is whether the isolation level is strong enough to stop write skew. Repeatable read isn't; serializable is, which is the level that actually rejects the classic bug where two on-call engineers each check that at least one other is covering and both go off duty."

Key Takeaways

  • MVCC is the default, not a special case — Postgres, MySQL/InnoDB, and Oracle give you non-blocking reads for free at the storage layer; the decision left on the table is isolation level, not whether to use MVCC at all.
  • Optimistic locking's retry cost is nonlinear under contention — cheap below roughly 10–20% conflict rate, but past that pessimistic locking usually wins on real throughput because you stop paying for doomed read-modify-write cycles.
  • Deadlocks are pessimistic locking's tax — take locks in a consistent order across the codebase (e.g. always lock the lower primary key first) to shrink the cycle space, and always keep an application-level retry path for the victim transaction.
  • Write skew is the anomaly snapshot isolation doesn't catch — repeatable read lets it through silently; only serializable (SSI in Postgres, CockroachDB's native serializable) rejects it, at the cost of more aborts under contention.
  • Vacuum lag is a production incident category, not a footnote — one long-running transaction pins the oldest visible MVCC snapshot, old tuples can't be reclaimed, and bloat degrades every query on the table, not just the contended row.
  • Distributed locking (15-distributed-locking) is this problem stretched across a network — a lock held past its real validity (GC pause, clock drift) is the distributed analogue of a deadlock victim that never got cleaned up, which is why fencing tokens — optimistic locking's version-check idea bolted onto a lock — are non-negotiable there.
