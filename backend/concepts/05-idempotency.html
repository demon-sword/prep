Idempotency

Why at-least-once delivery makes idempotency non-negotiable, the idempotency-key pattern (client-generated, atomic check-and-store), natural idempotency via conditional writes, and HTTP method semantics.

Theory

The definition

An operation is idempotent if performing it multiple times has the same effect as performing it once. SET x = 5 is idempotent; x += 5 is not. That's the whole vocabulary word — the interesting part is what falls out of taking it seriously.

Why it's non-negotiable

Every distributed system delivers at-least-once. Networks time out without telling you whether the operation succeeded on the other end. Retries are automatic and often invisible — a client library, a load balancer, an orchestration engine like Temporal, all of them retry on timeout by default. You cannot build a correct distributed system without idempotency somewhere — the only question is whether you designed for it or discovered you needed it in production.

The canonical failure: a payment request times out, the client retries, and the customer is charged twice. The server did nothing wrong on either attempt — it succeeded both times. The bug isn't in the request handling, it's in the absence of a mechanism to recognize "I've already done this."

The idempotency key pattern

The client generates a unique key per logical operation (a UUID) and sends it with the request. The server:

  1. Checks whether it has seen this key
  2. If yes, returns the stored response from the first attempt — it does not re-execute
  3. If no, executes, stores the result against the key, returns it

Critical details people miss:

Client-generated, once

The key must be generated by the client, once, before the first attempt — and reused across retries. A key generated per-attempt defeats the purpose entirely: the server sees a "new" key every time and happily re-executes.

Store the response, not a flag

The retry needs to receive the same answer, not a bare "duplicate" error. If you only record "this key was used," a retry has no way to learn what actually happened the first time.

Check-and-store must be atomic

Otherwise two concurrent retries both see "not seen" and both execute. Use a unique constraint on the key column, a transaction, or a distributed lock — a read-then-write with a gap in between is a race, not a guard.

Keys need a retention window

Long enough to cover any realistic retry (24h is common), then expire. Keep them forever and the store grows unbounded; expire too early and a slow retry re-executes.

Natural idempotency

Sometimes you get it free by design, and it's worth preferring these over key-tracking machinery where you can — less to get wrong:

  • Conditional writes — UPDATE ... WHERE version = 7. The second attempt matches nothing and no-ops.
  • Upserts on a natural key — the operation converges to the same state regardless of how many times it runs.
  • Set semantics — adding an element that's already present is a no-op by definition.
  • Deriving state rather than mutating it — recomputing a total from an event log is idempotent; incrementing a counter isn't. This is the same instinct behind event sourcing (16-event-sourcing-cqrs): state that's a pure function of an immutable log is idempotent to recompute by construction.

HTTP semantics

GET, PUT, DELETE are defined as idempotent; POST is not. This is why "create" endpoints are the ones that need explicit idempotency keys, and why PUT-with-client-generated-ID is sometimes a cleaner API design than POST-and-return-an-ID — it lets the transport-level idempotency guarantee do the work instead of bolting on a key.

Where this appeared in the Simbian design: execute_write_tool is idempotency-keyed precisely because a retried containment action is a customer-visible incident — isolating the same host twice, or worse, re-running a destructive remediation step twice, is not a "just retry it" situation the way a read is.

Interview Line

"The write tools carry an idempotency key generated when the action is first approved, so a Temporal retry after a timeout can't isolate the same host twice. The key is checked and the action recorded in one atomic operation — otherwise two concurrent retries both see 'not executed' and both fire."

Key Takeaways

  • At-least-once delivery is why idempotency is mandatory, not optional hardening — every queue, every retrying HTTP client, every orchestration engine (Temporal, SQS, Kafka consumers) gives you at-least-once by default, so idempotency is what makes those retries safe rather than a liability (see 02-queues-backpressure).
  • The key must outlive the attempt, not the request object — generate it once on the client (or at the point of first approval), before the first network call, and thread it through every retry unchanged. A key minted per HTTP call is indistinguishable from having no key at all.
  • Store the response, not just a "seen" bit — the whole point of a retry is the client wants the answer it missed the first time, not a 409.
  • Check-and-store must be one atomic operation — a unique constraint on the key column (or a transactional check-and-set) closes the race where two concurrent retries both see "not executed" and both fire. A naive read-then-write is a TOCTOU bug wearing a dedup costume.
  • Prefer natural idempotency when the domain gives it to you — conditional writes (WHERE version = 7) and upserts on a natural key need no key-store machinery at all, and that's less surface area to get wrong.
  • Idempotency is the precondition for every other reliability pattern that leans on retries — circuit breakers (06-circuit-breakers-bulkheads) only make sense to retry-and-trip against operations that are safe to repeat; without idempotency, a "helpful" retry is just a second bug.
