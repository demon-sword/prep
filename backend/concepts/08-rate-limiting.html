Rate Limiting

Protection vs compliance limiting, algorithm comparison (token bucket, leaky bucket, fixed/sliding window), distributed rate limiting across a fleet, and cost-based limiting for variable-cost requests.

Theory

Two distinct purposes

Rate limiting solves two different problems that get lumped together but need different designs:

  • Protection — stop any one client from exhausting shared capacity. Inward-facing. It's about you defending your own service.
  • Compliance — respect a downstream provider's limits so you don't get throttled or banned. Outward-facing. It's about you behaving as a good client of someone else's service.

These need different designs. Protection is per-client and can reject — a 429 is an acceptable, even correct, outcome. Compliance is global across your whole fleet and usually needs to queue rather than reject, because the work still has to happen; you can't tell your own users "no" just because your vendor has a budget.

Algorithms

Token bucket

A bucket holds up to B tokens, refilled at R per second. Each request takes a token; no token, no service. Allows bursts up to B while enforcing an average of R. The most common choice and usually the right default, because real traffic is bursty and pure smoothing is unnecessarily harsh.

Leaky bucket

Requests enter a queue and drain at a fixed rate. Output is perfectly smooth. Good when the downstream genuinely cannot tolerate bursts. Adds latency by design — you're trading burst tolerance for a flat output rate.

Fixed window

Count requests per calendar minute, reset at the boundary. Trivial to implement, but has the boundary problem: a client can send the full limit at 11:59:59 and again at 12:00:00, achieving 2x the intended rate in under two seconds.

Sliding window log

Store a timestamp per request, count those within the trailing window. Exact — no boundary exploit — but memory scales with request volume, which is the trade you're making for exactness.

Sliding window counter

Interpolate between the previous and current fixed windows. Approximates the sliding window with fixed-window memory cost. The usual production compromise: cheap to store, close enough to exact.

Distributed rate limiting

The hard part. With N instances, a naive per-instance limit of limit/N breaks under uneven load balancing and wastes capacity — one hot instance hits its share while others sit idle under the global limit.

  • Centralised counter (Redis) — accurate, but adds a network hop to every request and makes Redis a dependency on the hot path. Use atomic operations or a Lua script; a read-then-write is a race — two instances can both read "9 of 10 used" and both admit the 10th and 11th request.
  • Local buckets with periodic sync — each instance holds a portion and reconciles periodically. Fast, approximate, can overshoot briefly between syncs.
  • Gossip / lease-based — instances lease portions of the global budget from a coordinator, returning unused capacity. More complex, better utilisation than a static split.

In an interview, the honest answer is that approximate distributed rate limiting is usually fine — you're protecting against 10x, not enforcing an exact count. Say that; over-engineering exactness is a common trap that turns a rate limiter into the new bottleneck.

Design decisions to state

  • What's the key? Per user, per API key, per IP, per tenant, per endpoint, or a combination. Per-IP alone is weak (NAT, proxies) and can punish shared networks — an office or a mobile carrier's NAT pool looks like one very aggressive client.
  • Reject or queue? Rejecting returns 429 and is honest. Queueing preserves the work but converts a throughput problem into a latency problem — and needs its own bound (see 02-queues-backpressure).
  • Tiered limits — different quotas per plan, or per priority class.
  • Cost-based limiting — not all requests are equal. An LLM call costing 50k tokens shouldn't count the same as a health check. Rate limit on estimated cost rather than request count where the variance is large.

Client-side behaviour

When you're on the receiving end of a 429: respect Retry-After if present, back off exponentially with jitter, and cap total retries with a budget. Retrying a rate limit aggressively is how a throttle becomes a ban — the same jitter discipline that keeps circuit-breaker retries from synchronizing (06-circuit-breakers-bulkheads) applies here too.

Communicating limits

Return X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset headers, and 429 Too Many Requests with Retry-After when limited. Clients can only behave well if you tell them the rules.

Backpressure and rate limiting are the same instinct applied at different boundaries — one internal (protect your own queue/thread pool from your own producers), one external (protect a shared resource, or a vendor's budget, from all your clients or instances combined).

Interview Line

"The limiter has to be shared across the fleet, not per-instance, because the vendor's limit is global. I'd use a token bucket in Redis with an atomic decrement — it allows bursts up to the bucket size, which matches real traffic, while holding the average. And for LLM calls I'd rate limit on estimated tokens rather than request count, because a 50k-token investigation and a health check aren't the same load."

Key Takeaways

  • Token bucket is the default — it's the only one of the five algorithms that both tolerates real bursty traffic and holds a strict average, which is why it's the standard choice absent a reason to pick something else.
  • Fixed window's boundary problem is a 2x exploit, not a rounding error — a client can legitimately send the full limit at the last second of one window and the first second of the next, doubling the intended rate in under two seconds. Sliding window counter closes this for roughly the memory cost of fixed window.
  • A read-then-write counter in a distributed limiter is a race — two instances can both read "9 of 10 used" and both admit past the limit. Use an atomic Redis INCR with TTL or a Lua script, not a GET-then-SET.
  • Approximate distributed rate limiting is usually the right call — you're protecting against a 10x spike, not enforcing an audit-grade exact count. Reaching for a lease-based/gossip scheme before you need it is over-engineering the wrong dimension.
  • Cost-based limiting matters when request cost varies wildly — rate limit LLM calls on estimated tokens, not request count; a health check and a 50k-token investigation are not the same load, and counting them equally either starves the expensive path or lets it blow the budget alone.
  • Rate limiting and backpressure (02-queues-backpressure) are the same instinct at different boundaries — one protects a shared resource from many external clients, the other protects a queue from its own producers — and both share the same client-side discipline: jittered backoff, same as circuit breaker retries (06-circuit-breakers-bulkheads).
