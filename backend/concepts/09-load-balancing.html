Load Balancing

L4 vs L7 load balancing, algorithm choice (round robin, least connections, consistent hashing, weighted), health checks, and connection draining during deploys.

Theory

L4 vs L7

A load balancer sits at one of two layers, and the layer decides what it's allowed to know:

  • L4 (transport) — routes on IP/port, never parses HTTP. It sees packets, not requests. Fast, cheap in CPU, protocol-agnostic (works for raw TCP, gRPC, anything). Examples: AWS NLB, IPVS, HAProxy in tcp mode. It can't do anything content-aware — no path routing, no header inspection, no per-request retries.
  • L7 (application) — terminates the connection, parses HTTP, and routes on path, host header, cookie, or method. This is what enables path-based routing (/api/* to one fleet, /static/* to another), TLS termination at the edge, and request-level retries. Examples: AWS ALB, nginx, Envoy. The cost is real: terminating TLS and parsing HTTP per request is strictly more work than shuffling packets, and an L7 balancer is itself a stateful thing that can become the bottleneck.

The trade-off to state out loud: L4 is faster and simpler but blind; L7 is slower and more expensive per request but lets the balancer make smart decisions instead of pushing that logic into every backend.

Routing algorithms

Round robin

Cycle through backends in order. Trivial, stateless, and blind to actual load — if request cost varies (one backend is mid-query on an expensive report while another is idle), round robin still hands them equal shares and the slow one falls behind.

Weighted round robin

Same cycle, but each backend gets a static weight proportional to its known capacity (bigger instance type gets more traffic). Fixes known capacity differences, still blind to live load.

Least connections

Route to whichever healthy backend currently has the fewest in-flight requests. Adapts to real load — a backend stuck on a slow query naturally receives fewer new requests because its count stays high. The right default when request duration varies.

Consistent hashing

Hash a request key (client ID, session ID, cache key) onto a ring shared with backend positions; route to the nearest node clockwise. Gives you session affinity and cache locality — same client keeps hitting the same backend — with the same minimal-remap property as 04-sharding-partitioning's ring: adding/removing a node only reshuffles the keys adjacent to it, not the whole keyspace.

Power of two choices (P2C)

Pick two backends at random, route to whichever has fewer active connections. Approximates least-connections' quality without scanning the whole fleet on every request — the algorithm behind Envoy's default LB policy at scale, because true least-connections needs a global view that gets expensive with thousands of backends.

Health checks

Two flavors, usually run together:

  • Active — the balancer polls a health endpoint (GET /healthz) on an interval, independent of real traffic. Detects a dead backend before a user request has to.
  • Passive (outlier detection) — the balancer watches real traffic: a backend returning a run of 5xx or timing out gets ejected without a dedicated probe. Envoy's outlier detection works this way. Cheaper (no extra polling load) but only detects failure after real requests already hit it.

Both need thresholds, not single-sample decisions — eject after N consecutive failures (commonly 3), re-admit after M consecutive successes (commonly 2, and usually M ≥ N to avoid flapping a backend back in too eagerly). A single dropped health check is noise; three in a row is signal. This threshold creates an unavoidable detection-lag window: with a 5s check interval and a 3-fail threshold, a backend can be dead for up to 15 seconds while still receiving traffic. That gap is exactly why client-side circuit breakers (06-circuit-breakers-bulkheads) exist as defense-in-depth — the LB's health check is not fast enough to be your only protection.

Connection draining

During a deploy or scale-down, an instance being removed must stop receiving new requests but be allowed to finish the requests already in flight — that's draining, not killing. The balancer marks the instance "not accepting," waits for its in-flight count to hit zero (or a bounded drain timeout expires, forcing termination), then removes it. Skip this and a rolling restart looks green on every dashboard while silently cutting live connections mid-response. This is the load-balancer-level half of what 20-zero-downtime-deployments needs; the other half is the app not shutting down until its own in-flight work is done. In Kubernetes terms, this is exactly the job split between the readiness probe (flip to not-ready, get removed from the Service's endpoint list, keep running) and the liveness probe (actually kill the process) — conflating the two is a common way to get exactly this bug.

The trade-off that matters

Every step up in routing intelligence costs bookkeeping: round robin needs no state, least-connections needs a live counter per backend, consistent hashing needs the ring maintained across scale events. Pick the cheapest algorithm that's still blind to the failure mode you actually have. If request cost is uniform, round robin is fine and anything smarter is wasted complexity. If request cost varies by 10x (an LLM call vs a health check), round robin actively creates the imbalance and least-connections or P2C is the correct default, not a nice-to-have.

Load balancing and service discovery (10-service-discovery) are two halves of the same problem: discovery answers "who's alive," load balancing answers "which of them gets this request." A registry with stale entries makes even the smartest routing algorithm route into a hole.

Interview Line

"I'd default to L7 with least-connections or power-of-two-choices whenever request cost is uneven — round robin actively creates imbalance the moment one backend is doing something 10x more expensive than another. Health checks need consecutive-failure thresholds, not single-sample decisions, and that threshold times the check interval is a real detection-lag window your client-side timeouts and circuit breakers have to cover, not the load balancer alone. And connection draining is non-negotiable during deploys — readiness-false has to mean 'stop sending new traffic' while in-flight requests still get to finish, otherwise your rolling restart is dropping live connections while every dashboard says green."

Key Takeaways

  • Round robin is blind to load, not just naive — with uniform request cost it's fine; with variable cost (an LLM call next to a health check) it actively creates the imbalance it's supposed to prevent. Least-connections or P2C is the correct default the moment cost varies.
  • Health check thresholds trade detection speed for stability — a 5s interval with a 3-fail-to-eject threshold means a dead backend can eat traffic for up to 15s. That gap is exactly why circuit breakers (06-circuit-breakers-bulkheads) exist on the client side as a second layer, not a redundant one.
  • Consistent hashing at the LB layer is the same ring math as sharding (04-sharding-partitioning), just applied to request routing instead of data partitioning — same minimal-remap property, same hot-key risk if the key distribution is skewed.
  • Connection draining is the LB half of zero-downtime deploys (20-zero-downtime-deployments) — readiness probes pull an instance out of rotation without killing it; liveness probes kill it. Conflating the two turns a rolling restart into silent dropped connections.
  • Load balancing needs service discovery to know who's even in the pool (10-service-discovery) — the smartest routing algorithm is worthless against a registry with stale entries pointing at dead instances.
  • A newly re-admitted instance shouldn't get a full traffic share instantly — a cold JVM/JIT or empty local cache getting slammed at full weight right after passing health checks is its own mini thundering-herd; production LBs support a slow-start ramp for exactly this.
