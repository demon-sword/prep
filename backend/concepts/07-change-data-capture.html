Change Data Capture (CDC)

Why dual writes aren't atomic, log-based CDC off the replication log (WAL/binlog/oplog) vs trigger-based vs query-based, and the transactional outbox pattern for explicit event-schema control.

Theory

The problem it solves

You have data in a database. Something else needs to know when it changes — a search index, a cache, an analytics warehouse, another service. The naive options are all bad:

  • Dual writes (write to the DB, then publish an event) — not atomic. The process can die between the two writes, leaving them permanently inconsistent. This is the anti-pattern CDC exists to replace, and naming it is a strong signal in an interview.
  • Polling for changes — high latency, high load on the source table, misses deletes, misses intermediate states between polls.

CDC reads the database's own replication log — the WAL in Postgres, the binlog in MySQL, the oplog in MongoDB — and turns committed changes into a stream of events. Because it reads the log the database already writes for its own replication, the events are exactly the committed changes, in commit order, with no extra write path to fall out of sync with the source of truth.

Log-based vs the alternatives

Log-based

Debezium is the standard tool. Low overhead (reads a log the DB already writes), no schema changes required, captures deletes, preserves commit ordering. Requires access to the replication stream and some operational care (log retention, connector lag monitoring).

Trigger-based

Database triggers write to an audit table, which is then polled or streamed. Works on databases without log access, but adds write-path overhead inside the same transaction and can affect commit latency.

Query-based

Poll WHERE updated_at > last_seen. Simple to build, but misses deletes entirely, misses intermediate updates between polls, needs a reliable, indexed timestamp column, and has a race at the polling boundary.

The transactional outbox

The pattern to know when log-based CDC isn't available, or when you want explicit control over the event schema rather than raw row diffs:

  1. In the same transaction as the business write, insert a row into an outbox table.
  2. A separate relay process reads the outbox and publishes to the message broker.
  3. Mark the row published — or, more commonly, let CDC itself read the outbox table as its source, so you get log-based delivery with an application-controlled event schema.

Because the business write and the outbox insert share a transaction, they're atomic — the pair either both commit or both roll back, closing the exact gap dual writes leave open. The relay (or CDC connector) is at-least-once, so consumers still need to be idempotent.

Semantics

CDC events are usually at-least-once and ordered per key (per row, or per Kafka partition keyed by row id) — not globally ordered across the whole stream. Consumers must be idempotent (see 05-idempotency). Many CDC events are naturally idempotent if you treat them as upserts of the full row state rather than deltas — applying the same "row is now X" event twice produces the same result both times; applying "increment by 1" twice does not. That's another instance of "derive state rather than mutate it."

Two more things worth knowing:

  • Snapshot plus stream — a new consumer needs the current state of the table before it can meaningfully apply the change stream on top of it. Tools handle this with an initial full-table snapshot followed by streaming from the log position the snapshot was taken at, so nothing is missed and nothing is double-applied.
  • Schema evolution — the source table's schema will change over the system's lifetime. Consumers must tolerate added columns without breaking; a schema registry (Avro/Protobuf with Confluent Schema Registry, for example) enforces compatibility rules on both sides.

Where it's used

Cache invalidation, search index maintenance, materialized views, data warehouse replication, the strangler-fig migration pattern (dual-running an old and a new system off the same source of truth), and event-driven architectures generally.

Where this appeared in the Simbian design: alert enrichment data was originally dual-written to Postgres and a search index in the same request handler — a crash between the two writes left the index permanently stale for that alert with no automatic way to detect it. Switching to CDC off the Postgres WAL (via Debezium) removed the second write path entirely; the index became a consumer of committed changes instead of a second thing the request handler had to get right.

Visualization

Dual write vs. CDC vs. transactional outbox. Pick a strategy, then step through a write. In dual write mode you can crash the process between the DB write and the event publish — the DB and the event bus go permanently out of sync and nothing detects it. In CDC mode there's only one write path (the DB); the event stream is derived from the replication log after commit, so there's nothing to crash between. In transactional outbox mode the business row and the outbox row commit atomically in one transaction, then a relay (or CDC reading the outbox table) publishes at-least-once.

Interview Line

"Rather than dual-writing to the DB and the event bus — which isn't atomic and drifts permanently the first time a process dies between the two — I'd use CDC off the replication log, or a transactional outbox if I need control over the event schema. Consumers are idempotent because CDC is at-least-once."

Key Takeaways

  • Dual writes aren't atomic — naming that is the whole interview signal. A crash between the DB write and the event publish leaves them permanently inconsistent, and nothing in the naive design detects it, let alone repairs it.
  • CDC reads a log the database already writes for replication — the WAL in Postgres, binlog in MySQL, oplog in MongoDB — so there's no second write path to fall out of sync with. Debezium is the standard tool for turning that log into a Kafka stream.
  • The transactional outbox is the pattern when you need explicit event-schema control — the business write and the outbox insert commit in the same DB transaction, so they're atomic by construction; a relay or CDC connector then delivers at-least-once from the outbox table.
  • CDC events are at-least-once and ordered per key, not globally — consumers must be idempotent (see 05-idempotency). Treating events as upserts of full row state rather than deltas gets you idempotency for free in most cases.
  • A new consumer needs snapshot + stream — an initial full-table snapshot followed by streaming from the log position the snapshot was taken at, or the consumer starts with an empty view and silently drops history.
  • CDC is dual writes' fix inside one system boundary; the same "derive rather than mutate" instinct taken further — events as the actual source of truth instead of derived from row changes — is Event Sourcing (16-event-sourcing-cqrs).
