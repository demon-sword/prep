Distributed Locking and Fencing Tokens

Distributed locks (Redlock, lease-based locks) and why a naive lock built on a single key is dangerous under GC pauses or clock drift, and how fencing tokens close the gap between lock expiry and actual work completion.

Theory

The problem: mutual exclusion across a network you don't control

A distributed lock exists so that multiple independent processes — worker replicas pulling from a queue, cron jobs running on every pod, a fleet of API servers — can agree that only one of them should do a given piece of work at a time: run the nightly reconciliation job, process a specific order, hold the "primary" role. A local mutex works because the OS scheduler and a single process boundary give you an atomicity guarantee for free. Across a network there's no equivalent trusted referee built in — you have to build one, usually on top of a single system of record that supports atomic conditional writes (Redis SET key value NX PX ttl), an ephemeral session-backed node (ZooKeeper, etcd), or a database row with an owner column and an expiry timestamp. And critically: "I hold the lock" becomes a claim a client makes to itself, not a fact the system continuously verifies — which is exactly where this gets dangerous.

Lease-based locks — the mechanism

Every practical distributed lock is a lease: an exclusive claim with a time-to-live, not a permanent grant. SET lock:order-42 client-a NX PX 10000 in Redis acquires the key only if it doesn't already exist, with a 10s TTL — the owner must either finish inside that window or renew (heartbeat) before it expires, and must release with a compare-and-delete (a small Lua script checking the stored value equals its own client id, so it never deletes a lock someone else now owns). ZooKeeper and etcd do the equivalent with an ephemeral node tied to a client session: if the client's heartbeat lapses — crash, GC pause, network partition — the server-side session timeout fires and the node is deleted automatically, releasing the lock and firing a watch that wakes the next waiter. Redlock (Antirez's algorithm) runs the same SET-NX-PX pattern against a majority of N independent Redis instances (typically 5, needing 3) within a bounded acquisition window, arguing this removes the single-Redis-instance SPOF the same way a quorum removes a single-node SPOF in consensus.

Why a naive lock is dangerous — the Kleppmann critique

The TTL is enforced by the lock service's clock; the client's belief that it still holds the lock is enforced by nothing. There is no upper bound on how long a client can be delayed between "acquired the lock" and "finished the work and released it": a JVM stop-the-world GC pause of 10-30 seconds under load is a documented real occurrence, not a hypothetical; so is an OS scheduling stall, a slow disk fsync, or a network partition that hides the expiry notification from the client entirely. TTLs are typically chosen in the 5-30s range, trading "long enough that normal work doesn't expire mid-flight" against "short enough that a genuinely dead holder fails over quickly" — and every team that picks that number is picking a probability, not a proof. This is exactly Martin Kleppmann's 2016 critique of Redlock: its safety depends on bounded clock drift and bounded process pauses, and no real system actually guarantees either, so a distributed lock built this way is mutual exclusion most of the time, not mutual exclusion under adversarial timing. Antirez's rebuttal is fair as far as it goes — for coordination hygiene (avoid running the same cron job twice, dedupe non-critical work) that's an acceptable bet — but the distinction between "a lock as an efficiency optimization" and "a lock as a correctness guarantee" is exactly what an interviewer is listening for.

Fencing tokens — the fix that actually restores correctness

Instead of trusting the client's claim that it still holds the lock, make the resource being protected the arbiter. Every time the lock is granted — including to a second client after the first one's lease expired — the lock service hands out a monotonically increasing fencing token (a simple integer, incremented on every acquire). The client attaches that token to every write it makes. The protected resource — a database row, a file store, a queue — rejects any write carrying a token lower than the highest one it has already accepted. A client that paused past its TTL and wakes up believing it's still the owner sends its write with the old, now-stale token; the resource sees a newer token has already been accepted and rejects it outright, instead of silently letting a zombie writer corrupt state. This is the exact same idea as optimistic locking's version column (see 14-concurrency-control) — a monotonic counter checked at the point of the actual write — bolted onto a mutual-exclusion primitive instead of a plain row update.

The trade-off that actually matters

Fencing tokens only work if the thing being protected can enforce the check — a database row with a fencing_token column and a conditional WHERE fencing_token < :new_token update does this cleanly; an arbitrary side effect like sending an email or calling a non-idempotent third-party API generally can't be fenced, because there's no shared resource on the other end capable of comparing tokens. So the practical stance: reach for a distributed lock to reduce duplicate work under normal conditions, but never let the lock alone be the thing standing between you and a correctness bug. Either fence the resource where that's possible, or make the protected operation idempotent (05-idempotency) so that a duplicate execution from a stale holder is harmless instead of catastrophic — the two techniques are complementary, not either/or.

Stale lock holder (GC pause / clock drift)

A holder pauses past the lease TTL without knowing it — the lock is granted to a second client, and the first resumes still believing it's exclusive owner. Two writers, one "exclusive" critical section.

Redlock's timing-assumption debate

Redlock's safety proof assumes bounded clock drift and bounded process pauses between nodes — assumptions Kleppmann showed don't hold under GC pauses or NTP jumps, which is why it's treated as an efficiency mechanism, not a correctness one, absent fencing.

Single-instance Redis lock as a SPOF

A lock built on one Redis node can split-brain on failover: the primary accepts the SET, crashes before async-replicating it, and a promoted replica has no record of the lock — a second client acquires the "same" lock cleanly.

Thundering herd on release

When a popular lock frees, every waiter retries at once — same stampede shape as a cache-miss thundering herd (01-caching-strategies); jittered backoff on retry is the same fix.

This is the same "who do you trust, and for how long" question consensus algorithms answer more rigorously — a distributed lock is pessimistic concurrency control stretched across a network, and Raft/Paxos-backed lock services (etcd, ZooKeeper) are popular precisely because leader election already solved the "who's allowed to act right now" problem with a real majority quorum instead of a single node's TTL guess. Interview Line

"The naive version of a distributed lock — SET key value NX PX 10000 — works until it doesn't: a GC pause, a slow disk write, a network blip past your TTL, and the lock holder doesn't know it's already lost the lock. It keeps executing the critical section believing it's still the exclusive owner, another client legitimately sees the lease expired and acquires the same lock, and now you have two writers inside what was supposed to be a single-writer section — that's the exact scenario Kleppmann used to argue Redlock's timing assumptions aren't sufficient for correctness, only for efficiency. The fix isn't a longer TTL or a fancier lock algorithm; it's making every write downstream carry a monotonically increasing fencing token and having the resource itself reject any write whose token is lower than the last one it accepted. That turns 'I believe I hold the lock' into something the storage layer can actually verify instead of trusting the client's word for it — and if the resource can't be fenced, the fallback is making the operation idempotent so a duplicate from a stale holder is a no-op instead of a corruption."

Key Takeaways

  • A lease TTL is a bet, not a proof — pick it in the 5-30s range trading fast failover against normal-operation noise (GC pauses, slow disks), and know you're choosing a probability of correctness, not a guarantee.
  • Fencing tokens are optimistic locking bolted onto a lock — a monotonic counter checked at the point of the actual write, same mechanism as the version column in 14-concurrency-control, just applied to a mutual-exclusion primitive instead of a row update.
  • Redlock is a real, cited debate — not FUD — Kleppmann vs. Antirez; use majority-quorum locking to remove a single-instance SPOF, but don't treat quorum alone as a substitute for fencing when correctness, not just coordination hygiene, is on the line.
  • ZooKeeper/etcd ephemeral-session locks handle "the client crashed" cleanly via server-side heartbeat timeouts, but they still can't bound a GC pause on a client that's alive but stalled — the same risk class survives regardless of lock backend.
  • Thundering herd on lock release is the same shape as a cache stampede — many waiters retrying the instant a popular lock frees; jittered backoff is the same fix used in 01-caching-strategies and 08-rate-limiting.
  • When a resource can't be fenced, make the operation idempotent instead — a duplicate execution that's a safe no-op (05-idempotency) beats a lock that occasionally fails under real-world timing.
