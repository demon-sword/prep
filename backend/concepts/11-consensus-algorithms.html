Consensus Algorithms (Raft/Paxos)

Leader election and distributed consensus — how a cluster agrees on a single value despite node failures, why majority quorums prevent split-brain, and why consensus is expensive and reserved for metadata rather than data-plane traffic.

Theory

The problem consensus solves

A single node can always tell you the truth about its own state — the problem starts the moment you have several nodes and need them to agree on one value (who's the leader, what the next log entry is, whether a transaction committed) even though nodes crash, restart, and messages get delayed or dropped. Consensus is the protocol that gets a cluster to agree on that one value with a guarantee that once agreement is reached, it can't be silently overwritten by another node that missed the memo. It's the mechanism underneath almost every "who's in charge" and "what's the authoritative log" question in a distributed system — leader election for a database cluster, the source-of-truth log for a coordination service like etcd, the commit decision in some transaction coordinators.

Majority quorums and why they prevent split-brain

The core trick every practical consensus protocol uses is the majority quorum: with N nodes, a decision is only valid once more than half — ⌊N/2⌋ + 1 — have agreed to it. That single arithmetic fact is what makes split-brain structurally impossible: any two majorities out of the same N nodes must overlap by at least one node, so two different values can never both get a majority in the same term/round — there's always a node in the intersection that would have to agree to both, and it can't. This is why cluster sizes are almost always odd (3 or 5, rarely more) — 3 nodes tolerate 1 failure, 5 tolerate 2, and going from 3 to 4 buys you nothing (you still only tolerate 1 failure) while adding write latency, since a 4-node majority is ⌊4/2⌋+1 = 3, the same fault-tolerance ceiling as 3-node's majority of 2 but strictly more replication work per commit. This is also precisely why a network partition doesn't cause split-brain in a correctly implemented consensus cluster: the minority side of the partition can never reach a majority of the whole cluster, so it can never elect a leader or commit anything — it just stalls, unable to make progress, while the majority side proceeds normally. Consensus trades unavailability of the minority partition for correctness everywhere else — that's a direct CP choice in CAP terms (03-consistency-tradeoffs).

Raft mechanism: leader election + log replication

Raft (designed explicitly to be "Paxos, but understandable") splits consensus into two coupled sub-protocols:

  • Leader election. Time is divided into terms, each with at most one leader. Every follower runs a randomized election timeout (Raft's paper uses 150–300ms); if it hears no heartbeat from a leader before that timeout fires, it becomes a candidate, increments its term, votes for itself, and requests votes from every other node. A node grants at most one vote per term, and only to a candidate whose log is at least as up to date as its own (this is what stops a node that missed recent commits from becoming leader and rewriting history). Get votes from a majority and you're the leader for that term; the randomized timeout is specifically there to make it unlikely that two nodes become candidates simultaneously and split the vote — a real, named failure mode — and if it does happen, the term's election is void and everyone tries again after their (re-randomized) timeout, which converges quickly in practice.
  • Log replication. Once elected, the leader is the only node accepting writes. Every write becomes a log entry the leader appends locally and sends to followers via AppendEntries. The entry is committed — safe to apply and safe to acknowledge to the client — only once a majority of nodes (leader included) have persisted it, not merely once the leader has it. This is the same "write must survive a majority" idea as a quorum write in Dynamo-style systems (03-consistency-tradeoffs), just applied to an ordered log instead of a key. A stale or partitioned-away leader that still thinks it's in charge can keep appending to its own log all day — those entries never commit because it can't reach a majority, and the moment it reconnects and sees a higher term from the real leader, it steps down and truncates its uncommitted tail.

Paxos, ZAB, and the rest of the family

Paxos came first and solves the same problem with a two-phase (prepare/promise, then accept/accepted) protocol per value — it's provably correct but notoriously hard to reason about and extend to a replicated log without extra machinery (Multi-Paxos), which most descriptions leave as an exercise. Raft was designed to make the same guarantees explicit and implementable by separating leader election from log replication and requiring a strong leader (no other node accepts client writes directly), which is why almost every consensus library built since 2014 — etcd, Consul, CockroachDB's range replication, TiKV — is Raft, not Paxos. ZooKeeper predates Raft and uses its own protocol, ZAB (ZooKeeper Atomic Broadcast), which is conceptually similar — leader-based, majority-ack for commit — but ZK-specific. Google's Chubby and Spanner use Paxos variants internally. For interview purposes, the family resemblance matters more than protocol trivia: they all reduce to "elect one writer per epoch, commit only with a majority ack."

The trade-off that matters

Consensus is correct but expensive: every committed write needs a network round trip to a majority of nodes before it can be acknowledged, which is real added latency (and real cross-AZ cost if the cluster spans zones/regions) compared to a single node just writing to its own disk. That's why consensus is deliberately reserved for low-volume, high-value control-plane decisions — who's the leader, what's the current cluster membership, what's the authoritative config — and not run on the data plane's hot path. A service registry (10-service-discovery) runs Raft internally to keep its own directory consistent across replicas, but the millions of ordinary reads and writes that flow through the systems it coordinates never touch that consensus round trip directly. Distributed transaction coordinators lean on the same idea: 2PC (13-distributed-transactions) needs its own coordinator to be highly available, and that coordinator is often itself backed by a consensus system, because "can the coordinator's state survive a crash without losing the commit decision" is exactly the problem consensus was built to solve.

Where this shows up in practice: etcd (Raft) as Kubernetes' entire cluster state store, Consul (Raft) and ZooKeeper (ZAB) as service registries and distributed locks, CockroachDB and TiDB using per-range Raft groups so consensus cost stays local to the data actually being written, not global to the whole cluster.

Interview Line

"Consensus isn't magic — it's arithmetic. A majority quorum out of N nodes always overlaps with any other majority of the same N, so two conflicting values can never both get a majority in the same term, and that's the whole reason split-brain can't happen. That's also exactly why it's expensive: every committed write is a round trip to a majority before you can tell the client it's durable, so I don't run consensus on the data plane's hot path — I reserve it for low-volume, high-value decisions like leader election and cluster membership, and let the actual reads and writes flow through whatever that consensus-elected leader owns. If someone asks Raft versus Paxos, the honest answer is they're the same idea — elect one writer per epoch, commit only with a majority ack — and Raft just made the machinery explicit enough that you can actually implement it correctly, which is why etcd, Consul, and CockroachDB all ship it instead of raw Paxos."

Key Takeaways

  • Majority quorum is the whole mechanism — any two majorities of the same N nodes must overlap by at least one node, which is the arithmetic reason split-brain is structurally impossible, not just unlikely.
  • Odd cluster sizes are deliberate — 3 nodes tolerate 1 failure, 5 tolerate 2; going 3→4 buys zero extra fault tolerance while adding replication cost, which is why you almost never see 4- or 6-node consensus clusters in production.
  • A network partition doesn't cause split-brain, it causes unavailability — the minority side can never reach a majority of the whole cluster, so it stalls rather than electing a rogue leader; that's the CP choice made explicit (03-consistency-tradeoffs).
  • Randomized election timeouts exist to avoid split votes — a named Raft failure mode where two nodes become candidates in the same term and neither gets a majority; randomization makes simultaneous timeouts unlikely and the retry converges fast when it does happen.
  • Consensus is a control-plane tool, not a data-plane one — every commit costs a majority round trip, so it's reserved for leader election, cluster membership, and config, not ordinary application writes; per-range Raft groups (CockroachDB, TiKV) exist specifically to keep that cost local instead of global.
  • Registries and lock services are consensus systems in disguise — etcd and Consul run Raft, ZooKeeper runs ZAB, precisely because their own directory state (10-service-discovery) needs the same majority-agreement guarantee, and 2PC coordinators (13-distributed-transactions) are often themselves backed by consensus so the commit decision survives a coordinator crash.
