API Design and Evolution

REST vs gRPC vs GraphQL tradeoffs, backward-compatible schema evolution, and pagination strategies (offset vs cursor-based) — designing APIs that can change without breaking existing clients.

Theory

REST, gRPC, GraphQL: three answers to "how does a client ask for data"

These three aren't tiers of sophistication, they're optimized for different coupling assumptions. REST models the API as resources (/users/42/orders) manipulated with HTTP verbs, transported as JSON — its win is universality: any HTTP client, any language, cacheable by intermediaries via standard HTTP semantics, human-debuggable with curl. Its cost is that the response shape is fixed by the server, so a client that only needs an order's total still gets the full object — classic over-fetching — and a client that needs an order plus its items either gets a hand-rolled ?expand=items query param or makes a second round trip (under-fetching, N+1 at the network level). gRPC defines a strict typed contract with Protocol Buffers, transports over HTTP/2, and gets you binary encoding (smaller payloads than JSON), multiplexed streaming (server-streaming, client-streaming, bidirectional), and generated client/server stubs so a type mismatch is a compile error, not a 3am incident. The trade is that the response shape is still server-defined — gRPC doesn't let a client pick fields — and it's a much worse fit for public/browser-facing APIs (no native browser gRPC, tooling is heavier), so it's overwhelmingly an internal service-to-service choice where you control both ends of the wire. GraphQL flips the shape question to the client: one endpoint, the client sends a query describing exactly the fields it wants across a graph of types, and the server resolves each field, often fanning out to multiple backends. It kills over-fetching and under-fetching by construction — but it moves the N+1 problem server-side, into resolvers (fetching an order's items one row at a time per order unless you batch with something like Dataloader), and it makes HTTP-layer caching much harder since every query is technically a different request against the same POST endpoint.

The real hard problem: clients you don't control

Picking a transport is a one-time decision; evolving the schema afterward is the decision you live with for years, because a client and server API are two independently deployed processes, not two functions in the same binary — the same reason distributed transactions and consensus are hard applies here in a milder form. Once a mobile app version or a partner's integration is out in the world, you cannot force it to redeploy on your timeline, so the API is a contract with unknown, unversioned parties on the other end. The only reliably safe change is additive: add a new optional field, add a new endpoint, add a new enum value at the end — never remove a field, never repurpose a field's meaning, never make an optional field required. This only works if clients practice the tolerant reader pattern (a corollary of Postel's Law) — deserialize by field name and silently ignore anything unrecognized rather than failing on an unknown key; a client written to strictly validate the full response shape turns every additive, otherwise-safe change into a breaking one. When a field genuinely must go away, the pattern is a deprecation window, not a flag day: mark it deprecated in docs/schema, dual-write or dual-serve both old and new fields for a negotiated period (weeks to months depending on how well you can measure client version adoption), monitor usage of the old field via access logs, and only remove it once usage drops to zero or a hard EOL date passes with comms sent. This is the same expand-contract shape used for zero-downtime schema migrations (20-zero-downtime-deployments) — expand to support both old and new, migrate consumers, then contract by removing the old path — just applied to a public contract instead of a database column.

Pagination: offset looks simple and lies under concurrent writes

Offset pagination (LIMIT 20 OFFSET 40, or ?page=3) is trivial to implement and lets a client jump straight to page 40 — but the offset is a position in a list that keeps changing. If 3 new rows get inserted at the top between a client's page-1 and page-2 request (a live feed, a leaderboard, anything sorted by recency), the whole list shifts, and offset 20 now points at different rows than it did a moment ago: the client re-sees 3 items it already had (duplicates) and silently skips 3 it never saw. Deep pages are also expensive — the database still has to scan and discard the first 39,980 rows to serve OFFSET 40000 LIMIT 20, so cost grows with page depth even though the page size is constant. Cursor (keyset) pagination replaces the position with an anchor: the client passes the last item it saw (typically an opaque, base64-encoded composite of the sort key plus a tiebreaker ID, e.g. (created_at, id) > (last_created_at, last_id)), and the server does a direct indexed range scan from that anchor — WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20. Because the anchor is a value, not a position, inserts anywhere else in the list don't shift it — the client stays correct regardless of concurrent writes, and the query stays index-fast at any depth. The cost: you give up random access to "page 40" (you can only walk forward/backward from where you are), and the sort key needs a stable, indexed tiebreaker or ties can produce the same duplicate/skip bug offset has.

Non-additive breaking change

Removing, renaming, or repurposing a field breaks every client still parsing the old shape, silently, with no compile-time signal on the server side — the failure shows up as a spike in client-side parse errors or crashes days later, often for a client version the server team forgot existed.

Offset pagination skew under concurrent inserts

A live, frequently-inserted-into list paged by numeric offset duplicates or drops rows whenever the underlying set changes between page requests — the classic symptom is a user reporting "I saw this item twice" or "an item just vanished" while scrolling a feed.

GraphQL N+1 in resolvers

A naive per-field resolver fetching one row at a time (e.g. an order's items resolved one order at a time in a loop) turns a single client query into hundreds of DB round trips — fixed with request-scoped batching/caching (Dataloader pattern), not by avoiding GraphQL.

Strict client defeats additive evolution

A client that fails on an unrecognized field (instead of the tolerant-reader pattern of ignoring unknown keys) makes even a fully additive, spec-compliant server change a breaking one in practice — the contract violation is really on the client's parsing discipline, not the server's change.

Interview Line

    

      "REST vs gRPC vs GraphQL is a smaller decision than people treat it as — REST for public APIs where you don't control the client and want HTTP-native caching and debuggability, gRPC for internal service-to-service where you control both ends and want a strict typed contract plus binary encoding and streaming over HTTP/2, GraphQL when you've got many client shapes reading an overlapping graph and over/under-fetching is a real cost. The problem that actually bites in production is evolution, because the client and server deploy independently — you can't force an old mobile build to upgrade — so schema changes have to be additive-only: add optional fields, never remove or repurpose one, and give a deprecated field a real dual-write window before it goes away, not a flag day. That only works if the client is a tolerant reader that ignores fields it doesn't recognize instead of failing closed. Pagination has the same shape of bug: offset pagination is a position in a list that keeps moving, so concurrent inserts make a client duplicate or silently skip rows between page requests; cursor pagination anchors on the last item's actual key, so it stays correct no matter what gets inserted around it — the cost is you lose the ability to jump straight to page 40."
    

  


  

    
Key Takeaways

    
    
      
  • Pick the transport by coupling, not by fashion — REST for unknown/public clients and HTTP-layer caching, gRPC for internal typed contracts and streaming, GraphQL for many overlapping client shapes; gRPC and GraphQL both still leave the N+1 problem somewhere (client round trips for REST, resolver fan-out for GraphQL) — batching (Dataloader) doesn't disappear, it moves.
    • 
      
  • Additive-only evolution is the only safe default — new optional fields are fine, removing/renaming/repurposing a field is not; treat a deprecated field like a database column migration and give it an expand-then-contract window, the same pattern used for zero-downtime schema changes (20-zero-downtime-deployments).
    • 
      
  • The tolerant reader pattern is what makes additive changes actually safe — a client that strictly validates the full response shape converts every additive, spec-compliant server change into a breaking one; this is a client-side discipline problem as much as a server-side design problem.
    • 
      
  • Offset pagination breaks under concurrent writes, cursor pagination doesn't — offset is a moving position re-derived on every request, so inserts between page requests cause duplicate or skipped rows; cursor/keyset anchors on a value (typically (sort_key, id)) and stays correct regardless of what's inserted elsewhere, at the cost of random page access.
    • 
      
  • Deep offset pages get slower with depth even at constant page size — OFFSET 40000 still means the database scans and discards 40,000 rows before returning 20; cursor pagination's indexed range scan stays roughly constant-cost regardless of how deep the client has paged.
    • 
      
  • An API is a distributed-systems contract, not a function signature — server and client deploy independently and you don't control the client's redeploy timeline, which is the same "who do you trust and for how long" problem that shows up in distributed locking (15-distributed-locking) and consensus, just applied to a schema instead of a lock.
