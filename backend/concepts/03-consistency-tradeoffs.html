Consistency Trade-offs

CAP restated correctly via PACELC, the consistency spectrum (strong/sequential/causal/eventual), session guarantees, database isolation levels, and quorum math (W+R>N).

Theory

CAP, stated correctly

Under a network partition, you must choose between consistency and availability. That's the whole theorem, and the framing people get wrong is treating it as a permanent three-way choice you make once for a system. Partitions are rare; the interesting trade-off most of the time is latency vs consistency, which is what PACELC adds:

PACELC: if there's a Partition, choose Availability or Consistency;
        Else (normal operation), choose Latency or Consistency.

PACELC is the more useful model in an interview because it explains behavior on the 99.99% of days when there's no partition at all — CAP alone says nothing about that regime, and that's where most consistency decisions actually get made (do you read from the nearest replica, or pay a round trip to the leader?).

The consistency spectrum

Strong / linearizable

Every read sees the most recent write. Behaves as if there's one copy. Expensive — requires coordination, so latency scales with distance between replicas.

Sequential

All operations appear in some consistent order every node agrees on, but not necessarily real-time order.

Causal

Causally related operations appear in order everywhere; concurrent operations may be seen in different orders. Often the sweet spot — prevents the anomalies users actually notice (a reply appearing before the comment it replies to).

Eventual

Replicas converge if writes stop. Says nothing about when. Cheap and highly available.

Session guarantees — the practical middle ground

Full strong consistency is usually overkill; full eventual consistency produces baffling user experiences. Session guarantees split the difference — cheap to implement (route a session to the same replica, or track a version token) and they eliminate most user-visible weirdness:

  • Read-your-writes — a user always sees their own updates. The single most important one. Without it, a user edits their profile, reloads, and sees the old value.
  • Monotonic reads — you never see time go backwards (read a value, then read an older value on a later request).
  • Monotonic writes — your writes apply in the order you made them.

Isolation levels (the database-local cousin)

Don't confuse consistency (across replicas) with isolation (across concurrent transactions) — interviewers listen for whether you keep these separate. Know the anomalies each level does and doesn't permit:

  • Read uncommitted → dirty reads
  • Read committed → no dirty reads, but non-repeatable reads
  • Repeatable read → no non-repeatable reads, but phantoms possible
  • Serializable → transactions behave as if run one at a time

Snapshot isolation (what Postgres calls repeatable read) is common and has a specific named failure mode: write skew, where two transactions each read a consistent snapshot, each make a decision that's valid alone, and together violate an invariant. Classic example: two doctors on the same team both go off-call simultaneously because each independently sees that the other is still on call.

Quorums

With N replicas, W write acknowledgements required, R read responses required: if W + R > N, the read set and write set are guaranteed to overlap on at least one node, so a read is guaranteed to see the latest acknowledged write. Common configuration: N=3, W=2, R=2. Tuning W and R trades write latency against read latency against fault tolerance — push W down and reads get slower (or need more replicas to guarantee freshness); push W up and you lose availability faster when nodes are down.

Where this appeared in the Simbian design: verdicts needed strong consistency and an audit trail because a regulator asking what we knew in January can't get a stale answer — but the dedup cache was fine eventually consistent, because a duplicate investigation costs money, not correctness. The move is to identify which data needs which consistency, rather than picking one level for the whole system.

Key Takeaways

  • PACELC beats CAP in an interview because it explains the common case. CAP only describes behavior during a partition, which is rare; PACELC's "else" branch is what governs latency-vs-consistency on every normal request.
  • Consistency (across replicas) and isolation (across transactions) are different axes. Conflating them is a tell that someone hasn't operated a real multi-replica system — know both vocabularies and keep them separate.
  • Write skew is the failure mode snapshot isolation doesn't stop. Two transactions each read a valid snapshot, each make a locally-valid decision, and together violate an invariant — the fix is either serializable isolation or an explicit constraint/lock on the invariant itself.
  • W + R > N is a guarantee about overlap, not about which node you'll read. N=3,W=2,R=2 is the standard because it tolerates one node down while still guaranteeing overlap; dropping to W=1 buys write latency at the cost of that guarantee.
  • Session guarantees are the 80/20 most teams actually need. Read-your-writes alone (route a user's session to the same replica, or read-repair against a version token) kills most "why did my edit disappear" tickets without paying for full linearizability.
  • The senior move is picking consistency per data type, not per system. This is the same instinct as choosing per-key ordering in 02-queues-backpressure or per-endpoint idempotency in 05-idempotency — decide at the granularity the trade-off actually applies to.
