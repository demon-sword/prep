Indexing and Storage Engines (B-tree vs LSM-tree)

B-tree vs LSM-tree storage engines — why B-trees favor read-heavy in-place-update workloads and LSM-trees favor write-heavy workloads via compaction, and how this drives database engine choice.

Theory

Both are answers to the same question: where does a write land on disk?

Every general-purpose database index reduces to one of two families, and the split is entirely about what happens physically on disk when you write a row. A B-tree (almost always a B+tree in practice — data lives only in leaf nodes, internal nodes hold only routing keys) is a balanced, sorted tree of fixed-size pages, typically 4–16 KB. A write finds the correct leaf page by traversing from the root — height is O(log_B N) where B is the branching factor, usually in the hundreds, so even a billion-row table has a tree height of 3–4 — and then updates that page in place: the page is read, the record is inserted/modified/deleted within it, and the whole page is rewritten to the same location on disk (through a write-ahead log first, for crash safety). If the page overflows, it splits into two pages and the split propagates up if the parent also overflows. This is the storage engine behind InnoDB (MySQL), PostgreSQL's B-tree indexes, SQLite, and LMDB.

An LSM-tree (Log-Structured Merge-tree) never updates in place. A write is appended to an in-memory, sorted structure called the memtable (usually a skip list or red-black tree) after first being appended to a write-ahead log on disk for durability. When the memtable hits a size threshold, it's flushed to disk as an immutable, sorted file — an SSTable (Sorted String Table) — at level 0. The write path never seeks and never rewrites existing data; it's pure sequential append. This is the storage engine behind RocksDB, LevelDB, Cassandra, HBase, and BigTable.

The cost LSM defers: compaction

An LSM-tree accumulates SSTables over time, and a read for a key might have to check the memtable, then every L0 SSTable (which can overlap in key range since they're flushed independently), then successively larger levels below. Left unchecked, read cost grows without bound. Compaction is the background process that merges SSTables — reading several sorted files, merging them into fewer, larger sorted files at the next level down, and dropping any keys shadowed by a newer version or a tombstone (the marker written for a delete, since you can't remove a record in place). Two dominant strategies: leveled compaction (RocksDB/LevelDB default) keeps each level non-overlapping and roughly 10x the size of the level above it — read-optimized, because a key exists in at most one SSTable per level, but it rewrites data more times as it cascades down levels, so higher write amplification. Size-tiered compaction (Cassandra's default) merges same-sized SSTables together within a tier rather than across levels — lower write amplification, but more SSTables can exist at once, so higher read amplification and higher space amplification (multiple stale versions of the same key sitting around longer before they're compacted away).

The trade-off that actually matters: which amplification you're willing to pay for

Every storage engine pays three currencies, and the B-tree/LSM choice is about which one you're willing to spend more of: write amplification (bytes physically written to disk per logical byte written by the application), read amplification (number of disk reads per logical read), and space amplification (disk space used vs. logical data size). A B-tree pays write amplification per write — a 50-byte record update still rewrites an entire 8–16 KB page — but keeps read amplification low and roughly constant (one tree traversal, no merging). An LSM-tree pays write amplification later and in bulk, via compaction — the same byte can be rewritten across L0→L1→L2→... several times before it settles, with real-world figures commonly cited in the 10–30x range — in exchange for O(1) sequential appends on the write path itself, which is why LSM engines dominate write-heavy workloads (time-series, event logs, write-through caches) where B-tree's random-write page churn would thrash the disk and fragment the buffer pool. Bloom filters are the standard mitigation for LSM read amplification: a small per-SSTable probabilistic filter (~1% false-positive rate is typical) that lets a read skip an SSTable entirely if the filter says the key definitely isn't there, without doing an actual disk read — this is what makes LSM point-reads for recent keys competitive with a B-tree despite the multi-level structure.

Named failure modes

Compaction stall / write stall

If write throughput outpaces compaction throughput, SSTables (especially at L0) pile up faster than they can be merged. The engine throttles or blocks new writes to let compaction catch up — a classic cause of p99 write-latency spikes in Cassandra/RocksDB under sustained high write load.

B-tree page-split cascades

A burst of inserts into a densely packed page range (e.g. monotonically increasing keys hitting the same "hot" page) triggers repeated splits, generating extra I/O and page fragmentation — the reason UUID primary keys fragment a B-tree index far more than sequential/ULID keys do.

Tombstone accumulation

A delete in an LSM-tree is a written marker, not a removal. Until compaction merges the tombstone with the original write and both are dropped, storage isn't reclaimed and reads must scan past tombstones — a well-known Cassandra failure mode ("tombstone hell") when a workload deletes heavily and compaction can't keep up.

Space amplification under size-tiered compaction

Multiple stale versions of the same key can coexist across several uncompacted SSTables, so disk usage can be several times logical data size until compaction catches up — a real operational cost when provisioning storage headroom.

Where this shows up in practice: choosing InnoDB's B+tree clustered index vs. a time-series/event-heavy table backed by RocksDB (used inside MyRocks, CockroachDB, TiDB) is exactly this trade-off made explicit — read-heavy transactional tables stay on B-tree, high-ingest append-mostly tables move to LSM.

Interview Line

"B-tree vs LSM-tree is really a question of which amplification you're willing to pay and when. A B-tree updates a page in place, so every write — even a 50-byte one — costs a whole page rewrite, but a read is a single bounded tree traversal, so it wins on read-heavy, random-access, transactional workloads, which is why InnoDB and Postgres indexes are B-trees. An LSM-tree turns writes into sequential appends to a memtable and defers the real cost to background compaction, which can rewrite the same byte 10 to 30 times before it settles at its final level — that write amplification is the price for write throughput that doesn't degrade under high insert or update rates, which is why RocksDB, Cassandra, and time-series or event-heavy systems use it. The thing I actually watch for operationally is compaction falling behind — write stalls when L0 piles up faster than compaction can merge it, and tombstones not getting reclaimed under heavy delete load — because those are the failure modes that don't show up in a benchmark, only under sustained production write pressure."

Key Takeaways

  • Pick by write/read ratio, not by fashion — B-tree (InnoDB, Postgres, SQLite, LMDB) for read-heavy, point-lookup-heavy, in-place-update workloads; LSM (RocksDB, LevelDB, Cassandra, HBase) for write-heavy, append-mostly, high-ingest workloads. MyRocks, CockroachDB, and TiDB all let you swap the storage engine underneath a SQL layer for exactly this reason.
  • Write amplification is real money on an SSD — LSM engines commonly cite 10–30x write amplification from compaction; on cloud block storage billed by IOPS/throughput, that multiplier shows up directly on the infra bill, not just in latency.
  • Bloom filters are what make LSM point-reads viable — without them, a lookup for a key not present would have to check every SSTable at every level; a ~1% false-positive-rate filter per SSTable turns "check every table" into "check the 1–2 tables that might actually have it."
  • The write-ahead log underneath a B-tree is the same mechanism CDC reads off of — Debezium tailing MySQL's binlog or Postgres's WAL (07-change-data-capture) works because both storage engines already durably log every write before applying it; LSM engines have their own WAL for memtable durability, serving the identical crash-recovery purpose.
  • Sequential primary keys aren't just a convenience, they're a write-amplification decision — a UUID primary key spreads inserts randomly across a B-tree's leaf pages, causing far more page splits and cache misses than a monotonically increasing key (ULID, auto-increment, or Snowflake ID) that appends to the rightmost page.
  • Compaction backlog is the LSM equivalent of a saturated connection pool — both are a capacity mismatch between arrival rate and processing rate that looks fine until a burst, then produces a latency cliff (22-connection-pooling); watching L0 SSTable count / compaction pending bytes is the LSM-specific signal to alert on.
