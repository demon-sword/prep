Database Replication

Leader-follower vs multi-leader vs leaderless replication, synchronous vs asynchronous replication, replication lag, and failover mechanics when a follower falls behind or a leader dies.

Theory

What replication is actually solving

Replication means keeping the same data on more than one node, for three reasons that often get bundled together but are worth separating: durability (a copy survives losing any single node), availability (another node can keep serving if one is down or partitioned), and read scalability (spread read traffic across copies instead of hammering one node). It's the mechanism underneath "add a read replica," "we run three AZs," and "failover took 12 seconds" — all three are replication decisions wearing different clothes.

Three topologies

  • Single-leader (leader-follower). One node accepts all writes; it streams a log of changes to N followers, which apply them and serve reads (with a staleness caveat). This is the default for a reason — writes have one obvious order because there's only one writer. Postgres streaming replication, MySQL binlog replication, and MongoDB replica sets are all this shape.
  • Multi-leader. More than one node accepts writes, each replicating asynchronously to the others. The draw is local low-latency writes per region — a user in Singapore doesn't round-trip to a leader in Virginia. The cost is real: two leaders can accept conflicting writes to the same key before either has heard from the other, and that conflict has to be resolved after the fact, not prevented up front.
  • Leaderless (Dynamo-style). No leader at all. A client (or coordinator) writes directly to W of N replicas and reads from R of N, leaning on quorum overlap — the same W + R > N arithmetic covered in 03-consistency-tradeoffs — to make reads see recent writes without every replica needing to be up. Cassandra, DynamoDB, and Riak are this shape. There's no failover step because there's no leader to fail over from — that's the actual trade, not just a footnote.

Sync vs async — the trade-off that matters

This is the one decision that dominates every other replication question. Synchronous replication: the leader waits for an ack from the replica before acknowledging the write to the client. No acknowledged write is ever lost if the leader dies immediately after, but the leader's write latency now includes a full round trip to that replica, and if the replica is slow or unreachable, the leader either blocks or fails the write — replica availability has just become leader availability. Asynchronous replication: the leader acks the client the moment its own local write commits, and replicates in the background. Low latency, no availability coupling, but if the leader crashes before the replica catches up, an acknowledged write silently disappears on failover. This is a direct instance of PACELC's "else, Latency vs Consistency" branch (03-consistency-tradeoffs) — you are always making this trade, the only question is whether you made it on purpose. Semi-synchronous replication splits the difference: the leader waits for an ack from at least one replica, not all of them, buying a durability floor without paying for every replica's round trip on every write — Postgres's synchronous_commit = remote_write and MySQL semi-sync both work this way, and it's the common production default over full-sync or full-async.

Replication lag and its downstream symptoms

Async replication means followers are behind by some lag — usually hundreds of milliseconds under normal load, but a long-running migration, a VACUUM, or a network blip on the replica can spike it to minutes. That lag isn't abstract; it shows up as concrete, reproducible bugs if the application doesn't account for it: read-your-writes violations (a user writes, then immediately reads from a lagging replica and doesn't see their own write), and monotonic-read violations (a user reads from replica A, then a slower replica B, and watches time go backwards). These are exactly the session guarantees named in 03-consistency-tradeoffs — replication lag is the physical cause, session guarantees (pin a user's reads to the leader, or to a replica at least as caught-up as their last write's LSN/offset) are the application-level fix.

Failover — the actually hard part

Automatic failover sounds simple and isn't. It requires: (1) detecting the leader is genuinely dead, not just slow or on the far side of a network partition — get this wrong and both the old and new leader think they're in charge, which is split-brain; (2) picking whichever surviving replica has the most up-to-date log; (3) promoting it and repointing traffic/DNS/config; (4) reconciling the old leader if it comes back — it has to step down and often discard writes that were acknowledged to a client but never left its own disk. Step (1) is precisely the leader-election problem consensus protocols solve, which is why serious deployments wire failover through a consensus-backed coordinator — Patroni backed by etcd for Postgres, MongoDB's own Raft-derived replica set protocol — rather than a heartbeat-and-promote shell script. "Promote the first replica that responds" is a well-known way to manufacture split-brain (11-consensus-algorithms is the same majority-quorum machinery under the hood).

Multi-leader conflict resolution deserves its own line: last-write-wins by timestamp is the default because it's trivial to implement, but it silently drops the losing write with no merge attempt — fine for a shopping-cart quantity, quietly corrupting for two people editing the same document. CRDTs and vector clocks exist specifically to preserve both writers' intent instead of blindly picking one (this is the same tension 21-multi-region-architecture covers at the cross-region scale).

Split-brain during failover

A heartbeat-based promotion script promotes a new leader while the old one is only slow/partitioned, not dead — two leaders now accept writes concurrently.

Lost writes on async failover

The old leader acked a write to a client, crashed before replicating it, and the promoted follower never had it — the write is gone even though the client was told it succeeded.

Stale reads from replication lag

A follower serves a read before it has applied a write the client just made — read-your-writes and monotonic-read violations without any crash involved.

Write-write conflicts (multi-leader)

Two leaders accept different writes to the same key before either replicates to the other — resolved after the fact by LWW or a merge function, never prevented.

In practice: Postgres and MySQL default to single-leader with async or semi-sync followers; Cassandra and DynamoDB expose W/R as a per-request tuning knob rather than a cluster-wide setting; Patroni + etcd (or Consul) is the standard way to get consensus-backed Postgres failover instead of trusting a naive promote script.

Interview Line

"Replication's one real trade-off is sync versus async, and it's the same PACELC 'else, Latency versus Consistency' choice that shows up everywhere — synchronous means no acknowledged write is ever lost on failover, but it couples the leader's latency and availability to the replica's; async decouples them but an acknowledged write can vanish if the leader dies before it replicates. My default is semi-sync — wait for one replica to ack, let the rest catch up async — so I get a durability floor without paying for every replica's round trip on every write. The part people usually get wrong is failover: detecting 'the leader is actually dead, not just slow' is the exact same problem Raft and Paxos solve, so I don't trust a heartbeat-and-promote script to make that call alone — I want a consensus-backed coordinator, like Patroni on etcd, because 'promote the first replica that answers' is a textbook way to end up with two leaders taking writes at once."

Key Takeaways

  • Semi-sync is the usual production default — Postgres's synchronous_commit = remote_write and MySQL semi-sync wait for one replica's ack, not all of them, giving a durability floor without the full-sync latency tax.
  • Replication lag is normally sub-second but spikes hard — a long VACUUM, a schema migration, or a network blip on a replica can push lag to minutes; pin session reads to the leader or track an LSN/offset cursor rather than assume followers are fresh.
  • Split-brain during failover is why Patroni delegates the election to etcd instead of a heartbeat script — same majority-quorum mechanism as 11-consensus-algorithms, applied to "who gets to be the database leader" instead of "who gets to be the cluster leader."
  • Multi-leader conflicts aren't a bug, they're the trade you accepted — last-write-wins is the cheap default and it drops data silently; anything with concurrent edits to the same record (21-multi-region-architecture) needs CRDTs or app-level merge logic instead.
  • Leaderless replication turns durability into a per-request knob — Cassandra and DynamoDB let you tune W/R per query, so a client can trade consistency for latency on one slow write without a cluster-wide config change, which single-leader replication simply doesn't offer.
  • "The write succeeded" and "the write is durable" are different claims — async replication plus a leader crash is exactly the gap between them, and it's the detail interviewers listen for when they ask "what happens if the leader dies right after acking my write."
