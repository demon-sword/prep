Event Sourcing and CQRS

Storing state as an append-only sequence of events and separating write models from read models (CQRS) — rebuilding current state by replay, and the operational cost of eventual consistency between the two sides.

Theory

State as a log of facts, not a row of columns

A normal application stores current state: an accounts table with a balance column, and every deposit or withdrawal does an UPDATE that overwrites the old value. The history of how the account got to that balance isn't stored anywhere — it's gone the moment the row changes. Event sourcing inverts this: instead of storing current state, you store the immutable, ordered sequence of things that happened — AccountOpened, Deposited(50), Withdrew(30) — as an append-only log, and current state is a derived value, computed by folding (reducing) over that sequence. The balance isn't a fact the system stores; it's a fact the system calculates, every time, from the events. Nothing is ever updated or deleted — only appended — which is exactly why the pattern reads naturally onto an append-only commit log like Kafka or a purpose-built event store (EventStoreDB, Marten on Postgres, Axon).

Rebuilding state: replay, folds, and snapshots

Computing current state from an event stream is a left fold: state = events.reduce(apply, initialState). This is the mechanism, not a metaphor — it's literally how an aggregate's in-memory state is reconstructed when it's loaded: read every event for that aggregate ID in order, apply each one's effect, and the resulting object is "current state," ready to accept the next command. Replaying from the beginning of time on every load is fine for an account with 40 events and gets expensive fast for one with 4 million — so production systems snapshot: periodically persist the folded state alongside the sequence number it represents, and on load, start from the latest snapshot and only replay events after it. Replay is also the disaster-recovery story for the whole pattern: if a read model gets corrupted, or a bug shipped that computed something wrong, you don't run a data-fix script against mutated rows — you fix the projection logic and replay the entire event log from scratch to rebuild correct state. That's a genuinely different operational posture than a normal CRUD table, and it's the main reason teams reach for this pattern: an unimpeachable audit trail and the ability to answer "what did we believe on March 3rd" by replaying up to that point, not just "what do we believe now."

CQRS: splitting the write model from the read model

Command Query Responsibility Segregation is a related but independent idea: stop using the same model to handle writes and reads. The write side (command model) only needs to validate a command against current state and decide whether to accept it — it doesn't need to be shaped for fast queries, joins, or aggregation. The read side (query model) is a separate, denormalized, purpose-built view — a materialized table, a search index, a cache — optimized for exactly the query pattern the UI needs, with no obligation to look anything like the write-side schema. A background process called a projector (or projection, or read-model updater) consumes the event stream and asynchronously updates the read model to reflect each new event. CQRS doesn't require event sourcing — you can run CQRS against a normal CRUD write table and still project into a separate read store — but the two pair naturally: the event log is already the perfect input for a projector, so most event-sourced systems are CQRS by construction, while most CQRS systems aren't event-sourced.

The trade-off that actually matters

The write side commits synchronously and is instantly consistent with itself — the moment an event is appended, it's the truth. The read side is eventually consistent by design: there's a real, sometimes-visible gap between "the event was committed" and "the projector updated the read model," and a user can act on a command and then immediately query a view that hasn't caught up yet (submit an order, refresh the order list, and not see it for 200ms–2s depending on projector load). This isn't a bug to be engineered away — it's the whole trade being made, the same way an eventually-consistent replica trades staleness for availability (see 03-consistency-tradeoffs). The cost isn't just conceptual: you're now running and monitoring an extra asynchronous pipeline (the projector), you need idempotent projection logic because the same event may be reprocessed after a crash or replay, and you need a versioning strategy for the event schema itself, because events are immutable and permanent — you can never edit `Deposited` to add a field the way you'd run an `ALTER TABLE`; you upcast old event shapes to new ones at read time, or version the event type (`Deposited`, `DepositedV2`) and teach the projector to handle both, forever.

Projector lag / stale reads

Under load the projector falls behind the event log; a user who just wrote sees a read model that hasn't caught up, and "read your own writes" breaks unless you special-case it (route the post-write read to the write side, or return the command's result directly instead of re-querying).

Poison-pill events

A malformed or unexpectedly-shaped event crashes the projector on every retry, freezing the read model at that point in the stream indefinitely until someone patches the projection code and reprocesses — the queue-consumer equivalent of a stuck message.

Event schema evolution

Events are permanent and immutable, so you can't "migrate" old ones in place — every projector must be able to interpret every historical event shape forever, typically via upcasters that translate old versions into the current shape on read.

Replay cost at scale

Rebuilding a read model by replaying millions of events from the beginning is a real, sometimes multi-hour operation — snapshotting the write-side aggregates helps loads, but a full read-model rebuild after a bug fix still means reprocessing the whole stream.

This is CDC's logical endpoint taken further (07-change-data-capture): CDC derives a stream of change events from row mutations after the fact, reading the replication log as a proxy for "what happened." Event sourcing skips the proxy — the events aren't derived from state changes, the events are the source of truth, and state is just their side effect.

Interview Line

"Event sourcing means the balance isn't a value the system stores, it's a value the system computes — you fold over the ordered event stream, and current state falls out as a side effect, which is what gives you a true audit log and the ability to fix a projection bug by just replaying, instead of running a manual data-repair script against mutated rows. CQRS is the decision to stop using that same write-optimized model to serve reads — split off a denormalized, purpose-built read model that a projector updates asynchronously as events land. The trade you're signing up for is that the read side is eventually consistent with the write side, on purpose, and if a user submits a command and immediately re-queries, they can see stale data — which either has to be an acceptable UX or you special-case the read-your-own-writes path back to the write model. The real operational cost isn't the fold, it's that events are permanent and immutable, so schema evolution means writing upcasters that translate every historical event shape forever, and a corrupted or buggy read model means reprocessing the entire stream, which at scale is a real multi-hour operation, not a five-minute migration."

Key Takeaways

  • State is derived, not stored — state = events.reduce(apply, initial) is the actual mechanism, and snapshotting exists purely to bound replay cost as the event count grows into the millions.
  • CQRS doesn't require event sourcing — you can split write and read models against a plain CRUD table — but event-sourced systems are CQRS by construction, because the event log is already the ideal projector input.
  • Eventual consistency between write and read side is the trade, not a bug — same shape as replica lag in 03-consistency-tradeoffs; "read your own writes" needs an explicit fix (route back to the write model) if it matters for the UX.
  • Events are immutable and permanent — that's a schema-evolution tax: no ALTER TABLE equivalent, only upcasters or versioned event types that every projector must keep handling forever.
  • This is CDC pushed to its logical endpoint (07-change-data-capture) — CDC derives events from row changes after the fact; event sourcing skips the derivation and makes the events themselves the source of truth.
  • A poison-pill event or a buggy projector doesn't corrupt the source of truth — the write-side log is untouched, so the fix is always "patch the projection and replay," which is a fundamentally safer failure mode than a corrupted mutable table.
