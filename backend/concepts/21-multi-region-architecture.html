Multi-Region Architecture

Active-active vs active-passive multi-region designs, cross-region latency, data residency constraints, and conflict resolution (last-write-wins, CRDTs) when the same data is writable in two regions.

Theory

Why go multi-region at all

Three separate motivations get bundled under "multi-region," and confusing them leads to the wrong design. Disaster recovery wants a second region that can take over if the first one disappears (a cloud provider region outage, a natural disaster, a bad config push that only a full region cutover can escape). Latency for global users wants writes and reads served from the region closest to the user, because speed of light is real: a synchronous round trip from us-east-1 to eu-west-1 is commonly ~70-90ms, and to ap-southeast-1 it's ~180-220ms — numbers that show up directly in p99 if every request has to cross an ocean. Data residency / regulatory constraints — GDPR, data localization laws in India, Russia, China — require that a given user's data physically stays within a geographic boundary, which forces geo-sharding by user location rather than free routing to whichever region is fastest. A design driven by DR alone looks very different from one driven by residency, even though both get called "multi-region."

Active-passive: one region writes, the other stands by

All writes go to a single active region; one or more passive regions receive a continuous replication stream (usually asynchronous, given the latency numbers above) and stay ready to be promoted. This is architecturally simple — there's exactly one place that resolves write conflicts, because there's only one writer — and it gives strong consistency semantics on the active side. The cost shows up during failover: RPO (recovery point objective — how much data you can afford to lose) is bounded by replication lag at the moment the active region dies, and RTO (recovery time objective — how long until the passive region is serving traffic) is bounded by detection time plus promotion time plus DNS/traffic-manager propagation, which is rarely instant even with low TTLs. Users far from the active region also pay the full cross-region round trip on every write, all the time, not just during a failover.

Active-active: every region accepts writes

Multiple regions accept writes concurrently against (conceptually) the same dataset, each replicating to the others asynchronously. This buys local write latency for users in every region and higher availability — a full region going dark doesn't halt writes, it just removes one region's worth of capacity. The price is that conflicts are not an edge case, they're the normal operating condition: two regions can accept writes to the same key within the same tens-of-milliseconds window, before either has heard about the other's write, and something has to decide what the merged result is.

Conflict resolution: LWW vs CRDTs vs app-level merge

Last-write-wins (LWW) is the cheap default: attach a timestamp to every write, and when two versions of a key are compared, the later timestamp wins and the earlier write is discarded. It's simple and requires no data-model changes, but it silently drops data — the losing write isn't queued or surfaced, it's just gone — and it's only as correct as your clocks; NTP drift or a VM pause can make "later" wrong. This is unacceptable for anything where losing a write is a real loss (a payment, an inventory decrement) and merely annoying for things like a "last profile edit wins" field.

CRDTs (conflict-free replicated data types) sidestep the problem by choosing data structures whose merge function is mathematically guaranteed to converge to the same result regardless of what order updates arrive in — a G-Counter only increments so merging is "take the max per replica," an OR-Set merges to the union of adds minus tombstoned removes, a PN-Counter separates increments and decrements to support both. CRDTs need no coordination and no data loss for the operations they support, but they constrain your data model to what has a known convergent merge — you don't get to bolt a CRDT onto an arbitrary row update, you design the type around it. DynamoDB's vector clocks, Redis CRDTs (Redis Enterprise's Conflict-Free Replicated Data Types), and Riak's dotted version vectors are the production incarnations of this idea.

Application-level merge is the fallback when neither fits: detect the conflict explicitly (vector clocks, or comparing versions) and hand both versions to application logic that knows the domain well enough to merge them correctly — a shopping cart union, a document three-way merge. This is the most flexible and the most expensive to build and test.

The trade-off that actually matters

This is PACELC (03-consistency-tradeoffs) restated at the geography scale instead of the single-cluster scale: even absent a partition, you're trading latency against consistency, because cross-region synchronous replication is slow enough that almost nobody does it for the hot write path. Active-passive buys simple, strongly-consistent-on-the-active-side semantics at the cost of either write latency for distant users or an RPO/RTO gap during failover. Active-active buys low local latency and no single point of write failure at the cost of building and operating real conflict resolution — and conflict resolution that's wrong is a silent, hard-to-detect correctness bug, not a loud outage. The senior-level framing is: don't reach for active-active because it sounds more resilient — reach for it only when you've actually priced the conflict-resolution cost for your specific data model and it's still worth it over active-passive's simplicity.

Named failure modes

Split-brain during a network partition

If both regions in an active-passive setup believe they're active during a partition — a failover automation that fires without confirming the old active is actually down — you get two writers with no coordination, which is strictly worse than the single-writer guarantee active-passive was chosen for.

Silent LWW data loss

LWW conflict resolution doesn't fail loudly — the discarded write simply never existed as far as any client can tell, and clock skew between regions can make the "wrong" write win deterministically every time until the skew is fixed.

Replication lag masquerading as active-active

If asynchronous replication lag grows (a burst of writes, a network blip), reads in one region can be stale relative to a write that already succeeded in another — active-active only feels like a single consistent dataset when lag stays small relative to your read patterns.

RPO/RTO gap discovered during a real incident

Teams that never test failover find out the actual RTO (DNS TTL propagation, promotion scripts that were never dry-run, a passive region that turns out not to be warm) only when a real region outage forces it — the same "did we actually test the failure path" gap that shows up in circuit-breaker fallback logic (06-circuit-breakers-bulkheads).

Where this shows up in practice: Spanner and CockroachDB solve cross-region active-active with synchronous consensus (TrueTime / Raft-per-range) instead of eventual conflict resolution — trading write latency (a cross-region commit genuinely waits on a quorum) for the guarantee that there's never a conflict to resolve after the fact. That's a legitimate third option, not just LWW vs CRDT — it's paying the latency cost active-active usually avoids, in exchange for consensus's correctness (11-consensus-algorithms).

Interview Line

"Multi-region isn't one decision, it's three different motivations — disaster recovery, latency for global users, and data residency — and they push you toward different designs, so I always ask which one we're actually solving before picking active-passive or active-active. Active-passive keeps conflict resolution trivial because there's exactly one writer, but you're buying that simplicity with either cross-region write latency for anyone far from the active region, or an RPO/RTO gap you'd better have actually tested, not just assumed. Active-active gets you low local write latency everywhere, but conflicts stop being an edge case — they're the normal state — so the real engineering is the merge function: last-write-wins is cheap but silently throws away data and is only as trustworthy as your clock sync, while CRDTs guarantee convergence with no coordination but only for data models you deliberately shape around them, like a counter or an OR-Set. If someone asks for active-active without pricing that conflict-resolution cost, they're usually asking for a resilience story, not an architecture."

Key Takeaways

  • "Multi-region" bundles three different problems — DR, user latency, and data residency (GDPR-style geo-pinning) — and the right topology depends on which one you're actually solving, not on picking the most impressive-sounding option.
  • Active-active conflicts are PACELC restated at the geography scale — even with zero partitions, cross-region synchronous writes cost 70-220ms round trip depending on region pair, which is why almost nobody does synchronous cross-region commits on the hot path (03-consistency-tradeoffs).
  • LWW data loss is silent, not loud — the losing write just disappears with no error, no retry signal, nothing in a client response; that makes it dangerous for anything you can't afford to lose (payments, inventory) and merely annoying for "last profile edit wins" fields.
  • CRDTs trade data-model freedom for coordination-free correctness — a G-Counter, PN-Counter, or OR-Set has a mathematically guaranteed merge, but you design your schema around the CRDT, you don't bolt one onto an arbitrary row update after the fact.
  • Spanner/CockroachDB take a third path — synchronous cross-region consensus (TrueTime, Raft-per-range) so there's never a post-hoc conflict to resolve, paying active-active's usual latency savings for consensus's correctness guarantee (11-consensus-algorithms).
  • Untested failover is the same gap as untested fallback logic elsewhere — RPO/RTO numbers that were never dry-run tend to be discovered wrong during the actual incident, the same lesson circuit breakers teach about untested fallback paths (06-circuit-breakers-bulkheads).
