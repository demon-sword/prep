03Reproducible Feature Engineering Pipelines

One transformation definition shared by the batch and online paths, with fitted statistics — means, encoders, bucket edges — persisted as artifacts instead of recomputed, which is the fix for the classic bug where the serving path re-fits a scaler on live traffic.

Theory

A feature pipeline is code plus fitted state — and only one of them is in git

A transformation looks like pure code: clip the amount, take a log, one-hot the merchant category, bucket the account age. But most useful transformations need a number that came from the data before they can run. StandardScaler needs a mean and a standard deviation. OneHotEncoder needs a vocabulary. A quantile bucketizer needs its bin edges. A median imputer needs the median. A target encoder needs per-category label means. Every one of those is a full-pass statistic over the training set — a tiny model fit on training data. Git versions the code. It does not version those numbers, and that gap is where this whole class of bug lives.

The discipline is one sentence long: fit once, at training time; persist the result; at serving, call transform and never fit. Everything below is a consequence of violating it.

The re-fit-at-serving bug, mechanically

Suppose serving computes z = (x − mean(batch)) / std(batch) over whatever requests are currently in flight, rather than loading the training mean and standard deviation. Nothing throws. The feature is in range. Unit tests pass, because on the training distribution the two agree. Then traffic moves — a price increase, a new country, a marketing push toward larger baskets — and the two paths diverge deterministically:

z_correct = (x − μ_train) / σ_train   vs   z_refit = (x − μ_live) / σ_live

The re-fit version is centred on the live batch by construction, so the mean of the scaled feature is pinned at ≈ 0 no matter how far the raw distribution has moved. The model was trained to read a rising z as "this transaction is unusually large". It now never sees one. The shift has been normalised away before the model gets a vote. This is training-serving skew in its purest form, and it is silent degradation: no exception, no error-rate spike, and — critically — no alarm from a drift monitor that watches the transformed feature, because that feature is stationary by construction. Monitor raw inputs as well as transformed ones, or you monitor the bug's cover story.

The categorical version is worse because it is not a smooth degradation. Fit an ordinal or label encoder on the live batch and the vocabulary is re-derived from whatever categories showed up. One new merchant category sorts into the middle of the list, every code after it shifts by one, and the model reads "travel" where the row actually said "grocery". The values stay in the valid range, so no schema check fires either.

Where the fitted state should live

Bundle it with the model, not beside it. In scikit-learn, put the ColumnTransformer and the estimator in a single Pipeline and log that one object — MLflow's log_model stores the fitted preprocessor and the weights as one artifact under one version, so there is no way to deploy a model with the wrong scaler. TFX's Transform component goes further: it runs the full pass in Beam and emits a TensorFlow graph containing the constants, which is then attached to the serving graph, so training and serving execute literally the same operations. Feast and Tecton attack the same problem from the definition side — a feature is declared once and the framework is responsible for producing it in both the offline and the online path.

The other skew source: one definition, two engines

Even with statistics persisted correctly, training features are usually built in Spark or SQL and serving features in Python inside a request handler. Two implementations of "the same" logic diverge on the boring things: null versus empty string, trailing whitespace, case folding, timezone of a timestamp truncation, integer division, and how each engine rounds. Either share one implementation (a UDF, a compiled transform graph, an on-demand feature view) or accept two and run a scheduled parity job over logged serving features to measure the divergence rather than assume it away.

Fitting on the wrong rows: leakage

Fit the scaler or the target encoder before splitting and the statistics have seen the validation rows. Offline metrics come out optimistic and the gap only shows up in production. Fit inside the training fold — for target encoding, with out-of-fold means — so the validation set is scored by a transformer that never saw it.

Feature staleness is the honest counter-argument. Persisted statistics are frozen, and a scaler fit two years ago will centre today's traffic in the wrong place. That is real — but the fix is to refit on a retraining schedule and ship a new model version whose weights and statistics were fit together, not to refit at request time. Refreshing the scaler underneath a model that was trained against the old one is the same bug wearing a maintenance schedule.

What this looks like in code

# WRONG — serving re-derives the scaler from whatever traffic is in flight.
# Never raises. The drift is normalised away before the model sees it.
def score(batch):
    mu, sd = batch.amount.mean(), batch.amount.std()   # fitted at request time
    z = (batch.amount - mu) / sd
    return model.predict_proba(z.to_frame())[:, 1]

# RIGHT — fit once on the training split, persist, transform-only at serving.
prep = ColumnTransformer([
    ("num", StandardScaler(),                    ["amount", "velocity_1h"]),
    ("cat", OneHotEncoder(handle_unknown="ignore"), ["merchant_category"]),
])
pipe = Pipeline([("prep", prep), ("clf", LGBMClassifier())])
pipe.fit(X_train, y_train)          # full-pass stats computed exactly once

# The fitted stats travel with the weights as ONE versioned artifact.
mlflow.sklearn.log_model(pipe, artifact_path="model")

# serving: load that same artifact and call transform/predict — never fit.
pipe = mlflow.sklearn.load_model("models:/fraud@champion")
scores = pipe.predict_proba(X_live)[:, 1]

The line to say

"A feature pipeline isn't just code — it carries fitted state: the scaler's mean and variance, the encoder's vocabulary, the bucketizer's edges. Those are statistics fit on the training set, so they're part of the model artifact, not part of the serving code. The failure I look for first is a serving path that re-fits instead of loading — you compute the z-score against the live batch, which pins the scaled feature's mean at zero, so a genuine distribution shift gets normalised away before the model ever sees it. Nothing throws, and a drift monitor on the transformed feature stays green because that feature is stationary by construction. So I bundle the preprocessor and the estimator as one versioned artifact — an sklearn Pipeline logged through MLflow, or a tf.Transform graph baked into the serving graph — and I monitor raw inputs alongside transformed ones. Stats get refreshed by retraining and shipping a new version, never underneath a model that was trained against the old ones."

Key takeaways

  • Fit once, transform forever. Any call to .fit() in a serving code path is a bug. The mean, the variance, the vocabulary and the bin edges are training artifacts — version them with the weights, not with the deployment.
  • Re-fitting a scaler at serving is the drift-eraser. The scaled feature is centred on the live batch by construction, so its mean stays ≈ 0 through any raw shift. A monitor on the transformed feature is blind to it; only a monitor on the raw input catches it.
  • Categorical encoders fail discretely, not gradually. One unseen category re-derives the vocabulary and shifts every subsequent code, so the model reads a different category than the row contained — in range, schema-valid, and completely wrong. Set handle_unknown="ignore" (or an equivalent reserved bucket) and pin the vocabulary.
  • Ship the preprocessor inside the model artifact. One sklearn Pipeline logged via mlflow.sklearn.log_model, or TFX Transform emitting a graph attached to the serving graph, makes "wrong scaler with right weights" structurally impossible. Two files in two buckets makes it inevitable.
  • Two engines is the second skew source. Spark for training, Python for serving diverge on nulls, whitespace, case, timezone and rounding long before they diverge on maths. Share one implementation, or run a scheduled parity job over logged serving features and measure the mismatch rate.
  • Fitting before the split is leakage. Scalers and especially target encoders must be fit inside the training fold — target encoding with out-of-fold means — or the offline number is optimistic and production is the first honest measurement.
