06Point-in-Time Correct Feature Joins

Joining labels to the feature values as of the label's event time rather than the latest value — the as-of join and its watermark and TTL edge cases that keep future information from leaking into training and inflating offline AUC.

Theory

The join everyone writes first

A training set is a join: labels on one side, features on the other. The obvious query — join the feature table to the label table on entity_id and take the current value — is wrong in a way that is completely invisible offline and fatal online. It answers "what does this entity look like now?" when the model needs "what did this entity look like at the moment the decision was made?"

Take a fraud model with a feature chargeback_count. At the moment the transaction was scored the counter read 0. The transaction was fraudulent, the customer disputed it six weeks later, and the counter now reads 1. Join on the latest value and every fraudulent row in your training set carries a counter that was incremented because of the very label you are predicting. The model does not learn fraud; it learns to read the answer key. Offline AUC climbs to something that makes the team nervous in a good way, and production performance is whatever the model can do without the answer — usually barely better than the old one. This is point-in-time leakage, the most expensive species of target leakage, and one of the most common reasons an offline win fails to reproduce online.

Note the shape of the bug: nothing throws, no schema check fires, no drift detector notices. Both the training column and the serving column are the same feature with the same dtype and a perfectly reasonable distribution. Only the timestamps are wrong, and timestamps are not what most data-quality suites look at.

As-of semantics

The correct join is the as-of join, a backward-looking last-one-wins lookup evaluated per row:

value(e, t_L) = f.value where f = argmaxf.event_ts { f : f.entity = e ∧ f.event_ts ≤ t_L }

Two properties matter. First, the cutoff is per row, not per dataset: every training example carries its own t_L, so a single global train/test split date does not make a join point-in-time correct — a row labelled in January and a row labelled in June each need their own as-of lookup. Second, the same discipline has to reach inside every aggregate. A "7-day transaction count" must be computed over a strictly backward window (RANGE BETWEEN INTERVAL '7' DAY PRECEDING AND CURRENT ROW), never a centred or calendar-bucket window, or you have reintroduced the leak inside a column that looks like a legitimate feature.

The second clock: ingestion time

Every feature row has two timestamps: the event time at which the fact became true, and the ingestion time (Feast calls it created_timestamp) at which it was actually written to the store. Serving can only read rows that have already landed. An as-of join filtered on event time alone reconstructs rows that existed logically at t_L but had not yet arrived — so training gets a fresher world than production will ever see. Call it ingestion-time skew; it is the residual gap teams cannot explain after fixing the obvious latest-value bug.

The correct predicate is bitemporal: event_ts ≤ t_L AND created_ts ≤ t_L. Its magnitude is set by the ingestion lag relative to the feature's update interval — a feature refreshed every few minutes by a streaming job with a two-minute lag barely notices, while a feature landed by an hourly batch means the last hour of history is real to the offline join and invisible to serving. In streaming systems the equivalent reconstruction is the watermark: what had arrived by the watermark in force at t_L, not what eventually arrived. Late-arriving rows are the reason a backfill run today produces a different (and better) training set than the same query produced last week.

TTL: sometimes NULL is the correct answer

Online stores expire keys — a Feast FeatureView carries a ttl, Redis rows have their own expiry, and any store has a retention horizon. If an entity's last update is older than the TTL, serving returns nothing and the model takes its missing-value path. An as-of join with no lower bound cheerfully reaches back 400 days, finds an ancient row, and hands training a dense feature that production will serve as null. So the join needs both bounds: event_ts ≤ t_L AND event_ts > t_L − ttl. Match the null rate too, not just the values — a column that is 2% null offline and 30% null online will sink a launch on its own, and it is a training-serving skew you can measure before you ship rather than after.

How you find out you have it

  • The metric is implausibly good. A jump well past what the business baseline and prior models suggest is achievable is a leak until proven otherwise. Trust the implausibility, not the number.
  • Ablate the suspect column. Drop it and refit; if the metric collapses to roughly the old baseline, that column was carrying the answer rather than a signal.
  • Audit provenance, not correlation. For each feature ask what process writes it and whether that process can run after the outcome is known. Anything downstream of resolution — chargebacks, refunds, support tickets, a "final status" column — is guilty by construction.
  • Backtest forward in time. Train on rows labelled up to T, evaluate on (T, T+Δ] with every feature re-joined as-of its own row. A leak that survives a random split usually dies here.
  • Shadow the model. The definitive test: at serving time the future does not exist, so a leaking model's shadow prediction quality drops to its true level immediately. This is the only check that cannot be fooled, and it is why leakage should be caught before the offline result is presented, not after.

What the tools give you

pandas.merge_asof implements exactly this — by= for the entity key, direction='backward', and tolerance= as the TTL, which yields NaN rather than a stale value when nothing is in range. It raises unless both frames are sorted by the time key, and it cannot express the ingestion-time predicate per row, so the second clock has to be handled before the join. DuckDB and ClickHouse have a native ASOF JOIN. Open-source Spark SQL has no portable ASOF JOIN keyword; the usual implementation is a range join plus row_number(), and it is the step where a naive GROUP BY entity_id quietly creeps back in. Feature stores make it the default path: Feast's get_historical_features takes an entity dataframe with an event_timestamp column and does the as-of lookup per row bounded by each feature view's ttl, and Tecton offers the same time-travel semantics. Feast keeps created_timestamp and uses it to break ties among rows sharing an event timestamp — but "only rows that had already landed by t_L" is a predicate you generally still write yourself. 

-- Point-in-time correct training set. Three predicates, three different bugs.
SELECT l.entity_id, l.label_ts, l.y, f.txn_count_7d, f.chargeback_count
FROM labels l
LEFT JOIN LATERAL (
  SELECT txn_count_7d, chargeback_count, event_ts
  FROM features f
  WHERE f.entity_id  = l.entity_id
    AND f.event_ts   <= l.label_ts                          -- no future facts
    AND f.created_ts <= l.label_ts                          -- nothing that had not landed yet
    AND f.event_ts   >  l.label_ts - INTERVAL '14 days'   -- TTL: expire, do not stale-serve
  ORDER BY f.event_ts DESC, f.created_ts DESC
  LIMIT 1
) f ON TRUE;
# The same join in pandas. merge_asof raises unless both frames are sorted
# by the time key, and it cannot express the created_ts predicate per row —
# so drop rows that had not landed by the run's watermark before joining.
labels   = labels.sort_values("label_ts")
features = features[features.created_ts <= WATERMARK].sort_values("event_ts")

train = pd.merge_asof(
    labels, features,
    left_on="label_ts", right_on="event_ts",
    by="entity_id",               # per-entity lookup
    direction="backward",        # last value at or before the label
    tolerance=pd.Timedelta("14d"),  # TTL -> NaN instead of a stale value
)
# NaN rate here must match the online store's miss rate, or you have skew.
assert train.txn_count_7d.isna().mean() < 0.05

The line to say

"Any training set I build is an as-of join, not an entity join. Every label row carries its own cutoff, and I look up the last feature value at or before that row's decision time — because the alternative is that a counter like chargeback_count gets incremented by the dispute that is my label, and the model just reads the answer off the feature. That shows up as offline AUC that's too good and production performance that isn't."

"The part people miss is that there are two clocks. Filtering on event time alone still reconstructs rows that hadn't landed in the online store yet, so training sees a fresher world than serving ever will. The predicate has to be bitemporal — event time ≤ t_L and ingestion time ≤ t_L — and it needs a lower bound too, because if the last update is older than the online store's TTL, the correct training value is NULL. I match the offline null rate against the online miss rate; a column that's 2% null offline and 30% null online will sink the launch by itself."

"For catching it: I ablate the suspicious column and see whether the metric collapses to baseline, and I ask for every feature what process writes it and whether that process can run after the outcome is known. But the only check that can't be fooled is shadowing the model on live traffic — at serving time the future doesn't exist, so leakage dies on contact."

Key takeaways

  • The cutoff is per row, not per dataset. A global train/test split by date does not make a join point-in-time correct; each label needs its own as-of lookup, and every windowed aggregate inside it must be strictly backward-looking.
  • Bitemporal or it's still leaking. event_ts ≤ t_L alone reconstructs rows that hadn't been ingested yet. Add created_ts ≤ t_L (or the watermark in force at t_L) — this is the residual gap teams can't explain after fixing the obvious latest-value bug.
  • TTL turns a stale value into a NULL. Bound the lookback by the online store's TTL — Feast's FeatureView.ttl, or tolerance= in pandas.merge_asof — and then check that the offline null rate matches the online miss rate.
  • Provenance beats correlation for finding leaks. Any feature written by a process that can run after the outcome resolves — chargebacks, refunds, ticket counts, a "final status" column — is guilty by construction. Ablation confirms it; a forward-in-time backtest kills the leaks a random split hides.
  • Use a tool that does it natively. pandas.merge_asof (sort both frames first — it raises otherwise — and handle the ingestion clock separately), DuckDB/ClickHouse ASOF JOIN, or Feast get_historical_features with an entity dataframe. Open-source Spark has no ASOF JOIN keyword — hand-rolled range joins are where a GROUP BY entity_id sneaks back in.
  • Shadow deployment is the only unfoolable test. Leakage cannot survive live traffic, so a shadow run that scores far worse than the offline report is a leakage finding, not a serving bug.
