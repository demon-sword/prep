02Dataset Versioning

Content-addressed dataset snapshots — DVC-style pointers and table-format time travel — so a training run can be replayed against the exact rows it saw, and why treating the query as the version breaks the moment a late-arriving row lands.

Theory

A version is an identity for bytes, not a recipe for producing them

Model code gets a git SHA and everyone accepts that a commit is immutable. Data usually gets a path and a date filter, and everyone pretends that is the same thing. It is not. A dataset version has to be an identity — a name that resolves to one fixed set of rows forever — and the only way to guarantee that is to derive the name from the content: hash the bytes, or hash a manifest of the files and row-ranges that make up the snapshot. That is what content addressing buys you. If two runs report the same fingerprint they trained on the same rows; if they report different fingerprints you know it before you start bisecting the model code.

Why the query is not the version

The usual shortcut is to record the SQL — SELECT * FROM events WHERE event_date <= '2026-03-14' — and call that reproducible, on the theory that the predicate pins the data. It pins the event-time boundary. It does not pin the table, and the table underneath is mutable in at least three ways:

  • Late-arriving rows. A row whose event_date is inside the window but whose ingest_time is after your run lands next week and joins the result set retroactively. Re-run the query and you get more rows than the run saw. This is the common case in every event-driven pipeline with a mobile client, a partner feed, or an at-least-once queue behind it.
  • Restatements. An upstream job corrects amounts, re-attributes a transaction, or backfills a column that was null. Row count is unchanged; the checksum is not. This one is nastier than a backfill precisely because the obvious sanity check — did the row count match — passes.
  • Hard deletes. Erasure requests and de-duplication jobs remove rows. The historical row is gone from the live table, so the query can never return it again, however correct the predicate.

All three are the same failure under different names: the query is evaluated against the table as it is now, and the run was evaluated against the table as it was then. Recording the query records your intent, not the data.

Three implementations, and what separates them

File snapshots with a pointer in git. DVC writes a small .dvc pointer file — the hash of the file or directory content plus its size — which you commit next to the code, while the bytes live in remote object storage. The version is a git commit, so git checkout plus dvc checkout restores code and data together. Simple, storage-hungry, and it works for anything on a filesystem, including images and text corpora that no table format handles well.

Table-format time travel. Delta Lake, Apache Iceberg and Hudi each keep an append-only log of table versions, so a query can name a past state: VERSION AS OF 412 in Delta, FOR SYSTEM_VERSION AS OF <snapshot-id> in Iceberg. Cheap, because a version is metadata over shared data files rather than a copy — and that is also the catch. Time travel depends on the underlying files still existing. Delta's VACUUM has a default retention threshold of 7 days, and Iceberg's expire_snapshots does the same job on its own schedule; once files are collected, the pin still names a version that can no longer be read. Time travel is a debugging window, not an archive. Anything you must be able to reproduce a year from now needs a real snapshot written to a separate, retained location.

Git-like branching over the lake. lakeFS puts commits, branches and merges over an object store, so a pipeline can write to a branch, run validation, and atomically merge — versioning the whole lake rather than one dataset.

What a pinned dataset does not give you

A dataset hash is a necessary condition for reproducibility, not a sufficient one. Bit-identical metrics also need the code SHA, the config, the random seeds, the library and CUDA versions, and — for anything on a GPU — a deliberate choice to accept nondeterministic kernels or pay for deterministic ones. Pin the data first anyway: it is the input that changes underneath you without anybody editing anything, so it is the one that produces the "same code, different numbers" bug report.

The other honest caveat: a pin makes a run replayable, it does not make the data right. Reproducing a run that trained on a leaked feature reproduces the leak exactly. Versioning is what lets you prove which rows caused a problem — it is not a claim that the rows were good.

What to log, minimally

Every training run should record the snapshot URI, its fingerprint, the row count and the schema hash, alongside the git SHA. The row count is not redundant with the fingerprint: when the two runs differ, row count tells you instantly whether you are looking at a backfill (more rows) or a restatement (same rows, different bytes), and those have different owners and different fixes. 

# Materialize once, address by content, and log the pin with the run.
import hashlib, mlflow

def fingerprint(paths):
    """SHA-256 over the snapshot's files, in a fixed order.
    Order matters: sorted() makes the digest independent of listing order."""
    h = hashlib.sha256()
    for p in sorted(paths):
        h.update(p.encode())            # path is part of the identity
        with open(p, "rb") as f:
            for chunk in iter(lambda: f.read(1 << 20), b""):
                h.update(chunk)
    return h.hexdigest()

snapshot = "s3://lake/snapshots/txn/2026-03-14T00:00:00Z/"
files    = list_objects(snapshot)

with mlflow.start_run():
    mlflow.log_param("dataset_uri",    snapshot)
    mlflow.log_param("dataset_sha256", fingerprint(files))
    mlflow.log_param("dataset_rows",   row_count)
    mlflow.log_param("schema_sha",     schema_hash)
    mlflow.log_param("git_sha",        git_rev_parse_head())

-- Replay the exact table state, instead of re-running the predicate.
-- Delta Lake:
SELECT * FROM txn VERSION AS OF 412;

-- Apache Iceberg (Spark SQL):
SELECT * FROM txn FOR SYSTEM_VERSION AS OF 3821550127947089418;

-- Both fail once the underlying files are expired/vacuumed,
-- so long-lived pins get an explicit snapshot write:
CREATE TABLE txn_snap_2026_03_14 AS
SELECT * FROM txn VERSION AS OF 412;

The Interview Line

"I version datasets by content, not by query. Every training run logs a snapshot URI plus a hash of the materialized rows, the row count, and the schema hash, next to the git SHA. The reason isn't neatness — it's that WHERE event_date <= X is not stable. Late-arriving rows land inside a window you already trained on, upstream restates values, erasure requests delete rows. Re-run that predicate a month later and you get a different dataset with the same SQL."

"I keep the row count alongside the hash because the two together tell me which kind of change it was: more rows means a backfill, same rows with a different hash means a silent restatement — different team, different fix. And I'd be clear that table-format time travel is a debugging window, not an archive: Delta's vacuum defaults to a 7-day retention, so anything I need to reproduce for audit gets an explicit snapshot written somewhere retained, not a VERSION AS OF pin I'm hoping still resolves."

Key Takeaways

  • Hash the rows, log the hash. A run that records dataset_sha256, dataset_rows and schema_sha as MLflow params can be adjudicated months later in one query. A run that recorded only the SQL cannot be — and you will not find out until someone asks why the same code now scores differently.
  • Row count and checksum answer different questions. Checksum differs + row count grew → late-arriving data. Checksum differs + row count identical → upstream restated values in place, the failure mode that passes every naive sanity check.
  • Time travel expires. Delta's VACUUM defaults to a 7-day retention threshold and Iceberg's expire_snapshots removes old snapshots on its own schedule. A VERSION AS OF pin older than retention resolves to an error, not to data. Long-lived reproducibility needs a materialized snapshot in retained storage.
  • Pick the tool by the artifact. DVC pointers in git for files, directories and unstructured corpora; Delta/Iceberg/Hudi time travel for warehouse tables where copying is unaffordable; lakeFS when you want branch-and-merge semantics over the whole lake. Snapshotting a 10 TB table per run is a storage bill, not an architecture.
  • Immutable snapshots make backfills safe. Once training reads a pinned snapshot rather than the live table, a late-arriving batch can land at any time without silently changing what an in-flight or replayed run sees — the snapshot is the concurrency boundary as much as the audit record.
  • A pin is replayability, not correctness. Reproducing a run that trained on leaked or corrupted rows reproduces the leak precisely. Versioning tells you exactly which rows to blame; the validation gate is what stops them.
