09ML Pipeline Orchestration

DAG-based orchestration of ingest, validate, train, evaluate, and register steps in Airflow, Dagster, or Kubeflow — retries, idempotent task boundaries, backfills, and the sensors that stop a stalled upstream from silently training on stale data.

Theory

The DAG is a contract about what may run, not a script that runs

A training script is a sequence; a DAG is a set of tasks plus a partial order plus the states each task may legally be in. The orchestrator's job is not to "run your pipeline" — it is to decide, over and over, which tasks are currently eligible, and to keep that decision correct when a worker dies mid-task, when two runs overlap, and when someone asks for the same run again three weeks later. Everything difficult about orchestration follows from the fact that the scheduler will make that decision far more times than you expect.

In Airflow the eligibility rule is per-task and configurable: trigger_rule defaults to all_success, which is why a failed task turns every descendant into upstream_failed rather than into a failure of its own. Change one task to all_done and you have said "run me even if my parents failed" — occasionally right for a cleanup or notification task, and quietly catastrophic on build_features, because the run then trains and registers a model whose dataset snapshot task failed. The DAG goes red, a model still ships, and nobody reads the red because the model is in production.

Retries only help failures that are actually transient — and only if tasks are idempotent

Airflow's own default is retries = 0; almost every team sets 2 or 3 in default_args and stops thinking about it. Two things then bite. First, the retry is free only for transient faults — a throttled API, an evicted pod, a flaky network mount. A deterministic bug fails identically three times and all you have bought is retries × retry_delay of extra latency; with the default retry_delay of 5 minutes that is silent, but with a 30-minute delay on a six-hour pipeline it is the difference between recovering before the business day and not. Second, the retry is only safe if the task is idempotent. A task that appends rows for its data interval doubles them on the second attempt; a task that does DELETE WHERE dt = <interval> then insert, or writes to s3://.../dt=2026-08-30/ with overwrite semantics, converges to the same state no matter how many times it runs. Task boundaries should be drawn where the output is a replaceable artifact for exactly one data interval — that is the property that makes both retries and backfills sound.

Set execution_timeout too. Its default is None, so a task that hangs on a socket read stays running forever, holds its slot, and produces no alert at all — the DAG is neither succeeding nor failing, which is the one state most alerting setups don't cover.

Sensors, or: the difference between waiting and training on stale data

The upstream table you read is produced by a team you don't control. If your DAG fires at 02:00 and their partition lands at 02:40, and you have no sensor, your ingest task does not fail — it reads the previous day's partition, returns zero new rows, and succeeds. Every downstream task succeeds. The model retrains on yesterday's data and the pipeline is entirely green. This is feature staleness in its purest form: a silent degradation with no error to page on. The fixes are a sensor that waits for the partition marker, plus a hard assertion inside ingest that a zero-row read is an exception, not a result.

Sensors have their own trap. A sensor in the default mode="poke" occupies a worker slot for its entire life, so four sensors waiting three hours each can deadlock a small pool with nothing running. mode="reschedule" releases the slot between pokes, and deferrable operators hand the wait to the triggerer process entirely. Always set a timeout that is shorter than the point at which the data is useless: the sensor default is seven days, and a sensor that waits seven days is a sensor you will never notice is stuck.

One detail worth knowing because it surprises people: when a sensor exceeds its timeout it raises AirflowSensorTimeout, and Airflow treats that like AirflowFailException — the task is force-failed straight to failed without consuming retries. That is the behaviour you want (retrying a timed-out sensor would just restart the same wait), but it means retries in default_args buys the sensor nothing. The only thing bounding how long that wait lasts is timeout itself, which is exactly why leaving it at the seven-day default is dangerous.

Schedules, data intervals, and the catch-up storm

Airflow schedules over data intervals, not over wall-clock triggers: the run labelled 2026-08-30 for a daily DAG starts after that interval has closed, i.e. at the start of 2026-08-31. The consequence is that logical_date (the old execution_date) is the beginning of the window your task should process, and every partition path, every SQL predicate, and every feature cut-off should be derived from it rather than from datetime.now(). A task that reads "today" is not backfillable, because re-running it in November produces November's answer for an August run.

Then there is catchup. Unpause a DAG whose start_date is three months back with catchup on, and the scheduler creates every missed interval at once. The only thing bounding what happens next is max_active_runs, whose config default (core.max_active_runs_per_dag) is 16 — so sixteen concurrent training runs hit the warehouse in the same second, each one convinced it is a normal nightly run. Set catchup explicitly on the DAG rather than inheriting the deployment's default, and set max_active_runs=1 for anything that writes shared state. The related knobs are max_active_tasks_per_dag (per-DAG task concurrency, default 16), the cluster-wide parallelism (default 32), and pools for a shared resource such as a GPU node group. depends_on_past=True is frequently misdescribed in interviews, so be precise: it is a per-task flag, and it makes one task instance wait for that same task in the immediately preceding DAG run to have succeeded. It does not serialise DAG runs — runs still start concurrently up to max_active_runs and pipeline through, each task gated only on its own predecessor, so run N's train can be running while run N+1's ingest already has. What it buys you is per-task ordering for a stateful incremental job; what it costs you is that one failed run blocks that task in every later run until it is cleared. If you actually want one run at a time, the knob is max_active_runs=1 — nothing else gives you that.

Backfills and the blast radius of a clear

Re-running is the normal case, not the exception: a feature definition changed, a bug shipped, an upstream was corrected. airflow tasks clear --task-regex X --downstream resets that task and its descendants across a date range and lets the scheduler re-run them; tasks upstream that already succeeded are untouched. This is the whole payoff of drawing task boundaries at replaceable artifacts — you re-run build_features onward for 30 days without re-ingesting a terabyte. Two cautions: a backfill of 90 daily runs is 90 DAG runs against the same infrastructure your live pipeline uses, so it needs its own pool or a capped max_active_runs; and if a task is not idempotent, the clear is how you discover it.

Airflow, Dagster, Kubeflow — what actually differs

Airflow orchestrates tasks: the unit is "a thing that ran", and data lineage is something you bolt on. Dagster orchestrates assets: you declare the table or model each step produces, so the graph is over data objects, partitions are first-class, and "re-materialise everything downstream of this asset" is a built-in operation rather than a regex over task ids. Kubeflow Pipelines runs each step as a container on Kubernetes and caches step outputs keyed on the step's inputs and image, so an unchanged preprocessing step is skipped on the next run — excellent for iteration, and a source of confusion the first time a "fixed" step silently serves a cached result. The choice mostly follows what your team already operates; the reasoning about retries, idempotency, intervals and concurrency is identical in all three.

Failure modes to name out loud

  • Silent stale training — no sensor, upstream late, ingest succeeds on zero new rows.
  • Non-idempotent retry — an appending task retried once; the interval now has duplicate rows and the label rate shifts.
  • Catch-up storm — catchup=True plus the default max_active_runs=16 on unpause.
  • Zombie task — no execution_timeout; the task is stuck in running and nothing alerts.
  • Trigger-rule leak — all_done on a task that should have been gated, so a model is registered from a run whose snapshot failed.
  • Wall-clock dependence — tasks reading now() instead of the data interval, making every backfill wrong in a way that produces no error.
# One nightly training DAG, with the defaults that actually matter set explicitly.
from datetime import datetime, timedelta
from airflow import DAG
from airflow.operators.python import PythonOperator
from airflow.sensors.filesystem import FileSensor

default_args = {
    "retries": 2,                              # Airflow's own default is 0
    "retry_delay": timedelta(minutes=5),        # this IS the default
    "retry_exponential_backoff": True,
    "max_retry_delay": timedelta(minutes=30),
    "execution_timeout": timedelta(hours=2),    # default None = hangs forever, silently
}

with DAG(
    dag_id="churn_daily",
    start_date=datetime(2026, 1, 1),
    schedule="0 2 * * *",
    catchup=False,           # be explicit; do not inherit scheduler.catchup_by_default
    max_active_runs=1,       # config default is 16 -> 16 concurrent trainings on unpause
    default_args=default_args,
) as dag:

    wait_raw = FileSensor(
        task_id="wait_raw",
        filepath="/data/events/{{ ds }}/_SUCCESS",
        poke_interval=60,
        timeout=60 * 60 * 3,     # fail loudly after 3h; sensor default is 7 days
        mode="reschedule",       # poke mode would hold a worker slot the whole time
    )

    def _ingest(**ctx):
        # idempotent: the partition is derived from the data interval, never now()
        part = ctx["data_interval_start"].strftime("%Y-%m-%d")
        wh.execute("DELETE FROM events_clean WHERE dt = %s", (part,))
        rows = wh.copy_from_raw(part)
        if rows == 0:
            raise ValueError(f"empty partition {part}")   # never succeed on 0 rows
        return rows

    ingest         = PythonOperator(task_id="ingest", python_callable=_ingest)
    validate       = PythonOperator(task_id="validate", python_callable=_validate)
    snapshot       = PythonOperator(task_id="snapshot", python_callable=_snapshot)
    build_features = PythonOperator(task_id="build_features", python_callable=_features)
    train          = PythonOperator(task_id="train", python_callable=_train)

    # default trigger_rule=all_success: if snapshot fails, build_features is
    # upstream_failed and NO model is trained from an unsnapshotted dataset.
    wait_raw >> ingest >> [validate, snapshot] >> build_features >> train
# Re-run only the broken step and everything downstream, for a date range.
# Upstream tasks that already succeeded are not touched.
airflow tasks clear churn_daily \
    --task-regex "build_features" --downstream \
    --start-date 2026-08-01 --end-date 2026-08-30 --yes
Sort that list by whether the scheduler can see it. Only two of those six leave a state you can alert on from task metadata: the catch-up storm shows up as a queue of concurrent runs, and the trigger-rule leak leaves a red snapshot next to a green register — visible, if anyone looks at more than the DAG's overall status. The other four are green-and-silent. Silent stale training exits zero on a zero-row read. A non-idempotent retry produces duplicate rows and a task marked success. A wall-clock-dependent task computes the wrong window and raises nothing. And a task hung with execution_timeout=None just stays in running — Airflow's zombie detection only reaps tasks whose process stopped heartbeating, so a process that is alive and blocked on a socket sits there indefinitely without ever emitting a failure. A green DAG is evidence that your tasks exited zero; it is not evidence that the data was there or that it was the right data. Those checks have to be assertions inside the task (row counts, freshness of max(event_time), a primary-key uniqueness check after write), a sensor in front of it, and a timeout on it.

The line to say

"The orchestrator decisions I care about are boundaries and idempotency, not the DAG picture. I draw each task so its output is one replaceable artifact for one data interval — delete-then-insert the partition, never append — because that single property is what makes a retry safe and a 30-day backfill a clear --downstream instead of a project."

"Then the two settings people skip. Sensor plus a zero-row assertion in front of ingest, because a late upstream doesn't fail your pipeline — it makes it read yesterday's partition and go green while the model retrains on stale data, and there is no error to page on. And set catchup and max_active_runs explicitly: the default is 16 concurrent runs, so unpausing a DAG with three months of history is sixteen training jobs on your warehouse at once. If a task isn't idempotent I'd rather it be max_active_runs=1 and slow than parallel and non-deterministic."

Key Takeaways

  • Idempotency is the whole game. Derive every path and predicate from data_interval_start, never now(), and overwrite the interval's partition rather than appending. A retried appending task silently doubles a day's rows — and the model trains on it without a single red task.
  • Airflow's defaults are not your defaults. retries=0, execution_timeout=None, max_active_runs_per_dag=16, max_active_tasks_per_dag=16, cluster parallelism=32, sensor timeout=7 days, sensor mode="poke". Each of those has burned someone; set them in default_args and on the DAG explicitly.
  • A green DAG is not a fresh model. No sensor + late upstream = a zero-row ingest that succeeds. Put a FileSensor/partition sensor with mode="reschedule" and a real timeout in front, and raise inside the task on an empty read — this is the feature-staleness failure that monitoring dashboards miss.
  • Know what trigger_rule buys and costs. all_success is what stops a model being registered from a run whose snapshot task failed; all_done belongs on cleanup and alerting tasks, not on anything in the train-and-register path.
  • Backfills are production load. 90 daily runs cleared at once hit the same warehouse, feature store and GPU pool as live traffic — give them a dedicated Airflow pool or cap max_active_runs — that cap is the only knob that actually limits concurrent runs. depends_on_past=True is not it: it gates each task on the same task in the previous run, so runs still overlap in a pipeline, and its real cost is that one failed run blocks that task in every later run until it is cleared.
  • Pick the tool for the unit you reason about. Airflow's unit is a task, Dagster's is an asset (partitioned, with "re-materialise downstream" built in), Kubeflow's is a containerised step with input-hash caching. Only the last one will silently reuse a step's previous output after you "fixed" it.
