01Data Validation for ML Pipelines

Schema and distribution assertions run on every batch before it reaches training — catching null-rate spikes, unseen categorical values and silently rescaled units before they become a quietly worse model.

Theory

Three layers of assertion, not one

A validation gate sits between ingestion and training and answers three different questions, which fail in three different ways. Structural assertions cover the shape of the data: are the expected columns present, are the dtypes what they were last week, is the batch complete. Value-level assertions cover individual cells: is amount non-null, is it inside a plausible range, is merchant_category drawn from the set of codes the encoder was fitted on. Aggregate assertions cover properties only the batch as a whole has: row count, mean, distinct-value count, and the distance between this batch's distribution and a reference one.

The reason to keep these separate is not tidiness — it is that the remediation differs. A value-level failure is attributable to specific rows, so you can drop them and continue. An aggregate failure is a property of the batch, so there is nothing to drop; either the batch is acceptable or it is not.

Row-level tolerance vs. batch rejection

Great Expectations encodes exactly this with the mostly parameter: a column-value expectation succeeds when the fraction of rows satisfying it is at least mostly. That single number is your quarantine budget.

success_fraction = valid_elements / evaluated_elements   →   pass if ≥ mostly
pass → drop the offending rows, continue on the remainder
fail → the batch is not salvageable by dropping rows; reject it

One sharp edge here: column-value expectations in Great Expectations exclude missing values from the evaluated set by default. So expect_column_values_to_be_between on a column that just went 100% null passes — every value it evaluated was in range, because it evaluated none. The not-null expectation is what catches that, and it has to be written explicitly.

The failure modes worth naming

  • Schema drift — an upstream service adds an enum value, renames a column, or flips a dtype from int to string after an export format change. Your one-hot encoder maps the new value to the unknown bucket, or the join silently drops.
  • Null-rate spike — a partner feed times out and the join left-joins to nothing. Imputation happily fills the gap with the training mean, and the model degrades without raising a single exception.
  • Silent unit rescale — cents become dollars, or milliseconds become seconds. Every individual value stays plausible, so range checks stay green; only an aggregate check on the mean sees it.
  • Sentinel-for-null — upstream encodes missing as -1 or 999999. The not-null check passes; the range check is the only thing standing between that and a poisoned feature.
  • Partial delivery — half the expected partitions landed. A row-count expectation is the cheapest check in the suite and catches it.

What this gate cannot tell you

An input-side gate is not a performance alarm. Every expectation can pass while the model gets worse, because a change in P(y|X) — concept drift — leaves P(X) untouched. Validation stops garbage from reaching training; it says nothing about whether the model is still accurate. That requires labels, and labels usually arrive late.

Tools, and where the gate lives

Great Expectations gives you named expectation suites, checkpoints that run a suite against a batch, and Data Docs to render the result. TensorFlow Data Validation takes the opposite route: it infers a schema from a baseline dataset's statistics and validates later batches against it, surfacing anomalies such as unseen categorical values or missing features. Its schema carries a skew_comparator for training-vs-serving comparison and a drift_comparator for batch-vs-previous-batch, both using L∞ distance for categorical features and Jensen–Shannon divergence for numeric ones — with thresholds you choose, since there is no universal default. Pandera is the lightweight in-process option for pandas and PySpark dataframes, and Deequ the Spark-native one for batches too large to pull into a driver.

Wherever it lives, the gate has to be a hard stop in the DAG — an Airflow task that raises and blocks the downstream training task — not a report someone reads the next morning. And the suite belongs in git next to the pipeline, so that loosening a threshold shows up in a code review rather than in a model that quietly got worse.

The gate, written out

This is the whole mechanism the visualization runs, with nothing hidden behind a library. The only structural decision is the one that matters: which expectations can be remediated by dropping rows, and which cannot. 

# validate.py — row-level tolerance vs. aggregate rejection
KNOWN_MCC = {"5411", "5812", "5999", "4121", "7995"}

def validate(batch):
    n = len(batch)
    results, quarantine = [], set()

    # --- row-level: attributable to specific rows, so droppable ---
    def row_check(name, predicate, mostly, evaluate_nulls=False):
        # Great Expectations excludes missing values from the
        # evaluated set for column-value expectations.
        idx = [i for i, r in enumerate(batch)
               if evaluate_nulls or r["amount"] is not None]
        bad = [i for i in idx if not predicate(batch[i])]
        evaluated = len(idx)
        frac = 1.0 if evaluated == 0 else 1 - len(bad) / evaluated
        results.append((name, "row", frac, frac >= mostly))
        if frac >= mostly:
            quarantine.update(bad)      # tolerated: drop the rows
        return frac >= mostly

    row_check("expect_column_values_to_not_be_null(amount)",
              lambda r: r["amount"] is not None, mostly=0.98, evaluate_nulls=True)
    row_check("expect_column_values_to_be_in_set(merchant_category)",
              lambda r: r["merchant_category"] in KNOWN_MCC, mostly=0.98,
              evaluate_nulls=True)
    row_check("expect_column_values_to_be_between(amount, 0.01, 5000)",
              lambda r: 0.01 <= r["amount"] <= 5000, mostly=0.99)

    # --- aggregate: a property of the batch, so NOT droppable ---
    vals = [r["amount"] for r in batch if r["amount"] is not None]
    mean = sum(vals) / len(vals) if vals else 0.0
    results.append(("expect_column_mean_to_be_between(amount, 60, 100)",
                    "agg", mean, 60 <= mean <= 100))
    results.append(("expect_table_row_count_to_be_between(400, 900)",
                    "agg", n, 400 <= n <= 900))

    failed = [r for r in results if not r[3]]
    if failed:
        raise BatchRejected(failed)     # hard stop, nothing is salvaged
    return [r for i, r in enumerate(batch) if i not in quarantine]

Making it a hard stop in the DAG

Raising AirflowFailException marks the task failed without retrying — the right behaviour for a deterministic data problem, since retrying the same bad partition will fail the same way and only delay the page. 

# dags/train_fraud_model.py
from airflow.decorators import dag, task
from airflow.exceptions import AirflowFailException

@dag(schedule="@daily", catchup=False, max_active_runs=1)
def train_fraud_model():

    @task
    def validate_batch(ds=None):
        batch = load_partition(ds)
        try:
            clean = validate(batch)
        except BatchRejected as e:
            # non-retryable: the same partition will fail identically
            raise AirflowFailException(f"{ds}: {e.failed_expectations}")
        quarantined = len(batch) - len(clean)
        if quarantined:
            write_quarantine(ds, batch, clean)
        return write_clean(ds, clean)

    @task
    def train(path: str):
        ...

    train(validate_batch())

The Interview Line

"Before anything trains, every batch runs an expectation suite, and I split those expectations by what I can actually do about a failure. Row-level checks — nulls, out-of-range values, categories outside the set the encoder was fitted on — carry a tolerance; under it I quarantine the offending rows and let the batch through, over it the batch is rejected outright. Aggregate checks like a mean or a row count can't be fixed by dropping rows, so those always fail the whole batch — and that's the one that catches an upstream team switching cents to dollars, where every individual value is still perfectly valid and the model just quietly gets worse."

"The thing I'd want to be clear about is that this is an input-side gate. It stops bad data reaching training. It tells me nothing about whether the model is still accurate — a green suite is entirely compatible with concept drift, and I need labels for that."

Key Takeaways

  • Split expectations by remediation, not by column. Row-level value checks get a mostly tolerance and quarantine what fails underneath it; aggregate checks (mean, row count, distinct count) have no per-row attribution, so they can only pass or fail the entire batch. Getting this split wrong is why teams either reject good batches over three bad rows or accept a batch whose mean moved 40%.
  • Column-value expectations skip nulls by default. In Great Expectations, expect_column_values_to_be_between on a column that just went entirely null passes — the evaluated set was empty. Always pair a range expectation with an explicit not-null expectation, and add a range check to catch -1/999999 sentinels that make the not-null check useless.
  • Don't infer a schema from one day of data. TFDV's infer_schema and Deequ's constraint suggestion are starting points, not answers — bounds derived from a single batch will page you on the first legitimate seasonal outlier. Infer over a window, review the schema by hand, then commit it to git so threshold changes show up in a diff.
  • The gate must block, not report. A validation task that logs and returns success is decoration. In Airflow, raise AirflowFailException (non-retryable — the same partition will fail identically) or short-circuit the downstream training task, and route quarantined rows to a table someone actually looks at.
  • Validation is where training-serving skew gets caught early. TFDV keeps skew_comparator (training vs. serving) separate from drift_comparator (batch vs. previous batch) for exactly this reason — they compare different pairs of distributions and warrant different thresholds, using L∞ distance for categorical features and Jensen–Shannon divergence for numeric ones.
  • A green suite is not a healthy model. Data validation constrains P(X). Concept drift changes P(y|X) and shows up nowhere in these checks. Treat this as the cheapest layer of monitoring, not the whole of it — the rest needs prediction-distribution monitoring and, eventually, labels.
