10Model Registry and Stage Promotion

Immutable model versions with stage transitions (staging, production, archived), the metadata that must ride along (training dataset hash, metrics, input signature), and why serving resolves a registry alias rather than a filesystem path.

Theory

A registry is an indirection layer, not a file server

The naive way to ship a model is to write model.pkl somewhere and point the serving container at it. That works exactly until the first question you cannot answer: which model is currently answering requests, what data trained it, and how do I get the previous one back in under a minute. A model registry exists to make those three questions cheap. It does that by inserting a level of indirection between the artifact and the thing that loads it: training writes an immutable version, promotion moves a name, and serving resolves the name. Nobody in the loop types a path.

The consequence people miss is that promotion becomes a metadata write rather than a deploy. Moving @production from version 7 to version 8 does not rebuild an image, does not restart a pod, and does not touch the artifact store. That is also why rollback is fast — it is the same metadata write in reverse — and it is why a registry is worth having even on a team with three models.

Immutability, and the metadata that must ride along

A version is append-only. Registries assign monotonically increasing integers and fix the artifact source at creation time; you cannot re-point version 7 at different bytes, you can only register version 8. That single property is what makes "the model that scored this customer in March" a resolvable object rather than a guess. The moment someone overwrites artifacts in place, every audit answer downstream becomes unprovable.

Immutability is worthless without lineage, though, and lineage is the part teams skip because nothing breaks when they do. Four things have to be attached to the version at registration:

  • Training dataset identity — a snapshot hash or table version, not a query string. Without it the version is unreproducible: you can serve it forever and never rebuild it.
  • The input signature — column names and types the model expects. This is the only thing standing between a dropped upstream column and silent garbage predictions.
  • The evaluation metrics and the eval set they were computed on — a number with no denominator cannot be compared against the incumbent at promotion time.
  • Code provenance — the git SHA and the environment spec. "Trained by the notebook on someone's laptop" is not provenance.

Missing metadata is a broken lineage failure, and its defining trait is that it is silent at write time and expensive at read time — you discover it during an incident or an audit, months after the person who ran the training job left.

Stages, aliases and approval flags are three vocabularies for one idea

MLflow originally shipped fixed stages — None, Staging, Production, Archived — and has since deprecated them in favour of arbitrary named aliases such as @champion plus tags, because a fixed four-value enum cannot express "the model serving the EU region" or "the challenger". SageMaker's Model Registry never had stages at all: model packages carry a ModelApprovalStatus of PendingManualApproval, Approved or Rejected, and flipping it to Approved is the event a deployment pipeline subscribes to. Vertex AI does the same thing with version aliases including a default alias. Underneath, all three are a mutable pointer into an immutable version list, with an audit trail of who moved it and when. Interviewers care that you know it is a pointer; the vendor noun is incidental.

Why serving resolves an alias, not a path

Three resolution strategies, and only one of them survives an incident:

  • Alias — models:/fraud_scorer@production. Rollback is a pointer move. The one real cost is that resolution is usually cached, so your rollback takes effect after that cache expires; that TTL is your rollback latency floor, and it is worth knowing the number.
  • Pinned URI — the deployment hardcodes the artifact path of a specific version. Fully reproducible, but rollback now requires a redeploy: a config change, a review, an image roll. Reasonable for a regulated system where every change must be a tracked deploy, painful at 3am.
  • Mutable "latest" path — s3://models/fraud/latest/, overwritten by the training job. This is the trap. Any training run that finishes, including one that failed the evaluation gate and was never approved, silently becomes production. There is no previous version to roll back to because it was overwritten, and no record of when the change happened.

The named failure modes

Broken lineage: a version with no dataset hash or signature — servable, unreproducible. Registry/serving drift: the registry says version 8 is production while a pinned deployment is still running version 5, so the dashboard and reality disagree — always report the version the serving process actually loaded, not the one the registry believes is current. Schema drift reaching an unsignatured model: an upstream column disappears and, with no signature to enforce, the model scores a null-filled feature instead of raising; with a signature it fails loudly at the boundary, which is what you want. And promotion without a rollback path: promoting a version that archives its predecessor's artifact, or promoting from a training run whose environment was never captured, leaves you with a pointer that has nowhere to point back to.

Registering with lineage attached

import mlflow, hashlib, subprocess
from mlflow.models import infer_signature

with mlflow.start_run() as run:
    model.fit(X_train, y_train)

    # The signature is the schema contract the serving layer enforces.
    signature = infer_signature(X_train, model.predict(X_train))

    mlflow.sklearn.log_model(
        model,
        artifact_path="model",
        signature=signature,
        input_example=X_train.head(5),
    )
    mlflow.log_metric("auc", auc)
    mlflow.log_metric("auc_eval_n", len(X_eval))

    # Lineage: pin WHAT trained it, not the query that selected it.
    mlflow.set_tags({
        "dataset_hash": snapshot_sha256,
        "dataset_uri": "s3://lake/fraud/snapshots/2026-09-01/",
        "git_sha": subprocess.check_output(
            ["git", "rev-parse", "HEAD"]).decode().strip(),
    })

mv = mlflow.register_model(f"runs:/{run.info.run_id}/model", "fraud_scorer")

# Promotion is a pointer move — no rebuild, no redeploy.
client = mlflow.MlflowClient()
client.set_registered_model_alias("fraud_scorer", "production", mv.version)

# Serving never sees a path. Rollback = point the alias back.
predictor = mlflow.pyfunc.load_model("models:/fraud_scorer@production")
The gotcha: a registry version records the artifact and its metadata, not the runtime. If the serving image upgrades a library the model was pickled against, resolving the alias still succeeds and the load fails — or worse, succeeds with different numerics. Log the environment (conda.yaml / requirements.txt are emitted alongside the MLflow model) and pin it in the serving image, or your "immutable version" is only immutable on one axis.

The Interview Line

"The registry gives me two things I can't get from a file in S3: immutable versions and a mutable pointer. Training registers a version with the dataset hash, the input signature, the eval metrics and the git SHA attached — if any of those are missing the version is servable but unreproducible, and I gate Production promotion on them for exactly that reason. Serving then resolves models:/fraud_scorer@production, never a path, so promotion and rollback are both a pointer move rather than a redeploy."

"The trade-off I'd call out is the resolution cache. Alias resolution is cached in the serving process, so whatever that TTL is — say thirty seconds — that's the floor on how fast a rollback actually reaches traffic, and it's why I report the version the pod loaded rather than the one the registry thinks is current. The alternative, pinning the artifact URI, is more auditable but turns rollback into a redeploy. What I won't accept is a mutable latest path: that means any training run that finishes ships itself, including one that failed the eval gate, and there's nothing to roll back to."

Key Takeaways

  • Promotion is a metadata write, not a deploy. Moving @production from v7 to v8 touches no artifact and restarts no pod — which is exactly why rollback is cheap. If your rollback requires a CI pipeline, you have a pinned path, not a registry.
  • Four fields or the version is unreproducible: dataset snapshot hash (not a query), input signature, eval metrics with their eval-set size, and git SHA plus environment. MLflow's infer_signature + tags, SageMaker's model package metadata, Vertex's version labels — every registry has the slots; teams just don't fill them.
  • Stages are deprecated in MLflow; aliases replaced them. The fixed Staging/Production enum could not express per-region or challenger pointers, so MLflow moved to named aliases plus tags. SageMaker uses ModelApprovalStatus and Vertex uses version aliases — all of them a mutable pointer over an immutable list.
  • The alias cache TTL is your rollback latency floor. A serving process that resolves the alias once per N seconds cannot roll back faster than N. Know the number, and expose the loaded version on a health endpoint so registry state and serving state can be reconciled.
  • A logged signature converts silent degradation into a loud 4xx. When an upstream column disappears, an unsignatured model scores a null-filled feature and your metrics quietly sag; a signatured one rejects at the boundary and pages someone. Prefer the page.
  • Never serve from a mutable path. s3://models/fraud/latest/ means every finished training run self-promotes, including the ones that failed evaluation, with no prior artifact to return to and no record of when it changed.
