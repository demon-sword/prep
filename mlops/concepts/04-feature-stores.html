04Feature Stores

An offline store for training and an online store for low-latency lookup behind a single feature definition — materialization jobs, TTLs and entity keys — plus the honest question of when a feature store is over-engineering versus a plain cache and a shared library.

Theory

Two stores, one definition — and the definition is the point

A feature store is not a database. It is a registry of feature definitions plus two storage layers that the registry keeps in sync, and the value is almost entirely in the registry. The offline store is a columnar, historical, append-mostly table — Parquet on object storage, BigQuery, Snowflake, Delta or Iceberg — holding every value a feature has ever taken, each row stamped with an event timestamp. It answers "what was user_txn_count_7d for user 42 as of 3 March at 14:02?", which is the query training data generation needs and which is a point-in-time correct join, not a lookup. The online store is a key-value store — Redis, DynamoDB, Cassandra, Bigtable — holding only the latest value per entity key, sized for a single-entity read on the request path. It answers "what is user_txn_count_7d for user 42 right now?" in the low single-digit milliseconds on the same network.

Those two access patterns are irreconcilable in one system, so you get two systems. The failure that follows is obvious once stated: two systems, two code paths, two chances to compute the feature differently — that is training-serving skew with infrastructure behind it. A feature store's real claim is that the transformation is declared once, and the platform is responsible for producing it on both sides. If your feature store lets each team write the batch version in Spark SQL and the online version in a Python handler, you bought two databases and no guarantee.

Entity keys, materialization and the freshness ladder

Every feature is keyed by an entity — user, merchant, listing, driver — and joined at read time by that key. Getting the entity granularity wrong is the quiet killer: define a feature on user_id when the model actually scores (user_id, merchant_id) pairs and you cannot express the interaction at all without a new view and a backfill.

Materialization is the job that copies offline → online. Batch materialization on a schedule is the default, and it sets a hard floor on freshness:

worst-case online staleness ≈ materialization interval + job runtime + upstream table lag

An hourly job over a warehouse table that itself lands 40 minutes late gives you features up to ~1h40m old at serving time, while the offline store used for training saw the value at the exact event timestamp. That gap is skew you introduced yourself. The ladder out of it is: batch materialization (minutes to hours), streaming ingestion straight into the online store from Kafka or Flink (seconds), and on-demand transforms computed at request time from the request payload plus stored features (zero staleness, but you pay the compute in your latency budget). Feast calls these FeatureView, StreamFeatureView and OnDemandFeatureView. The right answer is per feature, not per platform: a 30-day spend average does not need streaming; "transactions in the last 60 seconds" cannot be served any other way.

TTL is not a cache-eviction knob

In Feast the ttl on a feature view bounds how far back a lookup will reach for a value: in the historical join it limits how old a feature row may be relative to the label's event timestamp, and on retrieval a value older than the TTL is treated as missing rather than returned. Set it shorter than your materialization interval and you get null gaps in every cycle by construction — the value ages past the TTL before the next job writes a fresh one. Nothing errors. The nulls flow into whatever default your pipeline imputes, the feature's distribution shifts toward that constant, and you have feature staleness presenting as a mild, unexplained accuracy decay. Set the TTL far too long instead and you happily serve a value from three weeks ago for an entity whose upstream job has been broken for three weeks. Neither case raises an exception, which is why serving-side null rates and value age belong on the monitoring dashboard next to latency.

When it is over-engineering

The store earns its keep on two axes: reuse (many models and teams needing the same features, with discovery and lineage) and point-in-time correctness at scale (many entities, many event-timestamped labels, where the as-of join is genuinely hard to write correctly). One team, one model, features computable from the request payload or a single indexed lookup? A shared transformation library plus Redis is the correct architecture, and it costs a fraction of the operational surface. The honest cost of a store is real: a registry to keep authoritative, materialization jobs to schedule and monitor, backfills whose compute bill scales with history × entities, and a new hard dependency on the request path. Feast is open source and is mainly definition, registry, materialization and serving over storage you already own — it orchestrates rather than replaces your compute; Tecton is a commercial platform that also owns the transformation pipelines and managed streaming aggregations. Databricks, SageMaker and Vertex AI each ship their own. Pick on how much of the pipeline you want to stop operating, not on the feature list.

The lookup is fast; the fan-out is what hurts. One key read is cheap. Forty features across four entities, fetched serially, is forty round trips, and your p99 is set by the worst of them. Batch every read into a single multi-get per entity type, and treat the online store as a hard dependency in your latency budget — see serving latency budgets.

The line to say

"A feature store is two storage layers behind one definition — an offline columnar store for point-in-time-correct training joins, and an online key-value store for a single-entity read on the request path — and the definition is where the value is, not the storage. What I'd actually check first in a running one is the gap between them: the online value is only as fresh as materialization interval plus job runtime plus upstream lag, while training read the exact value at the label's event timestamp, so any staleness there is training-serving skew that we introduced ourselves. The specific bug I've seen bite hardest is a TTL set shorter than the materialization interval — the value ages out before the next job writes it, lookups return null every cycle, the nulls get imputed to a default, and it shows up as a slow unexplained accuracy decay rather than an error. And I'd push back on adopting one for a single team with a single model: if the features come off the request payload, a shared transform library plus Redis is the right answer — the store earns its keep on cross-team reuse and on point-in-time joins you'd otherwise get wrong."

Key takeaways

  • Two access patterns force two stores. Offline is a historical, event-timestamped columnar table read by an as-of join for training; online is latest-value-per-key read in the low milliseconds at serving. Don't let a candidate answer collapse them — the whole design follows from the split.
  • Freshness is bounded by the materialization job, not by the store. Worst-case online staleness ≈ interval + job runtime + upstream table lag. Pick per feature: batch views for slow aggregates, stream views (Kafka/Flink into the online store) for second-level windows, on-demand views for anything derived from the request payload.
  • Feast's ttl bounds how old a value may be, not just when Redis evicts it. TTL shorter than the materialization interval produces guaranteed null gaps every cycle; the nulls get imputed and surface as silent degradation, never as an error. Alert on serving null rate and feature age, not only on latency.
  • Entity granularity is a one-way door. A feature keyed on user_id cannot express a (user, merchant) interaction; fixing it means a new view plus a full backfill whose cost scales with history × entities.
  • The p99 comes from fan-out, not from the lookup. Forty features fetched serially is forty round trips; batch them into one multi-get per entity type and budget the online store as a hard request-path dependency.
  • Know when to say no. Feast is open source and mostly orchestrates your existing compute and storage; Tecton is a managed platform that also owns the transformation pipelines and streaming aggregations; Databricks, SageMaker and Vertex ship their own. For one model in one team, a shared transform library plus a cache beats all of them.
