31Semantic Cache Serving

The production design behind a semantic response cache — admission control, quantized vectors, payload offloading, soft/hard TTL, and herd guards — and the failure modes that only appear at traffic.

Theory

A semantic cache is a serving system, not a dictionary lookup

The interview answer — embed the query, cosine-similarity against past queries, return the cached response past a threshold — fits in one sentence. The production system behind it does not. At 1M queries a day the cache holds millions of query vectors and response payloads, absorbs bursty duplicate traffic, serves stale answers while revalidating, and must survive embedding-model swaps and knowledge-base updates without a full cold restart. Six sub-mechanisms carry that load: admission, memory, freshness, concurrency, scoping, and measurement. Miss any one and the cache either OOMs, serves confidently stale answers, or melts the origin it was built to protect.

Admission: write on Nth hit, counted with a Count-Min Sketch

The naive design writes every (query, response) pair into the cache. In practice query traffic is Zipfian: a small head of repeated intents and an enormous long tail of one-off questions. Caching the tail buys nothing — a query asked once will never hit — while paying the full memory and index cost. Production caches therefore admit on the Nth hit (typically 2nd or 3rd): the first occurrence only increments a frequency counter, and the pair is written once the counter crosses the threshold. Exact per-query counters at this cardinality are themselves a memory problem, so the standard structure is a Count-Min Sketch — a probabilistic frequency table (Redis Stack ships it as CMS.INCRBY) that answers "seen N times?" in a few kilobytes with a tunable over-count error. The one-sided error direction matters: a sketch never under-counts, so it may admit a borderline query early but never starves a genuinely hot one. Tune N against your tail: N=2 for support bots with heavy repetition, N=3+ for broad consumer traffic where the tail dominates.

Memory: quantize the vectors, offload the payloads

A cached entry has two very different parts. The query vector (768–1536 fp32 floats, i.e. 3–6 KB per entry) lives in the similarity index and is read on every request. The response payload (the full answer text plus metadata, often 1–10 KB) is read only on a hit. Storing millions of fp32 vectors in FAISS is what blows the memory budget, so production deployments quantize the index vectors to int8 (scalar quantization, ~4x smaller) and accept the small recall loss — similarity search degrades gracefully under quantization because only the ranking order near the threshold matters, not exact distances. Payloads go the other way: keep a pointer in the hot path and offload the bytes to Redis (with eviction) or object storage for cold entries, fetching only after a similarity hit is confirmed. The split means the per-request working set is one int8 vector probe, and the expensive bytes move only when they earn their keep. Recompute the arithmetic whenever the embedding model changes dimension — a 768→1536 upgrade doubles the index overnight.

Freshness: soft TTL, hard TTL, and stale-while-revalidate

A single TTL forces a false choice: short TTLs crater the hit rate, long TTLs serve stale answers after the knowledge base changes. The production answer is a soft/hard TTL pair. Inside the soft window the entry serves directly. Between soft and hard expiry the entry serves stale while exactly one request revalidates in the background (stale-while-revalidate); every other concurrent request keeps getting the stale copy instead of queueing behind the origin call. Past the hard TTL the entry is dead and the request waits for a fresh generation. The soft window is sized from the content's change cadence (minutes for product data, hours for policy docs), the hard window from the maximum staleness the product will tolerate. This is what converts a KB update from "flush the world and eat a cold-start latency spike" into "stale for at most the soft window, then seamlessly fresh" — and it is the mechanism the simulator below lets you feel.

Concurrency: distributed locks and the thundering-herd guard

The ugliest production incident in this space is the thundering herd: a hot key expires (or a deploy cold-starts the cache) and fifty identical requests miss simultaneously, each firing a full LLM generation. Origin QPS spikes 50x, latency explodes, and the cache you built to protect the origin becomes the thing that synchronized the stampede. The fix is request coalescing — singleflight: the first miss acquires a short-lived distributed lock (Redis SET NX PX, tens of milliseconds), performs the single origin call, and parks the other forty-nine waiters on the same future. On lock timeout exactly one waiter retries the acquisition rather than all of them. The lock TTL is the critical number: too short and duplicates leak through, too long and a crashed holder blocks the key past the hard TTL. Size it from origin p99, not from the average. Scoping and invalidation: namespaces, versions, and the embedding-model swap

Two invalidations are routine and one is catastrophic. Routine first: partition the cache by knowledge namespace (kb:pricing:*, kb:hr-policy:*) and carry a kb_version in the key, so a CMS webhook deletes one prefix instead of flushing everything. The catastrophic one is an embedding-model swap: new vectors live in a different space, so every stored vector and every admission counter is instantly garbage — similarity scores against mixed-space vectors are meaningless, and worse, they fail silently by returning confident wrong matches. The only safe rollout is dual-write: index new-model vectors under a new key prefix, run both indexes during a shadow window while monitoring hit rate on each, then cut over and drop the old prefix. Never re-embed lazily in place; a half-migrated index is a wrong-answer generator with a healthy-looking hit rate.

Named failure modes

Stampede on cold start: deploy wipes the cache, all hot keys miss at once, origin melts. Mitigate with cache warming (replay top-K historical queries) or a rollout that keeps the old cache readable until the new one is warm. Stale storm: a KB update lands but the soft windows are long, so the whole hot set serves yesterday's answers for an hour — this is a TTL-classing failure, not a cache bug. Skewed hot keys: one celebrity query owns 5% of traffic; its expiry alone is a mini-herd, so give hot keys longer soft windows and pre-warming priority. Mixed-space index after a model swap (above) — the silent one. Lock pile-up: the singleflight lock TTL exceeds the hard TTL, so waiters queue longer than the entry's maximum age; always bound waiter waits below the hard TTL and fail open to origin. Monitor all of it with four dashboards: hit rate by namespace, stale-serve ratio, origin QPS vs cache QPS, and admission rate (writes per thousand requests — a spike means the tail is flooding in).

Reference: middleware sketch

The request path below is the shape every implementation converges on — GPTCache wires these stages as plugins, a hand-rolled Redis + FAISS stack writes them explicitly. Read it as the checklist, not the code: 

def serve(query, namespace):
    vec = embed_cached(query)              # embedding cache: text -> vector
    key = lookup(vec, namespace, thresh)   # int8 FAISS probe, namespace partition
    if key is None:
        if sketch_count(query) < N:      # Count-Min Sketch admission
            sketch_incr(query)
            return generate(query)         # tail: serve, don't store
        if acquire_lock(key, ttl=ORIGIN_P99):
            try:
                resp = generate(query)     # singleflight: one origin call
                store(key, quantize(vec), resp, soft_ttl, hard_ttl)
            finally:
                release_lock(key)
            return resp
        return wait_on_inflight(key)       # coalesced waiter
    entry = fetch_payload(key)             # payload offload: fetch only on hit
    if entry.age > HARD_TTL:
        return serve_uncached(query)       # dead entry: synchronous refresh
    if entry.age > SOFT_TTL:
        revalidate_async(key, query)       # stale-while-revalidate: one background refresh
    return entry.response                  # fast path: stale or fresh, served in ms

The Interview Line

"A semantic cache that just writes every query is a memory leak with a hit-rate dashboard — at real traffic most queries are asked once, so I admit on the Nth hit counted with a Count-Min Sketch, quantize the index vectors to int8, and offload response payloads so the hot path only ever probes one small vector."

"Freshness is a soft/hard TTL pair: inside the soft window I serve stale while one request revalidates, past the hard TTL the entry is dead — and a hot-key expiry without a singleflight lock is a fifty-way thundering herd against my own origin, so the first miss holds a short Redis lock and everybody else parks on its future. The failure I brief explicitly is the embedding-model swap: new vectors live in a different space, so I dual-write under a new key prefix and cut over, because a half-migrated index returns confident wrong answers with a healthy-looking hit rate."

Key Takeaways

  • Admit on the Nth hit, counted by a sketch. Query traffic is Zipfian — caching the long tail buys zero hits for full memory cost. A Count-Min Sketch (Redis Stack CMS.INCRBY) tracks frequencies in kilobytes; N=2 for repetitive support traffic, N=3+ for broad consumer tails. GPTCache's default write-on-first-hit is the dev-mode setting, not the production one.
  • Split vectors from payloads, then shrink each. int8-quantized FAISS index vectors cut the hot working set ~4x with only boundary-recall loss; response bytes live behind a pointer in Redis or object storage and move only on confirmed hits. Recompute the budget on every embedding-dimension change — 768→1536 doubles the index overnight.
  • Freshness is soft/hard TTL plus stale-while-revalidate, scoped by namespace. Soft window from content-change cadence, hard window from maximum tolerable staleness, kb:namespace:* keys so one CMS webhook flushes one prefix. A single global TTL is how you get a stale storm or a cold-start spike — pick which failure you prefer, or pick the pair.
  • The herd guard is one lock with a correctly sized TTL. First miss takes SET NX PX sized from origin p99; everyone else waits on the same future; lock timeout promotes exactly one waiter. No guard means every hot-key expiry is a synchronized 50x spike against the origin you built the cache to protect.
  • Four dashboards or you are flying blind: hit rate by namespace (Prometheus counter per kb:* prefix), stale-serve ratio (serves past soft TTL), origin-vs-cache QPS (Grafana — the herd shows up here first), and admission rate (writes per thousand requests; a spike means the tail is flooding in). Alert on stale-serve ratio, not just hit rate — a high hit rate with high staleness is the mixed-space index failing silently.
