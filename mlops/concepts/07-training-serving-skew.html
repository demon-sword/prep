07Training-Serving Skew

The three sources of skew — divergent transformation code, divergent data (training on a filtered sample), and feedback-loop skew from the model's own predictions — and how each shows up as offline metrics that do not survive contact with production.

Theory

The definition worth memorising

Training-serving skew is any difference between the world the model was fit in and the world it is asked to score in. It is not one bug, it is a category, and the reason it dominates this interview round is that it has no error signature: no exception, no failed schema check, no 500s on the dashboard. The model returns a well-formed float for every request. It is just a worse float than the offline report promised. The symptom is always the same sentence — "offline it was 0.84 AUC, online it's behaving like 0.71" — and the job is to know which of three mechanisms produced it, because they have three different fixes.

Source 1 — divergent transformation code

Training runs in a notebook or a Spark job; serving runs in a Go or Python service under a latency budget. Two implementations of "the same" transformation drift apart: a log1p that only one side applies, a null filled with the training median offline and with 0 online, an outlier bound that is winsorised only in the training code, a categorical hash seeded differently, a timezone that makes hour_of_day off by five. In all of those the raw request payload is byte-identical to what training saw; only the transformed vector differs, which is precisely why monitoring the raw inputs catches none of them, and why the single most valuable piece of instrumentation is logging the exact post-transform feature vector that was scored.

The one common member of this family that raw-input monitoring does catch is a unit mismatch — one upstream client sending an amount in cents when training saw dollars. That bug moves the raw value by 100×, so a PSI on the request payload lights up on its own. Treat it as the exception rather than the reassurance: it is detectable because the bug happens to live upstream of the transform, and the moment the divergence is inside the transform code — the fill, the clip, the missing log1p — the raw histogram goes back to being a perfect match while the model quietly gets worse.

The structural fix is to stop having two implementations. One transformation definition, fitted once during training, with the fitted state (medians, means, standard deviations, encoder vocabularies, bucket edges) persisted as an artifact that ships with the model version and is loaded, never recomputed, at serve time. tf.Transform does this by emitting a TensorFlow graph that is attached to the serving signature; a scikit-learn Pipeline logged through MLflow does the weaker version of the same thing; a feature store does it by making one feature definition the source of both the offline and the online value. Any of these beats a well-reviewed second implementation, because the failure mode here is not incompetence, it is two codebases diverging over eighteen months of small changes.

Source 2 — divergent data

Here the code agrees and the populations do not. The classic case is that labels only exist for a filtered subset: a credit model is trained on approved applicants because rejected ones never got a repayment outcome, then deployed on all applicants. A fraud model is trained on transactions that cleared an upstream rules engine, then scored on everything. The training distribution is a truncated slice, the fitted coefficients are the best fit for that slice, and the model extrapolates into a region it has never seen. Offline evaluation does not catch it because the holdout is drawn from the same truncated slice — the number is honest about a population that is not the one being served. Related members of the family: training on a stale snapshot while the population moves (feature staleness), a downsampled negative class whose base rate is never corrected back, and an upstream column that changed type or semantics between the snapshot and today (schema drift).

Source 3 — the feedback loop

The third source is the model's own effect on the data. Once deployed, the model declines transactions, filters what the ranker shows, or decides who gets an offer — so tomorrow's traffic is a population the model itself selected. The high-risk region it needs to discriminate is exactly the region it has stopped letting through, so both future training data and the online metric are computed on survivors. This is the hardest of the three because it looks like success: the observed bad rate falls, the model appears calibrated, and the degradation is slow and self-reinforcing. The counter is to keep a small randomised exploration holdout — a percentage of traffic scored but not acted on, or decided at random — so there is always an unbiased sample to retrain and evaluate against. It costs real money and it is the only thing that keeps the estimate honest.

What is actually detectable, and when

Be precise about this in an interview, because the common wrong answer is to treat a drift alarm as a performance alarm. Without labels you can measure the gap between two distributions — a PSI or an L∞ distance between the training reference and the served vectors — and nothing else. That tells you the input changed; it does not tell you accuracy fell, and it never will. Benign covariate shift fires the same alarm as a catastrophic unit mismatch. Real quality only becomes measurable when labels arrive, which for fraud chargebacks or loan default is weeks to months later — the label lag problem — so the interval between deploy and first honest quality number is a window of silent degradation that you cover with proxies: prediction-distribution stability, decision-rate stability, and per-feature skew against the training reference.

Two numbers, not one. The gap (offline minus online) tells you whether the offline report predicted production; the distance from online to the no-skew ceiling tells you whether the model itself got worse. They come apart, and the difference matters. A training set truncated to approved applicants often produces a model that ranks live traffic about as well as an unfiltered one would — the damage is that the offline number was 0.87 on a population you do not serve, so every promotion decision was made against a fiction. Conversely, a serving-side transform bug can leave offline and online agreeing with each other while both sit below what the model could have done. Only the first is visible by comparing your two reports; the second needs a known-good reference.

And before calling either one a finding, ask whether it is larger than the sampling noise on an AUC. The Hanley-McNeil standard error, SE = √([A(1−A) + (n₊−1)(Q₁ − A²) + (n₋−1)(Q₂ − A²)] / (n₊·n₋)) with Q₁ = A/(2−A) and Q₂ = 2A²/(1+A), is a few points of AUC on a holdout of a couple of thousand rows. Two AUCs measured on independent samples differ by roughly √(SE₁² + SE₂²), so a 0.02 “drop” on a small holdout is frequently nothing at all. Engineers roll models back over differences inside their own error bars more often than they roll them back for real regressions.

The one check that cannot be fooled and needs no labels is a replay: take yesterday's logged serving vectors, push them through the training pipeline, and diff. Any feature whose values disagree is skew, full stop — an exact-match assertion, not a statistical one. TFDV formalises the statistical form with a skew_comparator in the schema (L∞ distance for categorical features, Jensen-Shannon divergence for numeric ones), but the diff is stronger where you can afford it.

The rule to quote. Google's Rules of Machine Learning (Rule #29): the best way to make sure you serve like you train is to save the set of features used at serving time and pipe those logged features into training. It removes the entire class of Source-1 bugs by construction, because there is only ever one computation of the feature — the one that actually happened in production.

The fix, ordered by what it buys

# 1. Fit the transform ONCE, in training. Persist the fitted state as an artifact.
transform = FeatureTransform(
    log_cols=["amount"],
    winsorise={"txn_count_7d": (0, 8)},
    fill={"amount": "median"},      # the median is FITTED, never hardcoded
)
transform.fit(train_df)                  # learns median, mean, std, bucket edges
mlflow.log_artifact(dump(transform), "transform.pkl")
mlflow.sklearn.log_model(
    clf, "model",
    signature=infer_signature(X_train, preds),   # names + dtypes are a contract
)

# 2. Serving LOADS that artifact. It never re-fits and never re-implements.
transform = load(download_artifact(version, "transform.pkl"))
x = transform.transform(raw)             # identical code path to training
score = clf.predict_proba(x)[:, 1]

# 3. Log the EXACT vector that was scored. This is what makes skew measurable.
feature_log.emit({
    "request_id": req.id,
    "model_version": version,
    "served_at": now_utc(),
    "raw": raw.to_dict(),          # what the client sent
    "transformed": x.tolist(),    # what the model actually saw
    "score": float(score),
})

With those vectors logged, the detector is a scheduled job, not a research project. Bin the training reference, bin yesterday's served values, and compute PSI per feature — the conventional rule of thumb is that below 0.1 is no meaningful change, 0.1 to 0.25 warrants investigation, and above 0.25 is a significant shift worth acting on:

PSI = Σᵢ (aᵢ − eᵢ) · ln(aᵢ / eᵢ)   over bins i, with eᵢ = reference share, aᵢ = current share 
# Nightly skew job: served vectors vs the exact training reference.
served = read_feature_log(day, model_version=PROD_VERSION)   # post-transform
ref    = read_training_features(dataset_hash=PROD_DATASET_HASH)

def psi(ref_col, cur_col, bins=10, floor=1e-4):
    # np.unique sorts AND dedupes: a discrete or sparse column produces repeated
    # quantile edges, and zero-width bins make PSI read 0 on a real shift.
    edges = np.unique(np.quantile(ref_col, np.linspace(0, 1, bins + 1)))
    lo, hi = edges[0], edges[-1]
    # clip so values outside the reference range land in the outer bins
    # instead of being dropped — that tail is exactly the shift you care about.
    e = np.histogram(np.clip(ref_col, lo, hi), edges)[0] / len(ref_col)
    a = np.histogram(np.clip(cur_col, lo, hi), edges)[0] / len(cur_col)
    e, a = np.maximum(e, floor), np.maximum(a, floor)   # empty bin -> ln(0)
    return float(np.sum((a - e) * np.log(a / e)))

for col in FEATURES:
    s = psi(ref[col], served[col])
    if s > 0.25:
        page(f"skew: {col} PSI={s:.3f} vs training reference")

The line to say

"Training-serving skew isn't one bug, it's three, and I'd want to know which one before touching anything. First is divergent transformation code — two implementations of the same feature that drifted apart, a log that only one side applies, a null filled with the training median offline and zero online. Second is divergent data — the training set is a filtered slice, usually because only approved or accepted rows ever got labels, so the model is extrapolating in production and the offline holdout can't see it because it's drawn from the same slice. Third is the feedback loop: once the model is deciding, tomorrow's traffic is a population it selected, so the region it most needs to discriminate is the region it's stopped letting through."

"The fix for the first one is structural, not a code review — one transform definition, fitted once, the fitted state persisted as an artifact that ships with the model version and gets loaded at serve time, never recomputed. And I log the exact post-transform vector I scored, because that's the thing raw-input monitoring can't see: with a fill or clipping bug the request payload is byte-identical and only the transformed value moved. A unit bug is the exception — cents versus dollars shifts the raw value by 100×, so input monitoring does catch that one, but it's the only common member of the family it catches. For the feedback loop you need a small randomised exploration holdout — it costs money, and it's the only way the retraining sample stays unbiased."

"One thing I'd be careful about saying: a drift alarm is not a performance alarm. Without labels all I can measure is a PSI or an L-infinity gap against the training reference — 0.1 to 0.25 is investigate, past 0.25 I treat it as a real shift — and benign covariate shift fires that exactly like a broken unit conversion does. The check that needs no labels and can't be fooled is a replay: push yesterday's logged serving vectors back through the training pipeline and diff them. That's an exact-match assertion, not a statistical one."

Key takeaways

  • Name all three sources or the answer is incomplete. Divergent transformation code, divergent data (a filtered training sample), and the model's own feedback loop. Different mechanisms, different fixes — one shared transform artifact, an unbiased sampling strategy, and a randomised exploration holdout respectively.
  • Log the post-transform vector, not the request. Fill-value, clipping and missing-transform bugs leave the raw payload byte-identical, so raw-input monitoring shows a PSI of roughly zero while the transformed feature has moved several standard deviations. A unit mismatch is the exception that proves the rule — cents-for-dollars scales the raw value by 100× and does show up on the input histogram, because that divergence sits upstream of the transform rather than inside it. Google's Rules of ML #29 — pipe the logged serving features into training — deletes this class of bug by construction.
  • Fit once, load everywhere. Medians, means, standard deviations, encoder vocabularies and bucket edges are model artifacts. tf.Transform attaches the preprocessing graph to the serving signature; MLflow's infer_signature pins names and dtypes; a feature store makes one definition serve both paths. Re-fitting a scaler on live traffic is the canonical version of this bug.
  • A drift alarm is not a performance alarm. Pre-label, PSI (0.1 investigate / 0.25 act) or TFDV's skew_comparator — L∞ for categorical, Jensen-Shannon for numeric — only tell you the distribution moved. With chargeback or default labels arriving weeks later, the deploy-to-first-honest-number window is silent degradation you cover with proxies. And when the labels do land, quote a noise band before you quote a regression: the Hanley-McNeil SE of an AUC on a 2,000-row holdout is on the order of a point or two, and two independently measured AUCs differ by √(SE₁²+SE₂²), so plenty of “0.02 drops” are sampling noise.
  • The replay diff is the unfoolable check. Re-run yesterday's logged serving vectors through the training pipeline and assert exact equality per feature. It needs no labels, no thresholds and no statistics, and it localises the broken feature instead of telling you the model "got worse".
  • The feedback loop is the one that looks like success. Observed bad rates fall because the model stopped letting the bad population through, and both retraining data and the online metric are computed on survivors. Budget the exploration traffic explicitly — a model with no unbiased sample cannot be honestly re-evaluated at any price.
