05Online and Offline Feature Parity

Detecting the divergence between the feature values a model trained on and the ones it sees at inference by logging served features back to the offline store and running a scheduled parity job on the overlap — the failure that never raises an exception.

Theory

What a parity job actually compares

Parity monitoring answers one narrow question: for the same entity at the same event time, is the feature vector the model actually scored identical to the vector the training pipeline would have produced? Everything else — drift reports, schema checks, distribution tests — answers a different question. And you cannot answer this one by reconstruction, because the whole point is that reconstruction is the thing under suspicion. You have to log the served vector.

Google's Rules of Machine Learning makes this its Rule #29: the cheapest way to make sure you train the way you serve is to save the set of features used at serving time and pipe those features into training. That gives you two viable architectures. Log-and-wait uses the logged serving vectors directly as the training set — parity is true by construction, but you have to wait for traffic to accumulate and you cannot add a new feature retroactively, because nobody logged it. Backfill recomputes features from the warehouse, so you can add a feature and go back two years — but now you own a second implementation of every transformation, and the parity job is the only thing proving the two agree. Most teams end up on backfill, which is exactly why this page exists.

Where the divergence comes from

Four sources cover almost everything you will actually be paged for, and each has a different signature in the parity report.

  • Feature staleness. The online store serves the last materialized value. With a 60-minute materialization interval the served aggregate is on average half an interval behind, while the backfill recomputes as of the event timestamp and gets the fresh one. Mismatch rate scales with the product of the materialization interval and the entity's underlying update rate — so a streaming feature that changes every few minutes is mismatched constantly under an hourly job, and a 30-day average is barely affected. The nastier form is a materialization job that fails silently: the online store keeps serving the last good value forever, with no error and no null, just a frozen feature. Track materialization freshness (max key age) as its own signal; parity alone will show you the symptom hours later.
  • Divergent null and default handling. The serving path fills a missing value with 0.0 because that is the protobuf/Java primitive default; the training path fills with the column median persisted by the fit step. Every previously-null row is now a mismatch, nothing throws, and the model reads a hard zero as a genuinely low value rather than "unknown".
  • Timezone and clock skew. Serving computes in UTC; the warehouse session runs in a local timezone. Every calendar-derived feature breaks, but at wildly different rates, and the rate is what decides whether the parity threshold ever sees it. A 5-hour offset moves an event across the date boundary for the 5 hours of each day that straddle it — 5/24 ≈ 21% of rows — so a date-difference feature such as days_since_signup is off by one for roughly a fifth of traffic. is_weekend is derived from that same shifted date but only changes value when the day shift also crosses a weekend edge — 2 of the 7 day-of-week values — giving (5/24) · (2/7) ≈ 6%. An hour-of-day feature has no such damping: the offset lands on the hour itself, so the raw hour is wrong for essentially every row, and a bucketed version agrees only on the rows the shift happens to leave inside the same bucket. All three mismatch systematically rather than randomly — always the same slice of the clock, which is usually correlated with something the model cares about.
  • Numeric precision and casting. Serving runs float32, the warehouse runs float64. The relative error of a float32 round-trip is bounded by 2⁻²⁴ ≈ 6 × 10⁻⁸, so exact equality is the wrong test — it will light up every continuous feature and teach the team to ignore the report. Compare with a relative tolerance instead.
mismatch(f)  =  |v_served − v_offline|  >  max(atol, rtol · |v_offline|)    — for categoricals and booleans, strict inequality

Comparing distributions is not comparing rows

The most common wrong implementation is to run a drift report between the training feature table and the serving feature log and call that parity. Two samples can have identical marginals and still disagree on every single row. Join on the wrong key, shift the entity ID by one, mix up two users' vectors under load — every histogram lines up perfectly while every prediction is scored on somebody else's features. Parity has to be a row-level join on (entity_key, event_timestamp) with a per-row comparison. Distribution comparison is the fallback for the case where no join is possible, such as a request-time feature that has no offline counterpart at all.

Tolerances, sampling, and what a clean run proves

The job runs on a sample, because joining every logged vector against a full backfill is usually the most expensive query the team owns. That sample bounds what you can conclude. Observe zero mismatches in n = 10,000 sampled rows and the rule of three puts a 95% upper bound on the true mismatch rate at 3/n = 0.03% — you have not proved parity, you have bounded it. A defect touching 1 in 10⁵ rows walks straight through, and if the affected rows are the high-value ones (large orders, fraud attempts) the uniform sample understates the harm. Stratify the sample, and set the alert threshold per feature class rather than globally: a deterministic transform should have a zero-mismatch expectation and any hit is a bug worth paging on, while a cache-backed aggregate gets a budget sized to its materialization interval, because that staleness was a design decision.

What parity does not tell you

It proves the two paths agree. It says nothing about whether either is right — both can share the same wrong window definition or the same off-by-one on a lookback, and the report will be spotlessly green. It does not catch point-in-time leakage, which is a property of a single path and needs an as-of join to expose. And it is emphatically not a performance alarm: until labels land, a clean parity run and a quietly degrading model look exactly the same from the outside. Parity is how you rule out training-serving skew as the cause of an accuracy drop — it is a fast, cheap way to eliminate a suspect, not a measure of model health.

The two pieces of code that make it work

Log the vector after fills, casts and encoders. A pre-transform log hides exactly the null-fill and precision divergences you are hunting. 

# serving path — emit the exact post-transform vector that was scored
def score(request):
    raw = feature_service.get_online_features(
        entity_rows=[{"user_id": request.user_id}],
        features=FEATURE_REFS,
    ).to_dict()

    x = vectorize(raw)                  # fills, casts, encoders
    y = model.predict(x)

    parity_log.emit({                   # AFTER vectorize(), not before
        "entity_id":     request.user_id,
        "event_ts":      request.event_ts,   # the point-in-time join key
        "model_version": model.version,
        "features":      {k: float(v) for k, v in x.items()},
    })
    return y

Then join a stratified sample of that log against the batch path over the same keys, and roll the comparison up per feature: 

-- nightly parity job: row-level join, never distribution-vs-distribution
WITH served AS (
  SELECT entity_id, event_ts, feature_name, feature_value
  FROM   serving_feature_log
  WHERE  log_date = '2026-08-29'
    AND  MOD(ABS(FARM_FINGERPRINT(entity_id)), 100) < 5   -- 5% sample
), offline AS (
  SELECT entity_id, event_ts, feature_name, feature_value
  FROM   backfill_features(DATE '2026-08-29')      -- the batch path
), joined AS (
  SELECT s.feature_name,
         s.feature_value AS served_v,
         o.feature_value AS offline_v
  FROM served s
  JOIN offline o
    USING (entity_id, event_ts, feature_name)   -- as-of key, not "latest"
)
SELECT
  feature_name,
  COUNT(*)                                             AS n_rows,
  COUNTIF(ABS(served_v - offline_v)
          > GREATEST(1e-9, 1e-6 * ABS(offline_v)))     AS n_mismatch,
  APPROX_QUANTILES(ABS(served_v - offline_v), 100)[OFFSET(95)] AS p95_abs_diff
FROM joined
GROUP BY feature_name
ORDER BY n_mismatch DESC;
Failure mode to name out loud: training-serving skew, and its quiet cousin feature staleness. Neither throws an exception, neither shows up in your error rate, and both are invisible in offline evaluation because offline evaluation only ever sees the offline path.

The line to say

"The way I catch training-serving skew isn't a drift report — it's a row-level parity job. I log the exact post-transform vector the model scored, keyed by entity and event timestamp, and nightly I join a stratified sample of that log against what the batch pipeline recomputes for those same keys. It has to be a per-row join: two histograms can match perfectly while every row is joined to the wrong user, so a distribution comparison would pass on a bug that's scoring people on somebody else's features."

"I set the tolerance per feature class rather than globally — a deterministic transform gets a zero-mismatch expectation and any hit is a bug I page on, while a cache-backed aggregate gets a budget sized to its materialization interval, because that staleness is designed in. And I'd compare with a relative tolerance, not equality, or float32-vs-float64 lights up every continuous feature and the team learns to ignore the report."

"The thing I'd be honest about is what a green run buys me. With a 10k sample and zero mismatches, the rule of three only bounds the true rate at about 0.03% — that's a bound, not a proof. And parity only tells me the two paths agree; if both share the same wrong window definition it stays green, and it's never a substitute for a performance alarm once labels land."

Key takeaways

  • Log the served vector after transformation, not before. Google's Rules of ML #29 is the whole design: pipe the features used at serving time into training. A pre-fill log hides precisely the null-fill and float32 divergences you built the job to find.
  • Join on (entity_key, event_ts) per row — never compare distributions and call it parity. Identical marginals with a broken join key is a real, shipped bug class; only a row-level comparison catches it. Save the distribution tests (Evidently, Great Expectations) for the features with no offline counterpart.
  • Use a relative tolerance, around 1e-6. float32 round-trip error is bounded by 2⁻²⁴ ≈ 6e-8, so exact equality flags every continuous feature and trains the team to mute the alert. Booleans and categoricals stay on strict equality.
  • Threshold per feature class, not globally. Deterministic transforms get a zero-mismatch expectation; cache-backed aggregates get a budget sized to the materialization interval. Feast and Tecton both materialize offline→online on a schedule, and a failed materialization run keeps serving the last good value with no error at all — so alert on online-store freshness separately.
  • A clean parity run is a bound, not a proof. Zero mismatches in n rows only caps the true rate near 3/n (rule of three). Stratify the sample toward high-value traffic, because a uniform sample understates a defect concentrated in the rows that cost money.
  • Parity rules out skew; it does not measure the model. Both paths can be wrong in the same way, and with delayed labels a green parity report and a silently degrading model are indistinguishable.
