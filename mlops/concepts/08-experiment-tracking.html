08Experiment Tracking

Logging params, metrics, artifacts, and the git SHA per run so a result can be found and rebuilt months later — MLflow and W&B run hierarchies, nested sweeps, and why an untracked notebook run is not a result.

Theory

A run is the unit, and it is meant to be immutable

A tracked run is a tuple: the parameters that went in, the metrics that came out, the artifacts it produced, and enough provenance that someone else can rebuild it. The discipline that makes the tuple worth anything is that it is written once and never edited. MLflow enforces the important half of this — logging a different value for a param key already set on a run raises an error rather than overwriting it, because a run whose inputs can be revised after the fact is not evidence of anything. Metrics are the deliberate exception: they are append-only series keyed by step, so val_auc logged every epoch keeps the whole curve and you can see whether the reported number was the last epoch or the best one.

Four slots, four jobs

Params are the inputs you chose — learning rate, depth, seed, feature-set version. They are stored as strings and are length-limited, so an entire YAML config belongs in an artifact with only its hash logged as a param. Metrics are numeric outputs, stepped and append-only. Tags are mutable annotations — branch, ticket, owner, git_dirty — and being mutable is exactly why nothing you will later need to defend should live only there. Artifacts are files: the serialised model, the environment lockfile, the confusion matrix, the calibration plot. The split matters because immutability is per-slot, and people routinely put a load-bearing fact in the one slot that can be quietly rewritten.

The reproducibility set

A run is reproducible only if five things are recoverable: the code (a commit SHA, and a clean tree — MLflow records mlflow.source.git.commit automatically when the entry point sits in a git repo, and that SHA is a lie if there were uncommitted changes); the data; the environment; the seed; and the entry point plus params. The one people skip is data. Logging dataset_uri = s3://warehouse/txn/dt=2026-08-24 is logging a pointer, not a dataset — the rows behind that path move the moment a late-arriving event lands or a backfill runs. What survives is a content hash or a table-format snapshot id. Seeds have their own caveat: on GPU, a fixed seed still leaves non-deterministic reductions and autotuned kernels in play, so log the seed and expect agreement to a tolerance rather than bit-for-bit.

Sweeps, nested runs, and the winner's curse

A 64-trial random search should be one parent run with 64 children — mlflow.start_run(nested=True), or a W&B sweep id grouping its agents — so the sweep is a single object you can compare against last quarter's sweep rather than 64 loose rows. The statistical trap sits at the end of it. Selecting the maximum of 64 noisy validation scores is a biased estimate of that config's true quality. With 1,000 positives and 4,000 negatives, the Hanley–McNeil standard error of an AUC near 0.80 is about 0.009, and the largest of many draws lands well above its own mean, so a champion reported at 0.842 may genuinely be a 0.825 model. More tracking does not fix this; a test set scored once, after selection, does.

The named failure modes

  • The untracked notebook run. The result exists as a cell output and a screenshot in Slack. It cannot be found, compared, or rebuilt — and it is by far the most common.
  • Mutable dataset pointer. The run looks reproducible right up until the upstream table backfills, then reproduces a different number with no code change.
  • Metric-definition drift. val_auc in March was computed on a different slice than val_auc in August. Same key, incomparable numbers, and the leaderboard never says so.
  • Autolog gaps. mlflow.autolog() captures the training library's params, metrics and model. It does not capture your dataset hash, your feature-engineering config, or the decision threshold you picked afterwards.

Logging that is worth trusting looks like this — a parent sweep run, nested trials, and provenance the metric alone cannot give you:

import hashlib, subprocess
import mlflow
from sklearn.metrics import roc_auc_score

SEED    = 20260830
git_sha = subprocess.check_output(["git", "rev-parse", "HEAD"], text=True).strip()
dirty   = subprocess.check_output(["git", "status", "--porcelain"], text=True).strip() != ""

mlflow.set_experiment("fraud-xgb")

with mlflow.start_run(run_name="random-search-64") as sweep:
    mlflow.set_tag("space_sha", hashlib.sha256(SPACE_JSON.encode()).hexdigest()[:12])

    for trial in sample_space(64, seed=SEED):
        # one child run per trial — the sweep stays a single comparable object
        with mlflow.start_run(nested=True):
            mlflow.log_params({**trial, "seed": SEED})
            mlflow.set_tags({
                "git_dirty":      str(dirty),        # git_sha means nothing without this
                "dataset_uri":    DATASET_URI,       # a pointer...
                "dataset_sha256": SNAPSHOT_SHA,      # ...and the rows it pointed at
            })

            model = fit(train, **trial, random_state=SEED)
            auc   = roc_auc_score(val.y, model.predict_proba(val.X)[:, 1])

            mlflow.log_metric("val_auc", auc)
            mlflow.log_metric("val_pos_n", int(val.y.sum()))  # lets you recover the SE
            mlflow.sklearn.log_model(model, "model")
            mlflow.log_artifact("requirements.lock")

# A run whose git_dirty tag reads "True" is a number, not a result.
The line that separates senior from junior here: tracking is not a dashboard, it is a contract that any number on the leaderboard can be rebuilt. The cheapest way to test whether you have one is to pick a run from three months ago and actually try to reproduce it.

The line to say

“I treat a run as reproducible only if five things are logged: the commit SHA plus a clean-tree flag, a content hash of the training data rather than a path, the environment lockfile, the seed, and the entry point with its params. The one people skip is the data hash — they log s3://.../dt=2026-08-24 and call it versioned, and then a backfill lands and the same code produces a different number.”

“The other thing I'd flag is that a sweep leaderboard is a selection problem. If validation AUC carries a standard error around 0.01 and you rank 64 trials on it, the top score is optimistic by on the order of a standard error or more purely from taking the max — so I promote on a held-out set scored once after selection, not on the sweep's own best number.”

Key Takeaways

  • Params are immutable, tags are not. MLflow raises if you re-log a param key with a different value on the same run; tags can be overwritten silently. Anything you'd need to defend in a post-mortem goes in params or artifacts, never only in a tag.
  • A dataset URI is not a dataset version. Log a content hash, a DVC pointer, or an Iceberg/Delta snapshot id. A partition path is mutable, and late-arriving rows will silently break reproducibility months later with no code change to blame.
  • Autolog is a floor, not a ceiling. mlflow.autolog() gets the library's params, metrics and model artifact. Your feature config, data hash, and post-hoc decision threshold are still on you — and the threshold is usually what actually moved the business metric.
  • Nest your sweeps. One parent run with nested=True children (or a W&B sweep id) keeps 64 trials as one comparable object; W&B ships parallel-coordinates and sweep panels for exactly this, and MLflow's UI compares runs within an experiment.
  • The best-of-N score is biased upward. With 1,000 positives and 4,000 negatives the Hanley–McNeil SE of an AUC near 0.80 is about 0.009; ranking dozens of trials on that noise makes the winner look better than it is. Score the selected config once on data the search never saw.
  • Log the denominator with the metric. Logging val_pos_n alongside val_auc costs nothing and is the difference between "0.84 vs 0.83 is a win" and "0.84 vs 0.83 is inside one standard error."
