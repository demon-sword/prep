The ARCH Framework

Four components with specific things to mention

A Architecture — Components & Data Flow

What pieces exist and how they connect

What to Mention IRCTC Example
Components GitHub Webhook Receiver, Intent Router, Code Review Agents (Security, Style, Performance, Documentation, Test Coverage), Conflict Resolver, Notification Service, Review Aggregator, Historical Database
Data Flow PR Webhook → Router → Parallel Agents → Conflict Resolver → Aggregator → Notification/Historical DB
Agents Specialized agents: Security (vulnerabilities), Style (formatting), Performance (inefficiencies), Documentation (missing docs), Test Coverage (test gaps)
Services GitHub API, LLM API (for complex analysis), Vector DB (for historical patterns), Redis (for caching), PostgreSQL (for review history)
State Management PR Context (in-memory during review), Agent Findings (Redis cache), Historical Decisions (PostgreSQL), Review Templates (Config)
Key line: "We have specialized agents for Security, Style, Performance, Documentation, and Test Coverage. They run in parallel on the same PR, then a Conflict Resolver handles disagreements, and an Aggregator produces the final review."

R Routing — Agent Orchestration

How agents run and communicate

What to Mention IRCTC Example
Agent Orchestration Parallel execution for all agents; Conflict Resolver uses weighted voting; Aggregator combines findings
Communication Pattern Message queue (RabbitMQ/Kafka) for agent coordination; Shared state via Redis for findings
Decision Logic Weighted voting based on agent confidence and historical accuracy; Security agent has veto power on critical issues
Key line: "All agents run in parallel via message queue. Conflict Resolver uses weighted voting (Security agent has veto on critical issues). Aggregator combines findings into a single review with priority labels."

C Constraints — What Can Break

Failure modes, limits, and edge cases

What to Mention IRCTC Example
Timeout on Reviews Set SLA (e.g., 5 minutes); if agent times out, use historical average or skip with warning
Large PRs Chunk by file/module; process chunks in parallel; aggregate results; notify if exceeds threshold
API Rate Limits GitHub API limits: batch requests, cache results, exponential backoff, queue for retry
Conflicting Reviews Security agent veto on critical vulnerabilities; else weighted average; human escalation for irreconcilable conflicts
LLM Failures Fallback to rule-based analysis; continue with reduced functionality; alert on persistent failures
Key line: "For large PRs, we chunk by file and process in parallel. Security agent has veto power on critical vulnerabilities. If all agents time out, we use historical averages and flag for manual review."

H Heuristics — Why This Design

Trade-offs, scaling, and decisions

What to Mention IRCTC Example
Why This Architecture? Parallel agents for speed; specialized agents for depth; weighted voting for balanced decisions
Why Not X? Single agent would be slower and miss specialized insights; pure democracy would let low-confidence agents override experts
Scaling Path Kubernetes for horizontal scaling; sharding by repo/org; caching frequent patterns; async processing for non-blocking UI
Monitoring Track agent accuracy vs human reviews, review latency, false positive/negative rates, escalation frequency
Key line: "I chose weighted voting over pure democracy because Security expertise should outweigh Style preferences on critical issues. Parallel execution ensures we meet SLAs even with many agents."

E Evaluation — How We Measure Success

Offline benchmarks, online metrics, and per-agent KPIs

Type Metric Target / Example
Offline Security vulnerability detection > 95% recall, > 90% precision on OWASP benchmark dataset
Offline Style rule adherence 100% alignment with configured linter rules (ESLint, Black, etc.)
Offline Regression tests Zero regression on 100 historical PRs; no new false positives introduced
Online Review throughput > 100 PRs/hour; p95 review time < 5 minutes
Online Human agreement rate > 90% agreement with senior developer reviews
Online False positive rate < 5% false positives; < 2% false negatives on security issues
Per-Agent Security Agent True positive rate > 95%; Critical issues never missed
Per-Agent Style Agent 100% linter alignment; Zero false positives on formatting
Per-Agent Performance Agent N+1 query detection > 90% accuracy; Memory leak detection > 85%
System Developer satisfaction 4.2/5 rating; < 10% override rate (developer disagrees with AI)
System Escalation frequency Human escalation < 3% of all reviews; Security escalations < 0.5%
Key line: "We benchmark offline on OWASP dataset for security (> 95% recall) and historical PRs for style (100% linter alignment). Online, we track human agreement rate (> 90%) and false positive rate (< 5%). Auto-rollback if security recall drops below 95%."
