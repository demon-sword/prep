The ARCH Framework

Four components with specific things to mention

A Architecture — Components & Data Flow

What pieces exist and how they connect

What to Mention IRCTC Example
Components Ingestion Agent, Validation Agent, Transformation Agent, Lineage Agent, Orchestrator, Dead Letter Queue, Monitoring Service
Data Flow Source Systems → Ingestion → Validation → Transformation → Lineage → Target (with DLQ for failures)
Agents Specialized agents: Ingestion (fetches data), Validation (schema/quality), Transformation (cleaning/feature eng), Lineage (tracks provenance)
Services Message Queue (Kafka/RabbitMQ), Data Lake (S3/ADLS), Warehouse (Snowflake/BigQuery), Orchestrator (Airflow/Prefect), Monitoring (Prometheus/Grafana)
State Management In-flight data (message queue), Schema versions (schema registry), Processing checkpoints (checkpoint store), Error counts (DLQ metrics)
Key line: "We have four specialized agents: Ingestion (fetches from sources), Validation (schema/quality checks), Transformation (cleaning/feature engineering), and Lineage (tracks data provenance). They process data sequentially via message queue."

R Routing — Agent Orchestration

How agents run and communicate

What to Mention IRCTC Example
Agent Orchestration Sequential processing via message queue; backpressure handling; dead letter queue for failures
Communication Pattern Message-based (Kafka topics): raw-validated, validated-transformed, transformed-lineaged
Decision Logic Orchestrator manages flow; agents nack on failure → DLQ; backpressure when consumer lags producer
Key line: "Data flows sequentially through agents via Kafka topics: raw→validated→transformed→lineaged. Backpressure handled by consumer lag monitoring; failed messages go to Dead Letter Queue for replay."

C Constraints — What Can Break

Failure modes, limits, and edge cases

What to Mention IRCTC Example
Schema Evolution Schema registry with backward/forward compatibility; versioned schemas; gradual migration strategy
Backpressure Monitor consumer lag; auto-scale transformation agents; temporary buffering; alert on sustained lag
Data Quality Issues Quarantine bad records; alert on quality degradation; auto-retry transient errors; schema evolution handling
Agent Failures Retry with exponential backoff; DLQ after max attempts; circuit breaker for persistent failures
Volume Spikes Auto-scaling groups; buffer in message queue; prioritize by SLA; shed load if necessary
Key line: "We use schema registry for evolution handling. Backpressure is managed by monitoring consumer lag and auto-scaling. Failed records go to Dead Letter Queue for later inspection and replay."

H Heuristics — Why This Design

Trade-offs, scaling, and decisions

What to Mention IRCTC Example
Why This Architecture? Sequential agents ensure data integrity; specialized agents allow independent scaling; message queue provides buffering
Why Not X? Single monolithic ETL would be harder to scale and debug; batch-only would increase latency; no DLQ would lose data on failures
Scaling Path Horizontal scaling of agents; partitioning by data source; stream processing (Flink/Spark) for real-time; data lakehouse for cost optimization
Monitoring Track end-to-end latency, throughput, error rates, data quality metrics, schema version distribution, DLQ size
Key line: "I chose sequential processing via message queue to ensure data integrity and enable independent scaling of each agent. Backpressure handling prevents system overload during volume spikes."

E Evaluation — How We Measure Success

Offline benchmarks, online metrics, and per-agent KPIs

Type Metric Target / Example
Offline Data quality validation > 99.9% records pass schema validation; zero data loss in test runs
Offline Schema compatibility 100% backward/forward compatible schema changes; no breaking changes without migration
Offline Regression tests Zero regression on 30 days of historical data; no data quality degradation
Online End-to-end latency p95 < 5 minutes from ingestion to availability; p99 < 10 minutes
Online Throughput > 100K records/second; scale to 10x without manual intervention
Online Data quality score > 99% completeness; > 95% accuracy; < 0.1% duplicates
Per-Agent Ingestion Agent > 99.99% uptime; zero data loss; handle 10x volume spikes
Per-Agent Validation Agent < 1% false rejections; 100% schema violation detection
Per-Agent Transformation Agent 100% data fidelity; zero loss during transformations
System SLA compliance > 99.9% availability; < 0.01% data loss; meet RPO/RTO targets
System Cost efficiency < $0.001 per 1K records processed; auto-scaling for cost optimization
Key line: "We benchmark offline on 30 days of historical data with zero regression. Online, we track end-to-end latency (p95 < 5 min), throughput (> 100K records/sec), and data quality score (> 99%). Auto-rollback if data quality drops below 98%."
