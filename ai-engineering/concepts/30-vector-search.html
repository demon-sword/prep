#30 — Vector Search & KNN

Embedding-based retrieval, approximate nearest neighbor algorithms (HNSW, IVF, FAISS), exact vs approximate tradeoffs, and two-stage retrieval architecture.

Theory

What Is Vector Search?

Vector search (also called semantic search or embedding-based retrieval) answers the question: given a query embedding vector, which stored vectors are most similar? This is the retrieval backbone of every RAG system, recommender engine, and semantic deduplication pipeline in production. The core operation is computing a similarity metric between the query vector and a corpus of candidate vectors, then returning the top-K most similar ones.

The dominant similarity metric is cosine similarity: cos(θ) = (A · B) / (‖A‖ · ‖B‖), which measures the angle between two vectors regardless of magnitude. For unit-normalized vectors (which most embedding models emit), cosine similarity reduces to a simple dot product A · B, making it extremely fast to compute. L2 (Euclidean) distance is also used, especially in image embeddings. Inner product (unormalized dot product) is used in matryoshka representation learning contexts.

The Dimensionality Problem

Modern embedding models produce vectors of 768–4096 dimensions (e.g., OpenAI text-embedding-3-large: 3072d; sentence-transformers: 384–1024d; Cohere embed-v3: 1024d). A brute-force exact KNN search over 1M vectors at 1024d requires ~4GB of float32 memory and ~10⁹ multiply-accumulate operations per query — feasible at small scale, but at 100M vectors the brute-force approach becomes prohibitively slow (>1 second latency).

This motivates Approximate Nearest Neighbor (ANN) algorithms: trade a small, bounded recall penalty for orders-of-magnitude speedup. In practice, the best ANN algorithms achieve >95% recall at 10–100× the throughput of exact search.

Key ANN Algorithms

HNSW — Hierarchical Navigable Small World

HNSW (Malkov & Yashunin, 2018) is the gold-standard ANN index for in-memory retrieval. It builds a multi-layer graph where each node (vector) connects to its nearest neighbors. During search, the algorithm begins at the top (sparse) layer — which acts like a highway network — and greedy-descends to the dense bottom layer, narrowing the candidate set with each step. The skip-list-like layer hierarchy over a navigable small-world graph makes the hop count scale empirically logarithmically: under the paper's small-world assumptions, greedy search reaches the target region in expected O(log N) hops. This is a scaling observation, not a proof of correctness — HNSW is an approximate index and offers no formal recall guarantee. Recall is tuned, not guaranteed: with sensible beam widths you land at ~0.95–0.99 recall@10, and pushing higher costs latency.

Key parameters: M (max neighbors per node per layer, typically 16–64) controls index size and recall; efConstruction (build-time beam width, 100–500) controls index quality vs build time; ef (query-time beam width, called efSearch in some libraries) is tunable at runtime — higher ef = higher recall, higher latency. Recall is a dial on ef, never a property of the index.

Build time: O(N · M · log N)  |  Query time: ~O(log N) expected  |  Memory: ≈ N · (M + dim) · 4 bytes

Note the memory formula scales the link term with N: every one of the N nodes stores its own neighbor list, so you pay dim float32s (4 B each) for the raw vector plus on the order of M node ids (4 B each) per vector. The rule of thumb above is the low end — layer 0 actually allows up to 2·M neighbors per node, and the sparse upper layers add a further ~1/(1−1/M) multiplier (≈3% at M=32, ≈7% at M=16), so the true link cost sits between M and ~2·M links per vector.

HNSW is the default index in pgvector (PostgreSQL), Weaviate, Qdrant, and Chroma. It supports single-pass query without a two-stage pipeline and handles dynamic insertions without full rebuild.

IVF — Inverted File Index

IVF (used extensively in FAISS) partitions the vector space into nlist Voronoi cells via k-means clustering. At query time, only the nprobe nearest cluster centroids are searched exhaustively. This dramatically reduces the candidate set. IVF scales to billion-scale corpora because the index can be stored on disk, unlike HNSW which must reside in RAM.

IVF + PQ (Product Quantization): Sub-divides each vector into subvectors, then quantizes each to a codebook entry (typically 8 bits). This compresses a 1024d float32 vector (4096 bytes) to ~128 bytes — a 32× compression — at the cost of some recall. Facebook's FAISS library implements IndexIVFPQ which makes billion-scale retrieval feasible on a single machine.

Memory (IVF+PQ): N · (m · log₂(k)/8) bytes  |  where m = subquantizers, k = codebook size (often 256)

FAISS — Facebook AI Similarity Search

FAISS is the workhorse library behind most vector search at scale. It implements dozens of index types: IndexFlatL2 (exact brute-force), IndexHNSWFlat, IndexIVFFlat, IndexIVFPQ, IndexIVFSQ (scalar quantization). It supports GPU acceleration (10–100× speedup on A100 GPUs), multi-GPU sharding, and can operate in batch mode for offline retrieval. The factory string API (`faiss.index_factory("1024,IVF4096,PQ64"`) lets you compose index types declaratively.

Two-Stage Retrieval: Retriever + Reranker

Production RAG systems almost universally use two-stage retrieval:

  1. Stage 1 — Fast retriever: ANN index returns top-100 candidates in <10ms. Optimized for recall, not precision.
  2. Stage 2 — Expensive reranker: A cross-encoder model (e.g. Cohere Rerank, BGE Reranker, Jina Reranker) scores each of the 100 candidates against the full query. Cross-encoders see query+document jointly and are much more accurate than bi-encoders, but too slow to run over the full corpus.

Cross-encoders like cross-encoder/ms-marco-MiniLM-L-6-v2 run in ~5ms per pair on CPU, so reranking 100 candidates adds ~500ms. Using GPU brings this to ~20ms for 100 candidates. The latency budget determines how many candidates Stage 1 retrieves.

Hybrid Retrieval: Dense + Sparse

Embedding-based (dense) retrieval excels at semantic similarity but struggles with exact keyword matching, rare proper nouns, and out-of-distribution terminology. BM25 (sparse term-based retrieval) handles these cases well but has no semantic generalization.

Hybrid retrieval runs both in parallel and fuses scores via Reciprocal Rank Fusion (RRF) or a learned linear combination: score = α · dense_score + (1-α) · sparse_score. RRF is formula-based and parameter-free: RRF(d) = Σ 1/(k + rank_i(d)) where k=60 is standard. Elasticsearch, OpenSearch, and Weaviate all support hybrid retrieval natively.

Chunking Strategy

Before indexing, documents must be split into chunks that fit within the embedding model's context window (typically 512–8192 tokens). Key chunking decisions:

  • Chunk size: Smaller chunks (128–256 tokens) have higher precision but lower context. Larger chunks (512–1024 tokens) give more context but noisier embeddings.
  • Overlap: 20–50 token overlap between chunks preserves cross-boundary context.
  • Semantic chunking: Split at sentence/paragraph boundaries rather than character count. Better coherence.
  • Late chunking (JinaAI, 2024): Embed full document, then split the token embeddings — avoids loss of document-level context in each chunk.

Production Numbers & Tools

At 10M vectors (1024d, float32, M=16): the flat vector payload alone is 10e6 · 1024 · 4 = ~41GB; the HNSW graph adds 10e6 · 2·16 · 4 ≈ 1.28GB of layer-0 links plus ~0.04GB of upper-layer links, so the whole index is ~42GB RAM — about 1.03× flat, not a multiple of it. Build time ~30min on 32 CPUs. The overhead ratio only gets interesting when dim is small relative to M: at 128d with M=64 the flat payload is 5.1GB and the links are another 5.2GB, i.e. ~2× flat. IVF+PQ (m=64): ~640MB RAM, ~98% recall@10 achievable with enough nprobe. Query latency: HNSW ~1ms, IVF+PQ ~5ms. Managed solutions: Pinecone (serverless, ~$0.04/1M queries), Weaviate Cloud, Qdrant Cloud. Self-hosted: pgvector (PostgreSQL extension, HNSW support added v0.5), Qdrant (Rust, HNSW + scalar quantization), Milvus (scale-out, Kafka-backed).

Production Gotcha: Embedding model upgrades require full corpus re-embedding — you cannot mix vectors from different models in the same index. Plan for re-indexing pipelines (typically 24–72hrs for 10M docs) and blue/green index swaps to avoid downtime.

Key Takeaways

  • HNSW dominates for low-latency in-memory retrieval — but its recall is tuned, not guaranteed. The layered small-world graph buys empirically logarithmic search (expected O(log N) hops), not a correctness proof; HNSW + ef=50 typically lands ~0.95–0.99 recall@10 at <5ms P99, and you trade latency for recall by raising ef. Budget RAM at ~1.03–2× the flat vector size (10M × 1024d with M=16 ≈ 41GB flat → ~42GB indexed). Default choice for Qdrant, Weaviate, and pgvector; for billion-scale, IVF+PQ is unavoidable.
  • Two-stage retrieval is non-negotiable at production scale. Bi-encoder ANN retrieval finds candidates cheap and fast; cross-encoder reranking adds 30–60% nDCG lift at the cost of 200–500ms. Always budget latency for reranking in your SLA.
  • Embedding model choice locks your index. Switching from text-embedding-ada-002 to text-embedding-3-large requires full re-embedding and re-indexing. Plan for version-tagged indices and parallel rollout pipelines from day one.
  • Hybrid retrieval (dense + BM25) beats pure dense on most BEIR benchmarks. Dense search misses exact keyword matches (product IDs, version numbers, rare proper nouns). RRF fusion is free and adds 5–15% recall on heterogeneous corpora. Always enable it unless your corpus is purely conceptual.
  • Quantization is the lever for memory cost, not recall. IVF+PQ compresses 4GB → 128MB (32×) with ~5% recall penalty. Scalar quantization (INT8) halves memory with <1% recall penalty. In RAM-constrained deployments, quantize first before adding more nodes.
  • Chunking strategy is upstream of everything. A poorly chunked corpus defeats good indexing. 256-token chunks with 32-token overlap and sentence-boundary splitting outperform naive fixed-size splits by 10–20% in downstream RAG answer quality (measured with RAGAS). Late chunking is state-of-the-art for long-document corpora.
