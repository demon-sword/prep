Chinchilla Scaling Law

Hoffmann et al. (2022) optimal compute allocation: equal scaling of model size and tokens — and why GPT-3 was massively undertrained.

Theory: The Compute-Optimal Scaling Law

The Pre-Chinchilla World

Before 2022, the prevailing wisdom came from Kaplan et al.'s 2020 scaling laws paper from OpenAI. Their key finding was that as you increase compute budget, you should primarily increase model size — training tokens mattered less. This led to a generation of ever-larger models: GPT-3 at 175B parameters (300B tokens), Gopher at 280B parameters (300B tokens), and Megatron-Turing NLG at 530B parameters (~270B tokens).

The intuition seemed sound: bigger models learn more per token, so throw tokens at a big model and stop when compute runs out. But this reasoning was subtly flawed. It confused "more efficient per token" with "better use of compute." The actual question is: for a fixed compute budget, how should you split that compute between model size and data?

The Chinchilla Insight: Equal Scaling

DeepMind's "Training Compute-Optimal Large Language Models" (Hoffmann et al., 2022) — nicknamed "Chinchilla" after the 70B model they trained to validate their laws — answered this question definitively. Their central finding:

Chinchilla Optimal Allocation Rule N_opt ∝ C0.5    and    D_opt ∝ C0.5

⟹ For a fixed compute budget C (FLOPs):
  • Model size and training tokens should scale equally
  • Approximately 20 tokens per parameter is optimal
  • C ≈ 6 · N · D  (FLOPs to train ≈ 6× params × tokens)

Concretely, if you have a compute budget that could train GPT-3 (175B params, 300B tokens), the Chinchilla-optimal model would use ~3.5T tokens on a ~8-9B parameter model — or some intermediate point like 70B parameters trained on 1.4T tokens, which is exactly what Chinchilla itself is. Chinchilla (70B) outperformed Gopher (280B) on almost every benchmark, using the same compute budget.

The Mathematical Foundation

The paper models language model loss as a function of parameters N and training tokens D:

Loss Model (Hoffmann et al. 2022, Eq. 4) L(N, D) = E + A / Nα + B / Dβ

Where:
  E = irreducible entropy of natural language (~1.69 nats)
  A, B = fitted constants (A ≈ 406.4, B ≈ 410.7)
  α ≈ 0.34  (diminishing returns to model size)
  β ≈ 0.28  (diminishing returns to more data)

Given the compute constraint C ≈ 6ND, you substitute D = C/(6N) and minimize L over N. Using calculus (Lagrange multipliers / differentiation), the optimal allocation satisfies:

Optimal allocation (Approach 3 from the paper) N_opt(C) ≈ G · Ca
D_opt(C) ≈ C / (6 · N_opt) = C1-a / (6G)

Where a ≈ 0.46, G ≈ 0.0083

Simplified rule of thumb:
  N_opt ≈ (C / 120)0.5   [parameters]
  D_opt ≈ 20 · N_opt         [tokens]

The paper uses three independent methodologies (IsoFLOP profiles, minimum loss over fixed N, parametric fitting) and all three converge on the same finding, giving strong confidence in the 20 tokens/param rule.

The "Over-Training" Correction: Inference-Optimal Models

Chinchilla optimizes for training loss at a fixed compute budget. But there's a crucial nuance: the objective is often inference efficiency, not just training loss. If you're going to deploy a model and run billions of inference calls, using a smaller model trained on more tokens is better in two ways:

  • Inference cost: A 70B model is cheaper to serve than a 175B model, even if they achieve similar quality.
  • Quality retention: More tokens means the model has seen more diverse patterns, making it more robust.

This is why Meta's LLaMA and LLaMA-2 models deliberately "over-train" relative to the Chinchilla compute-optimal point — they use far more tokens than strict compute-optimality requires, accepting higher training cost in exchange for smaller, faster inference models. LLaMA-2 70B uses 2T tokens (29 tokens/param) while Chinchilla says 20/param is compute-optimal. The reasoning: training runs once, but inference runs millions of times.

Implications for Modern LLM Design

The Chinchilla paper triggered a fundamental rethink of LLM scaling strategy:

  • Data quality becomes paramount: If you need 20× more tokens than params, and you're training a 7B model, that's 140B high-quality tokens — enough to exhaust curated sources like books and Wikipedia. Data curation, deduplication, and quality filtering became critical infrastructure.
  • The compute frontier shifted: The most performant model for a given FLOP budget is much smaller than previously assumed. You don't need to be Google-scale to train a competitive model — you need a well-curated dataset.
  • Mixture of Experts (MoE) changes the equation: MoE models (like Mixtral 8x7B, GPT-4) have more total parameters but activate fewer per token, so the C ≈ 6ND formula changes — active parameters, not total parameters, determine training FLOPs per token.
  • Data depletion is now a real concern: If scaling laws require 20 tokens/param and you want a 100T parameter model, you'd need 2 quadrillion tokens. At current internet scale (~15T tokens), this is physically impossible without synthetic data generation.

Key Takeaways

  • The 20-tokens-per-parameter rule — The Chinchilla compute-optimal ratio D_opt ≈ 20·N holds surprisingly well across scales from 70M to 70B parameters. GPT-3's actual ratio was ~1.7 tokens/param — roughly 12× undertrained. This single finding made "large model" strategy obsolete.
  • Inference-optimal ≠ compute-optimal — Production models like LLaMA-2, Mistral, and Falcon deliberately over-train (use more tokens than Chinchilla says is compute-optimal) to make smaller, cheaper-to-serve models. A 7B model trained on 2T tokens is cheaper to run than a 70B model trained on 200B tokens at similar quality — even though the latter is "more compute-efficient" to train.
  • Training FLOPs formula: C ≈ 6·N·D is a critical identity. Forward pass ≈ 2·N·D FLOPs, backward pass ≈ 4·N·D FLOPs. This means you can estimate any training run cost from model size + token count — a routine sanity check before committing GPU clusters.
  • Data quality is now the binding constraint — At 20 tokens/param, a 70B model needs 1.4T quality tokens. The entire Wikipedia is ~3.5B tokens. Deduplicated CommonCrawl snapshots reach ~15-20T, but raw quality is poor. Data curation (quality scoring, dedup, domain mixing) is now as important as model architecture.
  • Chinchilla's law breaks for MoE models — For Mixture-of-Experts, C ≈ 6·N_active·D where N_active is the active parameter count per token (not total). Mixtral 8x7B activates ~13B/token despite having 47B total params, so its compute requirements are much lower than naive parameter count suggests.
  • Scaling laws may overfit to architecture choices — The Chinchilla law was fit on dense decoder-only transformers of 2021-2022 vintage. Different architectures (SSMs like Mamba, RWKV, hybrid models) have different compute-to-loss relationships. Applying Chinchilla blindly to non-transformer architectures can be misleading.
