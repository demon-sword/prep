CUDA Programming Model

How GPU code is really organized — grids of thread blocks running on streaming multiprocessors, the NVCC to PTX to SASS compilation pipeline, and the occupancy and memory rules that decide whether your LLM kernel flies or stalls.

Theory

The Execution Hierarchy: Grid, Block, Warp, Thread

Every CUDA kernel launch creates a grid of thread blocks. A block is the unit of scheduling: it lands on one streaming multiprocessor (SM) and stays there until all its threads finish, because threads inside a block can cooperate through fast on-chip shared memory and the __syncthreads() barrier. Threads in different blocks cannot synchronize — if your algorithm needs global sync, you end the kernel and launch another one.

Inside a block, hardware groups threads into warps of 32 threads that execute in lockstep (SIMT — single instruction, multiple threads). The warp is the real scheduling quantum: an SM hides memory latency by keeping many warps resident and swapping between them every cycle at zero cost. An A100 SM holds up to 64 resident warps (2048 threads); a dead cycle only happens when no resident warp has an instruction ready. Everything about CUDA performance is keeping that warp pool full.

Thread

One lane of execution. Has private registers and a unique threadIdx. Cheapest thing on the GPU — launch millions.

Warp (32 threads)

Executes in lockstep. Branch divergence inside a warp serializes both paths. Think in warps, not threads.

Block (≤1024 threads)

Runs on exactly one SM. Threads share fast shared memory and __syncthreads(). The scheduling unit.

Grid

All blocks of a kernel launch, spread across every SM. No cross-block sync. Scale by launching more blocks.

The Memory Hierarchy (and Why Order Matters)

CUDA exposes the memory hierarchy explicitly, and picking the wrong level is the most common performance bug in custom kernels. From fastest to slowest: registers (per-thread, ~1 cycle), shared memory (per-block, on-chip SRAM, ~20–30 cycles), L1/L2 caches, then global memory (HBM, hundreds of cycles). A100 numbers make the stakes concrete: 19 TB/s of on-chip SRAM bandwidth versus 2 TB/s of HBM — nearly a 10× gap. FlashAttention exists because someone refused to pay the HBM price for the N×N attention matrix and tiled the whole computation into shared memory instead.

Global accesses have one more rule: coalescing. When the 32 threads of a warp touch contiguous 4-byte floats, hardware merges them into a few 128-byte cache-line transactions. Strided or scattered access by the same 32 threads can cost 32× the bandwidth for the same bytes. LLM kernels live or die here: a reduction over the hidden dimension with contiguous access saturates HBM; a gather over random token indices does not.

NVCC to PTX to SASS: The Compilation Pipeline

nvcc compiles .cu files in two stages. First, device code lowers to PTX — a virtual, forward-compatible assembly (e.g. sm_80 target emits PTX that any Ampere-or-newer driver accepts). At install or load time the driver JIT-compiles PTX to SASS, the real machine code for the specific chip. You can also ship precompiled SASS inside a fatbin to skip JIT warmup — the first-token latency spike on a cold server is often PTX JIT, and shipping -gencode arch=compute_90,code=sm_90 for exactly your fleet's GPUs removes it.

This two-stage design is why one PyTorch wheel runs on many GPU generations but never quite as fast as a build pinned to your architecture, and why operators like FlashAttention ship hand-tuned SASS-adjacent schedules via CUTLASS templates rather than naive CUDA C++.

// A complete CUDA kernel: vector add, the "hello world" that shows the model.
// kernel<<<gridDim, blockDim>>> — grid of blocks, each block of threads.
__global__ void vecAdd(const float* a, const float* b, float* c, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;  // global thread id
  if (i < n) c[i] = a[i] + b[i];                 // one output per thread
}

int main() {
  const int N = 1 << 20, B = 256;
  // ... cudaMalloc + cudaMemcpy host -> device omitted ...
  vecAdd<<<(N + B - 1) / B, B>>>(d_a, d_b, d_c, N);  // ceil(N/B) blocks
  cudaDeviceSynchronize();  // wait for the grid to finish
}

Occupancy: Keeping the SM Fed

Occupancy is resident warps divided by the hardware maximum (64 per SM on A100/H100). Three resources cap it: threads per block, registers per thread, and shared memory per block. A kernel using 64 registers per thread can fit at most 1024 threads per SM (65536 registers ÷ 64) — 50% occupancy before shared memory even enters the picture. The compiler flag --maxrregcount and the __launch_bounds__(maxThreadsPerBlock, minBlocksPerSM) attribute trade registers for occupancy by forcing spills to local memory, which is a real tradeoff to measure, not a free win.

A100 SM limits: 2048 threads · 64K registers · 164 KB shared · 32 blocks Max blocks from each limiter = floor(limit ÷ per-block use) Occupancy = min over limiters (blocks × warpsPerBlock ÷ 64)

High occupancy is not the goal — hiding latency is. A kernel with 25% occupancy but perfect coalescing and no divergence can still saturate HBM. But low occupancy caused by register pressure or oversized shared-memory tiles is usually a bug, and the occupancy calculator (below) tells you which limiter is biting before you touch Nsight Compute.

Streams, Events, and Overlapping Everything

Kernels and copies in the same stream run in order; work in different streams can overlap. The standard inference pattern is double-buffering: while stream 0 runs the matmul on batch N, stream 1 copies batch N+1 host-to-device, synchronized with events (cudaEventRecord / cudaStreamWaitEvent). CUDA graphs go further by capturing a whole launch sequence once and replaying it with a single launch — removing microseconds of per-kernel CPU launch overhead that dominate small-batch decode steps. vLLM and TensorRT-LLM both lean on graphs for exactly this reason.

Production Reality: The Five Rules

In production LLM serving, nearly every custom-kernel win traces back to five rules. One: launch enough blocks to cover all SMs — an H100 has 144 SMs, so a grid of 32 blocks leaves three-quarters of the chip idle. Two: keep warp occupancy high enough to hide HBM latency, but measure achieved (not theoretical) occupancy in Nsight Compute. Three: coalesce global access and stage reuse in shared memory — tiling is the whole game for attention, softmax, and reductions. Four: avoid warp divergence on data-dependent branches; restructure (predication, branchless selects) when profiles show it. Five: overlap copies with compute via streams, and collapse launch overhead with CUDA graphs. When a kernel still will not move, the answer is usually not more CUDA — it is Triton, CUTLASS, or an existing fused kernel from vLLM or FlashAttention that already encodes these rules.

Key Takeaways

  • Think in warps of 32 lockstep threads: a block is the scheduling unit that must fill SMs, and a grid needs at least as many blocks as SMs (144 on H100) or silicon idles — Nsight Compute reports the achieved numbers when theory and silicon disagree.
  • Occupancy is a means, not a target: it is capped by threads, registers (64K/SM), and shared memory (164 KB/SM on A100) per block, and spilling registers to raise it can lose — always re-profile instead of assuming.
  • Coalesce global accesses into 128-byte transactions and stage reuse in shared memory; every fused kernel in vLLM, TensorRT-LLM, and FlashAttention is this rule compounded, and HBM bandwidth (2 TB/s on A100) is the ceiling you measure against.
  • Ship SASS for your fleet's exact architecture (-gencode arch=compute_90,code=sm_90) to skip PTX JIT warmup on cold starts, and collapse small-batch launch overhead with CUDA graphs — decode steps are launch-bound long before they are compute-bound.
  • Overlap with streams and events (copy batch N+1 while computing batch N), and reach for Triton or CUTLASS before hand-rolling SASS-level schedules — NCCL collectives and existing fused kernels already encode the hard-won lessons.
