Model & Tensor Parallelism

How to split a model that doesn't fit on one GPU — tensor parallelism (intra-layer), pipeline parallelism (inter-layer), context & sequence parallelism, and how to pick each strategy for training vs inference.

Theory

Modern frontier LLMs are simply too large to fit on a single GPU. GPT-4's rumored ~1.8T parameters, Llama-3-70B's 70B parameters at float16 (~140 GB), or even a 7B model with optimizer states during training (~100 GB) all exceed the VRAM of a single A100 (80 GB) or H100 (80 GB SXM). Model parallelism is the collection of strategies that spread computation across multiple GPUs or nodes so training and inference remain feasible.

There are four distinct strategies, each operating at a different granularity. In practice, production systems (Megatron-LM, vLLM, TensorRT-LLM, DeepSpeed) combine all of them simultaneously — this is called 3D parallelism (tensor × pipeline × data).

1. Tensor Parallelism (TP) — Intra-Layer Splitting

Tensor parallelism splits the weight matrices of individual layers across GPUs. The canonical example is the multi-layer perceptron (MLP) sub-block of a transformer. An FFN typically computes: 

Y = GELU(X · W₁ + b₁) · W₂ + b₂

With column parallelism on W₁ (split along output dim) and row parallelism on W₂ (split along input dim), each GPU holds a shard. Each device processes its shard independently and a single AllReduce collective synchronises partial sums at the end. For attention, the Q/K/V heads are partitioned: GPU 0 handles heads 0…h/2, GPU 1 handles h/2…h. This requires two AllReduce calls per transformer block.

Communication pattern: TP requires fast intra-node communication (NVLink, 600 GB/s+). Crossing PCIe or InfiniBand makes TP prohibitively slow due to per-block all-reduces. TP degree is typically limited to the number of GPUs on one node (8).

Megatron-LM introduced this approach in 2019. With TP=8 on an 8-GPU node, each GPU holds 1/8 of every weight matrix. A 70B model's 70 GB shrinks to ~9 GB per GPU — fitting handily in an H100's 80 GB. However, activation memory still scales with the full context × batch, so TP alone isn't enough for huge contexts.

2. Pipeline Parallelism (PP) — Inter-Layer Splitting

Pipeline parallelism assigns different layers to different GPUs. GPU 0 runs layers 0–7, GPU 1 runs layers 8–15, etc. Communication is a simple point-to-point send of the activation tensor between stage boundaries — far cheaper bandwidth than all-reduce. This makes PP suitable for cross-node communication over InfiniBand (200–400 Gb/s).

The naive problem: GPU 1 sits idle while GPU 0 processes the first micro-batch. This is the pipeline bubble. Its fraction is: 

bubble fraction = (p - 1) / (m + p - 1)

where p = pipeline stages, m = micro-batches. Sending many micro-batches (large m) amortises the bubble. GPipe uses flush scheduling; PipeDream and Megatron-LM use 1F1B (one-forward-one-backward) interleaving to keep all stages busy and maintain bounded activation memory.

Gotcha: Gradient accumulation is mandatory with PP. Each stage must hold activations for all in-flight micro-batches — activation memory grows as O(p × micro-batch activations). Gradient checkpointing (recomputation) is often necessary on each stage.

3. Data Parallelism (DP) — Replicated Model, Split Batch

Data parallelism is the oldest strategy: each GPU holds a full model copy and processes different data shards. Gradients are averaged with an AllReduce after each backward pass. DP scales training throughput linearly with GPU count but requires each GPU to hold the full model — so it does not solve the memory problem.

ZeRO (Zero Redundancy Optimizer) from DeepSpeed fixes this by partitioning optimizer states (ZeRO-1), gradients (ZeRO-2), and parameters (ZeRO-3) across DP ranks. ZeRO-3 effectively distributes the entire model across GPUs while still looking like data parallelism from the code's perspective. At ZeRO-3 with 8 GPUs, each GPU only stores 1/8 of parameters, gradients, and optimizer states.

4. Context / Sequence Parallelism — Splitting Along the Sequence Dimension

For very long contexts (128K+), attention memory itself becomes the bottleneck: attention scores are O(n²) in sequence length. Sequence parallelism (Megatron-LM) splits the sequence dimension of LayerNorm and dropout outputs across TP ranks, complementing tensor parallelism. Ring Attention (Liu et al., 2023) shards the sequence across hosts in a ring topology so each host processes its local chunk with a causal mask, passing KV chunks around the ring — enabling essentially unlimited context by paying bandwidth.

Context Parallelism (used in Llama 3's training) further distributes prefill computation across devices. This is distinct from tensor parallelism: it slices the batch × sequence dimension rather than the hidden dimension.

3D Parallelism: Combining All Strategies

Production systems nest all strategies. A typical Llama-3 405B training run uses:

  • TP = 8 — within each node (NVLink)
  • PP = 16 — across nodes (InfiniBand), 16 pipeline stages
  • DP = N — replicating the (TP × PP) unit across N data-parallel replicas
  • Total GPU count = TP × PP × DP
Megatron-LM defaults for 405B: TP=8, PP=16, with 8-GPU nodes. You need at least 8 × 16 = 128 GPUs just for one DP replica. With DP=8, that's 1,024 H100s. This matches Meta's reported training configuration.

Inference vs Training Differences

At inference time, batch sizes are much smaller (often 1–32), so the pipeline bubble is less amortised. vLLM uses TP across GPUs on a single node (e.g., TP=4 for a 70B model across 4×A100s) and often avoids PP because PP adds latency per layer boundary. TensorRT-LLM supports both but recommends TP-first for latency-sensitive deployments.

For pure inference at massive scale, disaggregated prefill-decode (Splitwise, Mooncake) is an emerging approach: dedicate separate GPU pools to prefill (compute-bound) and decode (memory-bandwidth-bound) phases, sending KV caches between them. This avoids mixing the two workloads on the same hardware, improving utilisation.

Practical Selection Guide

  • Single node, fits after TP=8: use TP=8, no PP needed.
  • Multi-node training: TP within node, PP across nodes, DP × ZeRO-3 on top.
  • Long contexts (>32K): add sequence or context parallelism.
  • Low-latency inference (batch=1): prefer TP over PP; PP adds latency proportional to pipeline depth × activation transfer time.
  • High-throughput inference: PP can be beneficial if stages are well-balanced; vLLM's continuous batching helps keep all stages full.

Key Takeaways

  • TP degree is bounded by NVLink bandwidth. TP=8 is the practical ceiling on a single DGX H100 node (all-reduce over NVLink at 900 GB/s bidirectional). Going TP=16 across nodes kills throughput — every transformer block pays two cross-node all-reduces.
  • Pipeline bubble tax is real and scales with stages. With PP=16 and only 1 micro-batch, 15/16 ≈ 94% of each stage is idle. Use micro-batch counts ≥ 4×PP to keep bubble below 20%. Megatron's 1F1B schedule halves peak activation memory vs GPipe at the same throughput.
  • ZeRO-3 effectively shards the model like TP but with data-parallel semantics. No code changes to the model graph are required. The trade-off: ZeRO-3 doubles all-gather communication vs ZeRO-1. In practice, ZeRO-2 is the sweet spot — it shards optimizer states + gradients (the 12-byte-per-param overhead) but keeps parameters replicated, avoiding the all-gather on every forward pass.
  • For inference, TP dominates; PP adds latency proportional to pipeline depth × inter-stage bandwidth. At 200 Gb/s InfiniBand (25 GB/s), transferring a 4096-token × 8192-hidden activation tensor (≈256 MB at fp16) takes ~10 ms per stage boundary — a 16-stage pipeline adds 160 ms to TTFT. vLLM uses TP=4 for 70B models instead.
  • Ring Attention + context parallelism enables 1M+ token contexts at the cost of O(n) all-to-all communication across the ring. Used in Llama 3's training (up to 128K context), Gemini 1.5 (1M context claims to use a similar approach). Bandwidth-efficient but requires custom CUDA kernels to pipeline communication with computation.
  • The 3D parallelism grid (TP × PP × DP) must divide evenly into total GPU count. Misconfigurations waste GPUs or cause OOM. Always verify: assert total_gpus == tp * pp * dp. Megatron-LM enforces this at launch; DeepSpeed does not, leading to silent under-utilisation bugs in naive configs.
