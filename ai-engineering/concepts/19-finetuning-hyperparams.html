Fine-Tuning Hyperparameters

Learning rate, batch size, epochs, and prompt loss weight — what each controls, typical ranges, and how to tune them systematically for LLM fine-tuning.

Theory

Fine-tuning an LLM is not equivalent to training a neural network from scratch. You start with a model that has already converged to a rich representation of language and world knowledge. Your goal is to steer that representation — not to discover it. This changes the entire philosophy of hyperparameter selection. Every decision must balance adaptation against catastrophic forgetting, and fast convergence against overfitting on a small dataset.

The four hyperparameters that matter most — learning rate, batch size, epochs, and prompt loss weight — interact in ways that can make the difference between a perfectly aligned specialist model and a model that either forgets how to be coherent or never learns the target distribution at all.

1. Learning Rate — The Most Critical Knob

The learning rate (LR) controls how much pretrained weights shift per gradient update. It is the single most impactful hyperparameter in fine-tuning. Unlike pretraining where LRs of 1e-4 to 3e-4 are common, fine-tuning demands much smaller values to avoid destroying the pretrained representations.

θ_{t+1} = θ_t − η · ∇_θ L(θ_t) where η (eta) = learning rate θ = model weights L = loss on the fine-tune batch

Typical production LR ranges for full fine-tuning:

  • 1e-5 to 5e-5 — safe zone for most instruction fine-tuning. Slow but preserves pretraining knowledge.
  • 1e-4 to 3e-4 — aggressive; may be needed if fine-tune dataset is large (100k+ examples), but risks forgetting.
  • 1e-6 or lower — so slow you'll need many epochs; use when your dataset is tiny (< 1000 examples) and quality is paramount.

For LoRA fine-tuning, the adapter matrices A and B are initialized differently (A with Gaussian noise, B with zeros), so they start at zero change. Higher LRs of 1e-4 to 3e-4 are common for LoRA adapters without risking the base weights, since the base is frozen.

Learning rate schedules matter as much as the initial value. The standard approach is a cosine decay with warmup: linearly ramp LR from 0 over the first 1–5% of training steps, then cosine-decay to a floor (often 10% of peak LR). Warmup prevents large updates when the gradient signal is noisy in early steps. Linear decay is simpler and often comparable in practice.

2. Batch Size — Gradient Noise and Gradient Accumulation

Batch size controls gradient noise and training stability. Larger batches produce smoother, more accurate gradient estimates but reduce update frequency and require proportionally higher LRs (the "linear scaling rule" from Goyal et al. 2017: double batch size → double LR approximately holds within a range).

In LLM fine-tuning, raw batch size is constrained by GPU memory. A 7B model at fp16 takes ~14 GB just for weights — leaving limited headroom for activation storage. The workaround is gradient accumulation: run micro-batches of size 1–4, accumulate gradients for N steps, then apply one optimizer update. Effective batch size = micro-batch × accumulation steps × number of GPUs.

Effective Batch Size = micro_batch_size × grad_accum_steps × num_gpus Example: 4 GPUs × micro_batch=2 × accum=8 = 64 effective batch size

Typical effective batch sizes for instruction fine-tuning: 32–256 sequences. Too small (< 8) and gradient noise dominates, causing erratic training. Too large (> 512) and you may need to run fewer total gradient updates, which can underfit when your dataset is small.

3. Epochs — When to Stop

An epoch is one full pass over the fine-tune dataset. Because fine-tune datasets are typically small (1k–100k examples vs pretraining's billions), overfitting can happen quickly — sometimes within 2–3 epochs.

Practical guidance from production systems like Alpaca, Vicuna, and Llama fine-tunes:

  • 1–3 epochs: standard for large datasets (50k+ instruction pairs). More will overfit.
  • 3–10 epochs: appropriate for small, high-quality datasets (1k–10k examples). Watch the validation loss.
  • More than 10 epochs: almost always overfitting. The model memorizes training formatting and degrades on held-out distribution.

Early stopping on a held-out validation split is strongly recommended. Track both validation loss and actual task metrics — it's common for validation loss to plateau while task performance (measured by an LLM judge or benchmark) continues improving, or vice versa. Use validation loss to detect overfitting but measure task metrics to determine the real stopping point.

4. Prompt Loss Weight (Instruction Masking)

In instruction fine-tuning, each training example has two parts: the prompt/instruction (input) and the completion/response (target). A critical but often overlooked hyperparameter is whether to compute loss on the prompt tokens.

Completion-only loss: L = − Σ_{t ∈ response} log P(x_t | x_{<t}) Full sequence loss: L = − Σ_{t ∈ all tokens} log P(x_t | x_{<t}) Prompt loss weight ∈ [0.0, 1.0] — scales the loss on prompt tokens
  • Weight = 0 (response-only): Model only learns from response tokens. Preferred when prompts are templated/repetitive (system prompts, few-shot examples) — no signal wasted on boilerplate.
  • Weight = 1.0 (full sequence): Include loss on all tokens. Can help when prompts are informative and variable, but hurts when prompts are formulaic (the model wastes capacity memorizing template text).
  • Weight = 0.1–0.5: Intermediate — used in models where prompt context matters but shouldn't dominate gradient signal.

The original Alpaca paper used full sequence loss (weight = 1.0). Later analysis showed response-only training (weight = 0) produces better instruction-following in most cases, especially when fine-tuning on chat templates with a fixed system prompt.

5. Interaction Effects and Systematic Tuning

These hyperparameters don't operate in isolation. A high LR requires more warmup steps. A small batch needs a lower LR. More epochs require stronger regularization (weight decay, dropout). The token budget — total tokens seen during fine-tuning — is the fundamental constraint:

Total tokens seen = dataset_size_tokens × num_epochs ≈ n_examples × avg_seq_len × num_epochs

For a 7B model fine-tuned on 10k examples of 512 tokens each for 3 epochs, you process ~15M tokens. Compare to the pretraining corpus of ~1T tokens — fine-tuning is a tiny perturbation. This is why LRs must be small and epochs few: you have almost no data relative to the model's prior knowledge.

Practical tuning order: (1) Fix batch size to fill GPU memory. (2) Tune LR with a short grid search (3–5 values on log scale). (3) Tune epochs by watching validation loss. (4) Tune prompt loss weight last — run 2 ablations.

Key Takeaways

  • Learning rate is the most consequential knob. Full fine-tuning on 7B+ models at LR > 1e-4 often causes catastrophic forgetting within the first epoch. Start at 2e-5 and double only if convergence is too slow after watching 1–2 epoch curves.
  • Gradient accumulation is a mandatory trick. With 40 GB GPUs and a 13B fp16 model, you can fit micro-batch = 1–2. Use gradient accumulation × 32 to reach an effective batch of 64 without buying more hardware. TRL, Axolotl, and LLaMA-Factory all handle this transparently.
  • Overfitting happens fast on small datasets. A fine-tune on 1k examples with 10 epochs will typically see val loss diverge by epoch 3–4. Always reserve 5–10% of data for a validation split and monitor it. Don't optimize train loss alone.
  • Prompt loss weight = 0 is almost always better for instruction tuning. Including loss on system prompt tokens causes the model to waste capacity memorizing template phrasing. OpenAI's supervised fine-tune guide and most production practitioners (Axolotl default) mask prompt tokens.
  • Warmup steps matter more than people realize. At LR 2e-5 with no warmup, early gradient estimates (when weights are still "wrong" for the new distribution) can cause destructive updates. Standard practice: warmup over 5% of total steps. Cosine decay vs linear decay rarely changes final quality by >0.5 loss points.
  • For LoRA, tune rank before LR. Rank 8–64 covers 95% of use cases. A higher rank (128+) with high LR on a tiny dataset will overfit the LoRA matrices — you get a model that perfectly copies training examples and generalizes poorly. Validate with a task-specific metric, not just loss.
