Inference Optimization

Compute vs memory-bound bottlenecks, quantization, pruning, distillation, speculative decoding, continuous batching, KV cache, prompt caching, and model/tensor parallelism.

Theory

Inference optimization is the discipline of making LLM serving faster, cheaper, and more memory-efficient without retraining. It spans algorithmic techniques (quantization, speculative decoding), systems techniques (continuous batching, KV-cache management), and hardware strategies (tensor/pipeline parallelism). Understanding it requires first diagnosing which bottleneck you actually face — compute-bound or memory-bandwidth-bound — because the optimal interventions are completely different.

1. The Two Bottlenecks

Modern GPUs can perform massive FLOP counts but are constrained by how fast they can move data from HBM (high-bandwidth memory) to on-chip SRAM. The arithmetic intensity of an operation — FLOP/byte — determines which resource is the bottleneck.

  • Compute-bound: matrix multiplications during the prefill phase (long prompts, large batch sizes). The GPU ALUs are the bottleneck. Solutions: flash attention, lower precision (fp16, bf16), tensor parallelism.
  • Memory-bandwidth-bound: autoregressive decode with batch size = 1 (each token generation loads all model weights from HBM). Solutions: quantization (reduce bytes/weight), continuous batching (increase effective batch size), speculative decoding, KV-cache offloading.

As a rough heuristic: a 7B model in fp16 is ~14 GB; at 900 GB/s bandwidth (A100 80GB), loading all weights takes ~15 ms — that's 67 decode tokens/sec max, even with zero compute overhead. Quantizing to int4 halves the load to ~7 GB and doubles the theoretical ceiling.

2. Quantization

Quantization maps high-precision weights/activations to lower-precision representations. The main options:

  • fp16 / bf16: Standard inference precision. bf16 has wider dynamic range (same exponent bits as fp32), favored by modern hardware. No quality loss vs fp32 in practice.
  • int8 (W8A8): Weights and activations quantized to 8-bit integers. Achievable with bitsandbytes, GPTQ, or SmoothQuant. Typical quality impact: <1% degradation on most benchmarks. ~2x memory reduction, ~1.5–2x throughput gain on supported hardware.
  • int4 (W4A16 / NF4): 4-bit weights, fp16 activations. Used in QLoRA (NF4 format) and GPTQ. ~4x memory reduction. Works surprisingly well for decoder-only models; some tasks see 2–5% degradation. llama.cpp runs a 70B-class open-weight model in int4 on a single 48 GB GPU.
  • GGUF / GGML: Quantization formats for CPU inference, popularized by llama.cpp. Support mixed-precision per tensor (sensitive layers kept at higher precision).
  • AWQ (Activation-aware Weight Quantization): Keeps 1% of weights at fp16 (those with high activation magnitudes), the rest at int4. Better quality than uniform int4 at same bit-width.

Post-training quantization (PTQ) requires no retraining. Quantization-aware training (QAT) bakes quantization into training for better results but is expensive.

3. KV Cache Management

During autoregressive decoding, each attention layer must recompute attention over all previous tokens — or cache the Key and Value tensors to avoid redundant computation. The KV cache grows as: 2 × num_layers × num_kv_heads × head_dim × seq_len × bytes/elem. For a 70B-class open-weight model (80 layers, 8 GQA heads, 128 head_dim, fp16): each token uses 2 × 80 × 8 × 128 × 2 = 327,680 bytes ≈ 320 KB. A 4096-token sequence fills ~1.3 GB — per request.

  • PagedAttention (vLLM): Stores KV cache in non-contiguous pages (like virtual memory), eliminating fragmentation. Allows near-zero wasted KV cache memory and enables sharing across requests with common prefixes.
  • GQA (Grouped Query Attention): Multiple query heads share a single K/V head (a modern open-weight model, Mistral). Reduces KV cache size by num_q_heads / num_kv_heads.
  • MQA (Multi-Query Attention): Extreme case — all query heads share one K/V pair. Used in PaLM, Falcon.
  • KV cache offloading: Move KV cache to CPU RAM when GPU VRAM is full. Adds latency (~50–200ms per layer on NVLink) but allows longer contexts.
  • Prompt caching: Cache the KV state for a fixed system prompt prefix across requests. Anthropic charges 10% for cache writes, 1% for cache hits. vLLM calls this "prefix caching."

4. Continuous Batching

Naïve batching waits for all requests in a batch to finish before starting new ones — causing GPU idle time when some requests complete early. Continuous batching (iteration-level scheduling, used in vLLM, TGI, TensorRT-LLM) ejects completed sequences and inserts new ones at every decode step. This dramatically improves GPU utilization — throughput gains of 2–10x on production traffic distributions, because real request lengths vary widely.

5. Speculative Decoding

A small draft model (e.g., 7B) generates K candidate tokens; the large target model verifies all K in a single forward pass (because verification is parallelizable like prefill). Accepted tokens are kept; the first rejected token is replaced with the target's sample, and drafting resumes. Achieves 2–3x speedup with no quality loss, because the target model's distribution is preserved. The key constraint: the draft model must match the domain/tokenizer of the target, and the speedup depends on acceptance rate (how often draft tokens match target distribution).

6. Pruning & Distillation

Structured pruning removes entire attention heads or FFN neurons. Unstructured pruning zeros individual weights — requires sparse hardware support (NVIDIA Ampere 2:4 sparsity) to yield real speedup. Knowledge distillation trains a smaller student model on the teacher's soft logits — Phi-3 (3.8B), Gemma-2-2B, and SmolLM are notable distillation-derived models that punch well above their weight class. Distillation is orthogonal to quantization and can be combined.

7. Model & Tensor Parallelism

When a model doesn't fit on one GPU, or when you need lower latency via parallelism:

  • Tensor parallelism: Split weight matrices column/row-wise across GPUs. Each GPU holds a shard; all-reduce after each layer. Requires fast interconnect (NVLink). Reduces memory per GPU and allows larger batch sizes. vLLM, Megatron-LM.
  • Pipeline parallelism: Assign layers to GPUs sequentially. Micro-batch pipelining hides the inter-GPU bubble. Better for slow interconnects. Higher latency than tensor parallelism for single requests.
  • Sequence/Context parallelism: Split the sequence dimension across GPUs. Enables very long contexts (1M tokens) that can't fit in one GPU's KV cache. Used in DeepSpeed Ulysses, Ring Attention.

8. Flash Attention

Standard attention requires materializing the full N×N attention matrix in HBM — O(N²) memory. FlashAttention (Dao et al., 2022) tiles the computation to keep everything in SRAM, reducing HBM reads/writes and achieving 2–4x speedup on long sequences. FlashAttention-2 and FlashAttention-3 (for Hopper GPUs) push further. It's now the default in all major frameworks (HuggingFace, PyTorch SDPA, vLLM).

9. Production Reality

vLLM

The de-facto open-source LLM serving engine. PagedAttention, continuous batching, tensor parallelism, speculative decoding, AWQ/GPTQ/int8 quantization. Often 10–20x throughput vs HuggingFace naive inference.

TGI (Text Generation Inference)

HuggingFace's production serving stack. Continuous batching, flash attention, token streaming. Used on the Inference API.

TensorRT-LLM

NVIDIA's framework. Deepest hardware-level optimization (kernel fusion, in-flight batching). Highest throughput on A100/H100 but complex deployment.

llama.cpp

CPU + GPU inference in GGUF format. Runs a 70B-class open-weight model on a Mac Studio or dual RTX 3090s. int4 quantization with per-layer mixed precision.

Key Takeaways

  • Diagnose before optimizing: Profiling is non-negotiable. Decode is almost always memory-bandwidth-bound at batch=1; prefill is almost always compute-bound for long prompts. The interventions are different — apply the wrong fix and you gain nothing.
  • Continuous batching is the highest-leverage systems win: vLLM's PagedAttention + continuous batching typically yields 10–20x throughput improvement over naïve HuggingFace generate() with zero model changes. Do this first.
  • int4 quantization on 70B+ models is production-safe: AWQ / GPTQ int4 on a 70B-class open-weight model loses <2% quality on most evals while fitting in 40 GB VRAM instead of 140 GB. The tradeoff is worthwhile for most applications.
  • Speculative decoding's speedup is acceptance-rate dependent: If draft and target models are misaligned (different tokenizer, different domain), acceptance rate collapses and you spend more compute than you save. Test empirically. 2.5–3x is realistic for well-matched pairs.
  • KV cache is the memory budget killer at long context: A 128K-context request on a 70B-class open-weight model occupies ~40 GB of KV cache alone. GQA reduces this by 8x vs MHA; prefix caching amortizes it across requests with shared system prompts.
  • FlashAttention is free quality: It produces mathematically identical outputs to standard attention — it's a pure systems optimization. If you're not using it (via torch.nn.functional.scaled_dot_product_attention in PyTorch 2.0+), you're leaving 2–4x prefill speed on the table.
