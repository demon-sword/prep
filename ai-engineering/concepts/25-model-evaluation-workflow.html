25. Model Evaluation Workflow

Hard vs soft attributes, pointwise vs comparative evaluation, the 5-stage workflow: filter → benchmark → experiment → monitor, and cost-performance frontier mapping.

Theory

Choosing a model is not a benchmarking exercise — it is an engineering decision under constraints. A model that scores highest on MMLU may be too expensive to serve, too slow for your latency SLA, or simply unable to follow your output schema reliably. A principled evaluation workflow treats model selection like system design: define requirements first, measure against them systematically, and track the frontier over time.

Hard vs Soft Attributes

The first cut in any model selection process is separating hard constraints from soft preferences. A hard attribute is a binary pass/fail: the model either satisfies it or it is eliminated regardless of quality. Soft attributes live on a continuous scale and contribute to a cost-quality tradeoff.

Category Attribute Typical Hard Threshold
Cost Input/output token price < $X / 1M tokens (from budget)
Latency Time-to-first-token (TTFT) < 500ms for interactive; < 2s for batch
Throughput Tokens/sec at target concurrency Sustain P99 within SLA
Privacy / Compliance Data residency, HIPAA, SOC2 On-prem or approved cloud region
License Commercial use allowed Binary: yes or eliminated
Context window Max input tokens ≥ your longest expected input

Soft attributes include task quality (accuracy, ROUGE, human preference score), output consistency, instruction-following fidelity, multilingual coverage, and structured output reliability. These form the axes of the cost-performance Pareto frontier.

Pointwise vs Comparative Evaluation

There are two fundamental evaluation modes, each with different noise profiles:

Pointwise (absolute scoring): Evaluate each model output independently against a rubric, reference answer, or LLM judge. Outputs a scalar score per sample. Advantage: easy to aggregate, compare to a fixed baseline, and track over time. Disadvantage: LLM judges exhibit position bias and verbosity bias — long outputs consistently score higher even when they are worse.

Comparative (head-to-head): Present model A vs model B outputs to a judge (human or LLM) and ask which is better. Advantage: higher signal-to-noise — humans are better at relative judgment than absolute. Disadvantage: O(n²) comparisons for n models; hard to establish a global ranking without an ELO-style system. Chatbot Arena uses this pattern at scale.

In production pipelines, a common hybrid is: run pointwise evaluation across all candidate models cheaply using an LLM judge, then run comparative evaluation on the top-3 finalists using human raters for the final decision.

① Filter by hard attributes. Before running a single inference, eliminate models that fail any hard constraint. This is free — it only requires reading documentation, pricing pages, and license terms. A model that costs $15/1M output tokens might be 30% better than a $1/1M option but fails a cost constraint and should never reach the benchmark stage.

② Benchmark on public datasets. Run surviving models against established benchmarks relevant to your task domain. For reasoning tasks: MMLU, HellaSwag, ARC. For coding: HumanEval, SWE-bench. For instruction-following: MT-Bench, IFEval. For multilingual: FLORES-200. Public benchmarks have known contamination risks — large models have often seen test sets during pretraining. Treat them as coarse signal, not ground truth.

③ Experiment on your task distribution. This is the highest-signal stage. Construct a golden evaluation set of 100–500 examples representative of your actual traffic (not public benchmarks). Include failure-mode examples, edge cases, and adversarial prompts. Run all surviving models. Use automated metrics (ROUGE, exact match, semantic similarity) plus LLM-as-judge for qualitative dimensions. This stage often reverses benchmark rankings — a model that scores 78% on MMLU may be worse than a 74% model on your medical note summarization task.

④ A/B Test in production shadow mode. Route a percentage of real traffic through the challenger model, log both outputs, and compare offline using your quality metrics. This catches distribution shift between your golden set and real traffic. A 1–5% canary is typical before full rollout. Tool integrations matter here: LangSmith, Braintrust, and Weights & Biases Prompts all support shadow evaluation.

⑤ Monitor ongoing quality. Model providers silently update models. GPT-4-turbo in November 2023 is not the same model as GPT-4-turbo in March 2024. Set up continuous evaluation with a scheduled golden set run (nightly or weekly) and alert on quality degradation > X%. Track response length, refusal rate, and structured output failure rate as proxy signals. OpenAI's model version pinning (e.g. gpt-4-0125-preview) partially mitigates drift but not indefinitely.

The Pareto Frontier

Most real model selections involve a cost-performance tradeoff. The Pareto frontier is the set of models where no other model dominates on both cost and quality simultaneously. A model on the frontier is "efficient" — you cannot get better quality without paying more, and you cannot pay less without losing quality.

Dominated: model A dominates B if: quality(A) ≥ quality(B) AND cost(A) ≤ cost(B) (with at least one strict inequality) Pareto-optimal: no model dominates you

In practice, the frontier changes weekly as new models arrive. The decision is which point on the frontier fits your quality floor and cost ceiling. A team running millions of inferences/day may prefer a frontier model with 2% lower quality but 5× lower cost. A high-stakes medical pipeline may pay the premium for the top-quality frontier point.

Evaluating the Evaluator

A meta-level trap: a flawed evaluation pipeline gives confident wrong answers. Before trusting your evaluation, assess the evaluator itself on four dimensions:

  • Signal quality: Does the metric actually correlate with the business outcome you care about? Run experiments with deliberately good and bad outputs and confirm the metric separates them.
  • Consistency: Run the same evaluation twice. LLM judges should agree with themselves >85% of the time on clear cases. Disagreement indicates too-coarse rubrics.
  • Calibration: Are metric scores meaningful across models and time, or do they drift? LLM judges trained on GPT-4 outputs are biased toward rating GPT-4-like outputs as better (self-evaluation bias).
  • Cost: Running GPT-4 as judge on 10,000 examples costs ~$20–80. At scale, use a smaller judge model validated against human raters for that task.

Production Reality

Real evaluation pipelines at companies like Anthropic, OpenAI, and scale-AI run continuously. The typical production setup involves: a curated golden set of 200–2000 labeled examples updated quarterly, a nightly evaluation job scoring deployed models, a dashboard tracking quality/cost/latency over time, and an alerting system that pages oncall when quality drops 3+ sigma from baseline. Teams that invest here catch silent model regressions days before users notice — teams that don't are reactive.

Tool ecosystem: LangSmith (LangChain's evaluation platform), Braintrust (evaluation and prompt management), RAGAS (RAG-specific metrics), Phoenix (Arize) (model observability), Weights & Biases Weave (tracing + evaluation), OpenAI Evals (framework for defining and running evals). Each has different strengths — LangSmith integrates most tightly with LangChain pipelines, Braintrust has the cleanest human review UI, and RAGAS excels at faithfulness/relevance metrics for RAG.

Key Takeaways

  • Filter before you benchmark: Eliminating on hard attributes (cost, latency, license, context window) before running any inference saves days of engineering time. Most real shortlists go from 20+ candidates to 4–6 in 30 minutes of documentation review.
  • Public benchmarks have contamination risk: MMLU and HumanEval scores for frontier models are unreliable — training data frequently includes test sets. A model ranking 1st on HumanEval can rank 3rd on your internal coding eval. Always build a domain-specific golden set.
  • The Pareto frontier changes weekly: A model that dominates in Q1 may be off the frontier by Q3. Chatbot Arena's ELO leaderboard updates continuously — build monitoring into your pipeline so you re-evaluate quarterly without heroic effort.
  • LLM judges have systematic biases: Verbosity bias (longer = rated better), self-evaluation bias (GPT-4 rates GPT-4 outputs highest), and position bias (first response in pairwise comparison gets a small boost). Use swap-test (A vs B and B vs A) and average to mitigate position bias. Use length normalization to reduce verbosity bias.
  • Shadow mode A/B is mandatory before full rollout: Your golden set cannot capture tail distribution of real traffic. 5% shadow routing for 24–72 hours before full promotion catches regressions that only appear on uncommon input patterns.
  • Silent model updates break production: OpenAI, Anthropic, and Google update models behind aliases without announcements. Pin specific model versions (e.g. claude-3-5-sonnet-20241022, not claude-3-5-sonnet-latest) and run your golden set nightly to detect drift before users do.
