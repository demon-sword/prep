Prefill & Decode Phases

▶ Prefill Phase — Compute-Bound

When you submit a prompt to an LLM, the entire token sequence is processed in a single forward pass. Every prompt token attends to every other prompt token simultaneously — this is the prefill phase. Because the attention matrix is dense (O(n²) operations for sequence length n), and weight matrices are applied in parallel across all positions, this phase is dominated by matrix multiplications: exactly the workload modern GPUs are designed for.

The result of prefill is threefold: (1) the hidden states for each token are computed, (2) the KV cache is populated for every layer, and (3) only the final token's hidden state is projected to produce the first output token — marking the end of TTFT (time-to-first-token).

Compute-bound
GPU util ~85–100%
Scales with prompt length²

▶ Decode Phase — Memory-Bandwidth-Bound

After prefill, the model enters the decode phase: tokens are generated one at a time, autoregressively. At each step, only the single new token is fed forward. It attends to all previous positions via the KV cache (no recomputation needed), and the next token is sampled from the output distribution.

Here the bottleneck flips entirely. Each decode step requires loading all model weights from HBM (high-bandwidth memory) plus reading the entire KV cache — but performs only a tiny sliver of FLOPs relative to the bytes transferred. Arithmetic intensity (FLOPs / byte) sits well below the GPU's roofline threshold, so the GPU sits idle waiting for memory transfers. A 70B model at FP16 has ~140 GB of weights alone; loading them per token at 2 TB/s HBM bandwidth gives ~70 ms/token — hence ~14 tokens/sec theoretical ceiling on a single A100.

Memory-bound
GPU util ~30–40%
~20 tok/s on Llama-2 70B / A100

▶ KV Cache Mechanics

In multi-head attention, each layer computes three projections per token: Query (Q), Key (K), and Value (V). During decode, Q is always the single new token — it's never reused. But K and V from all previous tokens are needed to compute attention — they are cached after prefill and reused every decode step.

KV cache memory = 2 × L × H × dh × S × dtype_bytes
// 2 = K and V tensors
// L = num_layers, H = num_heads, d_h = head_dim
// S = sequence length, dtype_bytes = 2 for FP16

Llama-2 70B example (S=4096):
2 × 80 × 64 × 128 × 4096 × 2 ≈ 10.7 GB

This is why long contexts are expensive: KV cache grows linearly with sequence length and must fit in GPU VRAM. At 128K context, that same model requires ~330 GB of KV cache — far beyond a single GPU.

▶ Roofline & Arithmetic Intensity

The roofline model characterizes GPU performance: if arithmetic intensity (FLOPs per byte transferred) is above the ridge point, the op is compute-bound; below it, memory-bandwidth-bound. A100 SXM has ~312 TFLOPS (FP16) and ~2 TB/s HBM, giving a ridge point of ~156 FLOPs/byte.

Prefill of a 512-token prompt against a 70B model performs ~O(n × d_model × d_model) FLOPs per layer — easily exceeding 156 FLOPs/byte. Decode of a single token achieves only ~2–10 FLOPs/byte — far below the ridge. This is why batching decode requests together (continuous batching) dramatically improves throughput: you amortize the weight-loading cost across many concurrent tokens, raising effective arithmetic intensity.

Prefill: >156 FLOPs/byte
Decode: 2–10 FLOPs/byte

▶ TTFT & TBT — Latency Decomposed

TTFT (Time-To-First-Token): the wall-clock time from request submission until the first output token appears. Dominated entirely by prefill latency. For long prompts, TTFT can be seconds — even if decode is fast. TTFT scales roughly linearly with prompt length (O(n²) attention ops but batched efficiently via tensor cores).

TBT (Time-Between-Tokens): the inter-token latency during decode. On Llama-2 70B with a single A100, TBT ≈ 50–70 ms (~15–20 tokens/sec). With continuous batching of 8 requests, effective throughput rises to ~120 tokens/sec total while per-request TBT barely changes — the key insight behind vLLM's throughput gains.

  • TTFT SLA: typically <500ms for interactive apps
  • TBT SLA: typically <100ms (human reading speed ~5 tok/sec)
  • Streaming output hides TBT jitter from users

▶ Production: vLLM, PagedAttention & Chunked Prefill

vLLM's PagedAttention manages KV cache memory using OS-style paging: instead of pre-allocating a contiguous block per request (wasting up to 60-80% of reserved memory due to fragmentation), KV cache is stored in non-contiguous pages of fixed block size (e.g., 16 tokens/block). Requests share a logical block table mapping to physical pages, enabling near-zero waste and dynamic growth.

Continuous batching (iteration-level scheduling) replaces static batching: decode steps are batched at each iteration, and new prefill requests are inserted as soon as a slot frees — no waiting for the entire batch to finish.

Chunked prefill addresses a critical jitter problem: a single 32K token prompt monopolizes the GPU during prefill, stalling all in-flight decode requests (spiking their TBT). By breaking the prefill into chunks (e.g., 512 tokens) and interleaving them with decode steps, TTFT jitter is smoothed and decode latency stays bounded. This is now default in vLLM ≥ 0.4 and SGLang.

  • PagedAttention: eliminates KV cache fragmentation
  • Continuous batching: maximizes GPU utilization across requests
  • Chunked prefill: prevents long prompts from starving decode

What Engineers Actually Need to Know

1

Decode throughput ≠ Decode latency

A single request on Llama-2 70B gets ~20 tok/s. But with continuous batching at batch-size 32, total throughput reaches 200+ tok/s while per-request TBT barely degrades. The memory bandwidth is the fixed ceiling — you amortize it across batch size. Always report throughput and latency separately in benchmarks.

2

Long contexts destroy throughput doubly

A 128K context on a 70B model requires ~330 GB of KV cache alone — beyond a single node. Even when it fits, every decode step reads the full KV cache from HBM, so TBT ∝ seq_len. Tokens-per-second at 128K context can be 10–30× worse than at 2K context. GQA (grouped-query attention) and MLA (multi-latent attention, used in DeepSeek) dramatically cut KV cache size.

3

vLLM's PagedAttention is OS-level memory management

Pre-vLLM, serving frameworks reserved the maximum possible KV cache per request upfront, wasting 60–80% of VRAM. PagedAttention allocates in 16-token pages on-demand, enabling 2–4× more concurrent requests on the same hardware. The block_size is a tunable — smaller blocks reduce waste but increase block table overhead.

4

Chunked prefill is essential for latency-sensitive multi-tenant serving

Without chunked prefill, a single 32K-token RAG prompt can block all concurrent decode requests for 1–3 seconds. With chunked prefill (chunk_size ≈ 512), the worst-case decode stall per chunk is ~10 ms. This is now on by default in vLLM ≥ 0.4 and is critical for meeting P99 TBT SLAs in production.

5

TTFT is a UX cliff, TBT is a UX floor

Users notice TTFT as "the wait before anything appears" — anything over 1–2 s feels broken. TBT is perceived as "typing speed" — humans read at ~5 tok/s, so 20 tok/s feels instant. This asymmetry means optimizing TTFT (e.g., smaller prefill models, speculative decoding draft warmup) often matters more than squeezing decode throughput for interactive products.

6

Prefill-decode disaggregation is the next frontier

Since prefill is compute-bound and decode is memory-bound, they have opposite hardware affinities. Systems like Mooncake (from Moonshot AI) and DistServe split them onto separate GPU pools — prefill on compute-heavy nodes, decode on memory-bandwidth-optimized nodes — achieving Pareto improvements in both TTFT and throughput simultaneously.
