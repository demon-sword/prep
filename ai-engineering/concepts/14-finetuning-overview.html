Fine-Tuning: When, Why & Decision Framework

When to fine-tune vs prompt-engineer vs RAG, the two capabilities it improves, cost realities, and the decision tree for choosing your approach.

Theory

What Is Fine-Tuning?

Fine-tuning is the process of continuing to train a pretrained base model on a curated, task-specific dataset using supervised learning. The base model already "knows" language — its weights encode world knowledge, reasoning patterns, and grammar from trillions of tokens. Fine-tuning adjusts those weights (or a subset of them) so the model behaves differently: following specific instructions, adopting a domain vocabulary, producing a particular output format, or avoiding certain response patterns.

Critically, fine-tuning does not give the model new knowledge from documents the way RAG does. It changes how the model responds — its style, format adherence, instruction-following, and learned behavioral patterns — rather than expanding what facts it can retrieve at query time.

The Two Capabilities Fine-Tuning Improves

Fine-tuning affects two distinct dimensions:

  • Domain knowledge & vocabulary: Adapting to specialized jargon, proprietary ontologies, or rare patterns not well-represented in pretraining (e.g., medical ICD codes, legal clause structures, internal API schema names). The model learns to "think" in your domain's language.
  • Instruction following & behavior: Reliable adherence to output formats (strict JSON, specific XML schemas), consistent tone, persona maintenance, refusal patterns, or multi-step task completion. A base model prompted to output JSON will drift; a fine-tuned model won't.

Most production fine-tuning targets one of these. Trying to solve both simultaneously with a single fine-tuning run often requires more data and risks catastrophic forgetting of general capabilities.

Fine-Tuning vs the Alternatives

Before committing to fine-tuning, engineers should exhaust cheaper options. The decision is not binary — it's a spectrum ordered by cost and complexity:

Approach Cost Latency Best For Limitation
Prompt Engineering ~$0 +0ms Format, tone, few-shot examples Context-length constrained; prompt costs at scale
RAG Low–medium (vector infra) +50–200ms retrieval Fresh/proprietary factual knowledge Can't change behavior, only grounding
Fine-Tuning High (GPU hours + data) Baseline (model is faster) Behavior, format, domain style Doesn't add real-time knowledge; training cost
Fine-Tuning + RAG Highest +retrieval overhead Domain behavior + fresh facts Complex pipeline; cost compounds

The Case for Prompt Engineering First

Modern LLMs (GPT-4, Claude 3.x, Llama 3) respond dramatically better to well-crafted prompts than their predecessors. A carefully structured system prompt with 5–10 high-quality few-shot examples can often achieve 80–90% of what a fine-tuned model would deliver. The cost difference is stark: iterating on a system prompt takes minutes; preparing a fine-tuning dataset takes days to weeks.

The key threshold: if the base model can't demonstrate the target behavior at all given examples in-context, fine-tuning won't magically teach it. If it can do it sometimes with prompts, fine-tuning makes it reliable. This is the "capability gap" test.

The Case for RAG First

If your problem is "the model doesn't know our internal documents / product catalog / recent events", RAG is almost always the right first step. RAG decouples knowledge freshness from model training. You can update the document store without retraining. Fine-tuning on private facts rarely works well because:

  • The model memorizes patterns but hallucinates variations it wasn't trained on
  • You can't update facts without rerunning fine-tuning
  • RAGAS-measurable retrieval precision typically outperforms fact memorization

The Case for Fine-Tuning

Fine-tuning is the right choice when:

  • Format reliability is mission-critical: You need 99.9% valid JSON, not 95%. Every failure is a parsing error in production.
  • Prompt cost is unsustainable: Long system prompts with many few-shot examples can add 500–2000 tokens per call. At 10M calls/day, that's millions in extra token costs.
  • Latency from context length is a constraint: Shorter prompts → lower TTFT and per-token latency. A fine-tuned model needs no few-shot examples in the prompt.
  • The behavior can't be expressed in a prompt: Nuanced domain-specific judgment (e.g., "flag claims where the attribution is ambiguous per our editorial standards") is hard to specify exhaustively.
  • Serving cost reduction: Fine-tuning a 7B model on a task where you'd otherwise use GPT-4 can cut inference cost by 50–100x.

Cost Realities

Fine-tuning is expensive — not just in compute, but in data preparation, iteration cycles, and evaluation. A realistic breakdown for a production LoRA fine-tune on 7–13B model:

  • Data: 500–10,000 high-quality examples minimum. At $2–5 per example with expert annotation, that's $1,000–$50,000 before touching a GPU.
  • Compute: LoRA on a 7B model for 1–3 epochs: $30–200 on 1x A100 via cloud. Full fine-tune on 13B: $500–2,000. Fine-tuning a 70B model: $5,000–20,000+.
  • Evaluation: Building a proper eval harness (not vibes-based) takes 1–2 weeks of engineering.
  • Maintenance: Every major base model version requires re-fine-tuning. Plan for quarterly cycles.

OpenAI's fine-tuning API prices GPT-3.5 at $0.008/1K tokens for training. Fine-tuning 100K examples of average length ~200 tokens = ~$160 — but this doesn't include the data pipeline cost which typically dominates.

The 80/20 trap: Teams often invest weeks fine-tuning to go from 80% to 85% accuracy on a task that 3 days of prompt engineering already brings to 78%. The marginal cost per percentage point rises sharply in the fine-tuning regime.

When Fine-Tuning Fails

Fine-tuning will not save you if:

  • The base model fundamentally lacks the reasoning capability (e.g., fine-tuning a 7B model for PhD-level theorem proving)
  • Your dataset has label noise or inconsistency (the model learns the noise)
  • You're trying to inject facts that may change (use RAG instead)
  • You only have <100 examples (overfitting is near-certain; use few-shot prompting)

Key Takeaways

  • Exhaust prompting before fine-tuning. GPT-4-class models with 5–10 curated few-shot examples in-context often reach 80–90% of fine-tuned quality. The iteration speed of prompting (minutes) vs fine-tuning (days) makes this the right first move every time.
  • Fine-tuning changes behavior, not knowledge. Use RAG for "the model needs to know X" and fine-tuning for "the model needs to reliably do X." Mixing them up wastes GPU hours and builds hallucination-prone pipelines.
  • Data cost dominates compute cost. 1,000 high-quality expert-labeled examples at $5/example = $5,000. The A100 hour costs are often 10–20% of that. Invest in data quality, not just quantity — 500 clean examples outperform 5,000 noisy ones.
  • Prompt cost is the hidden fine-tuning ROI driver. If your system prompt + few-shot examples add 800 tokens per call at 50M calls/month, that's 40B extra tokens — worth tens of thousands of dollars. Fine-tuning the few-shot examples away pays for itself in weeks at scale.
  • The capability gap test: If the model cannot demonstrate the target behavior even with examples in context, fine-tuning won't fix it. Fine-tuning amplifies latent capabilities; it doesn't create new ones. Test with in-context examples first.
  • Maintenance debt is real. Every base model update potentially breaks your fine-tune. Teams running fine-tuned models in production budget 1–2 weeks per quarter for re-evaluation and potential re-training as providers ship new base model versions (Llama 3.1 → 3.2 → 3.3, GPT-3.5 → 4o-mini, etc.).
