Agent Observability

Tracing, monitoring, and debugging multi-step agent runs — why console.log doesn't scale past 5 steps, the three pillars of observability, and the tools and metrics that matter in production.

Theory

Agent observability is more than LLM monitoring. A standard LLM call is a single request-response pair — you log the prompt, the completion, and the latency, and you're done. An agent run spans multiple LLM calls, multiple tool invocations, and a branching decision tree where each step's output becomes the next step's input. When a 20-step agent run fails on step 17 because of a hallucinated tool argument injected at step 9 and a truncated observation at step 13, you cannot debug that with unstructured logs. You need purpose-built observability infrastructure.

Why Agent Observability Is Hard

Three properties make agents uniquely hard to observe, compared to either traditional microservices or single-turn LLMs:

  • Non-determinism: The same prompt produces different outputs across calls. Two runs of the same agent on the same task can take different paths — different tool calls, different reasoning traces — and both succeed. This means comparing runs requires semantic comparison, not just diffing outputs.
  • Long-horizon cascading failures: A small error early in a run (bad retrieval result, slightly wrong tool argument) can cascade across subsequent steps. By the time the agent produces a wrong final answer, the root cause is 10 steps back. Without a trace of every intermediate state, debugging is guesswork.
  • External tool unreliability: Unlike an LLM inference which fails deterministically (timeout, rate limit, bad request), tool calls fail in non-deterministic ways — API flakiness, empty search results, permission errors, malformed responses. The agent's ability to recover from these failures is part of what you need to measure, not just log.
The console.log trap: Many teams start by logging agent steps with print statements or unstructured JSON blobs. This works for 3–5 step demos. At 20+ steps in production, you have hundreds of log lines per run, no way to correlate across steps, and no way to search for "all runs where the web_search tool returned empty results." Structured tracing with trace IDs is not optional — it's the difference between a 5-minute investigation and a multi-hour firefight.

The Three Pillars of Observability

Borrowed from distributed systems observability but adapted for agent workloads:

🔍
Tracing (Per-Run)

Capture the full execution graph of a single agent run: every LLM call, tool invocation, and intermediate reasoning step. Assign a unique trace_id per run. This is what you use to debug "why did this specific run fail?"

📊
Monitoring (Aggregate)

Roll up traces into aggregate metrics: p50/p95/p99 latency, tool success rate, token cost per run, step count distribution, error rate by tool type. This is what tells you "something changed after the last deploy" before users notice.

🧪
Evaluation (Offline)

Run the same agent against a fixed benchmark repeatedly, capturing traces to compare performance across model versions, prompt changes, or tool configuration tweaks. This is regression testing for agents — does the new prompt improve accuracy without increasing cost?

What to Trace — The Minimum Viable Span

Every agent run should emit structured spans at these granularities. At minimum, each span carries a trace_id, span_id, parent span_id, timestamp, and duration:

Span Type Key Fields Why It Matters
LLM Call model, prompt (or hash), response, input_tokens, output_tokens, latency_ms, finish_reason Token cost attribution and model performance regression detection. A sudden increase in average tokens per call signals prompt drift or a model routing issue.
Tool Invocation tool_name, args, result (truncated), error, duration_ms, retry_count Tool failure rate is the leading indicator of agent reliability. Track per-tool error rates separately — a 2% failure rate on web_search and a 30% rate on sql_query require different responses.
Agent Turn step_index, phase (plan/act/observe), action, reasoning_summary Step count is a leading cost indicator. A prompt change that adds 3 extra reasoning steps per run increases cost by 30%+ — you need per-step visibility to catch this.
Session trace_id, user_id, total_steps, total_tokens, total_cost, final_status (success/timeout/error/user_abort) Session-level aggregates power business metrics: cost per user, success rate per task type, average time-to-completion.

Key Metrics to Track

What you measure determines what you optimize. The following metrics should be on any production agent dashboard:

  • Time-to-completion (TTC): Wall-clock time from user input to final answer. Break down into LLM time vs. tool execution time — they have different scaling properties. Tool parallelism is the primary lever for reducing TTC.
  • Token cost per run: Sum of input + output tokens across all LLM calls in a run multiplied by model pricing. At a frontier model prices ($5/1M input, $15/1M output), a 10-step agent averaging 2K input + 500 output tokens per call costs roughly $0.13/run in input + $0.075/run in output = ~$0.20/run. At 50K runs/day this is $10K/day.
  • Tool call success rate: Percentage of tool invocations that return successfully (no error, non-empty result where expected). A rapid decline in a specific tool's success rate usually means an upstream API change or rate limiting.
  • Step count distribution: Histogram of steps per run. A long tail of runs requiring many steps often signals poor planning or ambiguous instructions — the agent keeps trying things that don't work. Cap it with a max_steps, but monitor how often you hit the cap.
  • User intervention rate: Percentage of runs where the user interrupts, asks for clarification, or rejects the agent's action. This is your best real-time signal for agent quality — lower is almost always better (except in high-stakes domains where confirmations are designed-in).

Tools and Ecosystem

The agent observability tooling ecosystem has matured rapidly. The major players:

  • LangSmith (LangChain): The most mature agent-specific tracing platform. Captures full traces with LLM calls, tool invocations, and chain steps automatically when using LangChain/LangGraph. Supports dataset creation from production traces for offline evaluation. Free tier for development; paid at scale.
  • Langfuse: Open-source alternative to LangSmith. Self-hostable, with a managed cloud option. Supports OpenTelemetry-native ingestion, which makes it easier to integrate with existing observability stacks (Datadog, Grafana). Strong on cost analytics — per-user, per-model, per-session cost breakdowns.
  • Phoenix (Arize): Open-source, focused on embedding-based analysis. Useful for RAG-heavy agents because it can visualize embedding drift and retrieval quality over time, not just text-based traces.
  • Weights & Biases: Strong for model-level tracking (training runs, prompt experiments) but increasingly used for agent evaluation pipelines via Weave.
  • OpenTelemetry: The emerging standard for agent span emission. Both Langfuse and LangSmith support OTel ingestion. If you're building custom agent infrastructure (not using a framework), emit OTel spans directly — don't invent a custom format.

Production Patterns

Beyond basic tracing, production-grade observability requires several patterns that go beyond what off-the-shelf tools provide out of the box:

  • Sampling: Not every run needs a full trace. For high-volume agents (100K+ runs/day), trace everything at the session level (cost, status, step count) but only capture full LLM/tool spans for a sample — 100% of errors, 10% of successes, or adaptive sampling based on anomaly scores. Full tracing at scale is cost-prohibitive — storing every token of every run can exceed the cost of running the agent itself.
  • Context window monitoring: Track how close each LLM call is to the model's context limit. If calls routinely approach 90%+ of the context window, older messages are being silently truncated. Emit a warning span when context utilization crosses 80% — this is a leading indicator of "the agent is forgetting things."
  • Cost anomaly detection: A simple moving average of cost per run, with alerting on 2σ deviation. An agent that normally costs $0.20/run suddenly costing $1.50/run usually means a prompt change increased step count, a model routing bug fell back to a more expensive model, or a tool started returning bloated responses.
  • Replay debugging: The gold standard for debugging agent failures. Capture the exact inputs and outputs of every LLM call in a run, serialize them, and build a replayer that can re-execute the agent deterministically by substituting stored LLM responses. This lets you step through a failed run like a debugger — inspecting state at each step, modifying tool results, and re-running to verify fixes. Without this, you're debugging with incomplete information.
  • Prompt versioning in traces: Every LLM call span should include a prompt_template_id or hash. When you change a system prompt between deploys, you need to be able to filter traces by prompt version to compare before/after metrics. Without this, prompt experiments are uninterpretable.
Start simple, add depth as you scale: For a new agent in production, the minimum viable observability is: (1) structured JSON logs with trace_id per run, (2) a dashboard showing run count, error rate, and p95 latency, (3) an alert on error rate > 5%. That's it. Add full span tracing, replay debugging, and cost attribution when you have enough volume to justify the engineering investment. The biggest mistake is overbuilding observability before you know what failure modes actually occur.

Key Takeaways

  • trace_id is the first thing you implement — not the last. Assign a UUID per run, attach it to every log line, span, and error message. Without it, correlating a user complaint ("the agent gave me a wrong answer at 3pm") with internal logs is a manual grep through thousands of lines. This is table stakes, not a nice-to-have.
  • Tool success rate is your leading health indicator. LLM output quality is hard to measure in real-time. Tool success rate is not — it's a simple count of errors vs. successes. A sudden drop from 98% to 92% on a specific tool is the earliest signal that something changed upstream (API deprecation, rate limiting, schema change) and it alerts you before users notice degraded quality.
  • Context window saturation silently degrades agent behavior. When an LLM call uses 85%+ of the context window, older messages are truncated, and the agent loses access to early instructions and observations. This produces subtle failures — not crashes, but wrong answers — that are extremely hard to diagnose without instrumentation. Monitor context utilization on every LLM call span.
  • Sampling full traces is essential at scale — trace everything at the session level, sample at the span level. Storing every token of every LLM call for 100K+ runs/day can cost more than running the agent. Log session-level aggregates (steps, cost, status) for 100% of runs; capture full span traces for 100% of errors and 5–10% of successful runs. Use adaptive sampling based on anomaly score if you have the infra for it.
  • Replay debugging is the only reliable way to fix long-horizon agent failures. A 20-step agent failure where the root cause is at step 9 is unsolvable from aggregate metrics alone. Store the exact prompt and response of every LLM call in a run, build a replayer that substitutes stored responses, and step through the agent like a debugger. Teams that skip this spend 10× longer debugging production incidents.
  • Cost instrumentation must be per-step, not per-run. A prompt change that adds a single extra reasoning step per run increases cost by 10–20%. If you only monitor total cost per run, you won't know which step became more expensive — and you won't know which prompt to fix. Attribute input tokens, output tokens, and model used to every individual LLM call span.
