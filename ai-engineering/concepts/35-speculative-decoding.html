Speculative Decoding

How a small draft model generates candidate tokens that the large target model verifies in parallel — achieving 2–3× speedup without quality loss.

Theory

The Core Bottleneck: Autoregressive Decoding Is Sequential

Standard LLM inference during the decode phase is fundamentally serial. To generate token t+1, the model must first produce token t. This creates a hard dependency chain: even if you throw 1,000 A100s at the problem, you cannot parallelize across the output sequence. Every generated token requires a full forward pass through all transformer layers, which — for large models — is expensive in both latency and compute.

The memory bandwidth problem compounds this. For a 70B-parameter model in FP16, the weights alone occupy ~140 GB. Each forward pass must stream these weights from HBM into the GPU's compute cores. With modern A100s providing ~2 TB/s of HBM bandwidth, a single token takes roughly 70ms to generate. Throughput is dominated by memory bandwidth, not FLOPs. The hardware is memory-bound, not compute-bound.

The Key Insight: Target Model Forward Passes Are Parallelizable

Speculative decoding (Leviathan et al., 2023; Chen et al., 2023, independently) exploits a structural asymmetry: while generating tokens sequentially is expensive, verifying multiple candidate tokens in parallel is cheap. A transformer can evaluate any sequence length in a single forward pass — this is how prefill already works. The question is: can we exploit this property during decoding?

The fundamental insight: Running the target model on a sequence of K+1 tokens takes roughly the same wall-clock time as running it on 1 token, because the bottleneck is weight loading, not flops. So if a fast draft model can propose K plausible tokens, the target model can verify all K in one shot — netting up to K tokens per round trip.

The Algorithm: Draft → Verify → Correct

The full speculative decoding loop has three stages per iteration:

  • Draft phase: A small, fast model (M_draft) generates K candidate tokens autoregressively. This costs K forward passes through a cheap model (e.g., 7B or even 70M parameters).
  • Verify phase: The large target model (M_target) runs a single forward pass on the original context + all K draft tokens simultaneously. This produces K+1 distributions: one per draft token position, plus the next position after all K.
  • Acceptance/correction: Starting from the first draft token, accept or reject each based on a ratio of the target's and draft's probabilities. The acceptance criterion ensures the marginal distribution of accepted tokens exactly matches M_target's distribution — no quality loss.

The Acceptance Sampling Math

For each draft token x_i sampled from the draft distribution q(x|context), compute the acceptance probability:

Accept with probability: min(1, p_target(x_i | context) / q_draft(x_i | context) ) If rejected: resample from adjusted distribution: p'(x) = normalize( max(0, p_target(x) − q_draft(x) ) )

This is a form of rejection sampling. The resulting sequence has the exact same distribution as if the target model had generated each token independently. The acceptance probability for a token is high when the draft model and target model agree — and the speedup is proportional to the average number of tokens accepted per round.

Mean Acceptance Length and Speedup

If the draft model proposes K tokens and each is accepted independently with probability α (the average acceptance rate), the expected number of accepted tokens per round is:

E[accepted tokens] = K · α + 1 (the bonus token from the target's K+1 distribution) Speedup ≈ (K · α + 1) / (K · cost_draft / cost_target + 1)

In practice, a 7B draft model paired with a 70B target achieves ~10× lower draft latency. With K=5 and α=0.8, you get ~4.5 tokens accepted per target forward pass instead of 1 — roughly 3–4× end-to-end throughput improvement. Real-world measurements from Google's work on PaLM showed 2–2.5× speedup; DeepMind's work on Chinchilla reported similar numbers.

Draft Model Selection and Alignment

The draft model must be significantly cheaper than the target while producing distributions that frequently agree with it. Common strategies:

  • Family-matched smaller model: Use the same model family (e.g., Llama-7B as draft for Llama-70B). High agreement because they share architecture and training distribution.
  • Self-speculation: Use early exit layers of the same model as the draft — no separate model needed. Used in Medusa and EAGLE variants.
  • Distilled draft: Fine-tune a small model specifically to match the target's distribution on your domain — maximizes α for domain-specific workloads.
  • Token trees (SpecTree, EAGLE): Instead of a single K-token chain, draft a tree of candidates. The target evaluates all branches in one forward pass and picks the longest accepted prefix.

EAGLE, Medusa, and Modern Variants

Medusa (2023): Adds multiple "head" layers to the base model that predict tokens at positions t+1, t+2, t+3, ... simultaneously from the same hidden state. No separate draft model. Achieves 2–3× speedup on LLaMA-2. Downside: requires fine-tuning the target model to add heads.

EAGLE (2024): The draft model is fed the target model's feature representations (not just token embeddings), making it dramatically better at predicting what the target will generate. Achieves 3–4× speedup — currently state-of-the-art among spec decoding variants.

SpecInfer: Combines speculative decoding with tree-structured speculation and batching, enabling multiple concurrent users to benefit from shared verification forward passes.

Production Constraints and When It Helps

Speculative decoding helps most when: (a) you're latency-bound with small batch sizes (batch=1 to ~8), (b) the draft model is readily available, and (c) prompts produce predictable continuations (low perplexity). It hurts or breaks even when batches are large (the target is already compute-bound, not memory-bound), or the task is highly creative/random (low acceptance rate).

vLLM integrates speculative decoding natively as of v0.3+. TGI from HuggingFace supports it via the speculative_decoding flag. For serving, you need to manage two models in memory simultaneously — the draft model adds memory overhead, but since it's small (7B vs 70B), the overhead is usually acceptable (~10% additional VRAM).

Quality Guarantee

This is speculative decoding's most powerful property: the output distribution is mathematically identical to the target model's distribution. Unlike approximate methods (quantization, pruning, distillation), speculative decoding is lossless. You can verify this empirically by computing token-level acceptance rates across your benchmark — any deviation from 100% marginal agreement indicates an implementation bug.

Key Takeaways

  • Lossless speedup: Unlike quantization or pruning, speculative decoding provides mathematically provable output-distribution equivalence to the target model — verified by rejection sampling math, not empirical approximation.
  • Batch-size cliff: Speedup degrades sharply above batch size ~8. Large batches already saturate GPU compute, making the target forward pass cheap and eliminating the memory-bandwidth bottleneck that speculative decoding exploits. It's primarily a latency optimization, not a throughput optimization.
  • EAGLE > Medusa > vanilla spec decoding in practice: EAGLE achieves 3–4× speedup by feeding the draft model target-model feature vectors (not token embeddings), dramatically increasing acceptance rate α. If you're implementing spec decoding in 2024+, start with EAGLE architecture.
  • Draft-target alignment is the key variable: A draft model from the same family (Llama-7B → Llama-70B) reaches α ≈ 0.7–0.85 on typical tasks. Mismatched families or heavily fine-tuned targets drop α to 0.4–0.5, making speedup marginal. Always measure α on your actual workload before committing.
  • Two models in memory = dual RAM overhead: For a 70B + 7B setup, you're paying ~140 GB + ~14 GB = ~154 GB VRAM. On an 8×A100 node (640 GB), this is manageable. On tighter deployments, self-speculation (Medusa heads, EAGLE with shared weights) avoids the extra memory cost.
  • vLLM, TGI, and SGLang all support it natively: vLLM v0.3+ has --speculative-model; SGLang has built-in EAGLE support. In production, combine speculative decoding with continuous batching carefully — the async accept/reject logic complicates request scheduling.
