The three-phase agent cycle, tool taxonomy, planning vs execution separation, observability, and failure modes that matter in production.

Theory: How Agents Work

What Is an AI Agent?

An AI agent is an LLM embedded in a loop that perceives an environment, plans an action, executes that action through external tools, and folds the result back into its context — repeating until a goal is achieved or a stopping condition is met. This is distinct from a single-turn LLM call: the agent persists across multiple steps, its outputs affect future inputs, and it interacts with the world beyond just token generation.

The canonical loop is a repeating three-phase cycle: Observe → Plan → Act, and then straight back to Observe — the result of every Act is the next Observe. Each iteration the model sees: (1) its original instruction, (2) the history of actions taken so far, (3) the results of those actions, and (4) any new observations. From this context it plans what to do next — or declares the task complete.

Agent Step: s_{t+1} = LLM(system_prompt, goal, history[0..t], observation_t) Action: a_t = tool_call(name, args) | final_answer(text) Observation: o_t = tool_executor(a_t)

The Three Phases

Observe: The agent receives input — initial user message, tool results, environment events, or memory retrievals. This is the only source of grounding. A bad observation (hallucinated tool output, truncated API response, ambiguous error) corrupts all downstream reasoning.

Plan: The model reasons over the observation and emits either a tool call or a final answer. Frameworks like ReAct interleave Reasoning and Acting traces explicitly in the prompt. Chain-of-thought is effectively planning. The quality here depends heavily on: model capability, system prompt clarity, and how well tool schemas are described.

Act: A tool executor dispatches the chosen action. Tools can be: read/write to memory, web search, code execution, API calls, browser control, file I/O. The agent is decoupled from execution — it emits a specification; the harness fulfills it. This separation is architecturally critical for sandboxing, logging, and retry logic.

Then the cycle repeats: the tool result becomes the next observation. There is no fourth phase — what a two-step run and a fifty-step run differ in is how many times these same three phases turn over before the model emits final_answer.

The optional outer loop (reflection / memory write-back): Separately from the core cycle, many harnesses run a reflection pass — summarize the trajectory, write durable facts into a memory store, score the run for later retrieval. This is outside the Observe → Plan → Act cycle, it is optional, and it is not what makes something an agent. Note also that in production this "learning" is usually just in-context accumulation plus a key-value write; true model learning from agent trajectories (e.g., via RL or STaR) is a separate offline training process, and in-context state is ephemeral — lost on session end.

Tool Taxonomy

Tools fall into three categories that matter architecturally:

Knowledge Augmentation
  • Web search (Bing, Google API)
  • RAG retrieval (vector DB)
  • SQL queries
  • Document readers (PDF, HTML)
  • Memory store reads
Capability Extension
  • Code interpreter / REPL
  • Calculator / solver
  • Image generation
  • Speech synthesis
  • Structured data extraction
Write Actions (Risky)
  • Send email / Slack message
  • Write to filesystem / DB
  • Execute shell commands
  • Deploy code, call APIs
  • Browser form submission
Write actions require escalating oversight. A read tool failure is recoverable — you retry. A write tool failure can be irreversible: email sent, DB record modified, money transferred. Production agent harnesses should enforce approval gates or dry-run modes for all write-category tools.

Planning vs Execution Separation

Naive implementations let one LLM call both plan and execute — blurring concerns. Better architectures separate a planner (high-capability model that writes a task decomposition) from executors (cheaper models that fulfill individual subtasks). This is the idea behind LangGraph's supervisor pattern, AutoGen's agent conversations, and CrewAI's role-based delegation. The planner can route tasks based on complexity, choose which executor to delegate to, and synthesize results without being bottlenecked on every tool call.

Multi-agent systems (MAS) extend this: multiple agents with different specializations collaborate via message passing. Key design decisions: synchronous vs asynchronous messaging, shared vs isolated memory, hierarchical vs peer-to-peer topology. OpenAI's Swarm, LangGraph, AutoGen, and CrewAI each make different choices here.

Observability and Failure Modes

Agents are notoriously hard to debug. In production you need to trace:

  • Every LLM call — model, prompt, response, latency, token cost
  • Every tool invocation — tool name, args, result, duration, error
  • Every agent turn — step index, chosen action, reason
  • Session-level metrics — total steps, total tokens, final status (success / timeout / error / human-interrupted)

Tools like LangSmith, Langfuse, and Phoenix (Arize) provide agent-specific tracing. At minimum, assign a trace_id per run and log structured events at every loop iteration. Without this, debugging a 20-step agent failure is a nightmare.

The critical failure modes every senior engineer should know:

Infinite Loop
  • Model keeps calling same tool
  • No stopping condition met
  • Fix: max_steps limit, cycle detection, explicit done-tool
Context Overflow
  • History grows past context limit
  • Oldest observations truncated silently
  • Fix: summarization, memory offload
Tool Hallucination
  • Model invents tool args or names
  • Calls non-existent tools
  • Fix: strict JSON schema validation, function calling APIs
Prompt Injection
  • Tool result contains adversarial instructions
  • Agent overrides its goals
  • Fix: output sandboxing, goal anchoring

Production Reality: Numbers That Matter

Cost. A GPT-4-class agent doing 10 reasoning steps with 5 tool calls each, averaging 2K tokens per LLM call = 100K tokens/run. At $30/1M tokens (input), that's $3/run. A 1000-user/day product = $3,000/day in agent costs alone — before infrastructure. This is why model selection per agent role is critical; many steps can use Claude Haiku or Llama-3-8B at 10–50× lower cost.
Latency. Each LLM call adds 1–5s latency (depending on model and token count). A 10-step agent = 10–50s worst case. Parallelizing independent tool calls (when possible) is the primary latency reduction lever. The ReAct pattern does tool calls sequentially by default; modern frameworks support parallel tool dispatch.
Reliability. In evaluations of production agents (Tau-bench, WebArena, SWE-bench), even frontier models achieve 30–60% task completion on realistic long-horizon tasks. This is far below human baselines (80–95%). Agents fail not just on reasoning but on error recovery — they rarely retry correctly after an unexpected tool error.

Key Takeaways

  • Write tools need approval gates, not just logging. A read-tool failure is retryable; a write-tool failure (email sent, row deleted, payment initiated) is often irreversible. Design confirmation steps and dry-run modes into all write-category tools from day one — retrofitting them after an incident is painful.
  • Cost per agent run compounds rapidly. At 10+ LLM calls per task at GPT-4 prices, a single run costs $1–5. At scale, tiered model routing — frontier model for planning, smaller model for execution — cuts costs by 5–20× with minimal quality degradation. Always instrument cost per step before going to production.
  • Task completion rates on realistic benchmarks hover at 30–60%. Even frontier models on SWE-bench, WebArena, and Tau-bench fall well short of human performance. Agents fail most on error recovery, not on initial reasoning — they don't retry correctly after unexpected tool output. Build retry logic and error normalization at the harness level, not inside prompts.
  • Observability is not optional. You cannot debug a 20-step agent failure without structured traces. Assign trace IDs, log every tool invocation with args/results/latency, and use purpose-built tools like LangSmith or Langfuse. Console.log-based debugging at scale is untenable.
  • Context overflow is the silent killer of long-horizon agents. As the history grows past the context window, early observations silently drop. The agent starts reasoning over an incomplete view without knowing it. Fix: proactively summarize history every N steps, offload to external memory, or use a model with larger context — but don't assume 128K context means you can ignore the problem (it's expensive too).
  • Prompt injection via tool results is a real attack surface. When an agent reads from external sources (web, DB, user-uploaded files), adversarial content can hijack the agent's goal. This is especially dangerous for write-capable agents. Mitigate with goal re-anchoring in the system prompt, output sandboxing, and monitoring for unexpected action patterns.
