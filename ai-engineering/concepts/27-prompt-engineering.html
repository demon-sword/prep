Prompt Engineering Strategies

Zero/few/one-shot prompting, chain-of-thought, system vs user prompts, persona, output format, self-critique — and how to compose them for reliable outputs.

Theory

Prompt engineering is the practice of structuring the text input to an LLM so that it reliably produces the desired output. While it can look like "trying different phrasings," the best engineers treat it as a systems design problem: what information does the model need, in what format, and in what order to minimise the probability mass on unwanted completions?

Why Prompts Matter so Profoundly

LLMs are next-token predictors. The model's behavior at inference time is determined entirely by the input token sequence — there is no other lever except sampling parameters. A 7B-parameter model can outperform a frontier model on a specific task when given a well-designed prompt, or a frontier model can fail spectacularly on a trivial task when the prompt is ambiguous. The prompt is the sole interface between your intent and the model's learned distribution.

The mechanism: every token in the context shifts the attention-weighted representation of downstream tokens. A poorly placed instruction gets "washed out" by subsequent tokens; a precisely placed system instruction sets the prior over the entire distribution that follows. Anthropic's research shows that models like Claude pay heavily disproportionate attention to early tokens in the context — front-loading your task definition matters.

Shot-Based Prompting: Zero, One, Few

Zero-shot prompting relies entirely on the model's pretrained priors. You describe the task and expect the model to generalise. Works well for tasks the model has seen in abundance during pretraining (summarisation, translation, QA). Fails on tasks with ambiguous output schema, unfamiliar domains, or required formats the model has no strong prior for.

One-shot provides a single input/output example that demonstrates the desired format. The model conditions its completion on that one example. Useful when format matters but you can't afford many tokens.

Few-shot provides N examples (typically 3–10). Each example acts as an in-context gradient update — not a real gradient, but an extremely strong conditioning signal. GPT-3's original paper (Brown et al., 2020) demonstrated that few-shot prompting can match fine-tuned models on many benchmarks with zero weight updates. The order of examples matters: models exhibit recency bias, weighting the last example most heavily. Randomly shuffling examples before each call can reduce this effect.

Chain-of-Thought (CoT) Prompting

Wei et al. (2022) showed that appending "Let's think step by step" to a prompt (or demonstrating reasoning in few-shot examples) causes the model to emit a reasoning trace before its final answer. This is not a cognitive trick — it works because the intermediate tokens become part of the input context for subsequent tokens. The model is literally reading its own intermediate reasoning when producing the final answer, which gives it more "compute" to solve the problem.

CoT primarily helps on tasks that decompose: multi-step arithmetic, symbolic reasoning, causal inference. It adds latency and token cost (output tokens at inference are expensive). For classification tasks with single-token outputs, CoT often hurts — it forces the model down a reasoning path that can veer from the answer. Zero-shot CoT ("think step by step") is often as good as few-shot CoT in practice, especially for models above ~100B parameters.

System vs User Prompt Architecture

Modern models (a frontier model, Claude, a modern open-weight model instruction) expose separate system and user message slots. The system prompt is processed with a different positional encoding and typically receives higher implicit weight in the model's attention. It should contain: task definition, persona, output format requirements, constraints, and safety rules. The user message is the per-request variable content.

In production, the system prompt is where you encode your company's brand voice, output schema, and negative examples. Because it's reused across calls, it also benefits from prompt caching (Anthropic, OpenAI both offer this) — the KV cache for system prompt tokens is precomputed and reused, reducing prefill cost by 80–90% on repeated calls. A 4096-token system prompt amortised over thousands of user calls becomes nearly free.

Persona and Role Assignment

Instructing the model to "act as an expert X" works because the model's training data contains an enormous volume of text written by subject matter experts, and role assignment biases the sampling distribution toward that subspace. It is not a trick — it changes which probability mass the model draws from. Effective personas are: specific rather than generic ("senior infrastructure engineer at a Series B SaaS company" vs "expert engineer"), domain-appropriate, and consistent with the task.

Output Format Control

Specifying the exact output format (JSON schema, markdown table, numbered list, specific headers) is one of the highest-ROI prompt changes. Without explicit format instruction, the model samples from a distribution over all formats it has seen — high entropy. With a schema example or explicit format instruction, that entropy collapses. For structured output, providing a JSON schema via the API's response_format parameter (OpenAI, Anthropic) is preferable to asking for JSON in the prompt — it adds a grammar constraint at the decoding layer, guaranteeing valid JSON.

Self-Critique and Iterative Refinement

Self-critique prompts ask the model to evaluate its own output and then improve it. The implementation: generate a draft → prompt the model to identify weaknesses → prompt again to produce a revised version incorporating the critique. This pattern exploits the model's capability gap between generation and evaluation — models are generally better critics than generators. Studies show self-consistency (sampling multiple outputs and taking a majority vote) improves accuracy on reasoning tasks by 5–15% without any fine-tuning.

Production Reality

In production, prompt engineering is never "set and forget." Model providers update models (silent version updates are common — a frontier model-turbo in Jan 2024 behaved differently from Nov 2023). What works for one model generation may regress on the next. Best practice: maintain a prompt test suite with expected outputs, run it against every model update, and pin to a specific model version (e.g. gpt-4-0125-preview) in production until you have validated the successor. Token cost is real — a 2000-token system prompt at a frontier model pricing costs ~$0.04 per 100 calls when not cached, which adds up at scale.

Prompting Anti-Patterns to Avoid

  • Vague task description — "Improve this text" vs "Rewrite this product description to emphasize the speed benefit, in 2 sentences, in a friendly tone"
  • Contradictory instructions — System: "Be concise." User: "Provide a detailed analysis." Model must guess the priority.
  • No negative examples — Models learn from examples of what NOT to do as much as what to do. Include 1–2 bad-output examples labeled as such in few-shot sets.
  • CoT on classification — Adding CoT reasoning before a binary classification answer can cause the model to "argue itself" into the wrong answer.
  • Instruction at the end — Models have a recency bias; the task instruction gets maximum weight when placed after examples, not before them. But the system prompt instruction should still come first — the sandwich structure (instruction → examples → instruction restatement) is a known pattern that helps.

Key Takeaways

  • Few-shot ordering is a silent accuracy killer: recency bias means placing your best/most representative example last in the list. Shuffling examples before each API call reduces positional dependence and variance across calls by 10–20%.
  • Chain-of-Thought is not universally better — it helps on multi-step decomposable tasks (math, logic) but hurts on single-token classification tasks where the reasoning trace can "argue" the model to a wrong answer. Gate CoT behind task type in production.
  • System prompt caching is a major cost lever at scale: a 4000-token cached system prompt costs 90% less per call on Anthropic (cache read vs full prefill pricing). Structure your prompts to maximise the stable prefix and put variable content at the end.
  • Self-consistency (sample K outputs, majority vote) is often cheaper than a larger model: 3× a small fast model calls with majority voting often matches or beats a single a frontier model call on reasoning tasks, at a fraction of the cost. Use it before upgrading model tier.
  • Maintain a regression test suite for your prompts — silent model version updates (common on OpenAI and Anthropic hosted endpoints) can shift output distribution significantly. Pin model versions in production and validate before migrating.
  • Prompt injection is a real attack surface: user-controlled inputs placed inside a system prompt can override instructions. Defense: clearly delimit user content with XML tags or sentinel strings (<user_input>...</user_input>) and run a secondary classifier on the assembled prompt before execution.
