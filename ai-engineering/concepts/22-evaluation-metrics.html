LLM Evaluation Metrics

Exact match, lexical similarity (ROUGE, BLEU, edit distance), semantic similarity (cosine), and LLM-as-judge — with their biases and when to trust each.

Theory

Why Evaluation is Hard for LLMs

Evaluating LLMs is fundamentally different from evaluating classical ML classifiers. A classifier has a ground-truth label — correct or not. An LLM answering "Summarize this article" can produce dozens of valid, high-quality responses. The question is not whether the output matches a stored string but whether it conveys the right information, maintains the right tone, avoids hallucinations, and follows instructions.

This multiplicity of valid outputs forces us to use approximate proxies. Every metric we use is a proxy — some coarser, some finer — and each captures a different facet of quality. Understanding what each metric actually measures and where it breaks down is essential before trusting any evaluation signal in production.

1. Exact Match (EM)

The simplest metric: score = 1 if prediction == reference else 0. Used in extractive QA benchmarks like SQuAD (after normalizing punctuation and casing). Extremely fast to compute, zero ambiguity.

Exact Match
EM = (# predictions that exactly equal reference) / (# total predictions)

EM is appropriate only when answers are short, unambiguous facts — named entities, dates, numbers. It completely fails for free-form generation: "Paris is the capital of France." vs "The French capital is Paris." are semantically identical but score 0 with EM.

2. Edit Distance (Levenshtein)

The minimum number of single-character insertions, deletions, or substitutions needed to transform one string into another. A normalized variant divides by the length of the longer string to produce a [0,1] similarity score.

Normalized Edit Distance
NED(a,b) = 1 − levenshtein(a, b) / max(len(a), len(b))

Edit distance is character-level — it's sensitive to surface changes but can't detect semantic equivalence. It's still useful as a cheap spell-check signal or to catch near-identical outputs.

3. ROUGE (Recall-Oriented Understudy for Gisting Evaluation)

Developed at USC ISI (Lin, 2004) for summarization. ROUGE computes n-gram overlap between a candidate and one or more reference summaries. Three common variants:

  • ROUGE-1: Unigram (word-level) overlap. Recall-oriented — penalizes missing content words.
  • ROUGE-2: Bigram overlap. More sensitive to fluency and phrase ordering than ROUGE-1.
  • ROUGE-L: Longest common subsequence (LCS). Captures in-sequence matches, more flexible than n-gram methods.
ROUGE-N F1
Precision = matched n-grams / candidate n-grams Recall = matched n-grams / reference n-grams F1 = 2 × P × R / (P + R)

ROUGE correlates reasonably well with human judgments on summarization tasks (~0.7 Pearson on DUC datasets) but breaks down for longer, more abstractive summaries, paraphrases, and multilingual settings. It rewards token overlap without understanding meaning. A model that copies verbatim gets high ROUGE; one that rewrites creatively gets penalized.

4. BLEU (Bilingual Evaluation Understudy)

Originally designed for machine translation (Papineni et al., 2002). BLEU computes precision of n-gram matches (1–4 grams) between hypothesis and reference, with a brevity penalty (BP) to punish short outputs.

BLEU
BLEU = BP × exp(Σ wₙ × log pₙ) BP = min(1, exp(1 − r/c)) where r=ref length, c=candidate length wₙ = 1/N (uniform weights, typically N=4)

BLEU correlates with human translation quality at the corpus level but poorly at the sentence level. It assumes translators and summarizers reuse source vocabulary heavily — an assumption that breaks down for LLMs that paraphrase. A well-known BLEU failure mode: two equally correct translations of the same sentence can have BLEU = 0 if they happen to use different valid word choices. BLEU scores below 10 are essentially random noise for single-sentence evaluations.

5. Semantic Similarity (Cosine)

Encode both candidate and reference with a sentence embedding model (e.g., all-MiniLM-L6-v2, text-embedding-3-small, or bge-large-en-v1.5), then compute cosine similarity of the embedding vectors:

Cosine Similarity
cos(a, b) = (a · b) / (‖a‖ × ‖b‖) ∈ [−1, 1] In practice, sentence embeddings cluster in [0.3, 1.0] for English text

Semantic similarity captures paraphrase equivalence that lexical metrics miss entirely. It's model-dependent — the quality of the signal is only as good as your embedding model. Risks: embedding models can be insensitive to negation ("the drug is safe" vs "the drug is not safe" can score ~0.95 semantic similarity on some models) and can miss factual errors that sound plausible.

6. LLM-as-Judge

Use a capable LLM (frontier models, or a fine-tuned evaluator) to score outputs on rubrics — accuracy, helpfulness, groundedness, fluency, safety. This approach dramatically reduces the need for expensive human annotation and captures nuances that lexical/embedding metrics miss. RAGAS uses LLM-as-judge for RAG pipeline evaluation (faithfulness, answer relevancy, context precision/recall).

LLM judges are powerful but carry three critical biases:

  • Self-bias: A model tends to prefer outputs that match its own style. a frontier model rates a frontier model outputs higher; Claude rates Claude outputs higher. Use cross-model judging to mitigate.
  • Position bias: When comparing two answers (A vs B), the judge often prefers whichever comes first. Always swap order and average to cancel this out.
  • Verbosity bias: Longer, more verbose answers get rated higher even when the shorter answer is more accurate. Empirically, a frontier model shows ~15–20% preference for verbose answers on factual tasks.
Critical gotcha: LLM judges can be systematically fooled. A model fine-tuned to get high judge scores without being actually better ("reward hacking" via judge proxies) is a real failure mode. Always cross-validate judge scores against human labels on a held-out set before fully trusting them.

7. Metric Selection Framework

No single metric is sufficient. A production evaluation harness typically uses 2–3 metrics at different granularities:

Exact Match
Range: {0, 1}

Use for structured extraction: dates, entity spans, classification labels. Fails for any free-form generation.

ROUGE-L / ROUGE-2
Range: [0, 1]

Use for summarization with fixed references. Reasonable human correlation for extractive tasks. Fails for abstractive / paraphrase-heavy outputs.

BLEU
Range: [0, 100]

Use for translation with multiple references. Corpus-level only — single-sentence BLEU is noisy. Penalizes valid paraphrases.

Semantic Similarity
Range: [0, 1] (practical)

Use when surface form varies but meaning should be preserved. Model-dependent. Poor at detecting factual errors that sound plausible.

LLM-as-Judge
Range: [1, 5] or [0, 1]

Best for complex, multi-dimensional quality (instruction following, groundedness, coherence). Expensive. Requires bias mitigation and human calibration.

Production stack: Start with cheap lexical metrics for CI regression detection. Add semantic similarity for paraphrase tolerance. Add LLM-as-judge for nuanced quality signals. Budget $0.01–$0.10 per LLM judge evaluation — compare to human annotation at $0.50–$5.00 per sample.

Key Takeaways

  • ⚠️ No single metric is sufficient. Lexical metrics (ROUGE, BLEU) punish valid paraphrases; semantic metrics miss factual errors; LLM judges carry systematic biases. Production harnesses stack 2–3 metrics at different granularities and calibrate against human labels.
  • 📉 BLEU below 10 is noise at sentence level. BLEU was designed for corpus-level MT evaluation with multiple human references. Using single-sentence BLEU on LLM outputs often produces misleading signals — two correct paraphrases can both score 0.
  • 🤖 LLM-as-judge requires bias controls. Always: (1) swap A/B order and average, (2) use cross-model judging not same-model, (3) validate judge–human correlation on a 200+ sample holdout before deploying. RAGAS provides a ready framework for RAG evaluation using these principles.
  • 🧲 Semantic similarity is blind to negation. Embedding models like MiniLM can assign cosine similarity >0.9 to "the treatment is effective" vs "the treatment is not effective". Never use semantic similarity alone for factual or medical/legal correctness checks.
  • 💰 Cost hierarchy matters. Exact match and ROUGE cost ~$0/1k evals. Semantic similarity via API costs ~$0.001/eval. LLM-as-judge via a frontier model costs ~$0.01–$0.05/eval. Human annotation costs $0.50–$5.00/eval. Design your evaluation pipeline as a funnel — cheap filters first, expensive judges on hard cases only.
  • 🎯 ROUGE-L outperforms ROUGE-1/2 for abstractive summaries. LCS-based matching is more robust to paraphrase than n-gram counting. For multi-document summarization, use multi-reference ROUGE to reduce variance — single-reference ROUGE has very high variance on creative tasks.
