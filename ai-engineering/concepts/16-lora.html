LoRA — Low-Rank Adaptation

Freeze original weights, inject trainable low-rank matrices A and B — adapt large models with ~0.1% of parameters and no inference latency penalty when merged.

Theory

The Core Problem: Full Fine-Tuning is Expensive

Fine-tuning a 7B parameter model in full precision (fp32) requires storing the model weights (~28 GB), their gradients (~28 GB), and optimizer states for Adam (~56 GB for first and second moments) — totaling ~112 GB of GPU memory before activations. At 13B parameters, you're looking at ~208 GB, which exceeds even the largest single-GPU configurations. Even with bf16 training cutting that in half, full fine-tuning a 70B model requires 4–8 × A100-80GB GPUs. The community needed a smarter approach.

Parameter-efficient fine-tuning (PEFT) methods emerged to solve this. LoRA (Low-Rank Adaptation of Large Language Models, Hu et al. 2021) became the dominant approach. The key insight: the updates to weight matrices during fine-tuning have low intrinsic rank. You don't need to update all 175 billion parameters — you can approximate the weight delta with two small matrices.

The Mathematical Mechanism

Consider a pre-trained weight matrix W₀ ∈ ℝ^(d×k) (e.g., a query projection matrix in an attention layer, where d might be 4096 and k might be 4096 for a large model). In full fine-tuning, the update is:

W' = W₀ + ΔW

LoRA constrains ΔW to be a low-rank decomposition:

ΔW = B · A where A ∈ ℝ^(r×k), B ∈ ℝ^(d×r), r ≪ min(d,k)

During training, W₀ is frozen — its gradients are never computed and optimizer states are never stored for it. Only A and B are updated. At initialization: A is initialized with random Gaussian values, and B is initialized to zero — this ensures ΔW = BA = 0 at the start of training, so fine-tuning begins from exactly the pretrained model's behavior.

The forward pass computes:

h = W₀x + (B · A · x) · (α / r)

Where α is a scaling hyperparameter (often set equal to r). The α/r scaling factor normalizes the contribution of the LoRA delta — as you increase rank, the delta magnitude would otherwise grow, destabilizing training.

Parameter Count Reduction

For a single weight matrix of shape d × k = 4096 × 4096:

  • Full fine-tuning: 4096 × 4096 = 16,777,216 parameters
  • LoRA r=4: (4096×4) + (4×4096) = 16,384 + 16,384 = 32,768 parameters — 99.8% reduction
  • LoRA r=16: 131,072 parameters — 99.2% reduction
  • LoRA r=64: 524,288 parameters — 96.9% reduction

In practice, LoRA is applied to multiple weight matrices — typically the Q, K, V, and output projections in attention, and sometimes the FFN layers too. Even applying LoRA to all Q and V matrices across all 32 layers of a 7B model at rank 8, the trainable parameter count is typically under 10 million — roughly 0.14% of total parameters. This is enough to substantially shift the model's behavior on a target task.

Rank Selection

Rank is the most important LoRA hyperparameter. The original LoRA paper found that surprisingly low ranks (r=4 or r=8) work well for most tasks. Intuition: the space of task-relevant updates is low-dimensional compared to the full weight space. However, rank sensitivity is task-dependent:

  • r=4–8: Adequate for style/format adaptation, simple instruction following. Memory optimal.
  • r=16–32: Better for domain knowledge injection, complex reasoning tasks.
  • r=64–128: Approaches full fine-tuning quality at specific tasks, used in QLoRA experiments for high-quality model merging.
  • r ≥ 256: Rarely justified — at some point you're almost doing full fine-tuning with extra overhead.

The paper showed that increasing rank beyond a task-specific threshold yields diminishing returns. You can empirically determine the "intrinsic rank" needed by training at multiple ranks and measuring validation loss plateau.

Which Matrices to Adapt

The original paper experiments found that applying LoRA to Q and V matrices (query and value projections in attention) gives the best parameter-efficiency tradeoff. Later work showed that including K (key), the output projection, and FFN layers helps for complex adaptation tasks. Modern practice:

  • Minimal: Q, V projections only (original LoRA default)
  • Standard: Q, K, V, O (all attention projections)
  • Aggressive: All attention + FFN gate/up/down projections (most common in production tuning today)

Embedding layers and LM head are typically excluded — modifying these can destabilize tokenization behavior.

Merging Adapters at Inference

LoRA's critical production advantage: the adapter can be merged into the base weights before serving. Since W' = W₀ + B·A, you can precompute this sum once, discard A and B, and serve exactly as if you had a fine-tuned model — with zero inference latency overhead. This is unlike adapter-based methods that require extra forward pass computations.

Key insight: LoRA adapters add zero inference latency when merged. During serving, the merged model is identical in computation to the base model — the only difference is the weights. This is what makes LoRA production-viable, unlike approaches that keep adapters separate at inference time.

You can also keep adapters separate (PEFT "hot-swap" mode) — useful when serving one base model with many per-tenant LoRA adapters, loading/unloading them per request. vLLM's LoRA serving support allows multiple adapters to be loaded simultaneously with minimal overhead.

QLoRA: Quantized LoRA

QLoRA (Dettmers et al. 2023) extends LoRA by quantizing the frozen base model to 4-bit (using NF4 — Normal Float 4, a quantization format optimized for normally-distributed neural network weights). Only the LoRA matrices are kept in bf16/fp16 for training.

This enables fine-tuning a 70B model on a single A100-80GB GPU, or a 7B model on consumer GPUs (RTX 3090/4090 with 24 GB VRAM). The compute path: for each forward pass, the 4-bit weights are dequantized block-by-block using stored quantization constants (double quantization further compresses these constants). The LoRA delta is computed in higher precision and added. Memory breakdown for a 7B model with QLoRA:

  • Base model (NF4): ~4 GB
  • LoRA adapters (bf16, r=16): ~120 MB
  • Optimizer states (AdamW on LoRA params only): ~240 MB
  • Activations + working memory: ~6–10 GB depending on sequence length
  • Total: ~12–16 GB — fits on a 16 GB or 24 GB consumer GPU

QLoRA typically achieves 95–99% of full fine-tuning quality on downstream tasks, making it the dominant technique for compute-constrained fine-tuning.

Production Reality

The Hugging Face PEFT library is the standard LoRA tooling. A minimal training setup requires fewer than 30 lines of code to configure LoRA on any supported model. Key production considerations:

Gotcha — merging precision: Always merge LoRA adapters in fp32 or bf16, not in the quantized base model format. Merging into a quantized model introduces quantization error in the delta, degrading quality. Dequantize → merge → requantize if you need a quantized merged model.
  • Multi-adapter serving (vLLM): vLLM supports loading dozens of LoRA adapters per instance with ~2% memory overhead per adapter at r=16. Requests are batched by adapter when possible.
  • LoRA + FSDP: For multi-GPU training with base model sharded across GPUs, LoRA adapters must be handled carefully — FSDP doesn't automatically shard them. Use `FullStateDictConfig` for saving.
  • Catastrophic forgetting: LoRA fine-tuning still suffers from forgetting. If you want to preserve general capability, include a replay buffer of general-purpose examples in your training data (typically 5–10% of the batch).
  • Rank-1 updates (LoRA-One): Research continues showing that even r=1 can be surprisingly effective for narrow task adaptation — worth experimenting before defaulting to r=16.

Key Takeaways

  • Parameter efficiency is extreme but task-sensitive: LoRA at r=8 trains ~0.1–0.5% of parameters yet captures most of the fine-tuning signal. However, for complex domain adaptation (e.g., fine-tuning for medicine or law), r=16–64 is often needed. Start low, validate on eval set, increase rank only if you hit a quality ceiling.
  • QLoRA is the production standard for resource-constrained training: NF4 quantization of the base model + bf16 LoRA adapters enables fine-tuning 7B models on 16 GB VRAM. The key cost: ~15–30% slower training vs fp16 due to dequantization overhead in the forward pass. Worth it for the memory savings.
  • Merge before serving, always: Keeping adapters unmerged costs 2 matrix multiplications per adapted layer per token. At 32 layers with 4 adapted matrices each, that's 256 extra matmuls per forward pass. Merge into base weights before deployment unless you need hot-swap multi-tenant adapter serving (where vLLM LoRA mode is designed for exactly this).
  • LoRA doesn't eliminate forgetting — it mitigates memory cost: A LoRA-fine-tuned model still forgets base capabilities if your fine-tuning data is too narrow or the rank too high. Including ~5–10% general-purpose data in the training mix significantly reduces catastrophic forgetting without meaningfully degrading task-specific performance.
  • Alpha/rank ratio governs effective learning rate: The α/r scaling factor is a hidden learning rate multiplier on the LoRA delta. Common practice is α = r (ratio = 1.0), but some recipes use α = 2r to amplify the adapter contribution. If training is unstable, check this ratio before blaming other hyperparameters.
  • LoRA composability is powerful: Multiple LoRA adapters can be linearly interpolated or summed (e.g., task adapter + style adapter). This enables model merging without retraining, a technique used to create Frankenstein-models on HuggingFace that combine specialized capabilities. However, interference between adapters trained on dissimilar tasks can degrade performance — validate merged adapters empirically.
