Production LLM Serving

The decode bottleneck and the three pillars that solve it — PagedAttention, continuous batching, and Flash Attention — converging in vLLM, TGI, and TensorRT-LLM into a unified serving stack.

Theory

The Decode Bottleneck: Memory-Bandwidth-Bound at Batch=1

Autoregressive decoding is fundamentally serial. To generate token t+1, the model must first produce token t. For a single request, each token requires loading all model weights from HBM (High Bandwidth Memory) into the GPU's compute cores. A 70B model in FP16 occupies ~140 GB — every single token generated streams this full weight matrix through the memory bus. With an A100 delivering ~2 TB/s of HBM bandwidth, each token takes roughly 70 ms to generate. The GPU's compute units sit idle while waiting for memory — this is the memory-bandwidth-bound regime, where throughput is determined by how fast you can move data, not how fast you can compute.

The naive approach to serving multiple users is embarrassingly wasteful: run each request sequentially, or spin up multiple model replicas each serving one request. A single A100 can only produce ~14 tokens/second at batch size 1 — costing thousands of dollars in idle compute per month. The solution requires three innovations that work together: making batching dynamic (continuous batching), eliminating memory fragmentation (PagedAttention), and speeding up the attention computation itself (Flash Attention).

Continuous Batching: Iteration-Level Scheduling

Static batching — where all requests in a batch must start and finish together — wastes enormous GPU time. In a batch of 32 requests, if Request #3 finishes at step 50 while Request #27 keeps generating until step 2048, the GPU slot for Request #3 sits empty for 1,998 useless decode steps. Multiply this across thousands of requests, and you lose over 50% of GPU capacity to padding.

The core insight of continuous batching: At every decode iteration, eject any requests that have finished (EOS token or max_tokens reached) and immediately insert new pending requests. Scheduling decision happens per iteration, not per batch lifetime. The batch composition evolves continuously as requests complete and new ones arrive.

Continuous batching transforms LLM serving from a batch-size scheduler into an iteration-level scheduler. This single change increases GPU utilization from 45-55% to 85-95%+ for high-volume production workloads. Orca (OSDI 2022) first introduced the idea; vLLM, TGI, and TensorRT-LLM all implement it today.

The math: with static batching, throughput T ≈ B / max(L_i / t), where B is batch size and L_i are individual decode lengths. The longest request dominates. With continuous batching, T ≈ B_avg / (L_avg / t), where B_avg stays near the max batch size because slots are refilled instantly. The throughput gain is roughly max(L_i) / avg(L_i) — often 3-5× in practice.

PagedAttention: Virtual Memory for the KV Cache

The KV cache is the single largest memory consumer during inference. For a 70B model with 2048 context serving 32 concurrent requests, the KV cache alone requires ~280 GB of memory — double the model weights. In a naive contiguous allocation scheme, each request reserves a KV cache block sized for its maximum possible context length (16K or 32K tokens), even if the actual context is only 1K tokens. This fragmentation wastes 60-80% of KV cache memory.

PagedAttention (Kwon et al., SOSP 2023) applies the OS virtual memory principle to the KV cache. Instead of allocating one huge contiguous block per request, the KV cache is divided into fixed-size pages (typically 16 tokens each). A request only allocates pages as it generates tokens, and different requests can share read-only pages when they share a common prefix (e.g., a long system prompt).

KV cache waste without PagedAttention: waste = sum_over_requests( max_len - actual_len ) * bytes_per_token With PagedAttention: near-zero internal fragmentation. Each request gets exactly the pages it needs — no pre-allocation. Shared prefix pages are stored once and mapped into multiple requests' page tables.

The practical impact is dramatic: PagedAttention reduces KV cache memory waste from 60-80% to under 5%. This lets you serve 2-3× more concurrent requests on the same GPU, or serve longer context lengths without OOM. It is the single biggest differentiator between vLLM's 10-20× throughput advantage over naive HuggingFace inference and competitors. Both TGI and TensorRT-LLM have adopted similar paged KV cache architectures.

Flash Attention: Never Materialize the N×N Matrix

Standard attention computes QK^T to produce an N×N attention matrix, applies softmax, then multiplies by V. This materializes an O(N²) matrix in HBM. For 32K context with 40 attention heads and batch=32, this single matrix is ~5 GB — per layer. A 70B model with 80 layers would generate 400 GB of intermediate attention matrices.

Flash Attention (Dao et al., 2022; Flash Attention 2, 2023; Flash Attention 3, 2024) eliminates this by tiling the computation. It loads small blocks of Q, K, and V into SRAM (on-chip memory, ~20 TB/s bandwidth vs ~2 TB/s for HBM), computes the attention for that tile entirely on-chip, and writes only the final output to HBM. The N×N attention matrix is never materialized.

Standard attention memory: O(N²) per attention head Flash Attention memory: O(N) per attention head Speedup: 2-4× for prefill (long sequences) Modest for decode (N=1 in autoregressive step) Quality: Mathematically identical output to standard attention. Not an approximation — same softmax, same output.

Flash Attention is now the default in PyTorch's torch.nn.functional.scaled_dot_product_attention (SDPA) since PyTorch 2.0, and is used internally by vLLM, TGI, and TensorRT-LLM. It is particularly impactful during the prefill phase, where sequences are long — cutting prefill latency by 2-4× for 8K+ prompts.

How the three pillars compose: Continuous batching maximizes GPU utilization by keeping all slots full. PagedAttention maximizes memory efficiency so you can fit more slots. Flash Attention minimizes per-iteration compute time. Together they create the modern serving stack that makes LLM APIs economically viable at scale.

Production Deployment Patterns

Prefill-decode disaggregation: The prefill phase (processing the prompt) and decode phase (generating tokens) have opposite hardware requirements. Prefill is compute-bound (parallel across sequence), demanding high FLOPs — H100's Transformer Engine excels here. Decode is memory-bandwidth-bound, where memory throughput matters more than raw FLOPs. Prefill-decode disaggregation splits these across separate GPU pools: a prefill pool of H100s handles all incoming prompts with maximum parallelism, then ships KV caches to a larger decode pool of A100s that churns through token generation. This reduces time-to-first-token by 2-5× and improves overall throughput by not letting decode requests block prefill.

Autoscaling on request backlog: Production serving systems should scale based on queue depth, not CPU/GPU utilization. When the pending request queue exceeds a threshold (e.g., 50 requests), spin up additional replicas. vLLM's API server supports this natively with --max-num-seqs and Kubernetes HPA integration via custom metrics. Scale-down should be slower than scale-up to avoid thrashing — a 5-minute cooldown is typical.

Request prioritization and queuing: Not all requests are equal. Implement priority classes: interactive users get high priority (target <500ms latency), batch processing gets low priority. vLLM supports priority-based scheduling via the priority field in the OpenAI-compatible API. Combine with request timeouts and max-token limits to prevent any single request from starving the queue.

Prefix caching in production: When many users share a common system prompt or few-shot examples, PagedAttention's prefix sharing eliminates redundant KV cache computation. vLLM's automatic prefix caching detects matching prefix hashes and reuses cached KV pages. For chatbot APIs where every request shares a 500-token system prompt, this saves ~500 tokens of prefill compute per request — roughly 30-50% prefill latency reduction at scale.

GPU memory fragmentation prevention: Even with PagedAttention, long-running serving instances can suffer from GPU memory fragmentation as allocations and deallocations interleave. Techniques: pre-allocate a fixed number of KV cache blocks at startup; use gpu_memory_utilization parameter (vLLM default 0.90) to reserve headroom; restart instances periodically (e.g., every 24h) as a safety measure; monitor with nvidia-smi for unexpected memory growth patterns.

Key Takeaways

  • Continuous batching is the single highest-leverage optimization for LLM serving. Moving from static batching to iteration-level scheduling increases GPU utilization from 45-55% to 85-95%+ — a 3-5× throughput improvement without any model changes. If you deploy exactly one optimization, make it continuous batching. Both vLLM and TGI implement this out of the box as their default scheduling strategy, so there is no excuse for static batching in 2025.
  • PagedAttention eliminates the KV cache fragmentation problem. Before PagedAttention, KV cache memory waste of 60-80% was normal because each request pre-allocated for worst-case context length. vLLM's page-based allocation (16-token pages, shared prefix pages via copy-on-write) brings waste under 5%, letting you serve 2-3× more concurrent requests. This is not a marginal improvement — it is architectural. Any serving framework without paged KV cache allocation is unsuitable for production workloads above ~100 concurrent requests.
  • Choose your serving framework based on your deployment profile, not raw benchmarks. vLLM is the best general-purpose choice for most teams — easy deployment, excellent community, solid performance. TensorRT-LLM wins on raw throughput (5-15% faster on H100) but requires significant engineering investment (C++ build system, NVIDIA-specific kernels, complex model conversion). TGI is the right choice if you are deeply integrated with HuggingFace (custom tokenizers, constrained generation). SGLang is emerging as the best choice for prefix-heavy workloads via RadixAttention. If you are on a budget or deploying to consumer hardware, llama.cpp with GGUF quantization is unbeatable.
  • Prefill-decode disaggregation is the next frontier. Splitting prefill and decode across separate GPU pools is not just an optimization — it reflects their fundamentally different hardware requirements. Prefill wants high-FLOPs GPUs (H100, B200) for parallel prompt processing; decode wants high-memory-bandwidth GPUs (even A100-80GB works well). This pattern reduces time-to-first-token latency by 2-5× and is being adopted by every major LLM API provider (Anthropic, Together AI, Fireworks). Expect this to become the default deployment architecture for large-scale serving by 2026.
  • Prefix caching delivers massive savings for chatbot and multi-turn workloads. When 80%+ of your requests share a 500-token system prompt or a large few-shot example block, automatic prefix caching (vLLM's enable_prefix_caching=True, SGLang's RadixAttention) eliminates redundant KV cache computation for every shared prefix. In high-volume chatbot deployments (100K+ requests/day), this saves 15-30% of total GPU compute. The savings compound with continuous batching because your decode slots stay filled with non-redundant work.
  • Production serving is not just about throughput — latency, fairness, and robustness matter equally. A 10× throughput server that delivers p99 latency of 15 seconds is worse than a 5× server with p99 of 2 seconds for an interactive chatbot. Implement request-level timeouts, max-token limits, priority classes (interactive vs batch), and queue-depth-based autoscaling. vLLM's --max-num-seqs and request scheduling priorities, combined with Kubernetes HPA on request queue depth, form the minimum viable production setup. Monitor GPU memory fragmentation over multi-day runs and plan for periodic restarts.
