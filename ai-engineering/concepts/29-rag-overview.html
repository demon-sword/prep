RAG: Retrieval-Augmented Generation

Full RAG pipeline: indexing → querying → retrieval → generation. Term-based vs embedding-based vs hybrid retrieval, chunking, query rewriting, and reranking.

Theory

Retrieval-Augmented Generation (RAG) was formalized in the Lewis et al. 2020 paper from Facebook AI, but the core intuition predates it: instead of forcing a language model to memorize all facts in its weights during training, let it look things up at inference time. This separates parametric memory (weights) from non-parametric memory (a retrieval corpus), enabling knowledge updates without retraining.

Why LLMs Need Retrieval

A standard LLM has three fundamental limitations that RAG addresses:

  • Knowledge cutoff: GPT-4's training data ends in early 2024. A RAG system can answer questions about events from this morning.
  • Hallucination on long-tail facts: Models interpolate from training distributions. For niche domain data (your company's internal docs, a specific legal corpus), the model never saw enough signal. RAG grounds the generation in retrieved source material.
  • Context window limits for large knowledge bases: You cannot fit 100,000 documents in a 128K context. RAG retrieves the ~5–20 most relevant chunks — typically 2,000–8,000 tokens — and fits them precisely.

The Full RAG Pipeline

A production RAG system has two distinct phases:

Offline Indexing Phase — runs once (or incrementally on updates):

  1. Document ingestion: Load PDFs, HTML, markdown, databases. Tools: LlamaIndex, LangChain document loaders, Unstructured.io.
  2. Chunking: Split documents into chunks. Typical sizes: 256–1024 tokens. Strategy matters enormously (fixed-size, recursive, semantic, document-structure-aware). Chunk overlap (10–15%) prevents boundary artifacts.
  3. Embedding: Encode each chunk using a dense retrieval model (e.g., text-embedding-3-large at 3072 dims, or bge-large-en-v1.5 at 1024 dims). Cost: ~$0.13 per 1M tokens with OpenAI.
  4. Vector store indexing: Store embeddings + metadata in FAISS, Pinecone, Weaviate, Qdrant, or pgvector. HNSW index gives sub-millisecond ANN retrieval even at 100M vectors.

Online Query Phase — runs per request:

  1. Query understanding: Optionally rewrite the query (HyDE, multi-query expansion) to improve recall.
  2. Retrieval: Fetch top-K candidates using term-based (BM25), semantic (vector ANN), or hybrid search.
  3. Reranking: Apply a cross-encoder reranker (Cohere Rerank, BGE reranker) on the top-K to re-score and cut to top-N (K=100 → N=5).
  4. Context assembly: Format retrieved chunks into the prompt. Include source metadata for citations.
  5. Generation: LLM generates grounded answer. The prompt instructs the model to cite sources and refuse if context is insufficient.

Chunking: The Most Underrated Hyperparameter

Chunking strategy has an outsized impact on RAG quality — often more than the choice of LLM. Key considerations:

  • Fixed-size chunking (e.g., 512 tokens, 10% overlap) is the default but breaks mid-sentence and loses context. Fast to implement.
  • Recursive character splitter (LangChain default): splits on paragraph → sentence → word boundaries in priority order. Much better than fixed-size.
  • Semantic chunking: embed sentences, split where cosine similarity drops sharply. Better boundaries, higher compute.
  • Document-structure-aware: respect markdown headers, HTML structure, PDF sections. Produces the most coherent chunks for structured docs.
  • Small-to-large retrieval: index small chunks for precision, but retrieve parent sections for context. Used in LlamaIndex's SentenceWindowNodeParser.

Advanced RAG Patterns

HyDE (Hypothetical Document Embeddings): Generate a hypothetical answer using the LLM, embed that answer, retrieve documents similar to the hypothetical answer rather than the query. Improves recall when queries are short/ambiguous (Gao et al., 2022).

Self-RAG: The LLM learns when to retrieve (via a retrieval token), critiques retrieved passages (relevant? supported? useful?), and decides whether to use them. Trained with special tokens; achieves better faithfulness than vanilla RAG.

RAPTOR: Build a hierarchical tree of chunk summaries; retrieve at multiple levels of abstraction simultaneously. Better for multi-hop questions requiring synthesis across many documents.

GraphRAG (Microsoft, 2024): Build a knowledge graph over the corpus; retrieve entity neighborhoods and community summaries rather than raw chunks. 2–3× better on global questions ("What are the main themes in this corpus?").

RAG Evaluation: RAGAS and Beyond

RAG introduces its own failure modes that standard LLM metrics miss. The RAGAS framework (Es et al., 2023) decomposes evaluation into:

  • Faithfulness: Does the answer only contain claims supported by the retrieved context? (Measures hallucination on top of retrieval)
  • Answer Relevance: Does the answer address the question? (LLM-as-judge)
  • Context Precision: Of the retrieved chunks, what fraction were actually useful?
  • Context Recall: What fraction of the ground-truth answer is supported by the retrieved context? (Requires ground truth)

Production rule of thumb: Context Precision is more important than K. Retrieving 5 highly relevant chunks beats retrieving 20 chunks where 15 are noise — noise chunks confuse the LLM and inflate latency. Use a reranker to achieve high precision at reasonable recall.

Key Takeaways

  • Chunking strategy often matters more than model choice. A poorly chunked corpus with GPT-4 will underperform a well-chunked corpus with a smaller model. Invest in document-structure-aware splitting, test with RAGAS Context Precision, and use small-to-large retrieval for length-sensitive documents.
  • Hybrid retrieval (BM25 + dense) wins on most benchmarks. BM25 catches exact keyword matches that dense retrieval misses (product codes, names, acronyms); dense retrieval catches paraphrase and semantic intent. Reciprocal Rank Fusion fusion at K=60 is simple and effective — use Elasticsearch or Weaviate's built-in hybrid mode in production.
  • A reranker is the highest ROI retrieval improvement. Retrieve K=100 with ANN (cheap), rerank to N=5 with a cross-encoder (Cohere Rerank API at ~$1/1000 requests, or BGE-reranker-large self-hosted). This dramatically improves Context Precision without rebuilding the index.
  • RAG ≠ no hallucination. LLMs still hallucinate on top of retrieved context — they misread chunks, confabulate details not in the context, or ignore retrieved content entirely. Measure Faithfulness (RAGAS) in addition to answer quality. System prompts like "Only answer based on the provided context; say I don't know if uncertain" reduce but do not eliminate this.
  • Knowledge graph RAG (GraphRAG) for analytical queries; chunk RAG for lookup queries. Flat chunk RAG fails on cross-document synthesis ("What themes appear across all company memos?"). GraphRAG or RAPTOR hierarchical retrieval handle these at the cost of a more complex offline pipeline. Pick based on your query distribution.
  • Embedding model choice has a hard floor. If your domain uses specialized vocabulary (medical, legal, code), a general-purpose embedding model degrades precision significantly. Fine-tune an embedding model on domain pairs (Matryoshka embeddings, MTEB-optimized) or use domain-specific models (MedCPT for biomedical, CodeBERT for code retrieval).
