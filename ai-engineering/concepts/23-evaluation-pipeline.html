Evaluation

Evaluation Pipeline Design

Turn-based vs task-based evaluation, evaluating the evaluator, and designing a full harness that produces reliable, cost-effective signal about your model's behavior.

Theory

Evaluation is the highest-leverage activity in an LLM system. A bad model with good eval catches and fixes regressions. A great model with bad eval ships silent bugs to production. The difference between teams that move fast and teams that thrash is almost always eval pipeline quality — not model capability.

Why evaluation is hard for LLMs

Traditional ML evaluation is straightforward: run held-out test set, compute accuracy or F1, done. LLMs break this for several reasons. First, the output space is vast — there are thousands of valid phrasings of a correct answer, and thousands of invalid-but-plausible phrasings of a wrong one. Second, the objective is often subjective — "helpful, harmless, and honest" cannot be reduced to a single number. Third, evaluation must generalize across tasks that weren't anticipated at training time.

This forces us to think carefully about what we're actually measuring and whether our measurement correlates with the real outcome we care about.

Turn-based vs Task-based Evaluation

There are two fundamental scopes for LLM evaluation:

Turn-based

Evaluate a single model turn in isolation. Metrics like BLEU, ROUGE, cosine similarity, or LLM-as-judge score applied to one (input, output) pair. Fast and cheap — can cover thousands of examples in minutes. Good for regression testing and format adherence. Poor signal for multi-step reasoning, coherence over a conversation, or tool-use accuracy.

Task-based

Evaluate the outcome of a full task: did the agent book the right flight? Did the code pass the unit tests? Did the summarized document preserve all key facts? Requires a concrete, binary-or-ranked success criterion that can be checked programmatically or via human review. Expensive but high-signal — it directly measures what the user actually cares about.

In practice, you need both: turn-based evals for cheap, fast regression coverage (CI/CD), and task-based evals for high-stakes decisions (which model to promote to production).

The 5-Stage Evaluation Workflow

Evaluation isn't a single metric — it's a pipeline with distinct stages, each with different cost-quality tradeoffs:

  • Stage 1 — Filter: Safety checks, format validation, rule-based refusals. Cheap, deterministic. Run on 100% of outputs.
  • Stage 2 — Benchmark: Automated metrics (exact match, code execution, ROUGE) across a curated eval set. 1,000–10,000 examples. Runs in minutes with a scoring function.
  • Stage 3 — Experiment: A/B comparisons, LLM-as-judge scoring, preference tournaments between model versions. Run on representative subsets when you're considering deploying a new checkpoint.
  • Stage 4 — Human: Expert annotation on the hardest cases your automated eval flagged or failed on. Expensive ($50–$500/hour for domain experts), but necessary for calibration and for rare-but-important failure modes.
  • Stage 5 — Monitor: Production feedback loops. Log outputs, sample for quality review, track user thumb-down rates, implicit signals like conversation abandonment. Closes the loop from deployment back to the eval set.

Evaluating the Evaluator

This is the most important and most overlooked part of evaluation design. Your eval pipeline is itself a system that can fail — and a bad evaluator gives you false confidence. There are four properties to verify in your evaluator:

  • Signal quality: Does the evaluator's score correlate with human judgment on the same examples? Compute Spearman/Kendall correlation between evaluator scores and expert human labels on a validation set. A good automated eval should have correlation ≥ 0.7 with human judgment.
  • Metric-outcome correlation: Does scoring better on this metric actually lead to better user outcomes? This requires you to track downstream metrics (retention, task completion, user satisfaction) and see if your eval scores predict them. Many BLEU/ROUGE improvements fail this test.
  • Consistency: Does the evaluator give the same score when the same example is evaluated twice? LLM-as-judge evaluators have 5–15% flip rate on re-evaluation — this noise floor caps how much you can distinguish between close models.
  • Cost: What is the total cost (latency × price × human hours) to run the full eval pipeline? An eval that costs $500/run won't get run before every deployment. Design for runnable eval — cheap enough that teams use it on every PR, not just on model launch days.
The Meta-Evaluation Principle: Every evaluator you deploy should have its own "meta-eval" — a fixed set of human-labeled examples where you know the ground truth, so you can measure evaluator accuracy. Without this, you're flying blind about your blind spots.

LLM-as-Judge: Biases and Mitigations

Using a larger model (GPT-4, Claude Opus) to judge smaller model outputs is now standard practice, but introduces well-documented biases:

  • Self-enhancement bias: GPT-4 rates GPT-4 outputs ~10% higher than equivalent outputs from other models. Always use a different judge than the candidate model.
  • Position bias: In A/B evaluation, the first option shown gets consistently higher ratings regardless of quality. Mitigate with randomized presentation order and symmetrized scoring (score both orderings, average).
  • Verbosity bias: Longer answers are rated higher even when they contain no additional useful information. Use length-normalized scoring or explicitly instruct the judge to penalize padding.
  • Sycophancy: If the judge is given hints about expected answer, it aligns with those hints. Keep the judge blind to which model produced which output.
Practical setup: Use 3–5 judge models and average scores. Log judge disagreements (high variance = uncertain example). On examples where judges disagree by >2 points (on a 1–5 scale), route to human annotation.

Production Reality

At scale, evaluation looks like this: GPT-4 class models cost ~$0.01–0.03 per judgment. A 10,000-example eval set with LLM-as-judge costs $100–300 per run. For teams deploying weekly, that's $5K–15K/year just for eval compute — before human labeler costs. This is why teams invest heavily in:

  • Representative sampling: 500 well-chosen examples beat 10,000 randomly selected ones. Use stratified sampling across task types, difficulty levels, and known failure modes.
  • Automated canaries: 50–100 golden examples with deterministic expected outputs that run on every PR in under 2 minutes. These catch regressions without requiring expensive LLM judges.
  • Tiered evaluation: Run cheap evals on all changes, medium evals on release candidates, expensive evals only on major version changes.
Tools in production: RAGAS (RAG-specific eval), EleutherAI lm-evaluation-harness (benchmark suites), LangSmith / Braintrust (eval tracking), Weights & Biases (experiment logging), Prometheus-Eval (open-weight judge model), MT-Bench and AlpacaEval (conversation quality benchmarks).

Key Takeaways

  • Evaluate the evaluator first. A bad automated judge gives false confidence and masks regressions. Before trusting any metric, measure its Spearman correlation with human judgment — target ≥ 0.7. Log disagreement rates between multiple judges; high variance = low signal.
  • LLM-as-judge has a 5–15% flip rate on re-evaluation. This noise floor means you cannot reliably distinguish two models that differ by less than ~2 points on a 10-point scale. Use at least 200+ examples to have statistical power to detect meaningful differences.
  • Design for runnable eval, not ideal eval. An eval that costs $1,000/run and takes 3 hours won't get used before every deployment. Tiered pipelines: 50 canary examples (2 min, free) on every PR; 500-example automated benchmark on release candidates; full human eval on major versions only.
  • Task-based > turn-based for real decisions. A model can score better on BLEU/ROUGE while being worse on actual task completion. Always have at least one end-to-end task-based eval tied to a production-relevant outcome before making a deployment decision.
  • Position and verbosity bias corrupt A/B evals. Randomize presentation order. Run symmetrized comparisons (A vs B and B vs A). Explicitly penalize verbosity in judge prompts. Blind the judge to model provenance. These mitigations reduce bias by 60–80% in practice.
  • Production monitoring closes the loop. Offline eval is a snapshot. User thumb-down rates, abandonment after model turn, retry rates — these surface failure modes your eval set never imagined.
