KV Cache Management

How the Key-Value cache grows during autoregressive decoding, why it becomes the memory bottleneck at long context, and how PagedAttention, GQA/MQA, and prefix caching manage it.

Theory

1. What Is the KV Cache and Why It Exists

During autoregressive decoding, each new token must attend to all previous tokens in every attention layer. Without caching, you would recompute Key (K) and Value (V) projections for every previous token at every decode step — an O(n^2) compute cost per step that quickly becomes catastrophic. A 2048-token sequence would require recomputing attention over 2048 tokens 2048 times.

The KV cache solves this by storing the computed K and V tensors from all previous decode steps. At step t, you compute K and V only for token t, append them to the cache, and compute attention of token t against the entire cached K/V — reducing per-step complexity from O(n^2) to O(n). This is the single most important systems optimization in LLM inference: it converts a repeated quadratic computation into a linear one, at the cost of memory.

2. The Memory Formula

KV cache bytes = 2 × num_layers × num_kv_heads × head_dim × seq_len × bytes_per_element

Why the factor of 2? Both K and V tensors are cached (Q is not cached — it's computed fresh for each new token).

Concrete example — Llama 3 70B (80 layers, 8 GQA KV heads, 128 head_dim, fp16):
2 × 80 × 8 × 128 × 2 = 327,680 bytes ≈ 320 KB per token
A 4096-token sequence: ~1.3 GB of KV cache per request.
A 128K context request: ~40 GB of KV cache alone — dwarfing model weights for most deployments.

Llama 3 8B (32 layers, 8 GQA, 128 head_dim, fp16):
2 × 32 × 8 × 128 × 2 = 131,072 bytes ≈ 128 KB per token
128K context: ~16 GB KV cache — still more than the model weights (~16 GB).

Without GQA, using standard MHA with 64 heads: the KV cache would be 8x larger — 320 GB for a 128K sequence on Llama 3 70B, completely infeasible on any single GPU.

3. The Fragmentation Problem (Naive Allocation)

The simplest approach pre-allocates KV cache memory for the maximum possible sequence length for every request. If you reserve slots for 128K tokens but most requests generate only 8K tokens, 94% of KV cache memory sits idle. This is a massive waste — imagine malloc'ing 128GB for every web request.

Worse, different requests finish at different times. When a request that reserved a contiguous 128K block finishes mid-sequence, it frees its block — but new requests with different sizes can't always fit in the resulting hole. Over time, the memory becomes fragmented with unusable gaps between active allocations. This is identical to the fragmentation problem that virtual memory solves in operating systems.

4. PagedAttention — vLLM's Virtual Memory for KV Cache

PagedAttention, introduced in vLLM (Kwon et al., 2023), models KV cache management directly on OS virtual memory:

  • Fixed-size pages: KV cache is divided into fixed-size blocks (typically 16 tokens per page). Each page stores K and V for a contiguous chunk of tokens.
  • On-demand allocation: Blocks are allocated only when needed, not pre-reserved for the maximum sequence length.
  • Non-contiguous physical, contiguous logical: Physical blocks can be scattered across GPU memory, but a page table maps them to a logically contiguous sequence for the attention kernel.
  • Shared prefixes: When two requests share the same system prompt or conversation prefix, the KV cache pages for that prefix are identical — PagedAttention enables both requests to reference the same physical pages. This is copy-on-write for LLMs.
  • Near-zero internal fragmentation: The worst-case waste is at most one partially filled page per request (~15 tokens max).

When a request finishes, all its pages return to the free pool instantly. No fragmentation buildup, zero defragmentation overhead. This is why vLLM can serve 10-20x more concurrent requests than naive implementations with the same GPU memory.

5. GQA — Architecture-Level KV Cache Optimization

Grouped Query Attention (GQA) divides query heads into groups that share a single K/V head pair. Instead of each query head having its own K and V (as in standard Multi-Head Attention), G groups of query heads share one K/V pair, reducing the number of K/V heads by a factor of G.

Llama 3 70B uses 64 query heads but only 8 KV heads (G = 8) — an 8x reduction in KV cache size compared to standard MHA. Llama 3 8B and Mistral models use GQA as well. The quality impact: MMLU scores on Llama 2 using GQA vs MHA differ by less than 0.5 percentage points — negligible for most production use cases.

Multi-Query Attention (MQA) takes this to the extreme: all query heads share a single K/V pair. Used in PaLM, Falcon, and older Google models. MQA offers the maximum KV cache reduction but with a slightly larger quality penalty than GQA — especially for tasks requiring fine-grained attention patterns (long-context retrieval, multi-document reasoning).

The tradeoff matrix: MQA gives Nx reduction (where N = num_heads), GQA gives Gx reduction, MHA gives no reduction. Most modern architectures converge on GQA as the sweet spot.

6. Prefix / Prompt Caching

When multiple requests share a common prefix — a long system prompt, a set of few-shot examples, or a document context — the KV cache for that prefix is identical across all requests. Instead of recomputing and storing it separately:

  • vLLM's Automatic Prefix Caching (APC) hashes KV cache pages by their content. When a new request shares a prefix, vLLM detects the hash match and reuses the cached pages — no recomputation, no duplicate storage.
  • Anthropic's Prompt Caching exposes this as a pricing mechanism: cache writes cost 10% of the full price, cache hits cost only 1%. This frames prompt caching as an economic optimization — you pay dramatically less for tokens already cached.
  • Efficiency impact: A 10K-token system prompt shared across 100 concurrent requests requires only one copy of the KV cache (10K tokens' worth) instead of 100 copies. That's a 99% reduction in KV cache memory for the prefix portion and near-zero prefill compute for cached tokens.

7. KV Cache Offloading and Escape Hatches

When even PagedAttention + GQA isn't enough for the desired context length, additional techniques stack:

  • CPU offloading: Swap KV cache pages to CPU RAM when GPU VRAM is full. Each layer swap adds ~50-200 microseconds over NVLink, or ~5-20 ms over PCIe — accumulating to significant latency for models with 80+ layers. Use as a last resort for extremely long contexts.
  • Sliding window attention: Only cache the most recent W tokens (Mistral uses W=4096). Older tokens' K and V are discarded — context beyond the window is lost. Acceptable for streaming/real-time use cases, problematic for long-document QA.
  • KV cache quantization: Store K and V tensors in int8 instead of fp16 — 2x memory reduction. Unlike weight quantization, KV cache quantization must happen dynamically during inference. Techniques like KIVI (2024) quantize per-channel with less than 1% quality degradation. NVIDIA's FP8 KV cache on H100 achieves similar reduction with hardware acceleration.

8. Multi-Turn Conversation Impact

In a chat application, every conversation turn appends tokens to the sequence. A 20-turn conversation with 400-token responses and a 2000-token system prompt:
System prompt: 2,000 tokens
Turns: 20 x (100 user + 400 assistant) = 10,000 tokens
Total KV cache: 12,000 tokens × 320 KB = ~3.8 GB for Llama 3 70B (GQA), or ~30 GB without GQA.

This is why serving systems must budget KV cache memory per user and enforce a max-context limit — an unbounded conversation will eventually exhaust even the best-optimized GPU memory. Some systems evict the oldest turns (LRU eviction of KV cache pages) to make room for new tokens, at the cost of the model "forgetting" earlier parts of the conversation.

Production Reality

vLLM PagedAttention

Open-source. Near-zero fragmentation via fixed-size KV pages. Automatic prefix caching via content hashing. 10-20x throughput vs naive. Default for most production LLM serving.

GQA in Modern LLMs

Llama 3 (all sizes), Mistral, Gemma, Qwen all use GQA with 4-8 KV head groups. Standard MHA is now rare in production models.

Anthropic Prompt Caching

Economic incentive for KV cache reuse: 10% price for cache writes, 1% for hits. Makes long system prompts 10x cheaper when reused across calls.

KIVI Quantized KV Cache

Per-channel int4 K + int8 V quantization with <1% quality loss. 2-4x KV cache reduction without hardware changes. Emerging technique (NeurIPS 2024).

Key Takeaways

  • KV cache is the memory budget killer at long context: A single 128K-context request on Llama 3 70B uses ~40 GB of KV cache alone — more than the model weights (70 GB). Without GQA (standard MHA), that same request would demand ~320 GB of KV cache, completely infeasible on any single GPU. Every decision about context length flows from this formula: 2 x L x Hkv x d x n x bytes.
  • PagedAttention is the virtual-memory solution applied to LLMs: vLLM's key insight is that KV cache management is isomorphic to OS virtual memory — fixed-size pages, on-demand allocation, page tables for logical-to-physical mapping, and copy-on-write prefix sharing. This eliminates fragmentation and enables 10-20x higher concurrent throughput. It is not an incremental optimization; it is a category-defining architectural change.
  • GQA is an architecture-level optimization that pays for itself 8x: Grouped Query Attention reduces KV cache by the ratio of query heads to KV heads (typically 8x) with less than 0.5% quality degradation on standard benchmarks. Every modern production model uses GQA — standard MHA is effectively obsolete for large-scale serving.
  • Prefix caching makes system prompts free (or nearly free): When 100 requests share a 10K-token system prompt, PagedAttention stores it once and serves all 100 from the same physical pages. Anthropic charges 1% for cache hits. This changes the economics of prompt design — you can afford elaborate system prompts, extensive few-shot examples, or long document contexts when they're cached.
  • Quantize the KV cache, not just the weights: Storing K and V in int8 (vs fp16) halves KV cache memory with negligible quality impact (<1% on most evals). KIVI (per-channel int4 K + int8 V) pushes this to 2-4x reduction. FP8 on H100 offers hardware-accelerated quantized KV cache. This is the cheapest way to double your effective context window without changing the model architecture.
  • In the long-context serving stack, GQA + PagedAttention + KV cache quantization + prefix caching compound multiplicatively: GQA gives you 8x baseline reduction. PagedAttention eliminates waste from fragmentation (~2-5x effective). Prefix caching amortizes shared prefixes (up to Nx for N concurrent requests with the same preamble). KV cache quantization gives 2x. Taken together, a workload that would require 320 GB of KV cache per request (MHA, naive allocation) can be served in ~2 GB (GQA, paged, shared, quantized).
