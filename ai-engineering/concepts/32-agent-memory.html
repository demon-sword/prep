Agent Memory Systems

Short-term (in-context) vs long-term (external storage) memory, why memory matters beyond context window, cross-session persistence, and consistency benefits.

Theory

AI agents are only as capable as the information they can recall and reason over. Unlike a stateless LLM call that begins fresh each time, a memory system allows an agent to maintain continuity — tracking what it has done, what the user has told it, and what knowledge it has acquired — across turns, sessions, and even deployments. Understanding memory architectures is essential for building agents that are reliable, personalized, and cost-efficient at scale.

Why Context Window Alone Is Not Enough

Every LLM operates on a fixed-length context window — typically 4K–200K tokens. Early GPT-3 was 4,096 tokens; a frontier model's context extends to 200K; a frontier model supports 1M tokens experimentally. But even a 200K context window has fundamental limits:

  • Cost: Prefilling a full 200K context on every turn costs ~$0.30–$1.00 per request at current API pricing, making it economically prohibitive for persistent agents.
  • Latency: Long prompts have longer time-to-first-token. A 100K token prefill can take 3–15 seconds even on fast hardware.
  • Lost-in-the-middle problem: Empirically (Liu et al., 2023), LLM accuracy degrades significantly for information positioned in the middle of a long context — models attend most reliably to the start and end.
  • Cross-session persistence: Context evaporates when the session ends. A user returning next week appears as a complete stranger without external memory.

External memory systems solve these problems by selectively retrieving only the relevant memories into the context window — maintaining the illusion of perfect recall without burning the full window.

Memory Taxonomy: Four Tiers

Agent memory systems map naturally onto four functional tiers, each with different latency, capacity, and persistence characteristics:

Tier Where Capacity Latency Persists
In-context (working memory) The active prompt 4K–200K tokens 0 ms (already there) Session only
Episodic (short-term) External KV store, conversation DB Millions of turns 1–20 ms Sessions
Semantic (long-term) Vector DB (Pinecone, Weaviate, pgvector) Billions of facts 5–50 ms Indefinite
Procedural (skill memory) Fine-tuned weights, cached tool schemas Model parameters 0 ms (baked in) Permanent

In-Context (Working) Memory

The simplest form: everything in the current prompt. The agent sees all prior conversation turns, tool results, and system instructions. This is the highest fidelity form of memory — the model has full attention over every token. But it's also the most expensive. A naive full-history agent doubles context length with every few turns, leading to quadratic cost growth and eventual truncation.

Gotcha: When context overflows, most frameworks silently truncate the oldest messages. This can cause the agent to "forget" critical setup instructions or user preferences that appeared early in the conversation. Always implement explicit memory management — don't rely on framework defaults.

Episodic Memory: Conversation History Retrieval

Episodic memory stores individual turns or chunks of past conversations in a fast database (Redis, DynamoDB, PostgreSQL). On each new turn, the agent retrieves the N most relevant prior exchanges — by recency, or by semantic similarity to the current query — and injects them into context. This is the approach used by systems like MemGPT (Packer et al., 2023) and LangChain's conversation memory modules.

The retrieval can be:

  • Recency-based: Always inject the last K turns. Simple, effective for conversational continuity. Risk: irrelevant old turns consume context.
  • Semantic retrieval: Embed each turn, retrieve top-K by cosine similarity to the current query. More precise for factual recall across long histories.
  • Summary-based: Periodically compress older turns into a rolling summary (using the LLM itself), then store the summary. Reduces token cost but introduces lossy compression.

Semantic Memory: Knowledge Stores

Semantic memory holds facts, documents, user preferences, and domain knowledge as embeddings in a vector database. This is architecturally identical to the retrieval side of RAG (Retrieval-Augmented Generation), but scoped to the agent's personal or task-specific knowledge base.

Production setups commonly use:

  • Pinecone / Weaviate / Qdrant: Managed vector databases for high-scale deployments. Weaviate supports native hybrid (BM25 + vector) search.
  • pgvector: Vector similarity search inside PostgreSQL — ideal when you already run Postgres and want to avoid a separate vector DB. Supports HNSW and IVF indexing.
  • Chroma / LanceDB: Lightweight local options for development and small-scale deployments.

A key design decision is the memory write policy: when does the agent commit a fact to long-term memory? Options include:

  • Explicit: Only on user instruction ("remember this"). Low write volume, high relevance.
  • Implicit: The agent automatically decides what's worth storing (using an LLM judge). Higher quality but adds latency and cost per turn.
  • Scheduled: Batch summarization and compression at session end — compress the full session into a few key facts before storing.

Procedural Memory: What the Model Already Knows

Procedural memory is implicit — it's the knowledge baked into the model's weights through pretraining and fine-tuning. An agent fine-tuned on a company's internal procedures "knows" those procedures without needing to retrieve them. This is the cheapest form of retrieval (zero latency, zero tokens) but is the hardest to update — changing it requires re-training or LoRA adaptation.

Memory Management Mechanics

Production agent frameworks implement memory management as an explicit policy layer, not as an afterthought. Key operations:

  • Consolidation: Merging near-duplicate memories. Two facts about a user's preference ("prefers Python" and "dislikes JavaScript") should be merged, not stored as 50 separate entries.
  • Decay / eviction: Memories not accessed in N days get demoted or deleted. Prevents unbounded growth and keeps retrieval precision high.
  • Conflict resolution: If a new memory contradicts an old one ("user moved to Berlin" vs. earlier "user lives in NYC"), the agent must update or retire the stale fact — not accumulate contradictions.
  • Privacy scoping: Different users must have isolated memory namespaces. Memory cross-contamination (agent recalling facts from another user's session) is a critical security failure.

Cross-Session Continuity: Why It Matters

The most valuable property of long-term memory is cross-session continuity — the user doesn't have to re-explain context every session. Research from Anthropic's internal deployments and published work on personal AI assistants consistently shows that cross-session memory is the single highest-rated feature for user satisfaction. Practically, this means:

  • User preferences stored once, recalled automatically.
  • Task progress persisted — a coding agent remembers what you were building last week.
  • Relationship history — the agent recalls past decisions and their outcomes, enabling better advice over time.
Production pattern: The OpenAI Assistants API implements a built-in thread model where each thread persists its message history. Memory retrieval is handled by the platform (sliding window). For more control, frameworks like LangGraph expose explicit memory nodes in the agent graph — you write the read/write/consolidation logic yourself, which is more work but gives full control over cost and retrieval strategy.

MemGPT: Self-Managed Memory

MemGPT (Packer et al., 2023) proposed treating an LLM's context window as a CPU register file, with external storage analogous to disk. The LLM itself is given tools to read/write its own memory: core_memory_append, archival_memory_search, conversation_search. The model decides what to remember, what to evict, and what to retrieve. This is compelling architecturally because it keeps memory management within the LLM's reasoning loop — but it also adds tool call overhead on every turn and depends heavily on the model's ability to make good memory decisions.

Consistency and Grounding Benefits

Memory doesn't just help with recall — it improves consistency. An agent with no memory can give contradictory advice in two different sessions. An agent with long-term memory can check its prior recommendations and maintain a coherent stance over time. This is especially important for professional use cases: a legal research agent should not contradict its own prior analysis without explicitly reasoning through the contradiction.

Key Takeaways

  • Context window ≠ memory. Even 200K tokens is too expensive to fill every turn. At $5/M input tokens, a 100K-token prefill costs $0.50 per request — a 1M DAU agent burns $500K/day just on memory. Selective retrieval is not optional; it's economic necessity.
  • The "lost-in-the-middle" problem is real and measured. Liu et al. (2023) showed accuracy drops 20–30% for retrieval tasks when relevant content is in the middle of a 128K context vs. at the start. Prioritize injecting memories at the beginning or end of context, never the middle.
  • Memory write policy determines system quality. Implicit "always-store" policies bloat vector DBs with noise, degrading retrieval precision. Explicit or scheduled consolidation (session-end summaries) keeps the store clean — but requires careful design to avoid lossy compression of critical facts.
  • Conflict resolution is the hardest problem. Unlike databases with atomic updates, LLM memory stores can accumulate contradictory facts silently. Production systems need an explicit conflict detection pass — either an LLM-as-judge at write time, or metadata versioning with timestamp-based precedence.
  • Privacy isolation must be enforced at the infrastructure level. Memory namespace bugs — where one user's agent recalls another user's facts — are catastrophic security failures. Use tenant-namespaced collection IDs in your vector DB, not just soft filtering. Chroma and Qdrant support collection-level isolation; pgvector needs RLS policies.
  • MemGPT-style self-managed memory trades tool-call overhead for flexibility. Every turn that requires memory operations adds 1–3 extra LLM calls. At scale, this can double per-turn cost. Evaluate whether this cost is justified vs. a simpler sliding-window + async summarization approach for your specific workload.
