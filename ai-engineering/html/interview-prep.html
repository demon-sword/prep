🔍 Hard Questions They'll Ask — Know These Cold

"Why persona-based routing instead of one general agent?"
Context window economics. A single agent with 47 tools + all domain context hits limits fast. Personas scope the tool surface — a Design persona doesn't need crash telemetry tools. It also lets you tune prompts per audience: Business Leaders get narrative, Engineering gets numbers, CS gets resolution paths. Routing reduces noise, improves answer quality, and keeps token cost predictable.
"How does the Planner work? What if it routes to the wrong persona?"
The Planner classifies intent + persona from the NL query using a structured prompt. For ambiguous queries that span personas (e.g. "why did conversion drop AND crashes spike?"), we use cross-persona synthesis in the Summary Agent which has access to all domain tools. Wrong routing falls back to the Summary Agent which can call across persona boundaries.
"How did you handle context window limits with 47 tools?"
Category-scoped tool discovery. Tools are registered per domain category, and only the relevant category's tools are exposed to the agent for a given query. This is the core design of pulse-mcp — balancing agent context limits with the full analytics surface. A Design persona query gets ~8 relevant tools, not all 47.
"Walk me through your dual RAG architecture."
Business-events RAG answers what happened — business metric context, event taxonomy, business terminology. Pulse-events RAG answers how users behaved — product analytics events, screen names, funnel steps. They feed the Executor with relevant context before tool calls, reducing hallucination on domain-specific terminology that the LLM wouldn't know natively.
"How did you solve hallucination in production?"
Three layers: (1) Prompt-level — anti-hallucination instructions, explicit "say I don't know if uncertain", no-fabrication ADK eval cases. (2) Output validation — deterministic overrides for safety-critical report fields (metric values pulled directly from DB, not LLM-generated). (3) Eval harness — 65+ Promptfoo cases including faithfulness checks run before every prod rollout to catch regressions.
"What would you do differently?"
Invest earlier in retrieval quality eval (precision@k on the RAG layer) — we caught hallucinations late and traced many back to bad chunk retrieval, not LLM generation. Also: cleaner separation between planner logic and persona definitions to make adding a 6th persona faster. The current tight coupling made the 5th persona (Business Leaders) take longer than it should have.

🧩 Technical Decisions — 1-Line Answers

Why MCP? Standardized tool contracts, composable across Cursor/Claude/ADK without glue code. Schema-first lets teams publish tools without touching core orchestration.
Why Google ADK? Strong tool-calling loop + eval framework built-in. ADK eval sets align directly with no-fabrication cases we needed for safety.
Why Qdrant? Fast ANN search, payload filtering for Confluence doc metadata, easy self-hosting. No managed infra dependency for internal RAG.
Why Promptfoo? Code-native YAML cases, CI-friendly, supports custom LLM judges — lets you ship 65+ eval cases without a separate platform or infra.

1 · RAG Pipeline — Core Skeleton

# Chunk → Embed → Store → Retrieve → Augment → Generate

def build_index(documents, embed_fn, vectordb):
    for doc in documents:
        chunks = chunk(doc, size=512, overlap=64)   # fixed or semantic
        for chunk in chunks:
            embedding = embed_fn(chunk)
            vectordb.upsert(embedding, metadata={"text": chunk})

def rag_query(question, embed_fn, vectordb, llm, k=5):
    # 1. Embed the question
    q_embedding = embed_fn(question)

    # 2. Retrieve top-k chunks by cosine similarity
    chunks = vectordb.similarity_search(q_embedding, k=k)

    # 3. Token-aware context packing
    context = fit_to_context(chunks, max_tokens=3000)

    # 4. Augment prompt
    prompt = f"Use only the context below.\nContext:\n{context}\n\nQuestion: {question}\nAnswer:"

    # 5. Generate
    return llm.generate(prompt)

def fit_to_context(chunks, max_tokens, tokenizer):
    selected, total = [], 0
    for chunk in sorted(chunks, key=lambda x: x.score, reverse=True):
        t = len(tokenizer.encode(chunk.text))
        if total + t > max_tokens: break
        selected.append(chunk.text); total += t
    return "\n\n".join(selected)

Key follow-ups: How do you chunk? (fixed/512 tokens with overlap)  ·  How do you eval? (precision@k for retrieval, faithfulness for generation, RAGAS framework)  ·  BM25 vs dense? (BM25 wins on exact keyword match; dense wins on semantic similarity; hybrid usually best)

2 · LRU Cache

from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int):
        self.cache    = OrderedDict()
        self.capacity = capacity

    def get(self, key) -> int:
        if key not in self.cache:
            return -1
        self.cache.move_to_end(key)   # mark as recently used
        return self.cache[key]

    def put(self, key, value) -> None:
        if key in self.cache:
            self.cache.move_to_end(key)
        self.cache[key] = value
        if len(self.cache) > self.capacity:
            self.cache.popitem(last=False)  # evict least recently used

# O(1) get AND put — both operations. Space O(capacity).

AI framing: caching LLM responses by prompt hash, caching embeddings by text hash, caching tool results by (tool_name, args_hash).

3 · Agent Tool-Calling Loop

def agent_loop(user_query, tools, llm, max_iterations=10):
    messages = [{"role": "user", "content": user_query}]

    for _ in range(max_iterations):
        response = llm.call(messages, tools=list(tools.keys()))

        if response.tool_call:
            tool_name = response.tool_call.name
            tool_args = response.tool_call.args

            # Execute the tool
            result = tools[tool_name](**tool_args)

            # Feed result back into context
            messages.append({"role": "assistant", "content": str(response)})
            messages.append({"role": "tool",      "content": str(result)})

        else:
            return response.text   # final answer — no more tool calls

    return "Max iterations reached — could not complete."

# Key: always add max_iterations guard to prevent infinite loops

Key follow-up: What if loop doesn't terminate? → max_iterations + circuit breaker. How to pick tools dynamically? → category-scoped discovery (your pulse-mcp work).

4 · Edit Distance (Levenshtein)

def edit_distance(s1: str, s2: str) -> int:
    m, n = len(s1), len(s2)
    dp = [[0] * (n + 1) for _ in range(m + 1)]

    for i in range(m + 1): dp[i][0] = i   # delete all chars from s1
    for j in range(n + 1): dp[0][j] = j   # insert all chars to reach s2

    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if s1[i-1] == s2[j-1]:
                dp[i][j] = dp[i-1][j-1]            # no op
            else:
                dp[i][j] = 1 + min(
                    dp[i-1][j],    # delete
                    dp[i][j-1],    # insert
                    dp[i-1][j-1]  # replace
                )
    return dp[m][n]

# Time: O(m*n)  Space: O(m*n), reducible to O(min(m,n)) with rolling array

5 · Top-K Retrieval (Heap)

import heapq

# Get top-k most similar chunks — O(n log k)
def top_k_chunks(query_embedding, chunks, k=5):
    return heapq.nlargest(k, chunks, key=lambda x: cosine_sim(query_embedding, x.embedding))

def cosine_sim(a, b):
    dot   = sum(x*y for x,y in zip(a, b))
    norm_a = sum(x**2 for x in a) ** 0.5
    norm_b = sum(x**2 for x in b) ** 0.5
    return dot / (norm_a * norm_b + 1e-8)  # epsilon prevents div by zero

# nlargest → max-heap internally. nsmallest → min-heap. heappush/heappop is O(log n).

Scenario Q&A — Talk-Through Questions

Often used as a 2nd question or follow-up in the 30-min window
"Your LLM gives confidently wrong answers — how do you debug it?"
Start from the bottom of the pipeline and work up:

1. Check retrieval first — is the right chunk even being fetched? Compute precision@k. If the wrong chunk is retrieved, the LLM never had a chance.
2. Check augmentation — is the context too long and the relevant part getting cut? Is the chunk actually readable in context?
3. Check generation — is the LLM ignoring the context and using its priors? Add explicit "use only the context below, say I don't know if unsure" instructions.
4. Eval harness — add a Promptfoo faithfulness case that flags this exact scenario for future regressions.
"Your agent loop isn't terminating — what's wrong?"
Three common causes:

1. Missing stop condition — LLM keeps calling tools because the final answer prompt isn't clear enough. Fix: explicit "return FINAL_ANSWER: ... when done" instruction.
2. Tool result not fed back — LLM doesn't see its own tool output, so it keeps calling. Fix: always append tool result to message history.
3. No max_iterations guard — no hard stop. Fix: add circuit breaker (10 iterations), return partial answer with "incomplete" flag.

Always add the guard. Never trust the LLM to self-terminate reliably.
"LLM context window fills up on long documents — how do you handle it?"
At ingestion time: chunk documents into overlapping windows (512 tokens, 64 overlap) so no single chunk is too large.
At retrieval time: only pass top-k relevant chunks (not the whole document) — RAG solves the context problem by design.
For conversation history: sliding window over recent turns + summarize older turns into a compressed memory block.
For very long agent contexts: token-aware packing — sort chunks by score, greedily add until budget exhausted.
"LLM doesn't return valid JSON / ignores output format — how do you fix it?"
Layer 1 — Prompt: be explicit. "Return ONLY valid JSON matching this schema: {schema}. No prose before or after."
Layer 2 — Retry loop: try json.loads(), on failure send back "That was invalid JSON. Return only the JSON object." with the error message. Max 3 retries.
Layer 3 — Model features: use JSON mode / structured outputs (OpenAI, Gemini, Claude) which constrain generation to valid JSON at the token level.
Layer 4 — Eval: add a Promptfoo case that fails if output isn't parseable JSON.
"How do you evaluate your RAG pipeline — what metrics do you use?"
Split into two layers:

Retrieval quality: precision@k (are the right chunks in the top-k?), recall@k (did we find all relevant chunks?), MRR (mean reciprocal rank of the first relevant result).
Generation quality: faithfulness (does the answer only use information from the retrieved context?), answer relevance (does it actually answer the question?), context relevance (are the retrieved chunks actually relevant?). RAGAS is the standard framework — uses an LLM judge to score these without human annotation.
Production metrics: user thumbs up/down, deflection rate, p95 latency.
