"I built PulseAI at Dream11 — a multi-agent AI system that lets product, engineering, and UX teams ask 'why did X break?' in natural language and get back a correlated root-cause report across crashes, funnels, and session replays — without touching a dashboard."

Open with that one sentence. Then follow with the full pitch below.

The problem: Our observability stack could tell us that something broke — crash rates, ANRs, funnel drops — but not why. A PM would see payment conversion drop and have to manually chase engineering for crashes, product for funnel data, UX for session replays, and stitch it together themselves.
The architecture: A Planner reads the query + pulls context from an Events RAG (our custom analytics event catalogue) → generates an ordered investigation plan → hands it to an Executor which calls three specialist agents as tools sequentially: EM (crashes, ANRs), Product (funnels, journeys), UX (heatmaps, session replays). Each agent calls curated APIs over ClickHouse — no raw SQL exposed to the LLM. Findings are written to a shared blackboard so each step builds on the last. Finally a Summarizer → Report agent synthesizes everything into graphs and tables in the chatbot UI.
The scale: ~50 APIs across 3 domains. Built and shipped in under a week using Google ADK — which gave us the agent framework, tool-calling loop, and eval harness out of the box. We also had a Google partnership at Dream11 which gave us direct engineering support.

🔍 Hard Questions They'll Ask — Know These Cold

"Why three separate agents instead of one general agent?"
Context window and expertise scoping. A single agent with all ~50 tools would flood the context window and make the LLM's tool selection noisy. By splitting into EM, Product, and UX, each agent only sees the tools relevant to its domain — maybe 15-20 each. It also lets us tune each agent's prompt for its audience: EM agents think in stack traces and ANR rates, Product agents think in funnel steps and conversion deltas. Separation of concerns at the agent level gives cleaner, more accurate answers.
"Why are the agents called sequentially as tools, not in parallel?"
Because the plan is order-dependent. If a user asks "why did payment conversion drop?", the right sequence is: first ask Product when exactly the drop happened, then ask EM whether there were crashes in that time window. If you run them in parallel, EM has no time anchor — it would scan everything and return noise. The Planner deliberately sequences steps so each agent's query is informed by the previous agent's findings on the blackboard. That's the whole point of the blackboard pattern.
"What is the Events RAG and why does it exist?"
Every company has custom analytics events that mean nothing to an LLM out of the box. An event called PAYMENT_INITIATION_TAPPED or CHECKOUT_V2_SCREEN_VIEWED — the LLM has zero context for what those mean. The Events RAG is a Qdrant vector store populated with the customer's event catalogue: event names, descriptions, and properties. The Planner queries it before generating a plan so it understands what events are available and what they mean — which directly determines how accurate the plan is. Without it, the Planner would generate plans referencing events that don't exist.
"What if the Planner generates a bad plan or wrong step order?"
The Planner is the most fragile part of the system — garbage plan in, garbage answer out. The main failure mode is wrong step ordering: asking EM about crashes before asking Product when the drop happened, so the EM query has no time window to anchor to. We mitigated this with explicit Planner instructions: always establish when before asking what, always establish which domain before drilling into sub-metrics. The Events RAG also helps — a Planner that understands the event taxonomy creates much more targeted, correctly ordered plans.
"Why not expose raw ClickHouse queries to the agent?"
Two reasons. Safety — an LLM generating raw SQL over a prod database is a security and cost risk. One bad query could table-scan billions of rows. Accuracy — our ~50 curated APIs encode domain knowledge: the right aggregations, the right filters, the right time-bucketing for each metric. A raw SQL-generating LLM would have to rediscover all of that from scratch and would frequently get it wrong. The APIs are essentially a guardrail layer — the LLM picks the right tool with the right parameters, we handle the query construction.
"How does the blackboard prevent the Report agent from hallucinating numbers?"
The Report agent doesn't generate numbers — it only reads from the blackboard. Every data point on the blackboard came directly from a ClickHouse API response, not from LLM generation. The Report agent's job is purely structural: which metric becomes a chart, which becomes a table, how to narrate the findings. This is an intentional design choice — we kept LLM generation away from the data layer entirely and only let it operate at the presentation and synthesis layer.
"How did you handle the LLM misreading API results?"
By constraining what the LLM is allowed to conclude. The Summarizer's prompt explicitly says: "synthesize only what is present on the blackboard. Do not infer causation unless it was established by a plan step. Say 'the data shows X' not 'X happened because Y' unless the plan explicitly traced that causation." The Events RAG also helps here — when an agent understands what a metric actually means in domain context, it's far less likely to misread a number that looks anomalous but is actually normal for that cohort.
"How did you handle the Qdrant RAG retrieving the wrong event?"
Companies often have similarly named events — PAYMENT_INITIATED vs PAYMENT_INITIATION_SCREEN_VIEWED — that mean very different things. We used metadata filtering in Qdrant: each event is tagged with its domain (payments, login, checkout) and we filter by domain before doing the similarity search. This cuts the retrieval space down and significantly reduces wrong-event retrieval. We also stored the full event description and properties in the payload so the Planner gets enough context to distinguish between similar-sounding events.
"Sequential agents must be slow — how did you handle latency?"
Sequential execution has an inherent cost — N plan steps means N LLM round trips plus N API calls in series. Our mitigation was making the Executor smart about true dependency: if two plan steps are genuinely independent (e.g. "check Product funnels AND check UX heatmaps for the payment screen"), the Executor runs those in parallel. Only steps where one result feeds the next are strictly sequential. In practice, most plans have 2-3 steps, so worst-case latency is bounded and acceptable for an async chatbot interface where the user expects a few seconds for a correlated root-cause answer.
"How do you onboard a new customer?"
Onboarding is essentially an ETL problem. The AI is useless without knowing the customer's custom event vocabulary. So we built an ingestion pipeline: the customer provides their event catalogue — event names, descriptions, properties — we chunk and embed it into Qdrant tagged with their org ID, and every Planner query is scoped to their org's events. The quality of the AI's plans is directly proportional to the quality of the event catalogue they give us — so part of onboarding is working with the customer to ensure their events are well-described.
"What would you do differently?"
Two things. First, invest earlier in retrieval quality eval — precision@k on the Events RAG. A bad event retrieval cascades into a bad plan which cascades into a bad answer, and that's hard to debug at the answer layer. We should have built a retrieval eval harness from day one. Second, the Planner prompt grew complex fast as we added edge cases. I'd refactor it into a more structured planning DSL — essentially a schema for what a valid plan looks like — so the LLM has a tighter output contract and bad plans are caught structurally rather than caught at execution time.

🧩 Technical Decisions — 1-Line Answers

Why Google ADK? Needed to ship in under a week. ADK gave us the agent framework, tool-calling loop, and eval harness out of the box — no glue code. Google partnership at Dream11 also gave us direct engineering support.
Why Qdrant? Fast ANN search with payload filtering — critical for scoping event retrieval by org ID and domain. Easy to self-host, no managed infra dependency for internal RAG.
Why curated APIs over raw SQL? Safety (no LLM-generated queries over prod ClickHouse) + accuracy (APIs encode domain knowledge — right aggregations, right filters, right time bucketing baked in).
Why a blackboard? Sequential agents need shared state. The blackboard lets each step's findings inform the next agent's query — turns 3 blind queries into one correlated investigation.
Why sequential not parallel? Plans are order-dependent — EM needs Product's time window before it can scope its crash query. Parallel execution would make each agent query blind with no anchor.

1 · RAG Pipeline — Core Skeleton

# Chunk → Embed → Store → Retrieve → Augment → Generate

def build_index(documents, embed_fn, vectordb):
    for doc in documents:
        chunks = chunk(doc, size=512, overlap=64)   # fixed or semantic
        for chunk in chunks:
            embedding = embed_fn(chunk)   # numeric vector for similarity search
            # Store BOTH: vector for search + original text as metadata/payload
            # Qdrant: payload={"text": chunk}
            # Pinecone: metadata={"text": chunk}
            # FAISS: separate docs[] array, index by position
            vectordb.upsert(embedding, metadata={"text": chunk})

def rag_query(question, embed_fn, vectordb, llm, k=5):
    # 1. Embed the question
    q_embedding = embed_fn(question)

    # 2. Retrieve top-k chunks by cosine similarity
    # similarity_search returns the original TEXT from metadata/payload, not raw vectors
    chunks = vectordb.similarity_search(q_embedding, k=k)

    # 3. Token-aware context packing
    context = fit_to_context(chunks, max_tokens=3000)

    # 4. Augment prompt
    prompt = f"Use only the context below.\nContext:\n{context}\n\nQuestion: {question}\nAnswer:"

    # 5. Generate
    return llm.generate(prompt)

def fit_to_context(chunks, max_tokens, tokenizer):
    selected, total = [], 0
    for chunk in sorted(chunks, key=lambda x: x.score, reverse=True):
        t = len(tokenizer.encode(chunk.text))
        if total + t > max_tokens: break
        selected.append(chunk.text); total += t
    return "\n\n".join(selected)

Key follow-ups: How do you chunk? (fixed/512 tokens with overlap)  ·  What does similarity_search return? (original text from metadata/payload, not raw vectors — vector DBs store both: embedding for search + text in metadata to return)  ·  How do you eval? (precision@k for retrieval, faithfulness for generation, RAGAS framework)  ·  BM25 vs dense? (BM25 wins on exact keyword match; dense wins on semantic similarity; hybrid usually best)

2 · LRU Cache

from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int):
        self.cache    = OrderedDict()
        self.capacity = capacity

    def get(self, key) -> int:
        if key not in self.cache:
            return -1
        self.cache.move_to_end(key)   # mark as recently used
        return self.cache[key]

    def put(self, key, value) -> None:
        if key in self.cache:
            self.cache.move_to_end(key)
        self.cache[key] = value
        if len(self.cache) > self.capacity:
            self.cache.popitem(last=False)  # evict least recently used

# O(1) get AND put — both operations. Space O(capacity).

AI framing: caching LLM responses by prompt hash, caching embeddings by text hash, caching tool results by (tool_name, args_hash).

3 · Agent Tool-Calling Loop

def agent_loop(user_query, tools, llm, max_iterations=10):
    messages = [{"role": "user", "content": user_query}]

    for _ in range(max_iterations):
        response = llm.call(messages, tools=list(tools.keys()))

        if response.tool_call:
            tool_name = response.tool_call.name
            tool_args = response.tool_call.args

            # Execute the tool
            result = tools[tool_name](**tool_args)

            # Feed result back into context
            messages.append({"role": "assistant", "content": str(response)})
            messages.append({"role": "tool",      "content": str(result)})

        else:
            return response.text   # final answer — no more tool calls

    return "Max iterations reached — could not complete."

# Key: always add max_iterations guard to prevent infinite loops

Key follow-up: What if loop doesn't terminate? → max_iterations + circuit breaker. How to pick tools dynamically? → category-scoped discovery (your pulse-mcp work).

4 · Multilingual RAG (Indic Languages)

# Cross-lingual RAG that works across 22 Indian languages
# Indexing: store embedding (for search) + text (in metadata/payload) per chunk

def multilingual_rag_query(question, embed_fn, docs_db, top_k=5):
    # 1. Embed question using multi-lingual model (MURIL, LaBSE, IndicBERT)
    q_emb = embed_fn.encode(question.strip().lower())

    # 2. Compute cross-lingual cosine similarity against all docs
    scores = []
    for doc in docs_db:
        # docs can be in ANY language — the embedding model aligns them
        sim = cosine_sim(q_emb, doc["embedding"])
        scores.append((sim, doc))

    # 3. Return top-k + script-normalized context packing
    scores.sort(reverse=True)
    return scores[:top_k]

def cosine_sim(a, b):
    dot = sum(x*y for x,y in zip(a, b))
    na  = sum(x**2 for x in a) ** 0.5
    nb  = sum(x**2 for x in b) ** 0.5
    return dot / (na * nb + 1e-8)

# Key: LaBSE/MURIL aligns Hindi-English across the same vector space
# so a Hindi query can retrieve English docs and vice versa.
# Cost: Distill to smaller student model + INT8 quantization for 1B+ users.

Key follow-ups: How to handle code-mix? (NFKC + script detection → segment by script before embedding)  ·  What does query return? (original text from metadata/payload, not raw vectors — stored alongside embedding during indexing)  ·  How to eval without gold sets? (LLM-as-judge, translate-in → judge → translate-out)  ·  Cost at 1B users? (Distill to smaller model, INT8 quant, edge caching on repeated queries, token-aware packing)

5 · Edit Distance (Levenshtein)

def edit_distance(s1: str, s2: str) -> int:
    m, n = len(s1), len(s2)
    dp = [[0] * (n + 1) for _ in range(m + 1)]

    for i in range(m + 1): dp[i][0] = i   # delete all chars from s1
    for j in range(n + 1): dp[0][j] = j   # insert all chars to reach s2

    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if s1[i-1] == s2[j-1]:
                dp[i][j] = dp[i-1][j-1]            # no op
            else:
                dp[i][j] = 1 + min(
                    dp[i-1][j],    # delete
                    dp[i][j-1],    # insert
                    dp[i-1][j-1]  # replace
                )
    return dp[m][n]

# Time: O(m*n)  Space: O(m*n), reducible to O(min(m,n)) with rolling array

5 · Top-K Retrieval (Heap)

import heapq

# Get top-k most similar chunks — O(n log k)
def top_k_chunks(query_embedding, chunks, k=5):
    return heapq.nlargest(k, chunks, key=lambda x: cosine_sim(query_embedding, x.embedding))

def cosine_sim(a, b):
    dot   = sum(x*y for x,y in zip(a, b))
    norm_a = sum(x**2 for x in a) ** 0.5
    norm_b = sum(x**2 for x in b) ** 0.5
    return dot / (norm_a * norm_b + 1e-8)  # epsilon prevents div by zero

# nlargest → max-heap internally. nsmallest → min-heap. heappush/heappop is O(log n).

Pattern 1 · Funnel Conversion

Q: "What % of users who saw the payment screen actually completed payment?"

# Per-user funnel: did each user hit both steps?
def funnel_conversion(df, step_a, step_b, group_by=None):
    if group_by:
        return (
            df[df['event'].isin([step_a, step_b])]
            .groupby(['user_id', group_by])['event']
            .apply(lambda x: (step_a in x.values) and (step_b in x.values))
            .reset_index()
            .groupby(group_by)[0]
            .mean()
            .rename('conversion_rate')
        )
    seen_a  = set(df[df['event'] == step_a]['user_id'])
    seen_b  = set(df[df['event'] == step_b]['user_id'])
    return len(seen_a & seen_b) / len(seen_a) if seen_a else 0

# Overall conversion
rate = funnel_conversion(df, 'PAYMENT_SCREEN_VIEWED', 'PAYMENT_SUCCESS')

# By device
by_device = funnel_conversion(df, 'PAYMENT_SCREEN_VIEWED', 'PAYMENT_SUCCESS', group_by='device')
# Key insight: narrate → "Android converts at X%, iOS at Y% — difference worth investigating"

Pattern 2 · Rolling Anomaly Detection

Q: "Flag the hours where latency spiked abnormally."

# Resample to hourly, then flag anomalies with rolling stats
hourly = (
    df.set_index('timestamp')
    .resample('1H')['latency_ms']
    .mean()
    .reset_index()
)

window = 6   # 6-hour rolling window
hourly['rolling_mean'] = hourly['latency_ms'].rolling(window).mean()
hourly['rolling_std']  = hourly['latency_ms'].rolling(window).std()
hourly['is_anomaly']   = (
    (hourly['latency_ms'] - hourly['rolling_mean']).abs()
    > 2 * hourly['rolling_std']
)

anomalies = hourly[hourly['is_anomaly']]
# Key insight: "2 std dev = ~95% confidence. For stricter alerting use 3 std dev."
# PulseAI framing: this is exactly how the EM agent spots crash spikes to give the Planner a time window.

Pattern 3 · Top-K by Group

Q: "Which OS version has the worst crash rate? Show top 3."

# Crash rate per OS version — groupby + agg + nlargest
crash_by_os = (
    df.groupby('os_version')
    .agg(
        total_sessions  = ('user_id', 'count'),
        total_crashes   = ('crashed', 'sum'),
        avg_latency_ms  = ('latency_ms', 'mean'),
    )
    .assign(crash_rate = lambda x: x['total_crashes'] / x['total_sessions'])
    .nlargest(3, 'crash_rate')
)

# Heap framing: nlargest() uses a min-heap internally → O(n log k)
# Same as heapq.nlargest() — same pattern, pandas wraps it for you.

Scenario Q&A — Talk-Through Questions

Often used as a 2nd question or follow-up in the 30-min window
"Your LLM gives confidently wrong answers — how do you debug it?"
Start from the bottom of the pipeline and work up:

1. Check retrieval first — is the right chunk even being fetched? Compute precision@k. If the wrong chunk is retrieved, the LLM never had a chance.
2. Check augmentation — is the context too long and the relevant part getting cut? Is the chunk actually readable in context?
3. Check generation — is the LLM ignoring the context and using its priors? Add explicit "use only the context below, say I don't know if unsure" instructions.
4. Eval harness — add a Promptfoo faithfulness case that flags this exact scenario for future regressions.
"Your agent loop isn't terminating — what's wrong?"
Three common causes:

1. Missing stop condition — LLM keeps calling tools because the final answer prompt isn't clear enough. Fix: explicit "return FINAL_ANSWER: ... when done" instruction.
2. Tool result not fed back — LLM doesn't see its own tool output, so it keeps calling. Fix: always append tool result to message history.
3. No max_iterations guard — no hard stop. Fix: add circuit breaker (10 iterations), return partial answer with "incomplete" flag.

Always add the guard. Never trust the LLM to self-terminate reliably.
"LLM context window fills up on long documents — how do you handle it?"
At ingestion time: chunk documents into overlapping windows (512 tokens, 64 overlap) so no single chunk is too large.
At retrieval time: only pass top-k relevant chunks (not the whole document) — RAG solves the context problem by design.
For conversation history: sliding window over recent turns + summarize older turns into a compressed memory block.
For very long agent contexts: token-aware packing — sort chunks by score, greedily add until budget exhausted.
"LLM doesn't return valid JSON / ignores output format — how do you fix it?"
Layer 1 — Prompt: be explicit. "Return ONLY valid JSON matching this schema: {schema}. No prose before or after."
Layer 2 — Retry loop: try json.loads(), on failure send back "That was invalid JSON. Return only the JSON object." with the error message. Max 3 retries.
Layer 3 — Model features: use JSON mode / structured outputs (OpenAI, Gemini, Claude) which constrain generation to valid JSON at the token level.
Layer 4 — Eval: add a Promptfoo case that fails if output isn't parseable JSON.
"How do you evaluate your RAG pipeline — what metrics do you use?"
Split into two layers:

Retrieval quality: precision@k (are the right chunks in the top-k?), recall@k (did we find all relevant chunks?), MRR (mean reciprocal rank of the first relevant result).
Generation quality: faithfulness (does the answer only use information from the retrieved context?), answer relevance (does it actually answer the question?), context relevance (are the retrieved chunks actually relevant?). RAGAS is the standard framework — uses an LLM judge to score these without human annotation.
Production metrics: user thumbs up/down, deflection rate, p95 latency.
"How would you build RAG for 22 Indian languages with limited annotated data?"
1. Embedding model: Start with MURIL/LaBSE/IndicBERT for cross-lingual semantic search — these models align semantic spaces across languages without parallel data.
2. Data augmentation: Back-translation, synthetic QA generation via LLM, transliteration mining (Devanagari ↔ Latin script) to increase training surface.
3. Retrieval: Script normalization (NFKC), Aksharantar for tokenization, hybrid BM25+dense for exact keyword match in native script (Hindi-English code-mixing is common).
4. Eval: LLM-as-judge (GPT-4o multilingual), automated faithfulness on translated gold sets, IndicXTREME/FLASK-Indic benchmarks (no human annotators for 22 languages).
5. Cost/scale: Distill the cross-lingual encoder to a smaller student model, INT8 quantization, aggressive caching on common queries. Serve lightweight at the edge for Jio's massive user base.
6. Fallbacks: If query in language X gets low confidence, translate to English → retrieve in English → generate in target language (translates-in, translates-out).
"How do you handle hallucination in low-resource Indian languages where there are no native eval sets?"
1. Transliterate and translate gold sets: Start from existing English eval sets (FLASK, AlpacaEval), translate to Hindi/Marathi/Telugu. Not perfect but catches baseline issues.
2. LLM-as-judge in English: For any generated answer, translate back to English before judging faithfulness with GPT-4o. One-directional translation risk but works at scale.
3. Binary safety rules: Instead of nuanced scoring, have hard rules — "answer must cite a source", "answer cannot invent dates/names". Deterministic, no eval annotation needed.
4. Human-in-the-loop early: For the first 2 weeks of a new language launch, every answer gets a thumbs up/down. Build a synthetic dataset from the failed cases (negative samples are most valuable).
5. Peer language transfer: Hindi safety patterns often transfer to Marathi/Urdu/Punjabi. Build eval once in a well-resourced language, adapt to siblings.
