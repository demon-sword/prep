04Hypothesis Testing & A/B Significance

Null vs alternative hypotheses, p-values, Type I/II errors, and statistical power — the inferential machinery that turns a raw conversion-rate difference into a defensible "ship it" or "kill it" call.

Theory

The Setup: Two Competing Stories

Hypothesis testing starts by fixing a null hypothesis H₀ — the boring, skeptical default ("the treatment has no effect on conversion rate") — against an alternative hypothesis H₁ ("the treatment changes conversion rate"). The test never proves H₀ true; it only asks whether the observed data would be surprising if H₀ were true. That asymmetry is the single most misunderstood idea in applied statistics: "failed to reject H₀" is not the same as "confirmed no effect," it just means the experiment didn't collect enough evidence to rule out chance.

The Test Statistic and the p-value

For an A/B test comparing conversion rates (or any two means), the standard approach is a two-sample z-test (large n) or Welch's t-test (unequal variances, safer default). Compute the standardized difference:

z = (x̄_treatment − x̄_control) / SE  where  SE = √(σ²_c/n_c + σ²_t/n_t)

The p-value is the probability of observing a test statistic at least as extreme as this one, assuming H₀ is true — p = 2·(1 − Φ(|z|)) for a two-sided test. It is not the probability that H₀ is true, and it is not the probability your result is a fluke — both are among the most common misinterpretations cited by the ASA's 2016 statement on p-values. A small p-value means the observed gap would be rare under a "no effect" world; it says nothing about effect size or practical significance, which is why a p=0.001 result on a 0.02% lift with n=50M users can be statistically significant and business-irrelevant.

The Two Ways to Be Wrong

DecisionH₀ actually trueH₀ actually false
Reject H₀Type I error (α, false positive)Correct (power, 1−β)
Fail to reject H₀Correct (1−α)Type II error (β, false negative)

α (significance level, conventionally 0.05) is a knob you set before the experiment — it's the false-positive rate you're willing to tolerate across many repeated tests of true nulls. β is the false-negative rate, and power = 1 − β is the probability of correctly detecting a real effect of a given size. Power depends jointly on effect size, sample size, variance, and α — shrink any one of the first three and power collapses, which is exactly what the visualization below lets you feel directly.

Sample Size and the Power Formula

For a two-sample z-test targeting power 1−β at significance α, the required per-group sample size is:

n = 2·(z_{α/2} + z_β)² · σ² / δ²

where δ is the minimum detectable effect (MDE) and σ the standard deviation. For α=0.05, power=0.80: z_{α/2}=1.96, z_β=0.8416, so (z_{α/2}+z_β)² ≈ 7.85. This is why halving your MDE roughly quadruples required sample size — detecting a 1% lift instead of a 2% lift costs 4× the traffic and runtime, a fact that routinely blindsides teams scoping experiment timelines.

Multiple Testing and Peeking

Run 20 independent tests at α=0.05 on truly null effects and you expect roughly one false positive by chance alone — the family-wise error rate inflates as 1 − (1−α)^m. Teams running dozens of simultaneous metrics per experiment (common in growth/product analytics) need corrections: Bonferroni (divide α by m, conservative), Benjamini-Hochberg FDR control (less conservative, controls expected proportion of false discoveries), or pre-registering a single primary metric. Separately, peeking — checking p-values repeatedly as data accumulates and stopping the moment p < 0.05 — inflates the true false-positive rate to 20–30%+ even at nominal α=0.05, because you're implicitly running many correlated tests across time. The fix is either a fixed sample size decided in advance, or a proper sequential testing method (group sequential designs, alpha-spending functions, or Bayesian/always-valid p-values as used by Optimizely's Stats Engine and Statsig's sequential testing).

Production Reality

Real experimentation platforms rarely use a textbook z-test unmodified. Conversion-rate metrics use proportion tests (or logistic regression with a treatment indicator for covariate adjustment via CUPED, which can cut variance 30–50% by regressing out pre-experiment behavior). Ratio metrics (revenue per user) need the delta method or bootstrap because the naive variance formula for a ratio of two random variables is biased. Cluster-randomized experiments (randomizing by user but measuring session-level metrics) need cluster-robust standard errors or the data needs aggregating to the randomization unit first, or your effective sample size — and hence your p-value — is badly overstated. And crucially: statistical significance is not the same as a ship decision — teams should pre-register a minimum practically significant effect size, not just chase p < 0.05 on noise.

Key Takeaways

  • p < 0.05 answers "would this be surprising under no-effect?", not "is the effect real/large." A statistically significant 0.03% lift on 50M users is real but often not worth shipping — always pair the p-value with a confidence interval on effect size and a pre-registered minimum practically significant effect.
  • Sample size scales with the inverse square of MDE. n = 2(z_{α/2}+z_β)²σ²/δ² means halving the minimum detectable effect requires ~4× the traffic. Teams that scope a 2-week test for a 1% MDE when they actually need to detect 0.25% are running an underpowered experiment that will almost always report "no significant difference" — not because there's no effect, but because β is enormous.
  • Peeking is the #1 practical way teams fool themselves. Checking a dashboard daily and stopping the moment p crosses 0.05 inflates the true false-positive rate to 20–30%+. Use a fixed pre-committed sample size, or a proper sequential/always-valid method (Optimizely Stats Engine, Statsig sequential testing, group-sequential alpha-spending) if you need to peek.
  • Multiple metrics need correction. Testing 20 secondary metrics at α=0.05 on a genuinely null experiment yields ~1 false "win" by chance. Apply Bonferroni for a handful of critical metrics or Benjamini-Hochberg FDR control for larger metric panels — and always designate one pre-registered primary metric for the ship decision.
  • CUPED and covariate adjustment aren't optional at scale. Regressing out each user's pre-experiment behavior (via CUPED or a simple ANCOVA) commonly cuts variance 30–50%, which is equivalent to running the experiment on far more traffic for free — this is standard in Microsoft's ExP platform and most mature experimentation stacks.
  • Ratio and clustered metrics need different variance estimators. Revenue-per-user needs the delta method or bootstrap (naive variance of a ratio is biased); randomizing by user but measuring per-session metrics needs cluster-robust SEs or aggregation to the unit of randomization, or your effective n — and p-value — is overstated. statsmodels' DescrStatsW, scipy.stats.ttest_ind(equal_var=False), and bootstrap CIs are the common tools.
