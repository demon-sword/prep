36A/B Testing for ML Products

Randomized experiment design for ML products — sample size/power calculation, novelty effects, and common pitfalls like peeking and Simpson's paradox.

Theory

Why Offline Metrics Aren't Enough

A model that improves offline AUC, NDCG, or RMSE does not automatically improve the business metric anyone cares about — revenue, retention, session length. Offline evaluation measures fit to historical labels, which were themselves generated under the old policy; deploying a new model changes user behavior in ways offline data can never capture (exposure bias, feedback loops, changed incentives). A/B testing closes that gap by randomizing real users into a control arm (existing system) and one or more treatment arms (new model/feature), then comparing outcomes under actual deployment. The randomization is what buys causal inference — without it, any observed difference is confounded with whatever correlates with who self-selected into each group.

Power, Sample Size, and Minimum Detectable Effect

Before running a test, teams fix a significance level α (probability of a false positive, conventionally 0.05) and a target power 1−β (probability of detecting a true effect, conventionally 0.80), then solve for the sample size needed to detect a given minimum detectable effect (MDE). For a two-proportion test the standard approximation is:

n ≈ 2·(z_{α/2} + z_β)² · p(1−p) / δ²

where p is the baseline conversion rate and δ is the absolute lift you need to detect. This is why detecting a 0.5% relative lift on a 2% baseline conversion rate can require millions of users per arm, while a 20% relative lift on the same baseline needs only a few thousand — MDE and required sample size trade off quadratically, which is the single most common reason "the test was inconclusive" (underpowered, not truly null).

The Peeking Problem

A p-value computed at day 3 and re-checked at day 7, day 10, day 14… is not a sequence of independent 5%-error tests — it's repeated significance testing on accumulating data, and the probability that at least one of those checks crosses p < 0.05 under the null is far higher than 5%. Johari et al. (2017, "Peeking at A/B Tests") showed this optional-stopping false-positive rate can climb to 25–30%+ over a multi-week experiment if analysts stop the moment they see significance. The fix is either a fixed-horizon design (commit to sample size and duration up front, look once) or a proper sequential testing framework — group-sequential designs with an alpha-spending function (O'Brien-Fleming, Pocock) or "always-valid" mixture-SPRT p-values (the approach behind Optimizely's Stats Engine), both of which are constructed so that peeking at any time preserves the nominal false-positive rate.

Novelty Effects, Simpson's Paradox, and Guardrails

Early lift often decays (novelty effect — users try the new thing, then habituate) or grows (primacy — a UI change needs a learning period), so experiments should run a minimum of one to two full weekly cycles to average out day-of-week seasonality before drawing conclusions. A subtler trap is Simpson's paradox: a treatment can win in every individual segment (country, device, cohort) yet lose in aggregate if the segment mix differs between arms — usually a symptom of a sample ratio mismatch (SRM) bug in the randomization or logging pipeline, which teams detect with a chi-square goodness-of-fit check on the actual vs expected traffic split before trusting any result. Production experimentation always tracks an Overall Evaluation Criterion (OEC) alongside guardrail metrics (latency, crash rate, unsubscribe rate) that must not regress even if the OEC improves, and applies multiple-testing correction (Bonferroni or FDR control) when many metrics or segments are checked simultaneously.

Production Reality

Variance-reduction techniques matter as much as raw sample size: Microsoft's CUPED (Controlled-experiment Using Pre-Existing Data) uses a user's pre-experiment metric value as a covariate to shrink outcome variance, often cutting required sample size by 30–50% for the same power. At scale, platforms like Booking.com (1,000+ concurrent experiments), Airbnb (ERF), Uber (XP), and open-source/commercial tools like Statsig, GrowthBook, and Eppo automate SRM checks, sequential p-values, and guardrail monitoring so individual analysts can't accidentally peek their way into a false launch decision.

Key Takeaways

  • MDE and sample size trade off quadratically — halving the minimum detectable effect roughly quadruples the required sample size (n ∝ 1/δ²); most "inconclusive" experiments are underpowered for the effect size that actually exists, not genuinely null.
  • Peeking inflates the real false-positive rate well past α = 0.05 — Johari et al. (2017) showed repeated daily significance checks can push the effective false-positive rate to 25–30%+; use a pre-committed fixed horizon, or a sequential framework (group-sequential alpha-spending, mixture-SPRT / Optimizely's Stats Engine) that's valid to check at any time.
  • CUPED can cut required sample size 30–50% — using a user's pre-experiment metric as a covariate to reduce outcome variance (Microsoft's technique) is now standard in mature experimentation platforms and shortens time-to-decision without touching the randomization.
  • Always run an A/A-style sample ratio mismatch (SRM) check first — a chi-square test on actual vs expected traffic split catches randomization/logging bugs before they masquerade as a real treatment effect; an undetected SRM is one of the most common causes of a false "win."
  • Simpson's paradox means segment-level results can contradict the aggregate — a treatment can win in every country and lose overall (or vice versa) if segment mix differs between arms; always slice by major segments, not just look at the topline delta.
  • Guardrail metrics gate the launch decision, not just the OEC — a model that lifts click-through but regresses p99 latency or crash rate should not ship; production platforms (Statsig, GrowthBook, Eppo, internal tools at Airbnb/Uber/Booking.com) enforce guardrails and multiple-testing correction automatically so individual analysts can't accidentally p-hack a launch.
