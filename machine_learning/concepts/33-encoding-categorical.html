Feature Engineering

33Categorical Encoding

One-hot, ordinal, target, and embedding encodings for categorical features — the cardinality/leakage tradeoffs of each.

Theory

Why Categorical Features Need Special Handling

Most ML algorithms operate on real-valued vectors, so a categorical column like city or device_type must be converted to numbers before it can enter a model. The naive move — assigning integers 0, 1, 2, … arbitrarily — silently injects a false ordinal relationship: a linear model or a distance-based method (kNN, k-means, SVM) will treat "Chicago"=2 as literally between "Boston"=1 and "Denver"=3 and will compute gradients/distances as if that ordering and spacing were meaningful, which for a nominal category it never is. The choice of encoding is therefore not a formality — it directly determines what relationships the downstream model is even capable of learning, and it is one of the highest-leverage, most failure-prone steps in a tabular ML pipeline.

One-Hot Encoding

One-hot encoding creates one binary column per category (pd.get_dummies, sklearn.preprocessing.OneHotEncoder), so a k-category feature becomes a k-dimensional (or k−1 with drop='first' to avoid the dummy-variable trap in linear models) sparse block. It makes no ordinal assumption and is the safest default for low-cardinality features (roughly k ≤ 15–20) feeding linear models, SVMs, or neural nets. Its failure mode is dimensionality explosion: a "zip code" or "user ID" column with 10,000+ levels turns a modest feature matrix into a sparse monster that blows up memory, slows down tree-based split search (which must now consider thousands of near-useless binary columns), and produces extremely sparse per-category statistics that most models can't learn from reliably.

Ordinal / Label Encoding

Ordinal encoding assigns each category a single integer (sklearn.preprocessing.OrdinalEncoder). It is correct only when the categories have a genuine, known order (e.g. low < medium < high, or education level) — using it on nominal categories injects a fabricated ordering, as noted above. The one major exception is tree-based models: because trees split on arbitrary thresholds and can carve out arbitrary subsets of the integer-coded values across multiple splits, an ordinal-encoded nominal feature is far less damaging to a GBM than to a linear model, and LightGBM's native categorical support in fact reduces to something conceptually similar to ordinal encoding combined with smart threshold search. It's also the cheapest encoding in terms of memory and compute, so it is often used as a first-pass baseline for tree models with high-cardinality columns.

Target (Mean) Encoding — and Its Leakage Trap

Target encoding replaces each category with a statistic of the target variable within that category — typically mean(y | category) for regression or the positive-class rate for classification. It compresses arbitrarily high cardinality into a single, highly informative numeric column, which is why it dominates on Kaggle for high-cardinality features like user_id or merchant_id. The danger is target leakage: if a row's own label is included when computing its category's mean, the encoded value partially is the label — most severely for rare categories, where a category with only 1–2 samples produces an encoded value that is exactly (or almost exactly) that row's own target, letting the model memorize training labels through the back door and collapse at inference time on unseen or rare categories. The fix is twofold: (1) leave-one-out or out-of-fold encoding — compute each row's encoded value from every row except itself (or from a different CV fold than the one being encoded), and (2) smoothing toward the global mean, weighted by category count: smoothed = (n·catMean + m·globalMean) / (n + m), where m is a prior-strength constant (commonly 5–20). This regularizes rare categories toward the population average instead of trusting a noisy 1-sample estimate. category_encoders.TargetEncoder and category_encoders.LeaveOneOutEncoder implement this correctly out of the box.

Frequency / Count Encoding

Replacing each category with its occurrence count or frequency (count(category)/N) is a cheap, leakage-free, single-column encoding that works surprisingly well for tree models because rarity itself is often predictive (e.g. rare merchant IDs correlate with fraud). It carries no target information, so it's safe with respect to leakage, but it also conflates categories that happen to have the same frequency, which can lose signal that target encoding would have captured.

Learned Embeddings

Neural nets handle high-cardinality categoricals with an embedding layer: each category is mapped to a small dense trainable vector (dimension often ~min(50, k^0.25 · 4) as a rule of thumb, though tuned per problem), initialized randomly and updated by backpropagation jointly with the rest of the network, exactly like word embeddings in NLP. This lets the model discover a continuous, task-specific notion of similarity between categories (Guo & Berkhahn's 2016 "Entity Embeddings of Categorical Variables" showed embeddings for store IDs in a sales-forecasting task self-organized by geographic proximity purely from gradient signal, with no geography ever given to the model). Embeddings scale gracefully to millions of categories via lookup tables and are the standard approach in deep tabular models and recommender systems, at the cost of needing enough data per category to learn a meaningful vector and losing the direct interpretability of one-hot/target encoding.

Production Reality

Always fit any target-derived encoder (target mean, frequency, WoE) on the training fold only and persist it as a model artifact, exactly like a StandardScaler — refitting encoders on train+val or on production data drift silently corrupts predictions. Handle unseen categories at inference explicitly: one-hot encoders need handle_unknown='ignore'; target/frequency encoders need a documented fallback (usually the global mean or zero); embeddings need a reserved "unknown" index. High-cardinality one-hot matrices should usually be stored as scipy.sparse to avoid memory blowups. In practice, XGBoost/LightGBM pipelines default to target or frequency encoding for high-cardinality columns (LightGBM also has built-in categorical_feature support using a variant of target statistics with regularization), while deep tabular pipelines (TabNet, fastai's tabular learner, recommender embedding towers) use learned embeddings end to end.

Key Takeaways

  • Naive target encoding is one of the most common real-world leakage bugs — a category with 1–2 samples produces an encoded value that is exactly (or nearly exactly) that row's own label; leave-one-out plus count-weighted smoothing (category_encoders.LeaveOneOutEncoder, or (n·catMean + m·globalMean)/(n+m)) is non-negotiable whenever target encoding is used, not an optional refinement.
  • One-hot is safe but doesn't scale — beyond roughly 15–20 categories, dimensionality explosion inflates memory, slows tree split search across thousands of near-constant binary columns, and fragments per-category statistics; switch to frequency, target, or embedding encoding once cardinality passes that range.
  • Ordinal encoding is a correctness bug for nominal features in linear/distance-based models, but is comparatively harmless for tree ensembles (XGBoost, LightGBM) since threshold splits can carve out arbitrary subsets of the integer codes — this is why LightGBM's native categorical handling looks conceptually closer to ordinal + target statistics than to one-hot.
  • Frequency/count encoding is leakage-free by construction (no target information used) and is a cheap, effective default for high-cardinality tree-model features where rarity itself carries signal — e.g. rare merchant IDs correlating with fraud.
  • Learned embeddings need enough data per category to be meaningful — a category seen only a handful of times gets a poorly-trained, near-random vector; production recommender/tabular systems reserve a dedicated "unknown/rare" embedding index and route low-frequency categories to it rather than giving each its own under-trained vector.
  • Any encoder derived from the training data is a model artifact — fit target/frequency/WoE encoders on the training fold only, persist them alongside the model (joblib.dump), and define an explicit fallback for categories unseen at serving time (global mean, zero, or a reserved embedding index); silently passing unseen categories through raises KeyErrors or produces NaNs that many teams only discover in a production incident.
