23ROC vs Precision-Recall Curves

ROC-AUC vs precision-recall AUC — why PR curves are more informative than ROC on imbalanced classes, and how to read both.

Theory

Two Threshold-Sweep Curves, Two Different Questions

Both the ROC curve and the precision-recall (PR) curve are built the same mechanical way: take a classifier's continuous score (a probability or a raw margin), sweep the decision threshold from 1 down to 0, and at every threshold recompute a confusion matrix and plot two rates against each other. The ROC curve plots true positive rate (recall, TP/(TP+FN)) on the y-axis against false positive rate (FP/(FP+TN)) on the x-axis. The PR curve plots precision (TP/(TP+FP)) against recall on the x-axis. They are two projections of the same underlying ranking of scored examples, but they answer structurally different questions: ROC asks "as I relax the threshold, how much do I trade off catching more true positives against wrongly flagging negatives, as a fraction of all negatives?" PR asks "as I relax the threshold, how much do I trade off catching more true positives against diluting my positive predictions with false alarms?"

Why FPR Lies to You When Negatives Are Abundant

The false positive rate has TN in its denominator. On a balanced dataset TN and TP are comparable in scale, so FPR behaves intuitively. But on an imbalanced dataset — say 0.5% fraud — the negative class is so large that even a large absolute number of false positives is a tiny fraction of all negatives, so FPR stays near zero and the ROC curve looks deceptively good (hugging the top-left corner, ROC-AUC ≈ 0.95+) even for a model that is, in absolute terms, flooding the fraud queue with false alarms. Precision has FP in its denominator alongside TP — both of which are drawn from the tiny positive-adjacent region of score-space — so it directly reflects "of the alerts I'm generating, what fraction are real," which is exactly what a fraud-review team or an on-call engineer cares about. This is the core reason senior practitioners default to PR curves on imbalanced problems (fraud, rare disease, click-through, defect detection) and reserve ROC for roughly balanced problems or when the negative class size genuinely doesn't matter to the downstream cost function.

Baselines Differ Too

A random classifier's ROC curve is the diagonal from (0,0) to (1,1), independent of class balance — ROC-AUC = 0.5 always for chance. A random classifier's PR curve, however, is a flat horizontal line at precision = prevalence (the positive class base rate): with 0.5% positives, random guessing gives precision ≈ 0.005 at every recall level, and PR-AUC (formally the average precision, AP = Σₙ (Rₙ − Rₙ₋₁)·Pₙ, the area under the precision-recall step function) for a random model equals the prevalence. This means PR-AUC values are not comparable across datasets with different base rates the way ROC-AUC roughly is — a PR-AUC of 0.3 is excellent at 0.5% prevalence and mediocre at 40% prevalence, so always report it alongside the base rate, and prefer a lift-over-baseline framing (AP / prevalence) when comparing across problems.

Reading and Using Both Curves

A perfect classifier hugs the top-left corner on ROC (FPR=0, TPR=1) and the top-right corner on PR (recall=1, precision=1); ROC-AUC and PR-AUC both max out at 1.0. In practice, look at the curve's shape, not just the scalar AUC: a PR curve that craters sharply past a certain recall tells you exactly where the model runs out of confidently-separable positives — that's often the natural operating recall to ship at. ROC-AUC has a clean probabilistic interpretation worth memorizing for interviews: it equals the probability that a randomly chosen positive example is ranked (scored) higher than a randomly chosen negative example — this is also exactly the statistic the Mann-Whitney U test computes, which is why ROC-AUC is sometimes called the "concordance statistic" (C-statistic) in the biostatistics literature. Because ROC-AUC is a pure ranking metric, it's threshold-independent and label-imbalance-somewhat-robust for ranking quality, which is why it's still useful even on skewed data for comparing two models' ability to separate classes — just don't use it alone to judge deployability of a fixed threshold on rare-event data.

Production Reality

scikit-learn's roc_curve/roc_auc_score and precision_recall_curve/average_precision_score are the standard tools; average_precision_score is preferred over naively trapezoidal-integrating precision_recall_curve because AP handles the curve's non-monotonicity correctly. A common production pattern: report both AUCs during model selection (ROC-AUC is more stable across bootstrap resamples and comparable across retrains), but pick the deployment threshold off the PR curve because that's the curve whose axes map onto business cost (alert volume vs miss rate). Watch for a subtle trap: if your training pipeline undersamples or oversamples the majority class to "balance" the data, PR-AUC and precision figures computed on that resampled set are not representative of production — always evaluate PR/ROC on a held-out set with the true production class distribution, then recalibrate the resampled model's probabilities (e.g. via Platt scaling or isotonic regression, or simply correcting for the prior shift analytically) before setting a threshold.

Key Takeaways

  • ROC-AUC has a clean probabilistic reading worth memorizing: it equals the probability that a randomly chosen positive example scores higher than a randomly chosen negative one — identical to the Mann-Whitney U statistic, which is why it's called the "concordance" or "C-statistic" in biostatistics.
  • On imbalanced data (fraud, rare disease, CTR, defect detection), prefer the PR curve — ROC-AUC can look great while precision is terrible. Because FPR's denominator is dominated by the huge negative class, a model flooding the alert queue with false positives can still post ROC-AUC ≈ 0.95+; precision directly exposes that the alerts are mostly noise.
  • PR-AUC baselines are not comparable across datasets — a random classifier's PR curve sits flat at the positive prevalence, not at 0.5. A PR-AUC of 0.3 is excellent at 0.5% prevalence and mediocre at 40%; always quote PR-AUC alongside base rate, or normalize with AP / prevalence ("lift over baseline") when comparing across problems.
  • Use average_precision_score, not a naive trapezoidal integral of precision_recall_curve. Precision is not monotonic in recall (it can bounce up and down as the threshold moves), and AP's step-function weighting handles that correctly; plain trapezoidal integration can overestimate the area.
  • If training used class-balancing (undersampling, SMOTE, class weights), evaluate PR/ROC on a held-out set with the true production prior — not the resampled distribution. Resampled-set precision figures are systematically inflated relative to production; recalibrate probabilities (Platt scaling, isotonic regression, or analytic prior correction) before picking a deployment threshold.
  • Use ROC-AUC for model comparison/ranking quality (it's more stable across bootstrap resamples and threshold-independent), but set the actual deployment threshold off the PR curve — its axes (precision = alert quality, recall = miss rate) map directly onto the business cost function that a fixed threshold has to satisfy.
