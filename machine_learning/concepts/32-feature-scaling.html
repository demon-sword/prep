Feature Engineering

32Feature Scaling

Normalization vs standardization vs robust scaling — which algorithms require scaling (gradient descent, kNN, SVM) and which don't (trees), and why.

Theory

Three Scaling Families

Min-max normalization maps each feature linearly into a fixed range, usually [0,1]: x' = (x − min) / (max − min). It preserves the shape of the original distribution exactly (just a linear rescale), which is desirable when you need bounded inputs (e.g. pixel intensities for a CNN, or inputs to a sigmoid-saturated layer) — but it is extremely sensitive to outliers, since a single extreme value stretches min or max and compresses every other point toward one end. Standardization (z-score scaling) centers each feature at zero mean and unit variance: x' = (x − μ) / σ. It doesn't bound the output range, but it's far more robust to moderate outliers than min-max and is the default choice for most linear models, SVMs, and neural nets because it matches the implicit assumptions behind weight initialization schemes and L2 regularization (which penalizes all coefficients on a comparable footing only if the underlying features are on a comparable scale). Robust scaling uses the median and interquartile range instead of mean/std: x' = (x − median) / IQR. Because median and IQR are themselves resistant to extreme values, this is the right default when a feature has heavy-tailed outliers (transaction amounts, latencies, income) that would otherwise dominate a mean/std or min/max computation.

Why Gradient Descent Needs It — the Conditioning Argument

For a linear model trained with squared error, the loss surface in weight space is an exact quadratic bowl whose curvature in each direction is governed by the Hessian H = XᵀX. The curvature along the axis of weight w_j is proportional to Var(x_j). If one feature has variance 10,000× another (e.g. "years of experience" 0–10 vs "annual income" 0–200,000), the loss surface is a long, narrow ravine: extremely steep along the high-variance feature's weight axis and nearly flat along the low-variance one. A single global learning rate then has no good setting — large enough to make progress in the flat direction and it overshoots wildly and diverges in the steep direction; small enough to be stable in the steep direction and progress in the flat direction becomes glacially slow, sometimes needing orders of magnitude more iterations to converge. This is precisely the condition number problem: κ = λ_max / λ_min of the Hessian. Standardizing every feature to unit variance drives all diagonal Hessian entries toward comparable magnitude, shrinking κ toward its best case (≈1 for uncorrelated features) and turning the ravine into something close to a circular bowl — a single learning rate converges quickly and directly to the optimum. This is exactly why unscaled features hurt not just linear/logistic regression but any gradient-descent-trained model, including deep nets — it's one reason batch normalization was invented (to re-impose comparable scale layer by layer, not just at the input).

Distance-Based and Variance-Based Methods

kNN, k-means, and SVMs with an RBF/polynomial kernel all rely on a distance metric — typically Euclidean. If one feature spans [0, 200000] and another spans [0, 10], the distance calculation is almost entirely determined by the large-scale feature regardless of which feature is actually more predictive; the small-scale feature is effectively invisible to the metric. The same logic applies to PCA: it finds directions of maximum variance, so an unscaled high-magnitude feature will dominate the first principal component purely because of its units, not because it carries more signal. All of these require standardization (or at least normalization) as a non-negotiable preprocessing step.

What Doesn't Need It — Tree-Based Models

Decision trees, random forests, and gradient-boosted trees (XGBoost, LightGBM, CatBoost) split on thresholds like x_j < t. Any monotonic transformation of x_j — min-max, standardization, log, or otherwise — leaves the ordering of values unchanged, so the optimal split point just moves to the corresponding transformed threshold and the resulting tree structure, splits, and predictions are numerically identical. Scaling features before training a random forest or XGBoost model is therefore pure wasted effort — it changes nothing about model quality, and empirically you'll measure zero difference in validation AUC/accuracy with scaling on vs off. Naive Bayes is also scale-invariant for the same reason its likelihoods factor per-feature. This is a common interview trap: candidates who reflexively scale everything "because that's what you do" without being able to explain why it's a no-op for trees signal shallow understanding.

Production Reality

Always fit the scaler (sklearn.preprocessing.StandardScaler, MinMaxScaler, RobustScaler) on the training split only, then transform validation/test/production data with those frozen statistics — fitting on the full dataset before splitting leaks test-set information into the mean/variance and inflates offline metrics relative to what you'll see in production. The fitted scaler is part of the model artifact: persist it (joblib.dump) alongside the model weights and load both at serving time — a scaler/model version mismatch (e.g. retraining the model but forgetting to refit and redeploy the scaler) is a real, hard-to-detect production bug that silently degrades predictions without throwing an error. For streaming/online learning where you can't refit on the whole dataset, maintain running mean/variance with Welford's algorithm so the estimate updates in O(1) per sample without numerical instability. Be careful with sparse data (e.g. TF-IDF/bag-of-words matrices): mean-centering (standardization) destroys sparsity by turning millions of zeros into small nonzero values, which can blow up memory and training time — use MaxAbsScaler or skip centering (with_mean=False) to preserve sparsity there.

Key Takeaways

  • Scaling is a conditioning fix, not cosmetics — for squared-error loss the Hessian's diagonal is proportional to each feature's variance, so a 100× scale mismatch between features creates a condition number in the tens of thousands; no single learning rate is then good in both directions, which is exactly what the visualization's "diverge in the steep direction / crawl in the flat direction" tradeoff demonstrates.
  • Tree ensembles (XGBoost, LightGBM, CatBoost, sklearn RandomForest) are provably invariant to monotonic feature transforms — splits are threshold comparisons, so scaling changes the threshold value but never the split decision or resulting predictions. Spending pipeline time scaling features before a GBM is wasted effort; verify this is understood before reaching for StandardScaler reflexively.
  • Fit the scaler on train only, then transform val/test/prod with those frozen stats — fitting on the full dataset before splitting is a data leakage bug that inflates offline metrics; in production, a stale or mismatched scaler artifact (model retrained, scaler not redeployed) degrades predictions silently with no error thrown.
  • Min-max is fragile to outliers, robust scaling isn't — a single extreme value stretches min-max's range and compresses everything else toward 0 or 1; RobustScaler's median/IQR basis is the right default for heavy-tailed production features like transaction amounts or latencies.
  • Sparse matrices need special handling — mean-centering a TF-IDF or one-hot matrix destroys sparsity (every zero becomes nonzero), inflating memory and training time; use MaxAbsScaler or StandardScaler(with_mean=False) to scale variance without breaking sparsity.
  • Distance- and variance-based methods (kNN, k-means, SVM-RBF, PCA) silently let the largest-magnitude feature dominate without scaling — not because it's more predictive, but purely because of its units; this is a distinct failure mode from the gradient-descent conditioning issue and applies even to non-iterative, closed-form methods like PCA's eigendecomposition of the covariance matrix.
