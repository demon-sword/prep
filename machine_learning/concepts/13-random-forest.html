Bagging plus random feature subsampling — how decorrelating trees reduces variance further than bagging alone, and feature importance from impurity decrease.

Theory

From Bagging to Random Forest: Decorrelating via Feature Subsampling

Random Forest (Breiman, 2001) is bagging with one deliberate extra source of randomness injected at every split. Plain bagging (see 12-bagging-vs-boosting) already trains each tree on an independent bootstrap resample of the rows, but every tree still gets to see every feature when choosing its splits. If one or two features are strongly predictive, nearly every bootstrapped tree will pick the same feature near the root, producing highly correlated trees — and averaging B trees with pairwise correlation ρ only reduces variance to ρσ² + (1-ρ)σ²/B, so a correlation floor of ρσ² survives no matter how large B gets. Random Forest attacks that floor directly: at each split, instead of searching all p features for the best split, it draws a random subset of m < p candidate features and searches only among those. This forces different trees — and even different branches of the same tree — to build around different features, actively decorrelating the ensemble and pushing ρ down, which is exactly the lever that squeezes out variance beyond what bagging alone can reach.

Choosing max_features

The subsample size m is the key knob. scikit-learn's RandomForestClassifier defaults to max_features='sqrt' (≈ √p features considered per split), while RandomForestRegressor defaults to max_features=1.0 (all features, i.e. bagging-with-bootstrap-only for splits, though row bootstrapping still applies) — the classification default reflects that classification boundaries typically need less per-split feature diversity to decorrelate usefully. Smaller m means more decorrelation (lower ρ) but each individual tree gets weaker, since it's sometimes forced to split on a mediocre feature when the best one wasn't sampled — this raises each tree's individual variance/bias slightly. The sweet spot balances the two effects, and in practice √p is a remarkably durable default across many tabular problems; log2(p) is the more aggressive alternative for very high-dimensional data. A further extreme is Extra Trees (ExtraTreesClassifier): it goes one step further by picking the split threshold randomly too (rather than the optimal SSE/Gini-minimizing threshold), trading a bit more per-tree bias for even lower correlation and faster training, since it skips the expensive threshold search entirely.

Feature Importance: Gini vs Permutation

Random Forest's default .feature_importances_ is mean decrease in impurity (MDI): for every split in every tree that uses feature j, accumulate the (sample-weighted) drop in Gini impurity or MSE that split produced, then average across trees. It's essentially free — a byproduct of training — but it has a well-known bias: it favors high-cardinality and continuous features simply because they offer more candidate thresholds to search over, so a random noise column with many unique values can outscore a genuinely predictive low-cardinality categorical. It also splits credit awkwardly among correlated features (if two features are near-duplicates, importance gets divided between them, making both look individually weak). The more trustworthy alternative is permutation importance (sklearn.inspection.permutation_importance): shuffle one feature's column in the held-out set and measure how much the model's score degrades. It's model-agnostic, uses out-of-sample data, and isn't biased toward high-cardinality features — but it costs one full re-scoring pass per feature per repeat, and it still under-credits importance shared across correlated features (shuffling one of two correlated columns barely hurts the model, since the other still carries the signal).

Out-of-Bag Error and Hyperparameters

Because each tree's bootstrap sample omits ~36.8% of rows on average, Random Forest inherits bagging's free out-of-bag (OOB) validation: RandomForestClassifier(oob_score=True) scores each row only on the subset of trees that never saw it during training, giving a near-unbiased generalization estimate without a separate CV loop — useful for fast iteration, though a true held-out test set is still worth keeping for a final reported number since OOB and CV can diverge slightly on small or non-iid data. The other major knobs are n_estimators (more trees almost never hurts test accuracy, only compute and memory — test error plateaus rather than degrading, unlike boosting), max_depth/min_samples_leaf (controls the bias of each individual tree; deep unpruned trees are the classic Random Forest base learner because they're already low-bias/high-variance, exactly what averaging is built to fix), and bootstrap (turning it off trains every tree on the full dataset, which removes the row-level diversity that OOB estimation depends on).

Production Reality

Random Forest is the "boring but robust" tabular baseline: near-default hyperparameters (n_estimators=300–500, max_features='sqrt') are competitive with meaningful effort spent tuning gradient boosting, training parallelizes trivially across cores (n_jobs=-1) since every tree is independent, and it's far more forgiving of label noise and outliers than boosting because no tree obsessively re-targets a mislabeled row's residual. It also requires no feature scaling (splits are threshold comparisons, invariant to monotonic transforms) and handles nonlinear interactions natively. The costs: prediction latency and memory scale linearly with n_estimators × tree depth — a forest of 500 depth-20 trees can be tens to hundrems of MB serialized and noticeably slower at inference than a single boosted ensemble of similar accuracy, which is why latency-sensitive production services sometimes distill a Random Forest down or switch to LightGBM once accuracy needs are met. It also can't extrapolate beyond the range of training data (predictions are always bounded by leaf averages seen during training), which regularly bites time-series or trending-target use cases where linear or boosted-tree monotonic-constraint models degrade more gracefully.

Key Takeaways

  • Random Forest = bagging + per-split feature subsampling — the second part is what makes it more than "BaggingClassifier with trees." Bagging alone leaves trees correlated because they all search the same full feature set; restricting each split to a random m < p subset of features actively decorrelates trees and squeezes variance below what row-resampling alone can achieve.
  • max_features defaults differ by task for a reason. scikit-learn uses 'sqrt' (≈√p) for classification and 1.0 (all features) for regression by default — classification boundaries tend to benefit more from aggressive decorrelation, while regression targets often need every tree seeing enough signal to avoid excess per-tree bias. Don't blindly reuse one default across both task types.
  • Gini/MDI feature importance is biased toward high-cardinality and continuous features — a noise column with many unique values can outrank a genuinely predictive low-cardinality categorical purely because it offers more candidate split thresholds. For anything importance-critical (feature selection, stakeholder-facing explanations), use sklearn.inspection.permutation_importance on held-out data instead, and expect both methods to under-credit importance shared between correlated features.
  • OOB score is a nearly-free validation signal, but it's not a substitute for a real test set on non-iid data. oob_score=True exploits the ~36.8% of rows each tree never trains on, giving a fast generalization estimate — useful for quick hyperparameter iteration, but time-correlated or grouped data (multiple rows per user, time-series) can still leak signal across the bootstrap boundary in ways a proper grouped/temporal split would catch.
  • More trees essentially never hurts accuracy — it only costs compute and memory. Unlike boosting, Random Forest's test error plateaus as n_estimators grows since each new tree is an independent, unbiased vote being averaged in. The real production tradeoff at scale is inference latency and serialized model size (a 500-tree, depth-20 forest can be tens of MB and noticeably slower than a comparable boosted model), which is why teams sometimes cap tree count or switch to LightGBM once accuracy targets are already met.
  • Random Forest can't extrapolate. Every leaf prediction is bounded by the range of target values it saw during training, so on inputs that drift outside the training distribution (a trending time series, a metric that keeps climbing) predictions flatten out at the boundary instead of continuing the trend — a failure mode linear models and monotonic-constrained gradient boosting handle far more gracefully.
