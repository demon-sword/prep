09Decision Trees

Recursive binary splitting, impurity measures (Gini, entropy), and how greedy splits build a tree — plus why deep trees overfit.

Theory

Recursive Binary Splitting

A decision tree partitions the feature space into axis-aligned rectangles (for 2D input) or hyper-rectangles in general, and assigns each region a constant prediction — majority class for classification, mean target for regression. It builds this partition greedily and recursively via the CART algorithm (Classification and Regression Trees, Breiman et al. 1984): starting at the root with all training data, it searches every feature and every candidate threshold for the single split that most reduces impurity, applies that split to create two child nodes, and then repeats the search independently within each child. This is a greedy procedure — at each node it picks the locally best split without looking ahead — so it does not guarantee a globally optimal tree (finding the optimal tree is NP-hard); a split that looks mediocre now might unlock a much better split one level down, but CART can't see that. The recursion stops at a node when it hits a stopping criterion: max depth reached, too few samples to split further, or the node is already pure (impurity = 0).

Impurity Measures

At each candidate split, CART evaluates how "pure" the resulting children would be. For classification, the two standard measures over class proportions p₁, ..., p_k in a node are:

Gini(node) = 1 − Σ pᵢ²      Entropy(node) = −Σ pᵢ log₂ pᵢ

Both are 0 for a pure node and maximal for a uniform 50/50 (binary case) node. A split's quality is the weighted impurity of the children versus the parent — the "impurity decrease" or information gain: ΔI = I(parent) − (n_L/n)·I(left) − (n_R/n)·I(right). CART's default in scikit-learn is Gini because it's cheaper to compute (no logarithm) and in practice produces trees nearly identical to entropy-based ones; entropy penalizes impure nodes slightly more aggressively near the extremes and is the criterion used by ID3/C4.5. For regression trees, the split criterion is variance reduction (equivalently, minimizing summed squared error within each child, criterion='squared_error' in scikit-learn). Finding the best threshold for a continuous feature at a node is O(n log n) (sort the feature values, then sweep the midpoints between consecutive distinct values, updating running class counts incrementally) — repeated across all features at every node, total tree-build cost is roughly O(n_features · n log² n).

Overfitting, Pruning, and Regularization

An unconstrained tree grown to purity perfectly memorizes the training set — every leaf can end up with a single point, giving 100% training accuracy and terrible generalization (the textbook high-variance, low-bias regime from 01-bias-variance-tradeoff). Trees are controlled either by pre-pruning (stopping growth early via max_depth, min_samples_split, min_samples_leaf, max_leaf_nodes) or post-pruning (grow the full tree, then cut back). The principled post-pruning approach is cost-complexity pruning: define R_α(T) = R(T) + α·|T| where R(T) is total training misclassification/error and |T| is the number of leaves, then find the subtree that minimizes this for a given α. Larger α trades training fit for a smaller tree. scikit-learn exposes this directly via DecisionTreeClassifier(ccp_alpha=...) and a helper, cost_complexity_pruning_path(), that returns the sequence of α values and corresponding subtrees, so you can cross-validate over the pruning path rather than guessing max_depth blindly.

Production Reality

A single decision tree is rarely deployed standalone for predictive performance — it's high variance: a small perturbation to the training data (removing a handful of rows, or a near-tied split) can flip which feature gets selected near the root and cascade into a completely different tree shape. This instability is precisely why bagging (Random Forest) and boosting (XGBoost/LightGBM) exist — both use trees as the base learner specifically to exploit this variance (averaging decorrelated trees) or convert it into a strength (sequentially correcting residuals). Where single trees still win: interpretability (the full decision path from root to leaf is a human-readable rule, valuable in regulated domains like credit scoring), zero feature-scaling requirement (splits are threshold comparisons, invariant to monotonic transforms — no StandardScaler needed, unlike SVM or linear models), and native handling of nonlinear interactions and mixed numeric/categorical features without manual feature crosses. Watch two production gotchas: feature_importances_ (mean impurity decrease per feature, weighted by node sample count) is biased toward high-cardinality and continuous features that offer more candidate split points, and toward correlated features splitting "credit" unevenly between them — prefer permutation importance or SHAP for trustworthy attribution. And scikit-learn's tree implementation does not handle missing values or categoricals natively (unlike LightGBM, which does) — you must impute and one-hot/ordinal-encode first, or the tree treats a raw NaN as a runtime error.

Key Takeaways

  • Trees are the only classical model that solves XOR-like patterns natively. Linear models and even RBF-kernel SVMs need the right feature engineering or kernel to separate a checkerboard pattern; a depth-2 tree does it automatically because each split only needs to be locally optimal, not globally linear.
  • Greedy ≠ optimal. CART never backtracks — a split chosen at the root is never revisited even if a different first split would have enabled a better second split. This is a real limitation (optimal decision tree construction is NP-hard) but it's what makes trees trainable in O(n_features · n log² n) instead of exponential time.
  • Gini vs entropy rarely matters in practice — they agree on the best split over 95% of the time on real data; scikit-learn defaults to Gini purely for speed (no logarithm per node). Don't spend tuning budget here; spend it on max_depth, min_samples_leaf, and ccp_alpha.
  • A lone tree is a high-variance model — retraining on a bootstrap resample of the same data can produce a visibly different tree near the root. That instability is a bug for standalone use but the entire reason Random Forest (average away the variance) and gradient boosting (exploit the residual signal) both use trees as their base learner.
  • feature_importances_ is biased toward high-cardinality/continuous features (more candidate thresholds to win a split) and splits credit unevenly among correlated features — cross-check with permutation importance (sklearn.inspection.permutation_importance) or SHAP values before trusting it for feature selection or stakeholder reporting.
  • No scaling needed, but encoding still is. Trees split on raw threshold comparisons so monotonic transforms and differing feature scales don't matter — but scikit-learn's tree still requires numeric input, so categoricals need one-hot/ordinal encoding (LightGBM's categorical_feature param handles raw categoricals natively via a smarter optimal-partition search, which is one reason it often edges out plain CART-based tools on tabular data).
